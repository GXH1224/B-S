## 2. 逐文件详解

### 2.1 `frontend/src/views/task/EvaluationWorkbench.vue`

**作用**：把「选项目 → 选指标体系版本 → 选数据快照 → 选算法与配参数 → 确认提交 → 跟踪执行」串成一条五步引导流程，是全系统唯一能创建评估任务的页面（对应方案 7.4「分步引导」工作台，路由 `/workbench`，见 `router/index.ts` 61-66 行）。

**被谁使用**：由路由 `/workbench` 懒加载（`router/index.ts` 64 行）；页内跳出的 `/tasks`、`/tasks/:id`、`/results?taskId=` 三个去向分别由分册 11 的另两个页面与分册 12 的结果页承接；调用的接口全部来自 `@/api`（`projectApi.options`、`indicatorApi.options/get/indicators`、`snapshotApi.list`、`taskApi.create/status/retry`）。

**关键设计点**：

1. **只有「输入装配」没有「结果选择」**。工作台的第 5 步是「执行跟踪」而不是「查看结果」：评估结果的产生者是这次提交出来的任务（结果以 `taskId` 关联），且结果还要走复核 / 发布工作流，因此工作台只负责把「项目 + 版本 + 快照 + 算法 + 参数」这一组输入装配正确并提交，结果查看交给 `/results?taskId=` 与 `/tasks/:id`（见 2.1.10 的说明）。这样页面上不会出现「还没执行就要选结果」这种无意义状态，也不会把结果页的筛选、图形、复核逻辑塞进一个 1600 余行的巨型组件。
2. **每一步都是「前端提示 + 步骤门禁 + 后端硬校验」三层防线**。用户在算法参数里填的阈值、判断矩阵、`comboFlow` 最终被后端 `TaskService.create` 的 `validateParameters` 与各算法引擎再次校验，前端 `stepIssue` 只是让错误尽早暴露。
3. **`parameters` 由一串 `ref` 文本派生，而不是直接绑定对象**。等级名称、阈值、指标编码都以「逗号分隔文本」保存（`weightedGradeNames` 等），再由 `computed` 解析成数组，好处是用户可自由编辑、支持中文逗号与顿号，解析失败也不会污染提交体（见 2.1.7）。

### 2.2 `frontend/src/views/task/TaskList.vue`

**作用**：评估任务列表页（路由 `/tasks`，`router/index.ts` 67-72 行）。提供「项目 / 算法 / 状态 / 关键字 / 时间范围」五维筛选、11 列表格、查看结果跳转、取消与重试操作，并在当前页存在「已排队 / 运行中」任务时以 5 秒间隔静默自动刷新。

**被谁使用**：由路由 `/tasks` 懒加载；是工作台（`goTaskList`）、任务详情（`goList`）、侧栏菜单的共同入口；调用 `projectApi.options` 与 `taskApi.list/cancel/retry`。

**关键设计点**：

1. **筛选参数「只带非空值」**，空条件不下发空串，交给后端 `blankToNull` 处理（`TaskService` 109-110 行），避免出现 `status=''` 把 `VALIDATING` 之类条件误判成精确匹配。
2. **自动刷新由数据驱动而不是由用户开关**：`watch(hasActiveTask)` 决定起停，页面提示行同步显示当前是否在自动刷新，用户不需要理解也不需要操作。
3. **操作按钮的前置条件只是 UI 优化**，真正的状态门禁在后端：`TaskService.cancel` 只允许 `QUEUED/RUNNING/VALIDATING/DRAFT`（566-569 行），`retry` 只允许 `FAILED/CANCELED/TIMEOUT`（579-582 行），越权调用会得到 `TASK_STATUS_ILLEGAL`。

### 2.3 `frontend/src/views/task/TaskDetail.vue`

**作用**：任务详情页（路由 `/tasks/:id`，`router/index.ts` 73-78 行）。用 6 张 StatCard、失败面板与 5 个标签页回答「这个任务是谁、用什么输入、跑成了什么样、为什么失败、产出了什么」，并提供取消 / 重试 / 查看结果 / 导出 Excel·Word·PDF。

**被谁使用**：由路由 `/tasks/:id` 懒加载；入口来自任务列表的「查看详情」、工作台的「查看任务 / 查看任务详情」、重试后的自动跳转，以及结果摘要里的任务跳转。调用 `taskApi.detail/status/cancel/retry`、`resultApi.byTask`、`reportApi.generate/download`。

**关键设计点**：

1. **双请求 + 2 秒轮询**：`detail` 提供全部静态内容（参数、输入摘要、状态历史、AHP 一致性、结果数），`status` 提供高频变化的小对象；轮询只打 `status`，**仅当状态真正变化时**才重新拉 `detail`（457-461 行），把 2 秒轮询的网络与渲染成本压到最低。
2. **终态集合比工作台更宽**：这里把 `PENDING_REVIEW / PUBLISHED / ARCHIVED` 也算终态（281 行），因为详情页是长期驻留页，任务进入审核发布链路后，详情字段不会再变，继续轮询纯属浪费。
3. **导出走「先生成、再下载」两步，并按 `report:create` 判权**：`reportApi.generate` 由后端渲染文件并落盘，返回 `reportId`；`reportApi.download` 再按 id 取流。这样报告文件在后端有记录、可重复下载、可审计（对应报告管理页）。「导出报告」按钮的可见性由 `canExport` 决定，而 `canExport` 只看 `report:create`（第 294 行）——该按钮调用的就是 `POST /api/reports`，需要的是生成权；本轮提交 `ce6c264` 把 `report:create` 从评估人员权限中收回后，**评估人员登录时 `canExport` 为 false，整个导出报告按钮组不再显示**，报告导出收紧为仅系统管理员。

**易错点/注意**：

1. `retryOf` 在「接口响应」里是任务编号字符串、在「任务实体」里是主键 id，两处不要互换（见 101-106 行说明）。
2. **权限判定口径必须与按钮真实调用的接口一致**。`canExport` 原先写成 `has(['report:create','report:download'])`，而 `userStore.has()` 对数组是「任一满足」（`.some`），于是「有下载权但没有生成权」也会显示「导出报告」按钮——点下去必然 403。该按钮走 `POST /api/reports`，真实依赖只有 `report:create`，本轮提交 `ce6c264` 已改为 `has('report:create')`（第 294 行）。**读这一页时要记住的通用规则**：`has()` 传数组是「或」，传单个字符串是「与」的语义更精确，写按钮权限前先确认它究竟调哪个接口。
3. 结果摘要只在切到该标签时加载一次；任务成功后再由轮询触发 `loadDetail` 不会自动刷新已加载的结果行，需点页头「刷新」或在标签间来回切换才会重取——这是当前的懒加载取舍。

## 3. 本册小结

- 本册共覆盖 **3 个文件、2773 行代码**（`EvaluationWorkbench.vue` 1618 行、`TaskList.vue` 453 行、`TaskDetail.vue` 702 行），与分配清单一致，无遗漏。其中 `TaskDetail.vue` 由 700 行增至 702 行：本轮提交 `ce6c264` 在 `canExport` 上方补了两行解释性注释，并把 `has(['report:create','report:download'])` 改为 `has('report:create')`。
- 三个页面构成评估任务的完整前端闭环：**工作台创建（`taskApi.create`）→ 列表监控与取消/重试（`taskApi.list/cancel/retry`）→ 详情追溯与导出（`taskApi.detail/status` + `resultApi.byTask` + `reportApi.generate/download`）**；三者共用 `utils/format.ts` 的算法字典与状态字典，因此中文文案与状态配色在全系统内一致。
- `parameters` 是前后端最紧的契约：前端由 `ref` 文本经 `splitList`/`splitNumbers` 解析成数组、`matrix` 逐行拷贝后提交；后端 `TaskService.validateParameters` 只做存在性校验，真正的语义校验与消费发生在 `AhpEngine`（矩阵、CR、`allowForceOnCrFail`）、`FuzzyEngine`（评语集数量、四种合成算子）、`WeightedAverageEngine`（降序阈值与默认值）与 `ComboEngine`（`comboFlow` 顺序）。改任一侧的字面量都必须同步另一侧。
- 三处轮询是三套独立的容错策略，不是重复实现：工作台 1.5 秒且连续失败 5 次降级为手动刷新；任务列表 5 秒且**仅当当前页存在 QUEUED/RUNNING** 时开启；任务详情 2 秒且仅打轻量 `status`、只在状态变化时补拉 `detail`。三者都在 `onUnmounted` 清理定时器。
- 前端的状态集合（可取消 / 可重试 / 终态）与后端 `TaskService` 的判定集合刻意保持一致：前端只是「藏按钮」，真正的门禁是后端的 `TASK_STATUS_ILLEGAL`，阅读这两层时必须成对查看。
- 最易被误解的三点：① 工作台没有「选结果」步骤（结果是任务的产出，且结果侧有独立的复核发布工作流）；② `versionInfo` 的 `leafCount/maxLevel` 必须靠 `indicatorApi.get` 补齐，`options` 接口不返回；③ 任务实体的 `retryOf`（主键 id）与 `/retry` 响应的 `retryOf`（任务编号字符串）语义不同。补充一点：步骤一「已选项目但没有可选指标体系版本」是**数据配置问题**（版本导入时的「关联项目」未指向本项目），页面上会同时出现「动态占位文字 + 61-72 行的解释性告警」，不要误判为前端缺功能。
