## 2. 逐文件详解

### 2.1 `frontend/package.json`

**作用**：前端工程清单，声明运行/构建依赖与 5 个 npm 脚本。
**被谁使用**：`npm install` / `npm run dev` / `npm run build`；`scripts\build-all.bat` 一键构建脚本调用其中的 `build`。
**关键设计点**：

1. **依赖全本地闭环**：`dependencies` 只有 8 个包，没有任何 CDN / 远程字体 / 在线图标服务，满足「私有化、内网离线部署、断网可完整走通评估闭环」的交付要求（README 第七节）。
2. **构建即类型门禁**：`build` 脚本先跑 `vue-tsc --noEmit` 再 `vite build`，类型不过直接构建失败，避免带类型错误的产物进入验收环节。
3. **另留 `build:only` 逃生口**：离线机器上若 `vue-tsc` 因缺少 node 类型缓存报错，可用它跳过类型检查快速出包，不影响功能验证。

### 2.2 `frontend/vite.config.ts`

**作用**：Vite 构建与开发服务器配置，是「离线部署 + 任意子路径 + 前后端分离」三项要求在工程侧的落地文件。
**被谁使用**：`npm run dev`、`npm run build`、`npm run preview`；`loadEnv` 读取 `.env*` 中的 `VITE_API_TARGET`（当前仓库未提供 `.env` 文件，走默认值）。
**关键设计点**：

1. **`base: './'`（第 16 行）——相对路径基址**：产出物中所有资源引用写成 `./assets/xxx.js` 而非 `/assets/xxx.js`。这样 `dist/` 既能放在站点根 `http://host/`，也能直接放在子路径 `http://host/ees/`、`http://host:8081/app/`，甚至用 `file://` 打开静态页也能加载资源，**换部署路径不需要重新构建**。这是「B/S 架构、主流浏览器访问 + 私有化离线部署」两条要求的工程保障。
2. **`/api` 代理（第 27-32 行）只在开发期生效**：开发时前端跑在 5173、后端跑在 8080，浏览器直接请求 8080 会撞同源策略；代理把 `/api/**` 转发到 `target`，前端代码里统一使用相对路径 `/api/xxx`（见 `api/index.ts`），因此**同一份前端代码在开发环境走代理、生产环境由后端单 jar 直接托管（也可走 Nginx 反向代理），无需改任何业务代码**。
3. **`manualChunks` 三包拆分（第 41-45 行）**：把 `vue + vue-router + pinia`、`element-plus + @element-plus/icons-vue`、`echarts` 拆成三个独立 chunk。收益有三：①**缓存粒度更细**——业务代码改动时这三个大包文件名（带内容 hash）不变，浏览器继续用缓存，只重新下载业务包；②**并行下载**——三个包可并发拉取，缩短首屏时间；③**体积可控**——`echarts` 与 `element-plus` 体积大且几乎不随业务变动，单独成包后主包（业务代码）显著变小。
4. **彻底无 CDN**：配置里没有任何 `external`、没有 `rollupOptions.external` 把依赖挂到全局变量，也没有在 `index.html` 里引入 `https://cdn...` 脚本；字体同样使用系统字体栈（见 `styles/index.scss` 第 48-49 行）。所有依赖都被打包为本地文件，断网环境可用。

- `base: './'` 必须配合 **hash 路由**（见 `router/index.ts`）才能真正免 rewrite：history 模式下刷新 `/ees/tasks/1` 时服务端找不到该路径，仍需 Nginx 配置 `try_files`。

- 仓库当前没有 `.env` 文件，`VITE_API_TARGET` 只声明在 `env.d.ts` 中（默认值生效）；若要改代理目标，需自行新建 `.env.local` 或在系统环境变量中设置。

### 2.3 `frontend/tsconfig.json`

**作用**：TypeScript 工程的**根配置**，本身不参与编译，只声明两个子工程引用（project references）。
**被谁使用**：编辑器/IDE 的语言服务以它作为工作区入口；`npm run build` 显式指定 `-p tsconfig.app.json`，不经过本文件。
**关键设计点**：`files: []` + `references` 是最小化复合配置写法——只做「引用聚合」，让 IDE 知道这个目录下有两个独立编译上下文，同时避免根配置的 `compilerOptions` 污染子工程。

| 行号 | 代码 | 说明 |
|---|---|---|
| 1 | `{` | 配置对象开始 |
| 2 | `"files": []` | 显式指定本工程不含任何源文件，因此不会有独立编译产物 |
| 3-6 | `"references": [ {"path": "./tsconfig.app.json"}, {"path": "./tsconfig.node.json"} ]` | 引用浏览器侧与 Node 侧两个子工程；两者的 `lib`、`types`、`include` 完全不同，必须分开，否则会出现「浏览器代码里能写 `process`」或「vite.config.ts 里报找不到 `document`」这类错误 |
| 7 | `}` | 结束 |

**易错点/注意**：不要在本文件里补 `compilerOptions`；需要调编译选项时改对应的 `tsconfig.app.json` / `tsconfig.node.json`。

### 2.4 `frontend/tsconfig.app.json`

**作用**：浏览器侧（`src/**` + `env.d.ts`）的 TypeScript 编译选项，是 `vue-tsc` 类型检查的实际依据。
**被谁使用**：`npm run build`、`npm run type-check` 都显式 `-p tsconfig.app.json`。
**关键设计点**：

1. `noEmit: true`：TS 只做类型检查，**产物完全由 Vite/esbuild 生成**，避免 TS 编译与 Vite 转换两套流程结果不一致。
2. `strict: true` 但 `noUnusedLocals`/`noUnusedParameters` 关掉：真正影响正确性的严格检查全开，而「未使用的变量」这类纯风格问题不阻塞构建——业务页面中常留临时变量，若开启会把类型门禁变成噪音源。
3. `forceConsistentCasingInFileNames: true`：保证文件名大小写严格一致，防止「Windows 上能编译、Linux 服务器上找不到模块」的部署事故（本项目要部署到 Nginx/Linux）。

### 2.6 `frontend/env.d.ts`

**作用**：项目级环境类型声明，让 TS 认识 Vite 客户端 API、`.vue` 模块与自定义环境变量。
**被谁使用**：被 `tsconfig.app.json` 的 `include` 显式收录，作用于整个 `src/`。
**关键设计点**：

1. `declare module '*.vue'` 是 Vue + TS 工程**必需的一段**：没有它，`import EesChart from './EesChart.vue'` 会在类型检查期报「找不到模块」。
2. `ImportMetaEnv` 只声明了**被允许使用**的环境变量，等于给 `import.meta.env` 加白名单，写错名字立刻报错。

| 行号 | 代码 | 说明 |
|---|---|---|
| 1 | `/// <reference types="vite/client" />` | 三斜线引用：引入 Vite 客户端类型，提供 `import.meta.env`、`import.meta.glob`、`?raw` 等；`tsconfig.app.json` 的 `types` 中没有列 `vite/client`，靠这一行补上 |
| 3-7 | `declare module '*.vue' { ... }` | 声明所有 `.vue` 文件的模块形状 |
| 4 | `import type { DefineComponent } from 'vue'` | 仅类型导入；`isolatedModules` + `type` 前缀可避免被转成运行时 import |
| 5 | `const component: DefineComponent<{}, {}, any>` | 把默认导出声明为通用组件类型；三个泛型参数（Props/Slots/…）用宽泛的 `{}`/`any`，因为真正的类型信息由 `vue-tsc` 从 SFC 内部推断，这里只负责「让 import 通过」 |
| 6 | `export default component` | 与 SFC 编译产物（默认导出组件）对应 |
| 9-12 | `interface ImportMetaEnv { readonly VITE_API_TARGET?: string; readonly VITE_APP_TITLE?: string }` | 声明两个可用环境变量：`VITE_API_TARGET` 被 `vite.config.ts` 第 13 行读取用于代理目标；`VITE_APP_TITLE` 为**预留项，当前代码中未见使用**（已确认仅出现在本文件） |
| 14-16 | `interface ImportMeta { readonly env: ImportMetaEnv }` | 把上面的环境变量接口挂到 `import.meta.env` 上，使 `import.meta.env.VITE_API_TARGET` 有类型 |

**易错点/注意**：`VITE_APP_TITLE` 目前是空挂声明，不要误以为站点标题可由此配置——实际标题在 `index.html` 第 7 行与 `router/index.ts` 第 190 行的 `document.title` 中硬编码。

### 2.7 `frontend/index.html`

**作用**：单页应用宿主 HTML，是 Vite 构建的入口（`vite build` 默认以根目录 `index.html` 为入口）；同时承担两件"不能依赖打包产物"的事——首屏加载占位与**入口脚本加载失败兜底**。
**被谁使用**：浏览器直接加载；`vite build` 处理它并注入打包后的 `<script>`/`<link>`。
**关键设计点**：

1. **内联 SVG favicon（第 8 行）**：图标以 `data:image/svg+xml,...` 形式直接写在 `href` 里，浏览器**不会**再发起 `/favicon.ico` 请求。收益是彻底消除那个常见的 404 请求，且在完全离线的内网环境、`file://` 打开、任意子路径部署下都能正常显示——不依赖任何静态文件路径。
2. **首屏 `boot-loading` 占位（第 12-15 行）**：在 JS 主包下载、解析完成之前，页面先显示一个转圈动画和「效能评估系统正在加载…」文案，避免长时间白屏。Vue 的 `app.mount('#app')` 会清空容器原有子节点，因此挂载后该占位自动消失，**不需要额外清理代码**。
3. **样式内联（第 18-29 行）**：占位样式直接写在 `<style>` 里而不放进 `styles/index.scss`——因为 `index.scss` 要等 JS 主包加载后才被注入，那时占位早该消失了；内联后浏览器在解析阶段就能渲染出加载态，也不会有 CSS 阻塞导致的白屏闪烁。
4. **入口加载失败兜底（第 30-50 行，本次改动新增）**：内联 `<script>` 用 `setTimeout(..., 12000)` 延迟 12 秒检查 `#app .boot-loading` 是否还在——正常挂载后 Vue 会清空 `#app`，占位不复存在，脚本直接 `return`；若仍在，说明入口资源（`src/main.ts` 打包后的 chunk）没能加载成功，此时移除转圈元素、把容器内容替换为「页面加载失败 / 可能是系统已更新，或浏览器缓存了旧文件。请点击下面的按钮重新加载。」+ 一个「重新加载」按钮（`#boot-retry`，点击执行 `window.location.reload()`）。**它必须内联在这里**：出现该故障时打包产物本身已不可信（浏览器里停留的旧页面引用了已被替换掉的 chunk 文件名），不能指望任何外部脚本或组件库来提示，所以只用原生 DOM API 与内联样式。

| 行号 | 代码 | 说明 |
|---|---|---|
| 1 | `<!DOCTYPE html>` | HTML5 文档声明 |
| 2 | `<html lang="zh-CN">` | 声明语言为简体中文，影响字体回退与浏览器翻译提示 |
| 3-4 | `<head>` / `<meta charset="UTF-8" />` | 必须用 UTF-8，否则页面中的中文文案会乱码 |
| 5 | `<meta name="viewport" content="width=device-width, initial-scale=1.0" />` | 移动端/缩放适配，保证在演示用笔记本与投影仪上比例正常 |
| 6 | `<meta http-equiv="X-UA-Compatible" content="IE=edge" />` | 强制使用最新渲染内核；内网机器若默认开兼容性视图，没有这几行可能进 IE7 模式导致白屏 |
| 7 | `<title>效能评估系统</title>` | 页面标题；路由切换后由 `router/index.ts` 第 189-190 行改写为「页面名 - 效能评估系统」 |
| 8 | `<link rel="icon" href="data:image/svg+xml,..." />` | 内联 SVG 图标：蓝色圆角方块（`%231f6feb` 即 `#1f6feb`，与设计令牌 `--ees-primary` 同色）+ 四根白色柱子，呼应「效能评测」业务语义。内联后无外部请求、无路径依赖 |
| 10 | `<body>` | 主体开始 |
| 11 | `<div id="app">` | Vue 挂载点，与 `main.ts` 第 31 行的 `app.mount('#app')` 对应 |
| 12-15 | `<div class="boot-loading">` + 旋转器 + `<p>效能评估系统正在加载…</p>` | 首屏占位块；文案与后端服务无关，纯前端加载等待提示 |

| 17 | `<script type="module" src="/src/main.ts"></script>` | 应用入口脚本；`type="module"` 以 ESM 方式加载。开发时由 Vite 直接提供；构建时 Vite 会把它替换为打包后的哈希文件名，且因为 `base: './'` 会被改写为相对路径 |
| 18-29 | `<style> ... </style>` | 内联首屏样式 |
| 19-23 | `.boot-loading { display:flex; ... height:100vh; background:#f4f7fb }` | 占位区全屏居中；背景色 `#f4f7fb` 与设计令牌 `--ees-workbench-bg` 一致，挂载后视觉无缝衔接，不出现颜色跳变；字体栈与 `styles/index.scss` 中的 `body` 保持一致 |

| 30-50 | `<script> ... </script>`（**本次改动新增**） | 入口加载失败兜底：第 31-34 行注释写明动机（12 秒后占位还在 ⇒ 入口资源没加载成功，例如系统更新后浏览器仍引用旧文件）；第 35-49 行 `setTimeout(function () {...}, 12000)`——第 36-37 行取 `#app .boot-loading` 并判空（已经挂载则直接返回，不打扰正常页面）、第 38-39 行移除 `.boot-spinner`、第 40-46 行用 `innerHTML` 写入「页面加载失败」标题 + 原因文案 + `#boot-retry` 按钮（全部内联样式，不依赖 Element Plus）、第 47-48 行取到按钮后绑定 `window.location.reload()` |

**易错点/注意**：占位内容必须在 `#app` **内部**。若放在 `#app` 之外，Vue 挂载不会清除它，加载完成后会一直留在页面底部；兜底脚本判断的也是 `#app .boot-loading` 这个后代选择器，把占位挪出 `#app` 会让兜底一并失效。
**易错点/注意**：12 秒是"慢网络下仍在正常加载"与"确实已经失败"之间的折中，不要随手改小——把正常但慢的加载误判为失败，会把可用页面替换成错误提示，反而制造故障。
**易错点/注意**：不要在此处添加任何指向外部域名的资源（CDN 脚本、Google Fonts、在线 favicon），否则会破坏「断网可用」这一验收项；兜底脚本同样刻意只用原生 DOM API 与内联样式，不引入任何依赖。

### 2.8 `frontend/src/main.ts`

**作用**：应用装配入口，创建 Vue 实例，安装 Pinia、路由、Element Plus，注册全部图标，设置全局错误处理，最后挂载；并在创建应用之前清理历史版本遗留在 `localStorage` 里的登录令牌。
**被谁使用**：`index.html` 第 17 行加载；`router`、`stores`、所有页面组件最终都挂在这棵实例树上。
**关键设计点**：

1. **Element Plus 中文 locale（第 4、24 行）**：`zhCn` 让分页器、日期选择器、表格空数据文案、`ElMessageBox` 的「确定/取消」等内置文本全部为简体中文。若不指定，组件内部默认英文，会在中文界面上出现「No Data」「OK」等不协调文案，这在验收时属于明显的界面缺陷。
2. **图标全量注册（第 5、18-20 行）**：把 `@element-plus/icons-vue` 的所有导出注册为全局组件。这样 `router/index.ts` 的 `meta.icon` 可以只写字符串（`'Odometer'`、`'Folder'`），`MainLayout.vue` 与 `StatCard.vue` 用 `<component :is="item.icon" />` 动态渲染。**代价**是图标全部进入产物（约几百 KB，已被 `manualChunks` 归入 `element` 包），**收益**是新增页面时不必逐个 import，配置化程度高——在离线内网、功能优先的场景下这个取舍是合理的。
3. **全局错误处理不向用户暴露堆栈（第 26-29 行）**：`app.config.errorHandler` 只把异常打到控制台供运维排查，**不弹窗、不显示堆栈**。这是私有化交付的安全与体验要求：面向领导/评审的演示环境中出现红色堆栈既影响观感，也可能泄露内部实现细节。
4. **安装顺序（第 22-24 行）**：Pinia 必须在 router 之前安装。因为 `router/index.ts` 的全局守卫里会调用 `useUserStore()`，而 `useUserStore()` 依赖已激活的 Pinia 实例；顺序颠倒会在首次导航时抛「getActivePinia 未安装」类错误。
5. **启动时清理历史遗留令牌（第 10、13-14 行，本次改动新增）**：在 `createApp` 之前调用一次 `dropLegacyPersistentToken()`（自 `./api/request` 引入），把老版本写在 `localStorage` 里的那个 `ees_token` 删掉。原因是**登录态已改为会话级**（令牌存 `sessionStorage`）：旧令牌留在 `localStorage` 里没有有效期，最长还能生效一个 JWT 周期（默认 480 分钟），等于「关掉浏览器再打开仍会自动以上一个账号进入系统」，与本次改动的目的直接冲突。放在创建应用之前执行，是为了在任何业务代码（含 Pinia store 初始化时读取令牌）之前就把存储清干净；清理函数内部用 `try/catch` 包住，浏览器禁用本地存储（隐私模式等）时静默跳过，不影响启动。

| 行号 | 代码 | 说明 |
|---|---|---|

### 2.9 `frontend/src/App.vue`

**作用**：根组件，只做一件事——渲染当前路由组件并为切换加上过渡动画。
**被谁使用**：`main.ts` 第 16 行 `createApp(App)`；所有页面（`MainLayout` 及 `Login`、`NotFound`）都是它的子节点。
**关键设计点**：

1. **`router-view` 的插槽写法（第 2 行）**：用 `v-slot="{ Component }"` 取出当前匹配组件，再交给 `<component :is>` 渲染，这样才能在中间插入 `<transition>`。直接写 `<router-view />` 无法包过渡。
2. **`mode="out-in"`（第 3 行）**：先播放旧页面离场动画，再播新页面入场动画，避免两个页面同时存在造成的高度跳动与布局闪动。
3. **动画只做轻微位移（第 17-24 行）**：入场 `translateY(6px)`、离场 `translateY(-4px)`，时长 0.18 s。幅度和时长都很克制——这是面向业务系统的取舍：动画仅用于提示「页面已切换」，不能拖慢操作节奏，也不能在密集看数据时造成干扰。
4. **`<script setup lang="ts">` 为空（第 9-10 行）**：根组件无需任何状态与逻辑，保持为空是显式声明「这里没有业务逻辑」，不做多余包装。

| 2 | `<router-view v-slot="{ Component }">` | 具名插槽方式取出当前路由组件，暴露为 `Component` 变量 |
| 3 | `<transition name="fade-slide" mode="out-in">` | 使用名为 `fade-slide` 的过渡，模式为「先出后进」 |
| 4 | `<component :is="Component" />` | 动态渲染当前路由组件 |

| 17-20 | `.fade-slide-enter-from { opacity: 0; transform: translateY(6px) }` | 入场起始态：透明且略微下沉，实现「向上浮现」的观感 |

### 2.10 `frontend/src/router/index.ts`

**作用**：定义全部路由（登录、主框架下的 18 个业务子路由、404 兜底），配置 hash 路由模式，实现「标题设置 → 登录校验 → 拉取用户 → 菜单级授权」的全局前置守卫（后三步即通常所说的三步守卫），并统一兜住**路由懒加载失败**（`router.onError`）。
**被谁使用**：`main.ts` 第 9、23 行安装；`MainLayout.vue` 通过 `<router-view>` 承载子路由，并用 `route.meta.title` 渲染面包屑；`api/request.ts` 401 分支用 `#/login` 跳转。
**关键设计点**：

1. **hash 路由选型（第 1、139 行 + 第 5-7 行注释）**：`createWebHashHistory()` 使 URL 形如 `http://host/ees/#/tasks/1`。**井号之后的内容不会发给服务端**，因此无论刷新、收藏、直接粘贴链接，服务端永远只需返回同一个 `index.html`。这带来两个直接好处：①离线部署到 Nginx、IIS 甚至 `file://` 时**完全不需要配置 rewrite/`try_files` 规则**，运维零门槛；②与 `vite.config.ts` 的 `base: './'` 配合，前端可以整体挪到任意子路径而无需重新构建。代价只是 URL 中多一个 `#`，对内部业务系统不构成问题。
2. **路由表与 `meta.menu` 的关系**：每条业务路由的 `meta.menu` 是一个**模块标识**（`dashboard`/`project`/`indicator`/…），共 14 个。它与后端 `AuthService.menusOf()` 返回的菜单码**逐字对应**，而 `menusOf()` 现在只有两个角色分支：`SYSTEM_ADMIN` 返回全部 14 个（`dashboard, project, indicator, dataSource, dataBatch, snapshot, task, result, report, baseline, user, role, audit, config`），`EVALUATOR` 返回 9 个（`dashboard, project, indicator, dataBatch, snapshot, task, result, report, baseline`）；`DATA_ADMIN`（9 个）、`REVIEWER`（5 个）、`VIEWER`（4 个）这三个角色**已随角色精简从前后端与数据库删除**，`menusOf()` 中不再有它们的 `case`（编码未匹配到已知角色时走 `default -> List.of("dashboard")` 兜底）。前端拿到 `menus` 数组后，既用于侧栏菜单过滤（`MainLayout.vue` 的 `visibleMenus`），也用于守卫里的菜单级授权。**同一套码值承担「显示过滤」与「访问拦截」两个职责**，避免两处配置漂移。
3. **三步守卫（第 188-233 行）**：
   - **第一步 · 登录校验**：`public` 路由直接放行；否则 `isLogin`（本地有令牌）为假就跳登录页，并把当前地址塞进 `query.redirect`，登录后可回到原页面。
   - **第二步 · 拉取用户**：令牌存在但用户信息未加载（刷新页面后 Pinia 内存清空、只剩 `sessionStorage` 里的令牌——同一标签页内刷新不会清空会话存储）时调用 `loadUser()` 向 `/api/auth/me` 补拉权限与菜单。失败说明令牌已失效，`resetLocal()` 清干净再跳登录，避免带着无效令牌死循环。
   - **第三步 · 菜单级授权**：比对 `to.meta.menu` 与 `hasMenu()`，无权则**重定向到驾驶舱**而不是抛 403 页面——驾驶舱是所有角色的公共可见页，这样处理既安全又不给用户「撞墙」体验。**这里还有一条本次新增的保护（第 214-230 行）**：当目标本身就是 `/dashboard` 时不再重定向，而是在控制台打一条 `[EES]` 警告后直接放行。原因是驾驶舱自己也带 `meta.menu = 'dashboard'`，一旦后端漏返回 `menus`（前端认为该角色没有任何菜单权限），「驾驶舱 → 驾驶舱」的重定向会让守卫反复触发、整页白屏；放行后最坏只是少几个菜单。
4. **隐藏路由的标记方式（第 42、78、90 行）**：详情页 `indicators/:id`、`tasks/:id`、`results/:id` 都带 `hidden: true`，且**不带 `icon`**。它们不在侧栏菜单里出现（`MainLayout.vue` 的 `menuTree` 里根本没有这三条），但**保留了 `meta.menu`**，因此仍受同一个菜单级授权约束；同时 `MainLayout` 的 `activeMenu` 会把它们的路径归并回列表页，保证侧栏高亮不丢。
5. **全部组件懒加载**：除守卫外，每个 `component` 都写成 `() => import(...)`，Vite 会为每个页面单独切 chunk，实现按路由分包，首屏只加载登录页。
6. **懒加载失败的兜底 `router.onError`（第 144-186 行，本次新增）**：懒加载的代价是**产物更新即失效**——重新构建后 chunk 文件名带新的内容 hash，浏览器里停留的旧页面再去加载旧 chunk 必然 404，界面只剩白屏且没有任何提示。兜底逻辑分三层：① 第 156-163 行的 `CHUNK_ERROR_HINTS` 白名单匹配动态导入失败的典型文案（`Failed to fetch dynamically imported module`、`Importing a module script failed`、`error loading dynamically imported module`、`Loading chunk`、`Loading CSS chunk`、`Unable to preload CSS`），第 165-168 行 `isChunkLoadError()` 只对这些文案返回 `true`，避免把普通运行时错误也当成资源失效；② 第 170-171 行的 `chunkReloading` 进程内标志 + `sessionStorage` 键 `ees:chunk-reload-at` 做**10 秒节流**（第 177-183 行），防止刷新后又失败导致无限刷新；③ 命中且未节流时先 `ElMessage.warning('检测到系统已更新，正在自动刷新页面…')`，400 ms 后再 `window.location.reload()`（第 184-185 行，留出提示渲染时间）；若 10 秒内再次失败，则改成 `ElMessage.error('页面资源加载失败，请按 Ctrl + F5 强制刷新后重试')` 的人工指引。这条兜底与 `index.html` 第 30-50 行的入口兜底是**两级防线**：前者管"页面已挂载、点菜单时 chunk 失效"，后者管"入口主包就没加载起来"。

### 2.11 `frontend/src/stores/user.ts`

**作用**：全局用户状态：持有令牌与当前用户信息，提供权限判定 `has()`、菜单判定 `hasMenu()`，以及登录、拉取用户、登出、本地重置四个动作；登录、登出、本地重置三处都会顺带清空 `stores/app.ts` 的「当前项目」上下文。
**被谁使用**：`router/index.ts`（守卫）、`MainLayout.vue`（显示名、角色、菜单过滤、改密码后登出）、几乎全部业务页面（`userStore.has('xxx:yyy')` 控制按钮显示）。
**关键设计点**：

1. **`has()` 权限判定（第 31-37 行）**：两级短路——① **超级管理员直接放行**（`isSuperAdmin` 为真立即 `return true`）；② **通配符 `*` 放行**。之后才做逐项比对，且支持传入数组（`list.some()`，任一项命中即可）。超级管理员放行是为了避免「新增权限码忘记配给 admin」导致管理员反而做不了事；`*` 通配则是给「全部权限」角色的显式写法。
2. **`hasMenu()`（第 40-43 行）**：同样对超管放行；非超管严格按后端返回的 `menus` 数组判定。**它控制的是「模块级」可见性**，粒度比 `has()` 的「按钮级」权限码粗，二者配合形成「菜单能看见 / 按钮能用」的两层控制。
3. **`login` / `loadUser` / `logout` / `resetLocal` 的差异**：
   - `login`（第 45-57 行）：**主动认证**。调接口拿到 `token` 与 `user`，写内存 + 写 `sessionStorage`（会话级），并置 `loaded = true`；最后清空上一个账号留下的「当前项目」上下文（第 51-55 行，见关键设计点 5）。
   - `loadUser`（第 59-66 行）：**被动补拉**。仅在「有令牌」时可用；默认命中内存缓存直接返回，只有 `force = true` 或缓存为空时才请求 `/api/auth/me`。刷新页面（同一标签页）后由守卫调用它恢复权限。
   - `logout`（第 68-80 行）：**先通知后端再清本地**。调 `/api/auth/logout` 让后端审计/吊销（失败也不阻断，`catch` 里注释写明「本地状态仍需清理」），然后清空 `token`/`user`/`loaded`、删掉 `sessionStorage` 中的令牌，并清空「当前项目」上下文（第 78-79 行）。
   - `resetLocal`（第 82-88 行）：**纯本地清理**，不调后端。用于「令牌已失效」场景（守卫第二步 `loadUser` 失败，`router/index.ts:204-212`；`request.ts` 的 401 分支也做同样的本地清理），此时请求后端没有意义甚至可能再次失败；同样清空「当前项目」上下文（第 87 行）。
4. **令牌改存 sessionStorage 的取舍（本次改动）**：**收益**——登录态不再跨浏览器会话残留。改之前令牌放在 `localStorage` 里，而 `localStorage` 没有有效期，关掉浏览器、重启电脑后它仍在，于是「打开网址就自动以上次那个账号进入系统」；共用电脑上等于把上一个人的身份（可能还是管理员）交给下一个人。改为 `sessionStorage` 后，**关闭浏览器再打开就必须重新登录**（同一标签页内刷新不受影响）。**代价**——`sessionStorage` 按标签页隔离，**新开标签页需要重新登录**；对单人单窗口的日常使用影响很小，代价换来的是共用终端上的身份隔离。至于令牌对同源 JS 可见、理论上存在 XSS 窃取风险这一点，**并未因这次改动而改变**：本项目仍通过「不引入任何外部脚本、不使用 `v-html` 渲染用户输入、内容全部本地打包」来压缩攻击面；而改用 `httpOnly` Cookie 需要后端配合 CSRF 防护与跨域凭据配置，且会与「下载接口支持 `?token=`」的设计冲突，因此当前方案仍是**刻意取舍**，不是疏忽。令牌自身的有效期不变，仍由后端 `ees.security.jwt-expire-minutes`（默认 480 分钟）控制。
5. **`login` / `logout` / `resetLocal` 都清空「当前项目」上下文（提交 `747fec4`，第 4、55、79、87 行）**：这是本次改动的核心，也是「令牌改存会话级」之后**残留的最后一处跨会话身份痕迹**。`stores/app.ts` 的 `currentProjectId` 存在 `localStorage: ees_project_id`（第 7-9、21-28 行），而 `localStorage` 没有有效期——上一个账号在驾驶舱选的项目，会被下一个登录的人继续带着去请求。改之前这只是「默认筛选不同」；**改动之后它会直接导致加载失败**：后端 `DashboardService.overview()` 对 `?projectId=` 先做可见性校验（`ProjectService.checkVisible`，与 `ProjectService.get(id)` 同一口径），该账号看不到这个项目就返回 **403**，驾驶舱整页统计进空态。因此在三处动作里各加一行 `useAppStore().setCurrentProject(undefined)`（`setCurrentProject(undefined)` 会删除 localStorage 键，见 2.12），生命周期与身份严格对齐：**换人登录（`login`）、主动登出（`logout`）、令牌失效被踢（`resetLocal`）之后，项目上下文一律归零为「全部项目」**。文件顶部为此新增 `import { useAppStore } from './app'`（第 4 行）——这是 `stores/user.ts` 唯一一处跨 store 依赖，方向是「用户态 → UI 态」，不会形成循环（`stores/app.ts` 不反向引用本文件）。注意**它刻意不动 `currentProjectId` 之外的任何东西**：记住的用户名（`ees_remember_user`）属于登录页的便利功能，不随登出清除。

### 2.13 `frontend/src/api/request.ts`

**作用**：前端与后端之间的**唯一 HTTP 通道**：创建 Axios 实例、注入令牌、统一判定业务响应、统一处理 401/403/超时、封装 `get/post/put/delete/upload/download`；同时是**令牌存储的唯一入口**（会话级 `sessionStorage` 读写 + 历史遗留令牌清理）。
**被谁使用**：`src/api/index.ts` 的所有模块对象；`stores/user.ts` 的 `getToken/setToken/clearToken`；`main.ts` 第 10、14 行的 `dropLegacyPersistentToken()`；个别页面直接使用 `http.download`（通过 `api/index.ts` 间接）。
**关键设计点**：

1. **统一响应拦截（第 86-94 行）**：后端所有接口都返回 `{ code, message, data, timestamp }` 外壳，`code === 0` 才代表业务成功（API.md 约定）。拦截器只在这一处判定，业务代码拿到的永远是「已经成功的 `data`」，不必每个调用点都写 `if (res.code === 0)`。判定前先检查 `typeof body.code === 'number'`，是为了兼容少数不返回该外壳的响应（如静态资源、纯文本），这类响应原样返回。
2. **401 用 `ElMessageBox` 引导重登 + `redirecting` 防重入（第 66、101-118 行）**：一个页面可能同时并发 5～6 个请求（如结果分析页同时拉详情、文本、表格、图表），令牌过期时会**同时**收到多个 401。若不防重入，就会连续弹出多个「登录状态已失效」对话框，用户点掉一个又冒一个，体验极差。`redirecting` 是一个模块级布尔值，第一个 401 把它置为 `true` 并弹框，后续 401 直接跳过弹框（但仍 `reject`，让各调用方正常走异常分支）。弹框关闭（确认或取消）时把标志复位，保证下一轮会话还能正常提示。跳转用 `window.location.href = '#/login'` 接 `window.location.reload()`：**全量重载**能彻底清空 Pinia 内存里残留的用户信息与页面状态，比 `router.push` 更干净。
3. **blob 下载响应的特殊分支（第 82-84 行）**：下载接口返回的是二进制流，**没有** `code/message/data` 外壳，如果按 JSON 逻辑去读 `body.code`，`body` 是 `Blob`，`body.code` 为 `undefined`，会走到第 94 行的兜底分支——虽然不报错，但下载流程需要读取**响应头** `Content-Disposition`，而兜底分支只返回 `response.data`，把 headers 丢了。因此在拦截器最前面显式判断 `responseType === 'blob'` 并返回**整个 `response`**，让 `download()` 能同时拿到 `headers` 与 `data`。
4. **`http.download()` 从 `Content-Disposition` 解析中文文件名（第 170-178 行）**：文件名由后端在响应头里给出。中文文件名有两种编码方式：`filename*=UTF-8''%E6%8C%87%E6%A0%87...`（RFC 5987，Percent-Encoding）与 `filename="xxx.xlsx"`（普通形式）。代码**优先匹配 `filename*=UTF-8''`**，因为后端导出中文报告时通常用这种形式；`decodeURIComponent` 还原为可读中文。若拿不到（后端只给了普通形式或没给），退回普通匹配，再退回调用方传入的 `fallbackName`（如「指标体系导入模板.xlsx」）。**顺序不能颠倒**——若先匹配普通 `filename=`，会把 `filename*=UTF-8''xxx` 中的用户名部分误截取成乱码。
5. **`upload()` 单独放宽超时到 600 秒（第 151-160 行）**：默认实例超时是 120 s（第 62 行），但文件上传走的是完全不同的量级——指标体系 CSV 可能几千行、试验数据 XLSX 可能数万行、还支持 ZIP 打包上传，后端要完成解压、逐行解析、指标匹配、质量规则校验、落库，耗时可能几分钟。若沿用 120 s，前端会在后端还在正常处理时先超时并提示失败，用户以为没成功而重复提交，直接造成**重复数据批次**。因此把上传与下载的超时独立设为 600 s，与后端 Excel 模板导入、报告生成的实际耗时上限对齐。
6. **令牌改为会话级存储（第 22、24-33、34-44、46-58 行，本次改动）**：`getToken/setToken/clearToken` 三个函数统一读写 `sessionStorage`（键名仍是 `ees_token`），不再是过去的 `localStorage`。原因见第 24-33 行的新增注释：`localStorage` **没有有效期**，关掉浏览器、重启电脑后令牌仍在，于是「打开网址就自动以上次那个账号进入系统」，共用电脑上等于把上一个人的身份（可能还是管理员）交给下一个人；改为 `sessionStorage` 后**关闭浏览器再打开就必须重新登录**，**同一标签页内刷新不受影响**，**代价是新开标签页需要重新登录**（会话存储按标签页隔离）。第 46-58 行的 `dropLegacyPersistentToken()` 负责清掉历史版本遗留在 `localStorage` 里的同名旧令牌——不清的话那个令牌会一直留在本机、最长仍生效 8 小时，与「不再持久保存登录态」的意图相悖；它由 `main.ts` 启动时调用一次，函数内部用 `try/catch` 兜住浏览器禁用本地存储（隐私模式等）的场景。**令牌自身的有效期没有变化**，仍由后端 `ees.security.jwt-expire-minutes`（默认 480 分钟）控制。

**易错点/注意**：成功分支返回的是**整个 `ApiResult` 外壳**而不是 `body.data`，因此必须经 `request()` 再取一次 `.data`。若某处直接 `await service(...)`，拿到的是带 `code/message` 的对象，容易误用。
**易错点/注意**：业务失败时拦截器**已经弹过一次 `ElMessage.error`**；调用方在 `catch` 里再弹一次会出现重复提示。约定是：调用方只负责复位 loading、记录状态，不重复提示。
**易错点/注意**：`download()` 返回 `Promise<void>`，没有返回值；若后端在下载接口上返回了 JSON 错误体（如 404 报告不存在），响应拦截器会因为 `responseType === 'blob'` 直接放行，前端会下载到一个内容是 JSON 的「假文件」。当前实现如此，使用时应确保下载地址有效。
**易错点/注意**：令牌已改为会话级（`sessionStorage`），因此**关闭浏览器再打开需要重新登录**，**新开标签页也需要重新登录**（会话存储按标签页隔离），只有同一标签页内刷新不受影响；浏览器「复制标签页」在不同浏览器上的行为不一致，不要依赖它保持登录态。不要再把令牌写回 `localStorage`——`localStorage` 里的 `ees_token` 已由 `main.ts` 启动时调用 `dropLegacyPersistentToken()` 清掉，写回去等于让「关掉浏览器仍自动登录」的问题复发。

### 2.14 `frontend/src/api/index.ts`

**作用**：把后端 REST 接口按业务模块组织成 12 个对象（`authApi`、`systemApi`、`userApi`、`projectApi`、`indicatorApi`、`dataSourceApi`、`dataBatchApi`、`snapshotApi`、`taskApi`、`resultApi`、`reportApi`、`baselineApi`），并定义 `LoginUser`、`LoginResponse`、`ChartData` 等共享类型。
**被谁使用**：全部业务页面与 `stores/user.ts`；`ChartData` 同时被 `utils/chartOptions.ts` 与 `components/ChartCard.vue` 引用。
**关键设计点**：

1. **「一模块一对象」的组织方式**：页面里写 `import { taskApi } from '@/api'` 后 `taskApi.cancel(id)`，比散落各处写 `http.post('/api/evaluation-tasks/' + id + '/cancel')` 更安全——URL 只在这里出现一次，后端改路径时只改一处；同时方法名（`cancel`/`retry`/`publish`）直接对应业务动作，代码可读性高。
2. **模块与后端 Controller 的一一对应关系**：

   | 前端模块 | 对应后端 Controller | 路径前缀 |
   |---|---|---|
   | `authApi` | `AuthController` | `/api/auth` |
   | `systemApi` | `SystemController`（驾驶舱、审计、参数、质量规则、算法基准）+ `HealthController`（`health`/`info`）+ `UserController`（`permissions`） | `/api` |
   | `userApi` | `UserController` | `/api/users`、`/api/roles`、`/api/permissions` |
   | `projectApi` | `ProjectController` | `/api/projects` |
   | `indicatorApi` | `IndicatorController` | `/api/indicator-versions` |
   | `dataSourceApi` | `DataSourceController` | `/api/data-sources` |
   | `dataBatchApi` | `DataBatchController` | `/api/data-batches` |
   | `snapshotApi` | `SnapshotController` | `/api/snapshots` |
   | `taskApi` | `TaskController` | `/api/evaluation-tasks` |
   | `resultApi` | `ResultController` | `/api/evaluation-results` |
   | `reportApi` | `ReportController` | `/api/reports` |
   | `baselineApi` | `SystemController` | `/api/baselines` |

   注意 `systemApi` 是**跨 Controller 的聚合模块**：它归集了「系统级」接口，其中 `/api/permissions` 实际由 `UserController` 提供（该 Controller 的类级映射是 `/api`，方法级映射才是 `/users`、`/roles`、`/permissions`）。
3. **`PageResult<T>` 的作用**：为所有分页接口（用户、项目、指标版本、数据源、数据批次、快照、评估任务、评估结果、报告、审计日志）提供统一的返回类型。它是 `request.ts` 中的接口，被本文件 `import type` 后用在 `http.get<PageResult>(...)` 上，使页面里 `res.records`、`res.total`、`res.pages` 都有类型提示，也统一了「分页列表」的心智模型。
4. **`ChartData` 的作用**：图形数据的**宽类型**（带索引签名 `[key: string]: any`）。八类图形的数据结构差异很大（柱状图有 `categories`+`series`，热力图有 `xLabels`+`yLabels`+`data`，箱线图有 `boxData`+`outliers`），但共享 7 个元字段（`chartType/title/unit/description/dataSource/emptyReason/generatedAt`）。用「固定元字段 + 索引签名」表达，既让 `ChartCard` 能统一展示标题/单位/来源并判断 `emptyReason`，又不强迫为 8 种结构写 8 个接口。`chartOptions.ts` 的每个构造函数再按 `chartType` 从 `any` 里取出自己需要的字段——**这是类型安全与八类图形异构性之间的折中**。

### 2.15 `frontend/src/utils/format.ts`

**作用**：全站共用的格式化与字典工具：数值/分数/权重/百分比/日期时间/时长/文件大小格式化、安全 JSON 解析、13 个业务字典导出（1 个选项数组 + 12 个映射表）、评判等级配色类生成、质量阻断文案提取。
**被谁使用**：几乎全部 `views/**` 页面；`LevelTag.vue` 使用 `levelClass`；`AuditLogList.vue` 使用 `AUDIT_MODULE_LABEL`；`TaskDetail.vue` 使用 `REVIEW_LABEL`/`PUBLISH_LABEL`/`parseJson`。
**关键设计点**：

1. **`parseJson`（第 58-67 行）——本文件最重要的函数**。后端有若干字段是**以 TEXT 列存储的 JSON**（`IndicatorVersion.validateResult`、`DataBatch.qualityReport` 与 `errorDetail`、`EvaluationTask.parameters` 与 `inputSummary`、`EvaluationResult.extra`、`SysAuditLog` 的详情映射），这类字段经 Jackson 序列化后**返回给前端的是字符串**而不是对象。若直接 `data.parameters.gradeNames` 会得到 `undefined`（字符串上没有该属性），页面会静默显示空白。`parseJson` 做三件事：①**空值短路**（`null`/`undefined`/`''` 直接返回调用方给的 `fallback`）；②**已是对象就原样返回**（兼容某些接口用 `@JsonRawValue` 或 MyBatis 之类映射成对象的情况，避免二次 `JSON.parse` 报错）；③`try/catch` 包裹 `JSON.parse`，解析失败返回 `fallback` 而**不抛异常**——历史脏数据、手工改库留下的非法 JSON 都不会让整个页面白屏。注意 `(v ?? fallback)`：即使 `JSON.parse` 成功但结果是 `null`，也回退到 `fallback`。
2. **`levelClass` 的等级配色（第 177-180 行）**：把评判等级映射成 CSS 类 `ees-level-tag ees-level-<等级>`。关键在于**白名单校验**：只有「优/良/中/差」四个标准等级才拼进类名，其他任何值（空、`null`、后端未来新增的等级、被篡改的字符串）一律归为 `未评级`。这既避免了「`ees-level-undefined` 这种不存在的类导致无样式」，也**防止了把任意字符串拼进 `class` 属性造成的属性注入**。配色本身定义在 `styles/index.scss` 第 326-345 行：优=绿、良=蓝、中=橙、差=红、未评级=灰。
3. **各字典与后端枚举的对应关系**（全部已核对后端源码；共 13 个导出，下表把 3 组同域导出合并为一行——算法选项与算法名映射、任务状态名与标签色、版本状态名与标签色——共 10 行覆盖全部 13 个导出）：

**易错点/注意**：`fmtNum` 的 `placeholder` 默认是半角连字符 `-`；若某处需要「—」（长破折号）或「N/A」，要显式传第三个参数，不能指望默认值。
**易错点/注意**：`TASK_STATUS_TYPE` 返回的是 Element Plus 的 `type` 取值（`success`/`warning`/`danger`/`primary`/`info`），不是颜色值；直接拿去当 CSS 颜色是错的。
**易错点/注意**：所有字典的下标访问都应保留 `\|\| x` 兜底（如 `PROJECT_STATUS_LABEL[row?.status] \|\| row?.status`），后端新增枚举值时界面显示原始常量总好过显示空白。

### 2.16 `frontend/src/utils/chartOptions.ts`

**作用**：把后端返回的图形数据（`ChartData`）转换为 ECharts 的 `option` 对象，覆盖八类图形：柱状图、折线图、饼图（拆两个）、雷达图、散点图、热力图、箱线图、排名条形图。
**被谁使用**：`components/ChartCard.vue`（第 44、62-63 行）是唯一调用方；`ChartCard` 又被 `views/result/ResultDetail.vue` 第 463-470 行连续使用 8 次。`Dashboard.vue` 自带两个简易 option（趋势图、等级分布），不经过本文件。
**关键设计点**：

1. **`buildChartOption` 的分发（第 39-62 行）**：一个 `switch (chart.chartType)` 按类型分发到 7 个构造函数（饼图除外）。**第 40 行的双重前置判断**是本文件的守门逻辑：`if (!chart || chart.emptyReason) return null` —— 数据对象不存在、或后端明确给出了 `emptyReason`（数据不足）时**直接返回 `null`，不构造任何 option**。这与方案 7.3「结果一致性」要求一致：**宁可不画图，也不能画出与表格数据不一致或误导性的图形**。`ChartCard` 收到 `null` 后会切换到「显示原因」而非「显示空图」的分支。`default` 分支返回 `null`，使未来新增图形类型时老版本前端能安全降级。
2. **`PALETTE` / `GRADE_COLOR` 的取值原则（第 4-27 行）**：
   - `PALETTE` 是一个 10 色循环色板，**首色 `#1f6feb` 与设计令牌 `--ees-primary` 完全一致**，保证图表与界面同色系；后续 9 色按「绿—橙—红—紫—青—橙红—青绿—紫—灰」的次序展开，相邻色相有足够区分度，且整体偏中低饱和度，打印成黑白报告时明度差也够。数组固定写死（不随机生成），保证**同一份数据每次渲染配色完全相同**——这是结果可复现的基本要求。
   - `GRADE_COLOR` 是**语义色**：优=绿 `#17a673`、良=蓝 `#1f6feb`、中=橙 `#e6a23c`、差=红 `#e04b4b`、未评级=灰 `#8b98ad`。**它与 `styles/index.scss` 的 `.ees-level-*` 配色、以及 Element Plus 的 success/primary/warning/danger 语义色三者一致**，因此同一份结果在表格里的等级标签、饼图的等级扇区、热力图的等级色块、排名条形图的条形颜色都是同一个颜色含义，用户不需要二次学习。取值原则是「等级色不参与 PALETTE 的循环」——等级是**语义分类**，不能用位置色板随意赋值。
3. **`num()` 辅助函数（第 29-33 行）**：把任意值转为 `number | null`。它承担**「只转类型、不算数值」**的职责：后端 JSON 里的数字有时被序列化成字符串（尤其来自 MySQL `DECIMAL` 的权重），ECharts 对字符串数据点可能渲染异常或按类目处理；`num()` 统一转成数字。**注意它不做任何业务计算**（不求和、不归一、不排序），严格守住「前端只渲染」的边界。
4. **八类图形的 option 构造逐个说明**：

   - **① 柱状图 `barOption`（第 65-99 行）**：`categories` 作 x 轴类目，`series` 数组（后端给出得分/贡献值/权重三条）逐条映射为 `type: 'bar'`。关键取舍：`barMaxWidth: 34` 防止类目很少时柱子宽得难看；`borderRadius: [3,3,0,0]` 只圆上方两角；`emphasis: { focus: 'series' }` 让鼠标悬停时高亮整条系列、其余变淡，便于多系列对比；`axisLabel.interval: 0` **强制显示每一个类目名**（ECharts 默认会自动隐藏过密的标签，指标名被抽掉会让人看不懂图）；类目数 >5 时标签旋转 28°、宽度截断 110px；类目数 >12 时**自动挂上 `dataZoom` 滑块**（`start: 0, end: 60`，初始只显示前 60%），避免几十个指标挤在一起。`grid.bottom: 62` 是给旋转后的标签和 dataZoom 留位置。
   - **② 折线图 `lineOption`（第 102-149 行）**：用于「多批次/多时间点趋势」。`boundaryGap: false` 让首尾数据点贴住坐标轴两端（趋势图的标准画法）；`smooth: true` 平滑曲线；`symbol: 'circle'` + `symbolSize: 7` 保留数据点标记，便于定位具体批次；`areaStyle` 用**线性渐变**（第 111-120 行）从 `rgba(31,111,235,0.22)` 渐变到 `0.02`，形成向下淡出的面积填充——注意渐变的 `colorStops` 用的是固定的主题蓝透明度，不随系列索引变色（多系列时面积仍为同色系，避免面积叠加后颜色混乱）。类目 >8 时标签旋转 26°，>14 时挂 dataZoom。
   - **③ 饼图——拆成两个独立 option（`buildPieChartOptions`，第 151-195 行）**：**这是本文件最重要的设计决策**。后端 `pie` 图形一次返回两组数据：`weightPie`（指标权重构成）与 `levelPie`（评判等级分布）。**为什么要拆成两个独立 option？** ①**两者语义完全不同**——一个是「权重占比」（同一个对象内部各指标的相对重要性，合计 100%），一个是「等级分布」（多个对象落在各评判等级的数量，合计为对象总数）。**把两组不同量纲的数据塞进同一张饼图会得出错误结论**（例如把 40% 的权重和 6 个「良」画在一个环里，读者会误以为它们在比较）。②**配色规则不同**——权重图用 `PALETTE` 位置色（每个指标一个色，颜色只是区分），等级图必须用 `GRADE_COLOR` 语义色（良必须是蓝、差必须是红），见第 154-163 行两个 `map` 的差异。③**布局不同**——`ChartCard.vue` 第 26-29 行把两张图并排放在 `.pie-pair` 网格里（各占 50%，窄屏下自动上下堆叠），若合成一张则只能做成双环，可读性差。函数内部还用 `make(data, title)` 工厂（第 165-185 行）复用同一套环形配置：`radius: ['40%','64%']` 是**环形图**（中空便于放图例/避免中心色块过重）；`tooltip.formatter: '{b}: {c} ({d}%)'` 展示名称、数值、百分比；`legend.type: 'scroll'` 在指标很多时可滚动翻页；`avoidLabelOverlap: true` 防止标签互相压盖；`label` 用 `'{b}\n{d}%'` 两行显示名称与百分比。第 188-189 行**只在对应数据非空时**才生成该 option（返回 `null`），因此「只有权重数据、没有等级数据」时也只会渲染一张图，而不是渲染一张空白饼图。第 193-195 行的 `pieOptionPlaceholder()` 是一个**显式占位**：`buildChartOption` 在主 `switch` 里遇到 `chartType === 'pie'` 时返回它（即 `null`），并在第 47 行注释说明「饼图由 `buildPieChartOptions` 拆分为两个独立图形」。这样做的好处是**调用约定清晰**——`ChartCard` 只要看到 `chartType === 'pie'` 就改走 `buildPieChartOptions` 分支，主分发函数不会误返回一张单图。
   - **④ 雷达图 `radarOption`（第 198-228 行）**：`radar.indicator` 由 `indicatorNames` 映射为 `{name, max}` 数组（`max` 取后端给的 `chart.max`，默认 100），形成多维坐标轴。`series` 只有一个 `type: 'radar'`，其 `data` 是「每个对象一条」的数组（`{name, value: [...]}`）；`areaStyle: { opacity: 0.14 }` 半透明填充以便多对象叠加对比；`legend.type: 'scroll'` 应对对象较多的情况；`axisName.fontSize: 11.5` 让指标名在小尺寸卡片里也不至于挤成一团；`splitArea` 用极浅的白/淡蓝交替填充，帮助读数。**注意 `value` 数组的顺序必须与 `indicatorNames` 严格一致**——这由后端保证，前端只做 `map(num)`，不重排。
   - **⑤ 散点图 `scatterOption`（第 231-272 行）**：用于观察两项指标之间的关系。后端 `points` 是 `[x, y, 对象名]` 三元组数组，第 232 行 `(chart.points \|\| []).map((p) => [num(p[0]), num(p[1]), p[2]])` **保留第三个元素**（对象名）——ECharts 的散点数据支持附加维度，这样自定义 `tooltip.formatter`（第 235-243 行）能在悬停时显示「对象名 + x 指标名: 值 + y 指标名: 值」。x/y 轴都是 `type: 'value'`，轴名用后端给的 `xIndicatorName`（回退到编码 `xIndicatorCode`），x 轴 `nameLocation: 'middle'` + `nameGap: 28` 把轴名放到轴下方居中位置。数据点样式用**半透明主题蓝**（`rgba(31,111,235,0.75)`）加白色描边：点重叠时颜色会叠加变深，这本身就是「此处数据密集」的可视信号，比不透明点更有信息量。
   - **⑥ 热力图 `heatmapOption`（第 275-319 行）**：呈现「指标 × 对象」的得分矩阵。第 276 行把 `chart.data` 的元素从 `{value:[x,y,得分], indicatorCode, objectCode, indicatorName}` **只取出 `value` 三元组**构成 ECharts 需要的数据（多余字段不传给 ECharts，避免其内部处理无关属性）；自定义 tooltip（第 280-283 行）用 `chart.yLabels[y]` 与 `chart.xLabels[x]` 把下标还原成对象名与指标名。**`visualMap` 的分档配色（第 300-309 行）是本图的核心**：`min`/`max` 取后端给的得分区间（默认 0~100），`inRange.color` 给出 5 段渐变色 `['#fdeaea', '#fdf3e3', '#e8f1fe', '#e6f7f0', '#17a673']`——**从浅红（低分）经浅橙、浅蓝、浅绿到实绿（高分）**，正好复用 `styles/index.scss` 里 `.ees-level-差/中/良/优` 的背景色阶梯，使得「热力图的颜色深浅」与「等级标签的颜色」含义一致。`calculable: true` 让用户可拖动 visualMap 的滑块动态筛选区间（例如只看 60 分以下）；`orient: 'horizontal'` + `left: 'center'` + `bottom: 8` 把色带放在图下方居中，不占用左侧空间。第 314 行 `label.show` 有条件开启——**只有当 x 类目数 × y 类目数 ≤ 40 时才在格子里显示数值**，超过 40 格则关闭，否则数字会糊成一片反而看不清颜色。`emphasis` 给悬停格子加阴影，让「当前看的是哪一格」一目了然。
   - **⑦ 箱线图 `boxplotOption`（第 322-364 行）**：展示各对象的得分分布（最小值、下四分位、中位数、上四分位、最大值）与离群点，用于判断稳定性。**数据组织是本题的难点**：后端给出 `boxData: [[min,q1,median,q3,max], ...]` —— 直接就是 ECharts `boxplot` 系列需要的五数概括格式，第 323 行只做 `map(num)` 而不重新计算分位数（**这正是「前端不重算」的具体体现：若在前端算分位数，就会与后端表格里展示的统计量产生口径差异**）。而**离群点必须转成 `[类目下标, 值]` 的散点**：后端 `outliers` 是「按类目分组的二维数组」，第 324-327 行用两层 `forEach` 把 `outliers[idx]` 里的每个值 `v` 展开成 `[idx, num(v)]`——第一维是 x 轴类目下标，第二维是数值，这样才落在对应类目的竖直位置上。图中共两个系列：`boxplot` 系列用**半透明填充 + 实线描边**（`rgba(31,111,235,0.16)` 填充、`#1f6feb` 1.6px 边框、`boxWidth: [10, 38]` 控制箱体与须线宽度），`scatter` 系列画离群点（红色 `#e04b4b`、`symbolSize: 7`）——**红色离群点与蓝色箱体形成强对比**，用户一眼就能看到「哪些对象的成绩异常偏低或偏高」。
   - **⑧ 排名条形图 `rankBarOption`（第 367-415 行）**：按综合得分给对象排名。**为什么把数组 `reverse()`（第 370-374 行）**：这里画的是**横向条形图**（x 轴是数值、y 轴是类目），而 ECharts 的类目轴**默认自下而上排列**——`categories[0]` 画在**最底部**，最后一个类目在最顶部。后端给的 `categories`/`series[0].data`/`rankings`/`levels` 都是**按得分降序**（第一名在前）。若不反转，第一名会出现在图的**底部**，与「排行榜从高到低、从上往下读」的直觉完全相反。因此第 371-374 行对四个数组**同时反转**：`revCats`（类目）、`revData`（得分）、`rankings`（名次）、`levels`（等级）。**四个数组必须一起反转**，否则 tooltip 里的名次和等级会张冠李戴。反转后：最后一名在最底、第一名在最顶，符合阅读习惯。其余细节：`grid.left: 128` 给左侧对象名留足宽度；`yAxis.axisLabel.width/overflow: 'truncate'` 在对象名过长时省略号截断；`label: { position: 'right', formatter: '{c}' }` 在条形末端直接标数值；**条形颜色由等级决定**——第 409 行 `color: (p) => GRADE_COLOR[levels[p.dataIndex]] \|\| '#1f6feb'` 是一个**回调函数**，按当前数据点索引查语义色，因此图上「优」是绿的、「差」是红的，一眼看出分布；`borderRadius: [0,4,4,0]` 只圆右侧两角（横向条形图的正确圆角方向）。tooltip 用自定义 formatter（第 380-384 行）显示「第 N 名　对象名 / 综合得分：x　等级：y」，其中 `p.dataIndex` 正是反转后数组的下标，`rankings[i]` 与 `levels[i]` 已同步反转，因此对应正确。
5. **所有 option 只做「渲染」，不做数值重算**（对应方案 7.3 结果一致性要求）：通读全文可以看到，本文件**没有任何求和、平均、排序、归一化、分位数计算或百分比换算**。所有数值——得分、贡献值、权重、五数概括、排名、等级、占比——都由后端在同一份评估结果数据集上算好后返回。前端只做三件事：①**类型归一**（`num()` 把字符串转数字）；②**结构重组**（把后端的二维离群点数组改成 ECharts 需要的 `[idx, value]` 散点、把 `chart.data` 的对象数组取出 `value` 三元组）；③**视觉映射**（配色、圆角、标签、缩放）。**这样做的根本原因是「三处展示必须同源」**：结果分析页的文本、表格、图形三种展示形式（对应方案对「结果展示 ≥ 3 种」的要求）以及导出的 Excel/Word/PDF 报告，必须给出完全一致的数值。若前端在画图时自行计算（例如按自己的规则重新分等级、自己算百分比），就会出现「表格里是 82.35 分（良），图里画成 82.4 分（优）」这类无法解释的矛盾，而这在评审与答辩场合是致命的。第 35-38 行的函数级注释把这条约束写在最显眼的位置：「数据全部来自后端评估结果数据集，前端不做任何数值重算（方案 7.3 结果一致性）」。

### 2.17 `frontend/src/styles/index.scss`

**作用**：全局样式入口：定义设计令牌（CSS 自定义属性）、页面基础样式、通用布局类、指标卡片、图表区、深色侧栏、等级标签语义色，并对 Element Plus 做少量局部覆盖。
**被谁使用**：`main.ts` 第 11 行全局导入；所有 `views/**` 页面用其中的 `ees-page`、`ees-card`、`ees-filter-bar`、`ees-stat-grid`、`ees-chart-grid` 等通用类拼装页面；`MainLayout.vue` 通过 `ees-sidebar` 给侧栏换肤；`LevelTag.vue` 通过 `levelClass()` 输出 `.ees-level-*` 类。
**关键设计点**：

1. **设计令牌集中定义（第 6-33 行）**：所有颜色、尺寸、圆角、阴影都在 `:root` 里以 `--ees-*` 命名。好处是**换肤只改一处**（例如甲方确认品牌色后只需改 `--ees-primary` 一行），并且组件里不出现硬编码色值，不会出现「这里蓝一点那里蓝一点」的不一致。命名上区分了三组：**品牌语义色**（primary/success/warning/danger/info，与 Element Plus 语义一致）、**结构尺寸**（侧栏宽 232px、顶栏高 58px）、**工作台色**（背景、卡片、边框、三级文字色）。
2. **浅色工作台与深色侧栏两套风格（方案 7.4 混合式 UI）**：文件头注释与令牌分组明确体现了这一设计——**深色侧栏**用 `--ees-sidebar-bg: #101a2c` 到 `--ees-sidebar-bg-2: #16233a` 的垂直渐变，配 `--ees-sidebar-text: #a9b6cc` 的中灰文字；**浅色工作台**用 `--ees-workbench-bg: #f4f7fb` 作底、`--ees-card-bg: #ffffff` 作卡片。这样领导驾驶舱/结果页看起来有「看板」的视觉分量，而数据管理、系统管理等长时间录入的页面保持浅浅的、不刺眼的工作台底色。两套风格共用同一套品牌色，因此不是两个割裂的界面。
3. **通用类（`ees-` 前缀）**：所有自定义类都加 `ees-` 前缀，**避免与 Element Plus 的 `el-` 前缀以及将来引入的其他库冲突**。这些类是**全局类**（不在任何组件的 `scoped` 样式里），因此可以被任意页面直接使用；组件自身的私有样式才写在各自的 `<style scoped>` 中。核心通用类的作用：`ees-page`（页面外边距）、`ees-card`（白底卡片）、`ees-filter-bar`（筛选条）、`ees-chart-grid`（图表网格，`minmax(430px, 1fr)` 自适应列数）、`ees-stat-grid` + `ees-stat`（指标卡片，`minmax(196px, 1fr)`）。
4. **等级标签配色类 `.ees-level-优/良/中/差`（第 328-347 行）**：**用中文作类名后缀**是刻意选择——`levelClass()` 直接把后端返回的等级字符串拼进类名，中文类名让「代码里的类名」与「业务上的等级」逐字对应，读 CSS 时不需要查映射表。每个等级是「浅色背景 + 同色系深色文字」的组合（优：`#e6f7f0` 底 / `#17a673` 字；良：`#e8f1fe` 底 / `#1f6feb` 字；中：`#fdf3e3` 底 / `#d68b1f` 字；差：`#fdeaea` 底 / `#e04b4b` 字；未评级：`#eef1f6` 底 / `#6b7c93` 字），保证在白底与灰底上都有足够对比度，且**浅色背景不会像实心色块那样在密集表格里造成视觉噪音**。这些背景色同时被 `chartOptions.ts` 的 `visualMap.inRange.color` 复用，实现「标签色 = 热力图色」的一致性。
5. **对 Element Plus 的局部覆盖（第 354-363 行）**：只改三处，**改动面刻意压到最小**——①表头背景改为 `#f7f9fd` 并加粗，让密集表格的表头与数据行有明确分界；②`el-descriptions` 的标签列改为次级文字色，弱化标签、突出值；③新增 `ees-scroll-x` 通用横向滚动类（供宽表格使用）。前两处都带 `!important`，原因是 Element Plus 组件内部选择器（如 `.el-table th.el-table__cell`）本身特异性较高，且组件样式可能在运行时被动态注入，`!important` 能确保覆盖稳定生效；同时 `styles/index.scss` 在 `main.ts` 中于 `element-plus/dist/index.css` **之后**导入（第 11 行 vs 第 6 行），保证顺序上也是后者覆写前者。
6. **`.ees-chart-head` 允许换行（提交 `5f8ba79`，第 242-250 行）**：图卡头原本是 `display:flex` + `justify-content:space-between`（左标题、右操作按钮），**提交 `5f8ba79` 起驾驶舱「任务趋势」卡头右侧多了一整行统计区间控件**（快捷区间下拉 + `el-date-picker` 起止日期，见 09 分册 2.3.6）。这些控件宽度是固定的（110px + 232px），在 `.ees-chart-grid` 的双列布局里卡片被压到 430px 左右时，若不换行就会把左侧标题挤到变形甚至溢出。加上 `flex-wrap: wrap` 后，空间不足时右侧控件自动折到标题下方一行——**这是「往既有卡头里塞控件」的标准解法：不改卡片宽度、不加媒体查询，只让卡头自己换行**。代价是图卡总高度会随换行略增，但因为图表容器高度由 `height="280px"` 固定，不会引起图表重排抖动。

### 2.18 `frontend/src/components/EesChart.vue`

**作用**：通用 ECharts 容器组件，负责实例的创建、渲染、尺寸自适应、图片导出与销毁。
**被谁使用**：`ChartCard.vue`（第 27-31 行，饼图用了两个实例、其他图一个实例）、`Dashboard.vue`（第 151、166 行两个实例）。
**关键设计点**：

1. **实例生命周期收口在这一个组件里**：`echarts.init` → `setOption` → `resize` → `dispose` 全部只在本文件出现，页面里不再直接接触 ECharts API。好处是**防内存泄漏只需改一处**：ECharts 实例持有 canvas、事件监听与内部计时器，若只把 DOM 从页面移除而不 `dispose()`，实例会一直留在内存中，长时间使用（反复切换结果、翻页）会持续涨内存直至卡顿。
2. **`ResizeObserver` 自适应（第 31-32 行）**：只监听 `window.resize` 是不够的——本项目里图表尺寸变化有更常见的触发路径：**侧栏折叠/展开**、**`.ees-chart-grid` 因窗口变窄而改变列数（图表被重新排布）**、**`el-tab` 切换标签页**。这些都不会触发 `window.resize`。用 `ResizeObserver` 直接监听容器元素尺寸变化，上述所有场景都能覆盖；同时第 45 行仍保留 `window.addEventListener('resize')` 作为兜底（部分老浏览器对 `ResizeObserver` 支持不完整）。
3. **`shallowRef` 而非 `ref` 保存实例（第 24 行）**：`ref` 会对对象做深度响应式代理，而 ECharts 实例内部持有大量 DOM 引用、算法对象与循环引用。把实例塞进深度响应式代理会带来两个问题：**性能损耗**（Vue 递归遍历代理）与**潜在错误**（某些内部判断在 Proxy 包裹下行为异常）。`shallowRef` 只对 `.value` 的赋值做响应，这正是这里需要的最小响应能力。
4. **`setOption(option, true)` 的第二个参数（第 34 行）**：`true` 表示 **notMerge**——完全替换旧配置而不是合并。合并模式下，上一次渲染的 series 若在新 option 里不存在，会**残留**在图上（比如从三个系列的柱状图切到单系列的排名图，会看到幽灵柱子）。用 notMerge 保证每次渲染都是干净状态。紧随其后的 `chart.resize()` 处理「option 内容改变导致图例/坐标轴占位变化」的情况。
5. **`getDataURL` 导出图片（第 63-66 行）**：`pixelRatio: 2` 生成 **2 倍分辨率**图片，粘贴到 Word/PPT 报告里放大也不模糊；`backgroundColor: '#ffffff'` 显式指定**白色背景**——ECharts 默认导出透明背景，粘到深色文档或转为 JPEG 时会变成黑底，白底是报告场景的正确选择。

### 2.19 `frontend/src/components/ChartCard.vue`

**作用**：图形卡片组件，把一张图形连同它的元信息（标题、副标题、单位、数据来源、导出按钮）打包成一个完整卡片；负责「数据不足时展示原因」与「饼图双图并排」两个特殊分支。
**被谁使用**：`views/result/ResultDetail.vue` 第 463-470 行连续使用 8 次，对应八类图形。
**关键设计点**：

1. **`emptyReason` 必须展示原因而不是空图（第 18-23 行，对应方案 7.3）**：当后端返回的图形数据里带 `emptyReason` 时（例如「该任务只有 1 个被评估对象，无法绘制箱线图」「缺少两个不同指标的数据，无法生成散点图」），前端显示一个带条纹底纹的提示区，把**原因原文**呈现给用户，并补一句口径说明「图形数据全部来自后端评估结果数据集，与表格同源」。**为什么不能画空图**：结果分析页的文本、表格、图形三种展示必须同源（方案 7.3 结果一致性）。如果这里画一张空坐标系，用户会怀疑「是不是系统算错了、数据丢了」；明确写出「为什么不能画」既解释了系统行为，也**反向证明了图形与表格同源**——只有在数据确实不足以支撑某种统计图形时才缺图，而不是因为渲染失败。
2. **饼图双子图分支（第 25-29 行）**：`isPie` 为真时不用单个 `EesChart`，而是渲染两个并排的实例（权重构成 + 等级分布）。这与 `chartOptions.ts` 把饼图拆成两个 option 的设计**必须配套**：`ChartCard` 是唯一知道「饼图要画两张」的地方，`buildChartOption` 对饼图返回 `null` 的约定在此被正确接住。窄屏（≤720px）时 `.pie-pair` 降为单列上下堆叠。
3. **每卡独立导出 PNG（第 73-87 行）**：每张图右上角有一个下载按钮，点击导出**当前这张图**的 PNG。实现上按 `isPie` 分支取对应的模板 ref——饼图优先取左图（权重构成）的实例。文件名直接用 `chart.title`，因此导出的文件天然叫「指标权重构成.png」「评判等级分布.png」，多张图导出后不会互相覆盖、也不需要用户重命名。
4. **`empty` 的三重判定（第 64-71 行）**：①没有 `chart` 对象或带 `emptyReason` → 空；②是饼图 → 两个子 option 都为空才算空（**只有一组数据时仍要画一张图**）；③其他图形 → `option` 为 `null` 才算空。这个判定与 `chartOptions.ts` 的返回约定严格对齐，保证「有 option 就一定有图、没 option 就一定显示原因」。

### 2.23 `frontend/src/layouts/MainLayout.vue`

**作用**：主框架（深色侧栏 + 浅色工作台）。负责：侧栏菜单树渲染与按权限过滤、当前路由高亮归并、顶栏面包屑、服务健康轮询、用户下拉（改密码/退出）、修改密码表单与校验、子路由承载与缓存。
**被谁使用**：`router/index.ts` 第 16 行作为 `/` 父路由的组件；所有业务子路由都渲染在它的 `<router-view>` 中。
**关键设计点**：

1. **`menuTree` 静态菜单树 + `visibleMenus` 按 `userStore.hasMenu` 过滤（第 143-186 行）**：`menuTree` 是**前端本地定义的菜单结构**（含分组：`/data` 下挂数据源/数据批次/数据快照，`/system` 下挂用户/角色/审计/参数），与 `router/index.ts` 的 `meta.menu` 取值逐字对应，也与后端 `AuthService.menusOf()` 的菜单码一致。`visibleMenus` 做两层过滤：**有 `children` 的分组**只保留有权限的子项，且**子项全被过滤掉时整个分组不显示**（第 180 行 `if (children.length) result.push(...)`）——否则会出现一个空的可展开分组，用户点开发现什么都没有；**无 `children` 的单项**直接按 `menu` 码判定。超管的 `hasMenu` 恒为 `true`，因此管理员看到全部菜单。
2. **`activeMenu` 对 detail 路由的高亮归并（第 188-194 行）**：`/tasks/1`、`/results/5`、`/indicators/3` 这些详情页**不在侧栏菜单里**（它们是 `hidden` 路由，`menuTree` 中也没有对应条目）。若直接把 `route.path` 交给 `el-menu` 的 `default-active`，详情页时**没有任何菜单项能被匹配到，侧栏高亮会整个消失**，用户会失去「我在哪个模块」的定位感。因此 `activeMenu` 把三类详情路径归并回它们的列表页前缀。这不是视觉美化，而是**导航可用性的必要修复**。
3. **健康状态轮询（第 207-219 行，60 秒）**：`onMounted` 里拉一次 `/api/health`，然后 `window.setInterval(loadHealth, 60000)` 每 60 秒刷新。**为什么是 60 秒**：健康检查是免登录的轻接口，60 秒的粒度足以让运维在服务挂掉后一分钟内从顶栏发现（标签变「服务异常」），又不会造成可感知的请求压力；内网部署、无人值守的场景下这个折中很实用。失败时把 `health` 置为 `{ status: 'DOWN' }`（第 212 行）而**不弹错误提示**——健康检查失败本身就是需要展示的信息，再弹一个错误框属于重复打扰。`onUnmounted` 里清除定时器避免泄漏。
4. **用户下拉（第 65-85、268-281 行）**：三项：①「当前账号：xxx」只展示信息、点击无动作；②「修改密码」打开对话框；③「退出登录」**先 `ElMessageBox.confirm` 二次确认**，用户取消时 `catch` 后直接 `return`（不执行登出），确认后 `await userStore.logout()` 再 `router.push('/login')`。二次确认的必要性：顶部下拉容易误触，登出会丢掉当前未提交的筛选与分页状态。
5. **修改密码表单校验与二次确认（第 230-266 行）**：三条规则——原密码必填；新密码必填且**长度 6~64**（与后端密码策略对齐）；确认密码用**自定义 `validator`** 比对两次输入是否一致。提交成功后 `ElMessage.success('密码修改成功，请重新登录')` → 关闭对话框 → `await userStore.logout()` → `router.push('/login')`。**改密后强制重新登录**是安全惯例：旧令牌可能仍在别处有效，重新认证能确保新密码立即生效且会话干净。
6. **侧栏折叠与样式（第 3-4、13-19、44-47 行 + 样式）**：折叠状态存在 `appStore.sidebarCollapsed`，宽度由 `appStore.sidebarWidth` 派生（64px/232px）。折叠时品牌区只留 `EES` 方块（`brand--mini`）、`el-menu` 的 `:collapse` 生效只显示图标。**侧栏底部原来的信息区（`.aside-foot`：`Connection` 图标 + 「离线内网部署」+ `v{{ version }}` 版本号）已随提交 `546ef92` 整块删除**（原第 40-46 行）——需求就是删掉左侧栏底部这块文字，因此它不再随折叠显隐，源码中也不再有 `aside-foot` 相关模板、脚本与样式。`collapse-transition="false"` 关闭 Element Plus 的折叠动画，因为**宽度过渡由 `.layout-aside` 的 `transition: width .2s ease` 统一控制**，两者同时动画会互相干扰产生抖动。
7. **子路由缓存（第 90-94 行）**：`<keep-alive :max="6">` 最多缓存 6 个页面组件，`:key="route.fullPath"` 让**不同路径参数视为不同实例**（`/results/1` 与 `/results/2` 各自缓存）。作用是在列表页与详情页间来回切换时保留列表的页码、筛选条件与滚动位置；上限 6 是内存与体验的折中（结果分析页含 8 个 ECharts 实例，缓存过多会显著占内存）。

- **登录态是会话级的（提交 `0a82886`）**：令牌存 `sessionStorage` 而不是 `localStorage`，因此**关闭浏览器再打开需要重新登录**、**新开标签页也需要重新登录**，只有同一标签页内刷新不受影响；令牌自身的有效期不变（后端 `ees.security.jwt-expire-minutes`，默认 480 分钟）。改动的动机是 `localStorage` 没有有效期，共用终端上会把上一个人的身份（可能还是管理员）带给下一个人。历史版本遗留在 `localStorage` 里的 `ees_token` 由 `main.ts` 启动时调用 `dropLegacyPersistentToken()`（`api/request.ts`）一次性清除。**注意 `localStorage` 里仍有两个刻意保留的键**：`ees_project_id`（`stores/app.ts`，当前项目上下文）与 `ees_remember_user`（登录页，只存用户名），它们不是登录态。
- **「当前项目」上下文也必须随身份清零（提交 `747fec4`）**：令牌改到 `sessionStorage` 解决了身份凭据的跨会话残留，但 `ees_project_id` 仍在 `localStorage` 里长期存留。后端把驾驶舱统计改为按数据权限过滤（`visibleProjectIds()`：`null` = 管理员不限制、否则只统计可见项目）之后，这个残留 id 会直接换回 **403** 而不是一份空数据——于是 `stores/user.ts` 在 `login`/`logout`/`resetLocal` 三处调用 `useAppStore().setCurrentProject(undefined)`，`Dashboard.vue` 再加一道「本地 id 不在可见项目列表中就重置」的安全网。**本册的结论是：凡是跨会话保留的状态，都要在「身份变更」的三个出口上显式清理，不能指望下一个页面自己发现。**
- **「离线内网」是贯穿全册的第一约束**：`package.json` 的依赖全部本地打包、`vite.config.ts` 无任何 CDN 与外部资源、`index.html` 用内联 SVG favicon 避免外部请求、`styles/index.scss` 使用系统字体栈、`EesChart.vue` 全量引入本地 echarts、`main.ts` 的全局错误处理不向用户暴露堆栈。交付时「断网后完整走通评估闭环」这一验收项就是靠这条链条保证的。
- **「结果一致性」是贯穿全册的第二约束（方案 7.3）**：`utils/chartOptions.ts` 全篇只做类型归一、结构重组与视觉映射，**不求和、不排序、不重算分位数、不换算百分比**；数据不足时 `buildChartOption` 返回 `null`、`ChartCard` 展示后端给出的 `emptyReason` 而不是画空图。这样结果分析页的文本、表格、图形三处展示以及导出的报告必然同源同值。
- **权限控制是「三层防线」，前端只是第一层**：`router/index.ts` 的守卫做菜单级拦截（无权则回驾驶舱）、`stores/user.ts` 的 `has()`/`hasMenu()` 做按钮与菜单显隐、后端方法级权限做最终校验。前端的两层只是**体验优化**，不是安全边界；`has()` 的「超管放行 + `*` 通配」两级短路保证了管理员不会因为漏配权限码而被挡住。
- **同一套「菜单码」串起了后端、路由与侧栏三处**：后端 `AuthService.menusOf()` 的 14 个码 → 路由 `meta.menu` → `MainLayout.menuTree` 的叶子项。这是本册最容易被误解的地方——三处必须逐字一致，任一处拼错都会出现「菜单能看见但点进去被弹回」或「路由能访问但侧栏无入口」的隐蔽缺陷。
- **接口层被收口在两处文件**：所有 HTTP 行为（会话级令牌读写与历史遗留令牌清理、令牌注入、`code===0` 判定、401 防重入引导重登、blob 与文件名解析、上传/下载超时）集中在 `api/request.ts`；所有 URL 与业务方法集中在 `api/index.ts`。页面只调用 `xxxApi.方法名()`，**URL 字符串不在任何页面出现**，后端改路径时改动面可控且可检索。
