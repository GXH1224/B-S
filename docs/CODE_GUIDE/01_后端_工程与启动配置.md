## 2. 逐文件详解

### 2.1 `pom.xml`（仓库根，聚合工程）

**作用**：仓库根的空壳聚合工程，不产出任何构件，只声明"`backend` 是本工程的一个模块"。
**被谁使用**：IntelliJ IDEA 打开仓库根目录时读取它完成 Maven 导入；命令行 `mvn -pl backend <goal>` 时由它定位子模块。
**关键设计点**：
1. 用聚合工程（`packaging=pom`）而不是把后端 pom 直接放在根目录，是为了让 IDEA 一次性识别"项目根 + backend 模块"，从而能直接使用 `.idea/runConfigurations/` 里预置的三个运行配置（其中 `① 启动系统（后端 + 页面 8080）` 的 `workingDirPath=$PROJECT_DIR$/backend`）。
2. 模块名 = 子工程 `artifactId` = `evaluation-backend`，与 `backend/pom.xml` 第 15 行一致；Maven 的 `-pl backend` 用的是**目录名**，两者容易混淆。
3. 只设 `project.build.sourceEncoding=UTF-8` 一项属性：编码错误是中文项目最常见的低级故障，在聚合层统一声明可避免子模块遗漏。

### 2.2 `backend/pom.xml`

**作用**：后端唯一的依赖与构建清单，定义 Java 21 + Spring Boot 3.5.16 基线，并把编译参数、打包插件一次性固定下来。
**被谁使用**：`mvn spring-boot:run` / `mvn clean package` 的全部构建行为；`spring-boot-maven-plugin` 产出 `target/evaluation-backend.jar`（由 `finalName` 固定），`docs/DEPLOY.md` 3.2 的 `java -jar target\evaluation-backend.jar` 依赖这一命名。
**关键设计点**：
1. **版本集中在两处**：Spring 生态的版本交给 `spring-boot-starter-parent` 的依赖管理（因此下面所有 starter 都不写 `<version>`，避免版本漂移）；第三方库版本抽成本文件的 `<properties>` 变量（`jjwt.version` / `poi.version` / `openpdf.version` / `commons.csv.version`），便于升版时只改一行。
2. **离线闭环**：所有依赖都能进本地仓库分发，运行时不访问互联网（README 第二节末）；`openpdf-fonts-extra` 与 `pdf-font-search-paths` 的组合就是"内网无字体也能出中文 PDF"的落地手段。
3. **`-parameters` 是刚性要求**：Spring 6 / Boot 3 在解析 `@RequestParam`、`@PathVariable`、`@RequestHeader` 的**参数名**时不再回退到字节码调试信息，必须在编译期写入 `MethodParameters` 属性。缺了它，控制器里所有"省略 value 的注解"会在启动或首次调用时报 `Name for argument of type [java.lang.String] not specified`。本册 2.3~2.12 中大量 `@Value("${server.port:8080}")` 属于属性占位符解析，不受影响，但控制器层受影响，所以必须全局开。
4. **单 jar 自带页面（本次安全整改一并补齐的交付项）**：新增的 `maven-resources-plugin` 执行把 `frontend/dist` 复制进 `target/classes/static`，因此打包出的 `target/evaluation-backend.jar` **自身就带前端页面**。prod 档不覆盖 `spring.web.resources.static-locations`，走 Boot 默认的 `classpath:/static/` 即可提供页面，企业离线部署只需 JDK + MySQL，不再需要 Node，也不再需要 Nginx。它与 dev 档的 `file:../frontend/dist/` 是**两条互不相干的链路**：dev 档从磁盘读前端产物，jar 内是构建时被复制进来的副本。

**易错点/注意**：
- **不要给 starter 补 `<version>`**：一旦手写版本，就会绕过 parent 的仲裁，出现"Boot 3.5.16 + 手写旧版 spring-web"的隐性不兼容。
- `-parameters` 只在 `maven-compiler-plugin` 的 `compilerArgs` 里；如果在 IDEA 里直接跑 `EesApplication` 而不经 Maven，需要 IDEA 的 Java Compiler 设置里也加上 `-parameters`（新版 IDEA 从 Maven 导入时会自动同步该参数）。
- `ojdbc11` 的 `classifier` 未指定，默认取通用 jar；如需 Oracle 的 `ojdbc11_g`（含原生库）要显式加 classifier。
- **打包前必须先 `npm run build`**：`copy-frontend-dist-into-jar` 在 `frontend/dist` 缺失时只 skip、不报错，`mvn clean package` 照样成功，但产出的 jar 里没有页面。症状是"dev 档跑页面正常、换 prod 档单 jar 就 404"，排查时先看构建日志里 `maven-resources-plugin` 是否有 skip 提示，再确认 `frontend/dist/index.html` 是否存在。
- jar 内的页面是**构建时的快照**：前端改动只重新 `npm run build` 对 dev 档立即生效；要让 jar 内页面更新必须重新 `mvn package`，不要试图在运行期替换 jar 内的 `static/`。

### 2.3 `EesApplication.java`

**作用**：唯一的启动类；不写业务，只负责"排除一个用不到的自动配置 + 打开四组横切能力 + 启动 Spring 容器"。
**被谁使用**：`mvn spring-boot:run`、`java -jar evaluation-backend.jar`、IDEA 运行配置、以及 `spring-boot-maven-plugin` 生成 jar 时写入 `Main-Class` 的依据。
**关键设计点**：
1. 类放在 `com.ees` 包根，`@SpringBootApplication` 的组件扫描基准就是 `com.ees`，于是 `algorithm / common / config / controller / domain / dto / repository / security / service / util` 十个子包全部被扫到——**这是"启动类必须放包根"的唯一原因**，挪到子包会导致大量 Bean 找不到。
2. **排除 `UserDetailsServiceAutoConfiguration`（本次安全整改的一部分）**：若保留它，Spring Boot 会额外创建一个名为 `user` 的内存用户，并把随机生成的密码**明文打印到启动日志**（`Using generated security password: ...`），直接违反技术方案 9.1 的"日志不得打印密码和敏感配置"，在企业离线交付的安全评审中会被判不合规。本系统的认证完全自建（`AuthService` 校验 BCrypt + `JwtService` 签发 JWT + `JwtAuthenticationFilter` 还原 `SecurityContext`），不使用 `AuthenticationManager` / `UserDetailsService` / `formLogin` / `httpBasic`，因此排除它不损失任何功能，只是消除了日志中的密码输出与一个无用账号。
3. 四个开关注解都写在启动类上而不是散落到各配置类，好处是"容器级别能力清单"一眼可见：配置绑定、JPA 审计、异步、定时。
4. `@ConfigurationPropertiesScan("com.ees.config")` 的包名限定是刻意的：`EesProperties` 上**没有** `@Component`，靠这个注解被扫描注册（详见 2.4）。而 `com.ees.security.JwtSecretProvider` 是带 `@Component` 的普通 Bean，走的是组件扫描那条路——两者由启动类上不同的注解分别负责，容易混淆。

### 2.4 `EesProperties.java`

**作用**：把 `application*.yml` 里 `ees.*` 开头的配置整体绑定成一个强类型对象，共 6 组：`security / storage / algorithm / datasource-connector / report / audit`。
**被谁使用**：`SecurityConfig`（免认证路径）、`AsyncConfig`（并发数）、`AlgorithmConfig`（引擎模式）、`AuditFilter`（审计开关与方法）、`StorageConfig`（目录）、`JwtService`（有效期/签发者，密钥直接来自构造注入的 `JwtSecretProvider`）、`CryptoUtils`（数据源密码 AES 加密的密钥派生，读的正是本字段）、`CppEngineAdapter`（C++ 服务地址与超时），以及数据接入、报告导出相关服务。其中 `jwtSecret` **不是**由 yml 单向写进来的：`JwtSecretProvider` 在构造时会把自己解析出的最终密钥**回写**到这里（第 84 行），因此读该字段拿到的一定是"本次启动真正生效的密钥"（`JwtService` 通过 `JwtSecretProvider.getSecret()` 拿到的是同一个值）。
**关键设计点**：
1. **不写 `@Component`**：类上只有 `@ConfigurationProperties(prefix="ees")`，由启动类的 `@ConfigurationPropertiesScan("com.ees.config")` 注册。这样"配置类"与"业务 Bean"的边界清晰。
2. **唯一一个刻意"没有默认值"的字段是 `jwtSecret`**：它的初值被写成空串（第 28 行），由 `com.ees.security.JwtSecretProvider` 按"环境变量 `EES_JWT_SECRET` → 本地密钥文件 `<ees.storage.root>/.jwt-secret` → 进程内随机密钥（仅告警）"三级顺序解析后回写。这样做是因为**内置默认密钥会随交付包一起给到甲方，等同公开值**：整改前的实测结论是用它本地签发 `role=SYSTEM_ADMIN` 的令牌即可访问 `/api/users`、`/api/configs`、`/api/audit-logs` 并 `POST /api/data-sources` 写入数据，属可越权读写的真实漏洞。其它字段仍保留默认值：`application.yml` 未覆盖时系统依然能离线启动，这也是 `docs/DEPLOY.md` 3.2 那张"生产必须注入的环境变量表"能成立的前提。
3. **派生方法而非派生字段**：`allowedExtensionList()`、`forbiddenKeywordList()`、`methodList()` 三个方法把逗号分隔字符串现算成列表。刻意**不缓存**，避免"改了配置但缓存没失效"的调试陷阱；这些方法每次调用都新建列表，调用频率低（过滤器每请求一次）因此可接受。
4. **内部类全部 `static`**：`Security/Storage/...` 都是静态嵌套类，避免隐式持有外部实例，也让 Spring Boot 的宽松绑定（kebab-case → camelCase）逐层生效。

- **`jwt-secret` 空着是正常的，不要"顺手补一个默认值"**：yml 里写 `${EES_JWT_SECRET:}`、字段初值写空串，都是刻意的，真正的密钥由 `JwtSecretProvider` 在启动时按三级顺序补上并回写。若再往 yml 或 `EesProperties` 里塞一个固定值，就等于把交付包里的密钥公开给甲方——整改前的漏洞正是如此（用内置密钥本地签发 `role=SYSTEM_ADMIN` 令牌即可越权读写），所以这条"图方便"的改动属于禁止项。
- **换密钥的影响是双重的**：已签发的 JWT 全部失效（用户需重新登录），已保存的数据源密码（`ENC:` 开头的 AES 密文，密钥同样派生自该值）也会解不开，报"密码解密失败…请重新录入数据源密码"。生产要自行指定密钥只走环境变量 `EES_JWT_SECRET`，并把"逐个数据源重新录入密码"写进变更步骤。
- `JwtSecretProvider` 会识别整改前内置的那两个公开密钥：如果启动日志里出现"配置中的 jwt-secret 仍是整改前内置的演示密钥"的告警框，说明甲方配置里还残留旧值，必须删掉（该类本身归第 02 册说明）。
- **"空密钥"已被两道防线挡住，不必再去担心 Base64 解码失败导致启动不了**：`JwtSecretProvider` 保证解析结果非空（最差退化为进程内随机密钥），`JwtService` 构造时又对"解码后长度为 0"做了显式拦截（第 52-58 行），抛出语义清晰的 `IllegalStateException("JWT 签名密钥为空：请设置环境变量 EES_JWT_SECRET，或确保存储根目录可写…")`，而不是让后面的取模运算抛 `ArithmeticException: / by zero`——那段代码的注释也写明"正常情况下不可达"。真看到这条消息，说明密钥不是经 Provider 正常解析来的（例如测试里手工构造了密钥），排查方向是"谁绕过了 Provider"，而不是配置项的格式。
- 新增配置项时**三处必须同步**：`EesProperties` 的字段 + `application.yml` 的默认值 + 本册/后续分册的说明；漏了 yml 会走字段默认值（不报错但行为与文档不符），漏了字段则会静默忽略（Boot 默认不因未知配置项报错）。
- `scoreScale` 与 `displayScale` 的语义是"计算"与"展示"，写反了不会报错但会造成结果精度异常，排查精度问题时先核对这两个值。

### 2.5 `SecurityConfig.java`

**作用**：定义整个后端的 HTTP 安全策略：无状态 JWT、路径级白名单、方法级权限开关、统一 401/403 JSON 响应、CORS。
**被谁使用**：Spring Security 自动配置在启动时取用 `SecurityFilterChain` 与 `PasswordEncoder` 两个 Bean；`AuthService`/`UserService` 注入 `PasswordEncoder` 做密码哈希与校验；`JwtAuthenticationFilter` 被插入到过滤器链。
**关键设计点**：
1. **为什么必须无状态（STATELESS）**：系统对内网多用户、对外以 REST 接口交付，认证凭据放在 JWT 里，服务端不存 Session。这样做的两个直接收益是——(a) 后端可任意横向扩副本而不需要会话粘滞或共享 Session 存储；(b) 与 `spring-security-test`、curl/Postman 调试天然兼容（一个 Header 即可）。代价是**服务端无法主动踢人**，所以退出登录只能在客户端丢弃 token，改密/停用账号要等 token 过期（默认 480 分钟）。
2. **哪些路径免认证**：白名单来自 `EesProperties.Security.permitPaths`（`/api/auth/login`、`/api/auth/captcha`、`/api/health`、`/api/health/**`、`/api/info`、`/error`）+ 代码内硬编码的 `OPTIONS /**`（CORS 预检必须放行，否则跨域请求在带 token 前就被拦）+ 前端静态资源（`/`、`/index.html`、`/assets/**`、`/favicon.ico`、`/static/**`、`/css/**`、`/js/**`、`/img/**`、`/fonts/**`）。**其余全部 `authenticated()`**——采用默认拒绝（deny by default）而不是默认放行，是安全基线的基本要求。
3. **`@EnableMethodSecurity` 与 `@PreAuthorize` 的关系**：`@EnableMethodSecurity` 在配置类上开启方法级安全，Spring 会为标注了 `@PreAuthorize` 的 Bean 生成代理，在方法**进入前**做表达式求值；控制器里共 85 处 `@PreAuthorize`（如按权限码校验）。两层分工明确——`filterChain` 只管"有没有登录"（认证），`@PreAuthorize` 管"这个角色/权限能不能做这件事"（授权）。**少了 `@EnableMethodSecurity`，所有 `@PreAuthorize` 会被静默忽略**：应用照常启动、接口照常返回 200，这是最危险的配置退化，评审时务必确认这一行存在。
4. 未认证/越权不由 Spring 默认的 HTML 登录页或 403 页面处理，而是由 `writeJson` 输出与业务一致的 `ApiResponse` JSON，保证前端拦截器只需处理一种响应格式。

### 2.7 `AsyncConfig.java`

**作用**：定义两个 `ThreadPoolTaskExecutor`，把"评估任务"与"IO 类工作"分池隔离，避免互相饿死（对应方案 3.4 并发目标）。
**被谁使用**：`@Async("evaluationExecutor")` 标注的评估任务执行服务；`@Async("ioExecutor")` 标注的 `AuditService.record`（审计落库）、报告导出与文件解析类服务；`TaskExecutor` 类型的注入点也按 Bean 名区分。
**关键设计点**：
1. **两池分离的理由**：评估任务 CPU 密集且可能一次跑十几分钟（`taskTimeoutSeconds=900`），若与审计/导出共池，一个长任务会把队列占满，导致审计日志延迟甚至丢失、导出请求排队超时。分池后两边的容量与耗时特征各自可控。
2. **评估池规模由配置推导**：`Math.max(2, properties.getAlgorithm().getMaxConcurrentTasks())`——`maxConcurrentTasks=4` 是"同时最多跑几个评估任务"的业务参数，把它同时用作核心线程数，可保证**不会出现线程多于业务允许并发的浪费**；下限 2 保证即使配置被误设为 1 或 0 也能跑起来。
3. **队列容量与拒绝策略的取舍**：`queueCapacity=500` 远大于并发数，采用"先排队、再涨max、最后拒绝"的默认策略。对本系统这是合理的——任务提交是人工操作，突发峰值有限；但要注意**队列是 500，一旦排满会抛 `TaskRejectedException`**，接口层需能把它转成"系统繁忙"的可读错误。
4. 优雅关闭：评估池设 `setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(60)`，停机时**先等正在跑的评估任务收尾**（最多 60 秒），避免任务停在中间状态；IO 池不设，因为审计/导出可安全丢弃。

| 33 | `}` | 方法结束 |
| 35-44 | `@Bean(name = "ioExecutor")` 方法体 | IO 池固定参数：核心 4、最大 16、队列 1000、线程前缀 `ees-io-`、初始化。**不读配置**是刻意的：IO 池服务的是审计与文件读写，属基础设施能力，不应随算法参数变化；4/16 的比例（核心小、弹性大）符合"平时少量线程、导出高峰临时扩容"的 IO 特征。未设 `waitForTasksToCompleteOnShutdown`，停机时允许直接丢弃未开始的审计写入 |

**易错点/注意**：
- `@Async` 生效的前提是**启动类有 `@EnableAsync`**（`EesApplication` 第 32 行）且方法是从**另一个 Bean** 调用的（同类内部自调用不走代理，异步会失效）。`AuditFilter` 调用 `auditService.record` 属跨 Bean 调用，成立。
- 线程池参数与 `ees.algorithm.max-concurrent-tasks` 强耦合：把该值调到 16 会同时把核心线程数提到 16，需确认机器 CPU 核数（评估任务是 CPU 密集型，线程数超过核数收益有限）。
- 任务被拒绝时抛 `TaskRejectedException`，接口层需要在全局异常处理器里给出可读提示，否则用户只看到 500。

### 2.8 `AlgorithmConfig.java`

**作用**：按 `ees.algorithm.engine` 组装算法注册中心 `AlgorithmRegistry`，决定"用内置 Java 实现"还是"调用外部 C++ 独立算法服务"。
**被谁使用**：评估任务执行服务注入 `AlgorithmRegistry` 后按算法编码取引擎；`SystemController` 的算法列表接口通过 `registry.supported()` 展示当前可用算法与版本。
**关键设计点**：
1. **注册中心不在类上标注 `@Component`**：`AlgorithmRegistry` 的注释写明"由 AlgorithmConfig 装配，以便按配置切换实现"。如果它自己就是 `@Component`，就会与这里的 `@Bean` 打架（或需要 `@ConditionalOnMissingBean`），配置驱动的能力也会消失。这是"装配权交给配置类"的标准范式。
2. **`@Primary` 的必要性**：多处注入 `AlgorithmRegistry` 类型，加 `@Primary` 表明"这就是唯一权威的注册中心"，避免未来出现 Mock/备用注册中心时的注入歧义。
3. **C++ 模式下的兜底策略**（第 43-45 行注释即需求）：C++ 服务只接管 AHP 与 FUZZY 两种甲方已有实现，**加权平均法（WEIGHTED）与组合流程（COMBO）继续用内置实现**。这样即使 C++ 服务不可用，系统仍能跑通完整评估闭环，符合"离线环境开箱可用"的要求。
4. **替换而非新增**：`AlgorithmRegistry` 构造器用 `Map.put` 以 `algorithmCode().toUpperCase()` 为键，`LinkedHashMap` 在**键已存在时 put 只覆盖值、保留原插入位置**。因此 C++ 适配器添加到列表尾部后，AHP/FUZZY 的键仍然排在原来的位置，但实现已被换成 `CppEngineAdapter`——"上层无需改动"正是靠这一点成立。

- C++ 服务不可达时任务会失败并报 `ALGORITHM_ENGINE_UNAVAILABLE`（见 `docs/DEPLOY.md` 故障处理表），应急手段是临时切回 `JAVA_NATIVE`；因此生产不建议无验证地常开 `CPP_ENGINE`。
- 新增算法时必须同时提供 `@Component` 的 `AlgorithmEngine` 实现并让 `algorithmCode()` 与 `AlgorithmType` 的 code 一致，否则注册中心按大写键查不到会抛 `ALGORITHM_NOT_SUPPORTED`。

### 2.9 `AuditFilter.java`

**作用**：对写操作（POST/PUT/DELETE/PATCH）自动登记审计日志，不受业务代码是否记得写审计影响；并把 URI 归类为登录/数据/任务/配置/导出五类模块。
**被谁使用**：作为 Servlet 过滤器由容器调用；依赖注入 `EesProperties`（审计开关与方法清单）与 `AuditService`（真正落库，异步）。
**关键设计点**：
1. **为什么必须在发起线程采集请求元信息**（第 46 行注释即答案），有两个独立原因：
   - **异步线程拿不到 `SecurityContext`**：`AuditService.record` 标注 `@Async("ioExecutor")`，Spring 的 `SecurityContextHolder` 默认策略是 `MODE_THREADLOCAL`，上下文不随任务传递。如果在异步方法里调 `SecurityUtils.currentUsername()`，拿到的必然是空值/`anonymous`，审计日志就失去"谁干的"这一核心字段。
   - **`request` 会被回收**：Servlet 容器在响应结束后复用/回收 `HttpServletRequest` 对象（对象池化），异步线程再去读 `getRequestURI()`、`getHeader("User-Agent")` 会读到**被下一个请求改写后的数据**或抛异常——这类 bug 只在并发下出现，极难复现。
   因此本类在 `chain.doFilter` **之前**就把 `userId`、`username` 与 `RequestInfo`（method/uri/ip/userAgent 的纯值快照）采集好，作为参数传给异步方法。
2. **`resolveModule` 为什么不能用 `"/results"` 这种子串判断**（第 66 行注释即答案）：真实接口路径是 `/api/evaluation-results`，其中**并不包含 `"/results"` 这个子串**（它是 `-results`，前面是连字符）。若按 `"/results"` 判断，所有评估结果相关操作都会被归到 `SYSTEM` 兜底类，审计分类直接失效。所以第 80 行用的是完整片段 `/evaluation-tasks` 与 `/evaluation-results`。
3. **顺序敏感的归类规则**：`/auth/` 最先（登录相关无论路径形态都属 AUTH）；**导出优先于任务**（第 75-78 行注释说明）——因为 `/api/evaluation-results/1/exports` 同时命中"结果"与"导出"，而方案 9.2 要求导出单独成类，所以必须把 `export` 判断排在 `evaluation-results` 之前。这类"多条件命中时谁先"的规则一定要写进注释，否则后人重排顺序就悄悄改了审计口径。
4. **审计自身接口被排除**（第 38 行 `!request.getRequestURI().startsWith("/api/audit")`）：否则管理员每次查询审计日志都会产生一条审计日志，形成自增噪声甚至递归。
5. **失败也要记**：无论业务成功还是异常/4xx/5xx，`finally` 块都会记录，并以 `response.getStatus() < 400` 判定 `success`，把 `HTTP xxx` 写入 `errorMsg`。这样"尝试越权/失败的删除"同样留痕，符合方案 9.2 的安全审计要求。

### 2.10 `StorageConfig.java`

**作用**：应用启动时创建存储根目录及其子目录（upload/snapshot/report/temp/logs），并提供一个路径规范化工具方法。
**被谁使用**：作为 `ApplicationRunner` 在容器启动完成后执行；`resolve(String)` 供需要绝对路径的存储/导出服务调用。
**关键设计点**：
1. **为什么用 `ApplicationRunner` 而不是 `@PostConstruct`**：`ApplicationRunner` 在**全部 Bean 就绪、容器刷新完成后**执行，此时数据源、JPA、以及 `spring.sql.init` 的脚本都已就绪；若用 `@PostConstruct`，目录创建可能早于配置绑定完成的边缘情况，也更容易被后续 Bean 初始化失败连带影响。用 Runner 还能与 `DataInitializer`（`@Order(100)`）、`StartupBanner`（`@Order(200)`）形成明确的先后次序。
2. **创建而非校验**：用 `Files.createDirectories`（会自动创建缺失的父目录，如 `D:\eesdata\logs` 的 `eesdata`）。离线部署常见场景是运维只给了盘符，父目录并不存在。
3. **失败只记日志不抛异常**：`catch (IOException e) { log.error(...) }` —— 目录创建失败（如无写权限）不阻止应用启动。这是权衡后的选择：错误尽早暴露在日志里，但让运维还能先进界面查看配置、导出数据；真正的写入失败会在业务操作时抛出更具体的错误。
4. **统一的路径规范化**：`toAbsolutePath().normalize()` 把 `./data` 变成绝对路径并消掉 `..`，使得"（相对工作目录的）配置值"与"（日志里看到的）真实位置"一致——README 第 5 节特别提醒 `mvn spring-boot:run` 从 `backend` 启动时相对路径是 `backend/data`，规范化后的日志能消除这个歧义。

### 2.11 `DataInitializer.java`

**作用**：应用启动时创建两个默认账号（`admin/admin123`、`evaluator/eval123`），**仅在用户表为空时执行**，绝不覆盖已有数据。系统角色已精简为**两类**——`SYSTEM_ADMIN`（系统管理员，`data_scope=ALL`）与 `EVALUATOR`（评估人员，`data_scope=PROJECT`），默认账号与角色一一对应；`DATA_ADMIN`/`REVIEWER`/`VIEWER` 三个角色已随本次精简从前后端与数据库删除，因此也不再创建对应的默认账号。
**被谁使用**：作为 `ApplicationRunner` 在容器就绪后执行，委托 `AuthService.initDefaultUsers()` 完成实际创建。
**关键设计点**：
1. **幂等由"表非空即返回"实现**：真正的判断在 `AuthService.initDefaultUsers()`（`if (userRepository.count() > 0) return;`）。这样每次启动都安全：首次建号，之后静默跳过。**与 `db/data.sql` 的 `INSERT IGNORE` 是两种不同的幂等机制**——SQL 层管角色/参数/质量规则/算法基准这些"字典数据"（`data.sql` 的 `sys_role` 现在只插入 `SYSTEM_ADMIN` 与 `EVALUATOR` 两条，`sort_order` 分别为 1、2，与"系统只有两类角色"的现状一致），Java 层管需要 BCrypt 加盐哈希的账号（SQL 里没法生成随机盐的 BCrypt 串，所以账号必须走代码）。
2. **`@Order(100)` 的排序含义**：`ApplicationRunner` 之间按 `@Order` 升序执行。`StorageConfig` 的 Runner 未标注 `@Order`（默认 `Ordered.LOWEST_PRECEDENCE`），`DataInitializer` 为 100，`StartupBanner` 为 200。于是次序是**建目录 → 建账号 → 打印横幅**；横幅放最后，保证运维看到横幅时系统已完全可用。
3. **异常被吞掉但记 ERROR**：账号初始化失败（如唯一索引冲突、数据库只读）不会阻止应用启动。理由与 `StorageConfig` 一致——让管理员能先进系统排查；但日志级别用 `log.error` 确保它在生产 `root: WARN` 的配置下依然打出来（`com.ees: INFO` 也会输出 ERROR）。
4. 委托而非直写 Repository：账号创建涉及密码哈希、状态、组织、备注等一整套约定，统一收敛在 `AuthService.createUser` 私有方法里，避免初始化路径与业务路径出现两套规则。

### 2.12 `StartupBanner.java`

**作用**：启动完成后在控制台打印一段带 `http://` 链接的信息横幅：页面地址、接口地址、健康检查地址、默认账号（口令只在 dev 档显示）、前端资源托管状态、当前激活的环境、**以及 JWT 签名密钥的来源**（本次整改新增的安全自检行，只打印来源不打印密钥）。
**被谁使用**：作为 `ApplicationRunner`（`@Order(200)`）在启动收尾时执行，只写日志、无业务副作用。
**关键设计点**：
1. **它解决什么问题**：IDEA（以及现代终端的日志渲染）会自动把日志里的 `http://...` 识别为**可点击超链接**。因此这段横幅的实际价值不是"好看"，而是让开发者/评委**在控制台点一下就直接打开系统页面**——省掉"复制端口、切浏览器、粘贴地址"的步骤，尤其在演示与答辩现场能显著减少操作失误。README 与 `.idea/runConfigurations` 的运行配置都在反复强调"运行后端即得到完整系统"，横幅是这条体验链上的最后一环。
2. **前端是否托管的判断是动态的**（`frontendAvailable()`）：区分"已由后端托管 dist"与"未找到 frontend/dist"，后者会提示"先执行 npm run build，或改跑前端 npm run dev 后访问 5173"。这解决了最常见的启动困惑——页面 404 时先看横幅，不必去翻日志找原因。
3. **链接必须能直接点**：因此地址用 `127.0.0.1` 而不是 `localhost`（避免个别环境把 localhost 解析到 IPv6 `::1` 而连接失败），且 context-path 被规范化（见下）。
4. **context-path 规范化**：`/` 与空串都视为无前缀，避免拼出 `http://127.0.0.1:8080//`；非 `/` 开头的值补前导 `/`，末尾多余的 `/` 循环去掉。`application.yml` 里 `context-path: /` 正是这个必须处理的情形——否则每次启动都会打印双斜杠地址。
5. **横幅自己不能变成新的泄漏点**（本次整改的设计约束）：新加的"签名密钥"一行只调用 `JwtSecretProvider.describeSource()`，拿到的是"环境变量 EES_JWT_SECRET""本地密钥文件 <路径>""首次启动自动生成（已保存到 <路径>）""进程内随机密钥（临时，未持久化）"这类**来源描述文字**，类里没有任何分支会打印密钥本身。价值在于"启动即自证"：运维不用翻配置文件就能确认本次生效的是环境变量密钥还是自动生成的本地密钥——这也正是识别"整改是否真的生效"的最快入口。
6. **初始口令只对开发档显示**：同一批整改中，默认账号一行由"无条件打印 `admin / admin123`"改为按 `isDevProfile()` 分支——dev 档显示口令方便本机调试，prod 档只显示账号名。技术方案 9.1 的"日志不得打印密码和敏感配置"因此在本册范围内被落实了**三处**：启动类的内存用户自动配置被排除（2.3）、默认账号口令分档显示（本条）、密钥只打印来源（上一条）。

### 2.13 资源配置 `application.yml` / `application-dev.yml` / `application-prod.yml`

**作用**：三个 YAML 共同构成后端的全部外部配置。`application.yml` 是主配置（所有环境共享），`application-dev.yml` / `application-prod.yml` 按 `spring.profiles.active` 覆盖差异项。
**被谁使用**：Spring Boot 在启动最早期加载（`application.yml` → `application-{profile}.yml`，后者优先）；`EesProperties` 绑定 `ees.*` 分组；数据源、Jackson、JPA、Multipart、日志由自动配置消费；`com.ees.security.JwtSecretProvider` 读取 `ees.security.jwt-secret` 与 `ees.storage.root`（前者判空、后者定位本地密钥文件）；`StartupBanner` 读取 `server.port`、`server.servlet.context-path`、`spring.web.resources.static-locations` 并打印密钥来源。
**关键设计点**：
1. **分层原则**：`application.yml` 只放"任何环境都成立"的项（服务端口、编码、序列化规则、算法默认参数、`ees.*` 六组默认值）；环境差异项（数据库连接、连接池规模、静态资源位置、日志级别）下沉到 profile 文件。这样生产部署不需要改主配置。
2. **敏感项一律用 `${ENV:默认值}` 形态**：三个 yml 共暴露 **13 个 `EES_*` 环境变量**（`EES_JWT_SECRET`、`EES_STORAGE_ROOT`、`EES_ALGORITHM_ENGINE`、`EES_ALGORITHM_VERSION`、`EES_CPP_ENGINE_URL`、`EES_PDF_FONT_PATH`、`EES_PDF_FONT_NAME`、`EES_PDF_FONT_ENCODING`、`EES_DB_HOST`、`EES_DB_PORT`、`EES_DB_NAME`、`EES_DB_USER`、`EES_DB_PASSWORD`），与 `docs/DEPLOY.md` 3.2 的表格一一对应（**改配置只改环境变量，不动文件**，是离线交付与多机部署的必要条件）。默认值只保证"开发机上能跑通"，生产必须注入。**唯一的例外是 `ees.security.jwt-secret`：它写的是 `${EES_JWT_SECRET:}`，冒号后面没有任何默认值**——见 2.13.1 与 2.4，这是安全整改的核心改动之一。
3. **幂等初始化是这套 yml 最重要的设计**：`spring.sql.init` 用 `schema-locations` / `data-locations` 指定脚本，配合脚本内部的 `CREATE TABLE IF NOT EXISTS` 与 `INSERT IGNORE`，做到**每次启动都执行、结果永远一致**。详见 2.13.1 的逐项说明。
4. **算法引擎两态**：`ees.algorithm.engine` 的 `JAVA_NATIVE` / `CPP_ENGINE` 只影响 `AlgorithmConfig` 的装配分支，所有其它配置（超时、并发、精度、一致性阈值）两种模式共用。

**易错点/注意**：
- `spring.sql.init` **没有在 prod 档关闭**，因此生产每次启动仍会执行这两个幂等脚本。若按 DEPLOY 2.4 的建议已在 Navicat 里手工执行过 `01/02`，可在生产 profile 中把 `mode` 设为 `never` 以缩短启动时间。
- `spring.mvc.throw-exception-if-no-handler-found: true` 只解决"找不到处理器"；Spring Boot 3.2+ 对**静态资源缺失**抛的是 `NoResourceFoundException`，`GlobalExceptionHandler` 未单独处理它，会落到通用 `Exception` 分支返回 500（`SYSTEM_ERROR`）。排查前端资源 404 时不要只看状态码，要结合日志。
- **`jwt-secret` 现在没有任何默认值，这是刻意的**：整改前这里是 `${EES_JWT_SECRET:<一段演示 Base64>}`，任何人都能从交付包里读到它，并据此伪造 `role=SYSTEM_ADMIN` 令牌（实测可用它访问 `/api/users`、`/api/configs`、`/api/audit-logs`，甚至 `POST /api/data-sources` 写入数据）。留空之后，`JwtSecretProvider` 会在首次启动生成 64 字节随机密钥并持久化到 `<ees.storage.root>/.jwt-secret`，因此**不改任何配置也能离线跑起来**；甲方有统一密钥管理要求时再注入 `EES_JWT_SECRET`。改密钥的代价是双重的：已签发 token 全部失效、已保存的数据源密码解不开（见 2.4 易错点）。

- 本档把 `com.ees` 设为 DEBUG，生产档为 INFO；两档日志量差异显著，压测或长时间运行请勿使用 dev 档。
- **本档的 `EES_DB_PASSWORD` 默认值是演示口令（`Ees@2026`），只为"本机开箱即跑"**：第 5-7 行注释已经把这一点写明并指向 prod 档，prod 档的 `password` 默认为空、必须由环境变量注入。安全评审时这是容易被误判为"交付物硬编码口令"的一处，解释时按这三行注释与 2.13.3 对照回答。
- 本档不覆盖 `ees.security.jwt-secret`，也不覆盖 `ees.algorithm.*`，因此 dev 与 prod 共用主配置的算法参数与密钥解析逻辑（密钥来源由环境变量有无决定，与档位无关）。

## 3. 本册小结

- 本册共覆盖 **13 组文件**（根 `pom.xml`、`backend/pom.xml`、`EesApplication.java`、`config` 包 9 个类、3 个 `application*.yml`）、**1480 行代码与配置**。
- **工程结构上，构建配置分两层**：根 `pom.xml` 只做聚合（让 IDEA 与 `mvn -pl backend` 能定位模块），`backend/pom.xml` 直接继承 `spring-boot-starter-parent` 并集中管理四个第三方版本变量。依赖选择的共同逻辑是"离线闭环 + 私有化可交付"：jjwt 三件套的 api/impl 分离、openpdf-fonts-extra 解决中文 PDF、commons-csv 解决 CSV 边界、ojdbc11/mssql-jdbc 的 runtime+optional 保证"驱动位存在但不强绑"。新增的 `maven-resources-plugin` 执行把这条逻辑延伸到**交付形态**上：`frontend/dist` 在 `prepare-package` 阶段被复制进 `target/classes/static`，于是 prod 档单 jar 自带页面，目标机只需 JDK + MySQL，既不需要 Node 也不需要 Nginx。
- **本次安全整改在本册范围内有四个落点，需要整体理解**：① `application.yml` 的 `ees.security.jwt-secret` 改成 `${EES_JWT_SECRET:}`，**不再有任何默认值**（第 68 行）；② `EesProperties.Security.jwtSecret` 初值改为空串，运行时由 `JwtSecretProvider` 按"环境变量 → 本地密钥文件 → 进程内随机密钥"三级解析并回写（第 28、84 行）；③ `StartupBanner` 构造签名变为 `StartupBanner(Environment, JwtSecretProvider)`，横幅新增"签名密钥 : <来源>（未打印密钥本身）"一行（第 32-35、67 行），且默认账号口令只在 dev 档打印（第 52-58 行）；④ `EesApplication` 排除 `UserDetailsServiceAutoConfiguration`，消除启动日志里的随机密码（第 29 行）。四者共同服务于两件事：**交付包里不再含可用密钥**、**日志里不再出现口令与敏感配置**（技术方案 9.1）。整改前用内置密钥伪造 `SYSTEM_ADMIN` 令牌即可越权读写接口，因此这四条都是"改了才合规、退回去就复现漏洞"的刚性配置。
- **`-parameters` 不是可选优化**：Spring 6 起 `@RequestParam`/`@PathVariable` 的参数名解析完全依赖编译期写入的 `MethodParameters` 属性，缺了它控制器层会在运行时报错。同一类"看起来可选、实际刚性"的配置还有 `classpath:/static/` 与 `@EnableMethodSecurity`——前者漏掉会让静态资源整体 404，后者漏掉会让 **85 处 `@PreAuthorize` 静默失效但应用照常启动**，是本册最需要警惕的配置退化。
- **配置的分层约定是"环境无关项进主配置、环境差异项进 profile、敏感项走环境变量"**。三个 yml 共暴露 13 个 `EES_*` 环境变量，与 DEPLOY 3.2 的表格一一对应；其中只有 `EES_JWT_SECRET` 写成 `${EES_JWT_SECRET:}`（冒号后留空），这是刻意为之——密钥绝不内置。dev 与 prod 的关键差异只有四处：数据源是否环境变量化、连接池 30/50、密码默认值有/无、日志 INFO+DEBUG / WARN+INFO。
- **`spring.sql.init` 用 `schema-locations`/`data-locations` 实现幂等初始化**，是"每次启动都执行且结果恒定"的组合：`mode: always`（MySQL 非嵌入式库必须显式开启）+ `CREATE TABLE IF NOT EXISTS`（24 张表建表幂等）+ `INSERT IGNORE`（四张字典表灌数据幂等）。`continue-on-error: false` 则保证脚本写错时**启动即失败**而不是带病运行。
- **启动期四件事的次序由 `@Order` 固定**：`StorageConfig` 建目录（无 `@Order`）→ `DataInitializer` 建默认账号（100）→ `StartupBanner` 打印可点击横幅（200），配合主配置里 `spring.sql.init` 建表灌数据，构成"零手工步骤启动"的完整链路。而 `StartupBanner` 的价值被严重低估——它是"IDEA 控制台点一下直达页面"这一交付体验的实现者。
- **两处最容易误读的细节**已在本册标注：其一，`AuditFilter` 必须在**发起线程**采集请求元信息，因为 `@Async` 线程既拿不到 `SecurityContext`，`HttpServletRequest` 也已被容器回收（异步里读到的是下一个请求的数据）；其二，`AuditFilter.resolveModule` 不能用 `"/results"` 做子串判断，因为真实路径是 `/api/evaluation-results`（连字符而非斜杠），一旦写错整类审计会静默落到 `SYSTEM` 兜底。
