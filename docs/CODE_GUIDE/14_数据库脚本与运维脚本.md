## 2. 逐文件详解

### 2.1 `backend/src/main/resources/db/schema.sql`（636 行，24 张表）

**作用**：整个系统的**唯一权威 DDL**。24 张表覆盖角色权限、用户、审计、系统参数、项目、指标体系、
数据接入、数据批次、字段映射、数据快照、评估任务、评估结果与报告、质量规则、算法基准。
**被谁使用**：
- Spring Boot 启动时由 `spring.sql.init` 执行（`application.yml` 第 48-54 行：`mode: always`、
  `continue-on-error: false`、`schema-locations: classpath:db/schema.sql`、`data-locations: classpath:db/data.sql`）；
- 人工排查/换机时执行 `db/01_schema.sql`（本文件副本）；
- `db/99_reset_demo_data.sql` 的 `TRUNCATE` 列表与本文件的表名一一对应（19 张业务表）。
**关键设计点**（对应方案「数据库设计」整章与「私有化部署可重复初始化」要求）：
1. **`ddl-auto: none`（`application.yml` 第 37 行）—— 本文件是 DDL 的唯一来源**。JPA 实体只做映射、
   不改表结构，所以实体字段与这里的列必须手工保持一致，改表就是改这个文件。
2. **全部 `CREATE TABLE IF NOT EXISTS`**：脚本幂等，启动时每次执行都不会报「表已存在」而中断启动；
   配合 `continue-on-error: false`，任何一条语句真出错都会让启动失败并暴露问题，而不是悄悄跳过。
3. **不建任何外键约束**，表间关系只用 `xxx_id` 字段 + 索引表达。原因见 2.1.0 第（3）条。
4. **枚举值全部用 `VARCHAR` 存字符串**（`status`、`algorithm`、`severity`…），而不是 MySQL 的 `ENUM`：
   与 Java 侧常量、前端字典、错误码一一对读，且后续加状态值时不用 `ALTER TABLE`。

#### 2.1.0 全局约定与文件头（第 1-10、636 行）

| 行号 | 代码 | 说明 |
|---|---|---|
| 1-7 | `-- 效能评估系统 - 数据库结构 …` | 文件头声明适用版本（MySQL 8.0/8.4）、字符集（utf8mb4）与「脚本幂等、可重复执行；由 Spring Boot 启动时自动执行，也可在 Navicat / mysql 客户端中手工执行」——后面所有设计都服务于这两句话 |
| 9 | `SET NAMES utf8mb4;` | 让本次会话的 `client/connection/results` 三处字符集都按 utf8mb4 解析。中文注释、中文默认值（如角色名）才不会乱码；CJK 与 emoji 都能存（utf8 只有 3 字节，存不下 4 字节字符） |
| 10 | `SET FOREIGN_KEY_CHECKS = 0;` | 关闭外键检查。本文件确实没有外键，但成对写上，为「将来加外键」或「按任意顺序重建表」留余地；`99_reset_demo_data.sql` 同样成对使用 |
| 636 | `SET FOREIGN_KEY_CHECKS = 1;` | 恢复默认，避免影响同一连接里后续执行的语句 |

跨表统一的 7 条约定（下面各表不再重复）：

1. **主键**：`id BIGINT NOT NULL AUTO_INCREMENT` + `PRIMARY KEY (id)`。用 `BIGINT` 而非 `INT`：批次记录表
   （`raw_data_record`）按「对象 × 指标 × 时间」增长，单批可达 20 万行（`data.max.rows` 默认 200000），
   演示与真实试验数据叠加后 `INT` 上限不够安全。
2. **业务唯一键单独建唯一索引**（`uk_*`）：`role_code`、`username`、`project_code`、`batch_code`、
   `snapshot_code`、`task_code`、`report_code` 等。这样主键只做代理键，业务编码由数据库兜底防重
   （`05` 分册里 `CodeService` 按当天最大值推导编号，唯一键是它的最后一道保险）。
3. **不用外键约束，只用 `xxx_id` + 索引**。四个原因：
   ① **幂等重跑与迁移顺序**：`CREATE TABLE IF NOT EXISTS` 让建表语句可以乱序/重复执行，一旦有外键，
      建表顺序、导入顺序、`TRUNCATE` 顺序都会互相卡住（`99_reset_demo_data.sql` 就得严格拓扑排序）；
   ② **逻辑删除**：`deleted TINYINT(1)` 是逻辑删除标记，被删除的行物理仍在，外键的 `RESTRICT/CASCADE`
      语义与「保留历史、只标删除」冲突；
   ③ **批量导入性能**：`raw_data_record`、`snapshot_value`、`result_detail` 都是十万级行表，逐行校验外键
      会显著拖慢导入与结果落库；
   ④ **与 JPA 用法一致**：实体之间全部用 `Long` 外键 id 关联、不用关联注解（见 03 分册），
      数据库层保持同样的「弱关联」风格，关联完整性由 Service 层校验（如任务校验快照绑定的版本一致性）。
      代价是：**数据库层无法阻止孤儿数据**，删父行不会级联，需要靠业务代码保证（本册小结会再提醒一次）。
4. **布尔值统一 `TINYINT(1) NOT NULL DEFAULT 0/1`**（`deleted`、`built_in`、`read_only`、`is_leaf`、
   `enabled`、`valid`、`passed`、`null` 相关标记等）。理由：MySQL 没有独立布尔类型（`BOOL/BOOLEAN` 只是
   `TINYINT(1)` 的同义词），显式写 `TINYINT(1)` 能让 Navicat/Workbench 显示成勾选框、Java 侧映射 `Boolean`
   时也不会有歧义；全部 `NOT NULL + DEFAULT` 避免三值逻辑（`NULL` 既不是真也不是假）导致的
   `WHERE deleted = 0` 漏行。
5. **权重、指标值、得分用 `DECIMAL` 而不是 `DOUBLE`**：
   - `DECIMAL(18,8)`：权重、标准化值、贡献值、得分、λmax/CI/RI/CR、容差。8 位小数足够覆盖
     「权重 0.10868」「λmax 5.072084」这类中间量，且**十进制精确**——用 `DOUBLE` 时 `0.1+0.2 != 0.3`，
     权重合计校验、`CR < 0.1` 边界判定、基准样例的容差比对都会随机地「差一点」而失败；
   - `DECIMAL(24,8)`：原始指标值（`indicator_value`、`raw_value`、`min_value/max_value/optimal_value` 等）。
     原始值来自甲方试验数据，量纲跨度大（毫秒级时间、上亿的吞吐量），24 位整数部分留足空间。
   - **反例提醒**：`total_score` 用 `DECIMAL(18,6)`（第 490 行），因为它是展示口径的最终得分
     （`algorithm.display.scale` 默认 2 位、计算口径 4 位），6 位小数足够且省空间。
6. **JSON 一律存 `TEXT`**（`permissions`、`detail`、`configure_value`、`validate_result`、`quality_report`、
   `error_detail`、`parameters`、`combo_flow`、`input_summary`、`vector`、`weights`、`contributions`、
   `details`、`warnings`、`extra`、`matrix_data`、`eigen_vector`、`score_rule`、`input_payload`、
   `expected_payload` 等 20 余处）。**为什么不用 MySQL 的 `JSON` 列**：
   ① 这些字段只在 Java 侧**整体读写**——`JsonUtils.toMap/toStringList` 序列化后整列存取，
      从不按 JSON 内部字段查询（全仓库没有任何 `JSON_EXTRACT` / `JSON_TABLE` / 原生 SQL 查 JSON 的代码）；
   ② `JSON` 列是 MySQL 5.7+ 专有类型，`db/schema.sql` 声称「使用标准 SQL，仅少量 MySQL 方言」
      （`README.md` 第九节），用 `TEXT` 更易迁移到达梦/人大金仓等甲方库；
   ③ `JSON` 列会做解析校验与二进制存储，导入十万级行时带来额外开销，而这些字段往往只是留档。
   **代价（必须知道）**：不能在数据库里按 JSON 内部字段过滤、聚合、建索引；要查
   「所有 CR 超限的任务」只能全表捞出 `parameters` 在内存里判断，或改用 `ahp_consistency` 这种
   已经拆成独立列的宽表（这正是为什么要单独建 `ahp_consistency` 表，而不是把一致性结果只塞进 `extra`）。
7. **字符集与注释**：每张表结尾统一 `ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '中文表名'`，
   每个业务字段带 `COMMENT '中文说明'`。目的就是**便于在 MySQL Workbench / Navicat 里看懂表**：
   鼠标悬停列名即见中文含义与枚举取值（如 `'DRAFT/VALIDATED/PUBLISHED/INVALID/ARCHIVED'`），
   交接与答辩时不必回头翻代码。InnoDB 保证事务、行锁与崩溃恢复，与 JPA 的事务语义一致。

### 2.2 `backend/src/main/resources/db/data.sql`（68 行）

**作用**：初始化基础数据。四段：2 个角色（方案 4.1，系统只保留系统管理员与评估人员）、17 个系统参数、8 条数据质量规则（方案 5.3）、
4 个算法基准样例（方案 6.6）。
**被谁使用**：Spring Boot 启动时由 `spring.sql.init` 的 `data-locations` 执行（每次启动都执行）；
人工初始化时执行 `db/02_seed.sql`。
**关键设计点**：
1. **`INSERT IGNORE` 保证「不覆盖已有数据」**：所有插入都带 `IGNORE`，配合四张表上的唯一键
   （`uk_role_code`、`uk_config_key`、`uk_dqr_code`、`uk_baseline_code`），已存在的键会**被跳过而不是报错、
   更不会覆盖**。于是「每次启动都跑」与「管理员改过的参数不能被改回去」两件事同时成立：
   管理员把 `algorithm.allow.force` 改成 `true` 后重启，`INSERT IGNORE` 因 `config_key` 已存在而跳过，
   改动得以保留。（注意：`IGNORE` 只保证不覆盖，**不保证数据同步**——后续新增内置参数不会自动补进老库，
   需要手工补 SQL，这算是这套方案明确的取舍。）
2. **不插入默认用户**：`data.sql` 里没有 `sys_user`。默认账号由 `DataInitializer` →
   `AuthService.initDefaultUsers()` 在「用户表为空时」创建（**只建 2 个账号**：`admin`、`evaluator`，密码用 `BCryptPasswordEncoder(10)`
   现算哈希）。原因是 BCrypt 哈希带随机盐，**同一个密码每次生成的哈希都不同**，写在 SQL 里既不好维护、
   也无法与「首次登录后请修改密码」的流程配合。
3. **一切可重复执行**：整段脚本没有 `DELETE`/`UPDATE`/`TRUNCATE`，只做「不存在则插入」。

### 2.6 `db/99_reset_demo_data.sql`（31 行）

**作用**：反复演示时的重置脚本——清空全部**业务数据**，保留用户、角色、系统参数、质量规则与算法基准，

**关键设计点**：
1. **用 `TRUNCATE` 而不是 `DELETE`**：`TRUNCATE` 是 DDL 级操作，直接重建空表、重置 `AUTO_INCREMENT`
   （让演示数据的 id 从 1 开始，截图与文档对得上），且不写 undo/redo 日志逐行记录，速度远快于 `DELETE`；

2. **`SET FOREIGN_KEY_CHECKS = 0` 成对包裹**（第 7、29 行）：虽然本库没有外键，但保留这一对是「防御性写法」——

**文件编码**：**GBK (代码页 936) + CRLF 换行，无 BOM**（实测：**165 个 CRLF**，即
`CR 数 = LF 数 = 行数`；首字节 `40 65 63 68 6F` 即 `@echo`，无 UTF-8 BOM）。
四个 `.bat` 都统一为这一编码与换行。

#### 2.7.1 为什么脚本必须用 GBK(936) 保存（本册必写的坑之一）

- cmd.exe 是按**当前 OEM/ANSI 代码页**解析批处理文件的：中文 Windows 默认是 936（GBK）。
  它**不认 UTF-8 无 BOM**，也不看文件内容的「真实编码」——只按字节流用 936 解码。
- 若把带中文的 `.bat` 存成 **UTF-8**，cmd 会把每个汉字的 3 个字节按 GBK 两两组合解码，结果是乱码：
  `echo` 出来的提示变成「锟斤拷」一类字符，`title` 变成一堆符号。
- 更严重的是**执行层面的坑**：UTF-8 汉字的字节序列里可能解出 `&`、`|`、`>`、`<` 等 cmd 元字符，
  于是原本只是「注释里的中文」或「echo 的一句话」会被切成两条命令——轻则报错，重则**真的执行了
  一段本不该执行的命令**。经典案例是 `REM` 注释行里出现中文时，`&` 之后的半句被当成命令跑掉。
  这就是本项目所有 `.bat` 一律 GBK 保存的原因。
- 为什么不用 `chcp 65001` + UTF-8 的方案：切换代码页只影响当前控制台**之后**的输出解释，
  而 cmd 解析脚本本身的字节流仍然按 936；并且 `chcp 65001` 会让 `mvn`/`npm` 输出的中文变成乱码，
  还会影响 `timeout` 等命令的行为。**用 GBK 保存是最省事、最不容易出问题的做法**，代价是只能用
  支持 GBK 的编辑器打开（VS Code 需手动选 GBK，IDEA 会自动识别）。
- 同理，脚本里的中文输出（`echo [1/4] 检查运行环境 ...`、`echo   [OK] java / mvn / npm 均可用`）
  只有在 GBK 编码下才能在 cmd 里正常显示。
- **换行符统一为 CRLF**：这 4 个脚本实测都是 **`CR 数 = LF 数 = 行数`**（165/165、75/75、90/90、112/112），
  即标准 Windows 批处理换行。cmd 对 LF 换行的脚本多数情况下也能解析，但这些脚本里大量使用
  `call :label` / `goto` 标签跳转与括号块，**CRLF 是 Windows 批处理的传统写法、也是最保守的选择**，
  所以有意统一成 CRLF，不在这上面做「能不能省一个字节」的实验。
  **真正致命的是编码被改成 UTF-8**：中文会乱码，甚至把注释里的中文当命令执行（见本节第一条）——
  这跟换行符无关，别把两件事混在一起。本册按实际字节记录。

#### 2.7.2 为什么用 `ping -n N 127.0.0.1 >nul` 代替 `timeout /t N`（本册必写的坑之二）

- `timeout /t N` 在**标准输入被重定向**时会立刻返回并报 `ERROR: Input redirection is not supported`，
  既不等待也不报错退出——等待循环因此变成「空转」：3 秒的等待变成 0 秒，40 次轮询在一瞬间烧完，
  后端还没起来就打印「后端启动较慢」。
- 什么时候 stdin 会被重定向？① 脚本被别的脚本 `call` 或 `for /f` 调用；② 从 IDE、
  计划任务、CI 或某些终端（含 VS Code 任务、PowerShell 管道）里启动；③ 双击运行时也偶发。
  也就是说「在作者机器上好好的、换台机器就空转」——这类问题极难排查。
- 因此脚本改用 `ping -n N 127.0.0.1 >nul`：`ping` 会真实等待（`-n 4` ≈ 3 秒、`-n 9` ≈ 8 秒），
  不依赖 stdin，在重定向环境下行为一致；`>nul` 屏蔽它的输出，避免刷屏。
  **代价**：本机必须装 TCP/IP 且 `ping 127.0.0.1` 能通（Windows 上必然成立），并且等待时长
  只能按整秒批量近似（`-n N` 是 N-1 秒左右），对启动等待来说足够。

#### 2.7.3 为什么用 `:probe` 子过程 + `curl -s -f -o nul` 轮询 `/api/health`（本册必写的坑之三）

- 判断「后端是否就绪」不能靠固定等待（机器快慢差好几倍，等少了报错、等多了浪费时间），
  所以要**主动探测**：`GET /api/health` 是 `HealthController` 提供的健康检查（免认证，见
  `application.yml` 的 `permit-paths`），返回 `{status, components:{database,algorithm,storage}}`
  （`DEPLOY.md` 3.3、验收项 3.5）。
- **探测动作抽成了 `:probe` 子过程**（第 158-165 行），调用点只有一行 `call :probe <url>`
  （第 64 行传 `%BACKEND_URL%/api/health`）。抽出来的收益是**探测策略只有一份**：将来要加认证头、
  要改成 `wget`、要改超时，只改这一处；`start-offline.bat`（2.10）也复用了同一段代码。
- **子过程是「直线 + 跳转」结构，不是括号块结构**（本册这次修订的重点）：`where curl` 成功就顺着往下走
  curl 分支，失败则 `if errorlevel 1 goto probe_by_powershell` 跳到 PowerShell 分支。
  **为什么不用 `if errorlevel 1 ( … )` 括号块**：见下面那条坑点——块内的 `%VAR%` 是**解析期**展开的，
  而每条分支末尾的 `exit /b %ERRORLEVEL%` 必须拿到**刚刚执行完的那条命令**的退出码，所以它必须待在块外。
  `goto` 把这个问题一次消掉：两条分支都是「标签 + 直行语句」，每一行都独立解析。
  另外 `:probe_by_powershell` 这个标签**排在 curl 分支的 `exit /b` 之后**，所以 curl 分支执行完就直接返回，
  不会「掉进」PowerShell 分支。
- **为什么不是只有 `curl`**：`curl.exe` 是 Windows 10 1803 / Windows Server 2019 之后才随系统提供的，
  交付现场常见的 Server 2016 或长期未打补丁的机器上并没有它。所以 `:probe` 先用 `where curl >nul 2>&1`
  试探，缺失时退回 `powershell -NoProfile -Command "try{Invoke-WebRequest -UseBasicParsing
  -TimeoutSec 3 '%~1' | Out-Null; exit 0}catch{exit 1}"`：用 `try/catch` 把「连不上 / 4xx / 5xx」统一
  转成退出码 1，`-UseBasicParsing` 不依赖 IE 引擎、`-TimeoutSec 3` 与 3 秒轮询间隔对齐、
  `-NoProfile` 不加载用户配置（启动更快、不受个人环境影响）。
- curl 分支的三个参数各有用途：`-s` 静默（不打进度条与统计，避免刷屏）；`-f` 让 curl 在 HTTP 状态码 ≥ 400 时
  **以非 0 退出**（22）——这样「端口开了但应用还在报 500」不会被误判成就绪；`-o nul` 把响应体丢进
  Windows 的空设备（`nul`），只关心退出码。
- **调用方只看「退出码是否为 0」，不要死记某个具体错误码**（本册实测）：curl 分支下活着的 URL 返回 `0`，
  **死掉的 URL 返回 curl 的退出码 `7`（连接失败），并不是 `1`**；HTTP 4xx/5xx 则是 `22`。
  所以脚本里判的是 `if !ERRORLEVEL! EQU 0 goto backok`，**非 0 一律当未就绪**——
  写成 `if errorlevel 1`（语义是「≥1 就成立」）在本例恰好也能工作，但要清楚它是「非 0」而不是「等于 1」，
  更不要写成 `==1`。
- **判定与循环写法**：`call :probe <url>` 之后紧跟 `if !ERRORLEVEL! EQU 0 goto backok`（第 65 行），
  再配 `if !COUNT! GEQ 40 ( … goto backok )`（第 66-69 行）与 `ping -n 4` + `goto waitback`（第 70-71 行）。
  这正是脚本第 11 行必须写 `setlocal enabledelayedexpansion` 的**根本原因**：`COUNT` 每轮自增、
  `ERRORLEVEL` 每轮都变，而 `%COUNT%` / `%ERRORLEVEL%` 写在括号块里是**解析期一次性展开**的
  ——用 `%` 就会永远读到循环开始前的旧值（计数永远到不了 40、退出码永远是第一轮的），
  只有 `!COUNT!` / `!ERRORLEVEL!` 才是**执行期求值**。这也是**为什么用 `goto :waitback` 标签循环
  而不是 `for /l`**：标签循环天然逐行解析，配合 `!VAR!` 双重保险。
- **本节最值得记住的坑：`exit /b %ERRORLEVEL%` 不能写在括号块内（本册实测过的缺陷，现已修复）**。
  上一版 `:probe` 的 PowerShell 分支写成 `if errorlevel 1 ( powershell … / exit /b %ERRORLEVEL% )`，
  `%ERRORLEVEL%` 会在**整块解析时**就展开，取到的是进块前的值——也就是上一行 `where curl` 的失败码 `1`。
  后果：**在没有 curl 的机器上探测恒定返回 1**，后端其实已经起来，脚本却还是走满 40 次（约 2 分钟）
  并打出「后端启动较慢」的误导告警。现在两个脚本都改成了 `goto probe_by_powershell` + **块外**
  `exit /b %ERRORLEVEL%`。**A/B 对照实测**（两边都把 `where` 的探测目标改成必然不存在的名字以强制走
  PowerShell 分支，URL 指向真实在跑的后端；唯一变量就是 `exit /b` 在块内还是块外）：
  **修复前 `RESULT=1`（后端明明是活的）→ 修复后 `RESULT=0`（正确）**。
  这条也顺带印证了本节的循环写法：**凡是块内要读「本轮才产生」的值，一律用 `!VAR!`；
  而退出码这类刚产生的值，最稳的做法是干脆不要放进块里**。
- 等待上限设为 40 次 × 3 秒 ≈ 2 分钟（`mvn spring-boot:run` 首次启动要编译 + 执行 schema/data 脚本，
  慢机器上确实要一分钟以上）；超时不报错，只提示「后端启动较慢，请查看 EES-Backend 窗口日志」并继续
  启动前端——**首启失败的代价小于卡住不动**，因为后端看日志就能定位。

#### 2.7.4 为什么新增「检查运行环境」与「MySQL 两级探测」（企业离线交付的准备工作）

- **第 [1/4] 步用 `where` 而不是「先试着跑」**：`where java` / `where mvn` / `where npm` 只查 PATH、
  不启动任何进程，代价近乎为零，却能把「装没装、加没加进 PATH」在**第 3 秒**就报出来。
  若不做这一步，缺 `mvn` 要等后端窗口闪出一句 `'mvn' 不是内部或外部命令` 才发现，而窗口一关信息就没了。
  提示文案里**同时给出动作**（「请先安装 JDK 21 并加入 PATH」/「可通过环境变量 `JAVA_HOME` 指定安装目录」），
  并统一 `pause` + `exit /b 1`：双击运行的人来得及看清错误，上层脚本/CI 也能拿到失败码。
- **不再写死任何本机绝对路径**（本轮的重点修改）：旧版脚本里是 `call D:\DevEnv\start-mysql.bat`，
  出错提示里还带着 `D:\DevEnv\mysqldata\mysql-error.log`——那是作者本机的开发环境路径，换台机器必然失败。
  现在 `:start_mysql`（第 110-153 行）改成**两级探测**：
  ① 环境变量 `EES_MYSQL_START` 优先（由甲方运维指定自己的启动方式，最灵活，与 `DEPLOY.md` 第 73 行的
  说明一致）；② 否则用 `for %%S in (MySQL80 MySQL84 MySQL57 MySQL56 MySQL)` 逐个 `sc query` 探测
  Windows 服务名，命中第一个存在的就记进 `MYSQL_SVC`，再 `net start` 启动。
- **两级都探测不到时只提示、不中断**（第 130-135 行）：企业现场数据库常在另一台主机上，或由甲方 DBA
  统一维护，本机根本没有 MySQL 服务。这时继续往后走（后端连不上库会由 `/api/health` 的 `database`
  组件与后端日志报出来）比直接 `exit /b 1` 更贴合实际；提示里也写清了补救办法（设置 `EES_MYSQL_START`）。
- **为什么服务名要「猜」而不是查注册表**：MySQL 的 Windows 服务名由安装方式决定（MSI 默认 `MySQL80`、
  ZIP 手工注册常见 `MySQL`、旧版本 `MySQL57`/`MySQL56`），**没有**统一可枚举的依据；用 5 个候选名 +
  `sc query` 是代价最低的启发式。`sc query "名字"` 在服务不存在时返回 `1060`（非 0），
  所以 `if not errorlevel 1` 恰好等价于「服务存在」。
- **`if not defined MYSQL_SVC` 能配合 `for` 块正确工作，恰好也是 cmd 的一个细节**：`defined` 是
  **执行期**判断的动态条件，因此第 2、3 次迭代能看到上一轮刚赋的值，「取第一个命中的服务名」才成立。
  反过来若写成 `if "%MYSQL_SVC%"==""`，`%MYSQL_SVC%` 会在整块解析时展开成空串，循环会把每个存在的
  候选都覆盖一遍，最终拿到**最后一个**匹配（`MySQL`）——同一类坑，同一个对策（见 2.7.3）。
- **`sc query … | findstr /I "RUNNING"` 先判「已在运行」**（第 137 行）：已运行就不必 `net start`
  （否则会输出「请求的服务已经启动」这类噪音）；`/I` 忽略大小写，避免因 `sc` 输出的本地化措辞差异误判。
- **权限：`net start` / `net stop` 需要管理员**。脚本刻意不做 UAC 自提升（提升后的进程工作目录会变成
  `system32`，相对路径全部带偏），而是在失败分支里把最可能的原因与可手工执行的命令一起打出来
  （`net start <服务名>`）——**报错要能直接指导下一步动作**，这是这套运维脚本的统一口径。

### 2.8 `scripts/stop-all.bat`（75 行，GBK 编码）

**作用**：一键停止——按窗口标题关掉服务窗口 → 按端口释放 8080/5173 → **探测并**停止 MySQL 服务。
**被谁使用**：`README` 一键脚本、`DEPLOY.md` 备份恢复流程（第 1 步就是「停止后端」）；
`start-offline.bat` 的结束提示也指向它（见 2.10.5 第 97 行）。
**文件编码**：GBK(936)、**CRLF 换行**、无 BOM（实测：75 个 CRLF，`CR 数 = LF 数 = 行数`，同 2.7.1）。
**关键设计点**：
1. **两道保险：先按窗口标题杀，再按端口杀**。第一道针对「由 `start-all.bat` / `start-offline.bat` 起的
   那些服务窗口」（两者的后端窗口标题都是 `EES-Backend`，所以这里一视同仁），干净且快；
   第二道兜住所有漏网情况——比如有人手工在别的窗口跑了 `mvn spring-boot:run`、`npm run dev`，
   或窗口被关过但进程还在。
2. **为什么必须按端口杀（本册必写的坑之四）**：
   ① `npm run dev` 会派生 `node`/`esbuild` 子进程，`mvn spring-boot:run` 会派生出独立的 `java` 进程
      （Maven 自己是一个 JVM，`spring-boot:run` 默认 fork 出另一个 JVM 跑应用），**父窗口标题与真正占用
      8080/5173 的进程不是同一个**——只关窗口时，`java.exe` 常常还在占着端口，重启时就会
      `Port 8080 was already in use`；
   ② 反过来，如果上一次启动是崩溃或断电留下的僵尸进程，窗口早没了，只能靠端口找 PID；
   ③ 加 `-o`/`--strict-port` 之类的参数或改端口都治标不治本，**按端口 kill 是唯一能保证「端口一定被释放」
      的做法**，也是脚本能反复运行的前提（幂等）。
3. `taskkill /FI "WINDOWTITLE eq EES-Frontend*"` 里的 `eq` 支持通配符 `*`，配合脚本起的
   固定标题就能精确匹配；`/T` 杀进程树（窗口 + 子进程），`/F` 强制结束。
4. **停 MySQL 也改成「两级探测」、不再写死路径（本轮修改点）**：旧版是 `call D:\DevEnv\stop-mysql.bat`
   （与 `start-all.bat` 里那处被删掉的写死路径是同一批问题），现在换成 `:stop_mysql` 子过程
   （第 47-75 行）：优先环境变量 `EES_MYSQL_STOP`，否则用与 `start-all.bat` **完全相同的候选名列表**
   （`MySQL80 MySQL84 MySQL57 MySQL56 MySQL`）探测出服务名再 `net stop`。
   **探测不到就不动数据库**——这是刻意的克制：甲方 DBA 维护的库不该被一个演示脚本顺手停掉
   （脚本头部注释第 7-8 行写了这句话）。两边候选名必须同源，否则会出现「启动脚本认得出、停止脚本认不出」的错位。

### 2.9 `scripts/build-all.bat`（90 行，GBK 编码）

**作用**：一键构建产物——**先**前端 `npm run build` 出 `frontend/dist`，**再**后端
`mvn clean package -DskipTests` 出 `target/evaluation-backend.jar`（`backend/pom.xml` 在 `prepare-package`
阶段把 `frontend/dist` 复制进 jar 的 `classpath:/static/`，所以这个 jar **内含前端页面**），
最后打印离线部署说明。
**被谁使用**：`README` 一键脚本、`DEPLOY.md` 3.2 生产打包、离线交付前打包
（2.10 的 `start-offline.bat` 直接消费它的产物）。
**文件编码**：GBK(936)、**CRLF 换行**、无 BOM（实测：90 个 CRLF，`CR 数 = LF 数 = 行数`，同 2.7.1）。
**关键设计点**：
1. **构建顺序不能颠倒（本轮修改点）**：旧版是「先后端、后前端」，现在改成「**先前端、后后端**」。
   原因是 `backend/pom.xml` 第 170-207 行用 `maven-resources-plugin` 新增了
   `copy-frontend-dist-into-jar`，绑定在 `prepare-package` 阶段，把 `../frontend/dist` 复制到
   `${project.build.outputDirectory}/static`（即 jar 里的 `classpath:/static/`）。`prepare-package`
   早于 `package`，因此**打包后端时前端产物必须已经存在**——否则插件按它自己的注释「仅跳过并提示，
   不会导致构建失败」，结果是**构建成功但 jar 里没有页面**，部署后表现为「后端起来了、页面打不开」。
2. **构建前后各有一道检查**：`where npm` / `where mvn` 的存在性检查（缺了立刻报错，别等 maven 跑一半），
   以及构建后**校验 `frontend\dist\index.html` 存在**——`npm run build` 返回 0 不等于产物真的落在预期位置
   （改过 `vite.config.ts` 的 `outDir`、或构建被中断留下空目录）。检查入口文件是「产物可用」的最小充分证据。

   JDK 21 与 MySQL 后执行 `scripts\start-offline.bat` 即可，无需 Node，也无需 Nginx」，

（本项目用「Nginx 托管 dist + 反代 /api」的部署方式）」——**这条现在不成立了**。
当前 `backend/pom.xml` 第 185-207 行的 `maven-resources-plugin`（执行 id 为 `copy-frontend-dist-into-jar`，
绑定 `prepare-package`）会把 `../frontend/dist` 复制到 `${project.build.outputDirectory}/static`，
也就是 jar 内的 `classpath:/static/`；`DEPLOY.md` 4.3 的首选方案因此改成**单 jar 部署**
（目标机器只需 JDK 21 + MySQL，不需要 Node、不需要 Nginx），Nginx 那套降级为 4.4 的备选方案。
由此带来三条必须记住的纪律：
① **构建顺序不能颠倒**——`prepare-package` 早于 `package`，若此时 `frontend/dist` 还不存在，
   插件会静默跳过（它的注释写着「仅跳过并提示，不会导致构建失败」），结果是**构建成功但 jar 里没有页面**，
   表现就是「后端起来了、页面打不开」；所以脚本先跑 `npm run build`，并用第 48-52 行校验
   `dist\index.html` 真的存在；
② **干净仓库里只跑 `mvn clean package` 会得到不带页面的 jar**：`frontend/dist` 是前端工程的产物目录，
   `mvn clean` 不会删它，因此**磁盘上有 dist 时**单跑 maven 也能带上页面；但在全新克隆的仓库里，
   dist 从来不存在，插件就什么都不复制。`DEPLOY.md` 第 339 行的故障表因此把
   「确认构建时已先执行 `npm run build`（jar 内 `BOOT-INF/classes/static/index.html` 应存在）」
   写成了排查第一步；
③ **dev 档与 prod 档的静态资源来源不同**：dev 档 `static-locations` 指向磁盘上的
   `../frontend/dist`（见 01 分册），所以开发时改前端后刷新即可；prod 档只认 `classpath:/static/`，
   页面必须由构建时"打进 jar"这一步产生——这正是本轮把构建顺序改过来的根本原因。

### 2.10 `scripts/start-offline.bat`（112 行，GBK 编码）

**作用**：**离线交付用的单进程启动脚本**（prod 生产档，4 步）——[1/4] 检查 `java` 与后端 jar →
[2/4] 准备数据库连接参数（环境变量优先，缺口令时 `set /p` 现场输入）→ [3/4] 用 `start /D` 开新窗口
跑 `java -jar target\evaluation-backend.jar --spring.profiles.active=prod` 并轮询 `/api/health` →
[4/4] 用默认浏览器打开页面并打印页面地址、默认账号与日志路径。
**被谁使用**：`DEPLOY.md` 4.3「推荐方式：单 jar 运行（离线交付首选）」明确写了「也可以直接双击
`scripts\start-offline.bat`」；`build-all.bat` 第 85-87 行的构建输出也指向它。交付到甲方机器上时，
**只需 JDK 21 + MySQL**，不需要 Node、不需要 Nginx，也不需要 Maven（现场不构建）。
**文件编码**：GBK(936)、**CRLF 换行**、无 BOM（实测：112 个 CRLF，`CR 数 = LF 数 = 行数`，同 2.7.1）。

#### 2.10.2 为什么密码用 `set /p` 现场输入，而不是写进脚本

- `application-prod.yml` 第 5 行是 `password: ${EES_DB_PASSWORD:}`——**默认值为空**，这是 prod 档刻意的
  安全设计（生产不落任何内置口令，未注入就让连接失败并明确暴露配置缺失，而不是用弱口令「悄悄跑起来」）。
- 于是脚本面对一个现实矛盾：交付物里不能带口令，但现场双击运行的人不一定知道要先设环境变量。
  折中方案是「**环境变量优先，缺了才提示输入**」（第 50-54 行）：`if not defined EES_DB_PASSWORD` 成立时
  才 `set /p EES_DB_PASSWORD=  请输入数据库密码:`，并在提示里写明「先设置环境变量 `EES_DB_PASSWORD`
  可跳过本次输入」——这句是给自动化/批处理留的无交互通道。
- 权衡也写在本册里：`set /p` 是**明文回显**，口令只存在于本次 cmd 会话（`setlocal` 作用域内）的环境变量里，
  不落盘、不进日志；而写进 `.bat` 或写进 `application-prod.yml`，等于交付物一出去就把口令一起交付了。
  这就是「**离线交付物不含口令**」这条要求的落点。
- 空输入会被拦住（第 55-59 行 `pause` + `exit /b 1`）：让后端带着空口令去连库，只会得到一行
  `Access denied for user 'ees'`；不如当场说清「未提供数据库密码，已终止」。

#### 2.10.3 为什么用 `start /D` 而不是 `cd /d`（本册必写的坑之五）

- 另一种常见写法（`start-all.bat` 第 58 行那种）是 `start "标题" cmd /k "cd /d <目录> && <命令>"`。
  这条命令**遇到含空格的路径容易翻车**：`start` 的第一个引号参数被当作**窗口标题**，于是
  `start "C:\Program Files\..." cmd /k ...` 里的路径会被当成标题吞掉；经典绕法是先给空标题
  `start "" "C:\..."`，但当命令里还要嵌套引号（`cmd /k "…"`）时，引号层数很容易数错。
- 本脚本改用 `start "EES-Backend" /D "%BACKEND%" cmd /k "java -Dfile.encoding=UTF-8 -jar %JAR%
  --spring.profiles.active=prod"`（第 65 行）：`/D` 是 `start` 自己的**起始目录**参数，工作目录由 `start`
  保证，不必再往 `cmd /k` 里塞一条 `cd /d`；`cmd /k` 后面的命令里只剩 `java -jar …`，**没有任何路径需要
  加引号**，空格路径问题从根上消失。顺带的好处是 `%JAR%` 写的是相对路径 `target\evaluation-backend.jar`，
  相对的就是 `/D` 指定的工作目录。
- **为什么工作目录必须是 `%BACKEND%`**：prod 档的日志路径是
  `logging.file.name = ${EES_STORAGE_ROOT:./data}/logs/evaluation-backend.log`（`application.yml` 第 142 行），
  其中 `./data` 是**相对工作目录**的。工作目录不对，日志就会写到别处去，而第 95 行打印的
  `%BACKEND%\data\logs\evaluation-backend.log` 也就成了错的——现场排查时「按提示去找日志却找不到」
  多半就是这个原因。
- `-Dfile.encoding=UTF-8` 显式指定 JVM 默认字符集：中文 Windows 上 JVM 的默认字符集随区域设置变化
  （GBK 或 UTF-8 都可能），写死可以避免中文日志、中文文件名在不同机器上表现不一致。

#### 2.10.4 与 `start-all.bat` 共用的部分（含一处已修复的共用缺陷）

- `:probe` 子过程（第 105-112 行）与 `start-all.bat` 第 158-165 行**逐字相同**；等待循环
  （`:waitback` / `if !ERRORLEVEL! EQU 0` / `if !COUNT! GEQ 40` / `ping -n 4` / `goto waitback`）
  也是同一套路，连「40 次 × 3 秒 ≈ 2 分钟」的上限都一致（2.7.3）。
  **为什么不抽成公共文件**：`start-offline.bat` 常常连同 jar 一起被单独拷到甲方机器，
  多一个 `common.bat` 依赖反而多一处出错面（少拷一个文件就整个跑不起来）；
  代价是**改动要同步两处**，本册把这句话写在这里作为维护提醒。
- **「复制两份」的代价，在 `:probe` 上真实发生过一次（缺陷已修复）**：上一版两个脚本的 `:probe`
  都把 PowerShell 分支写在 `if errorlevel 1 ( … )` 括号块里，块内的 `exit /b %ERRORLEVEL%` 因为
  **解析期展开**取到的是进块前的值（上一行 `where curl` 的失败码 1），于是**在没有 curl 的机器上
  探测恒定返回 1**：后端其实已经起来，本脚本仍会走满 40 次约 2 分钟，并且因为第 81 行的
  `if !COUNT! LSS 40` 不成立，**连 `[OK] 后端已响应` 都不打印**（第 87 行的浏览器仍会照常打开）。
  现在两个脚本一起改成了 `goto probe_by_powershell` + **块外** `exit /b %ERRORLEVEL%`，
  行为重新对齐（A/B 对照实测见 2.7.3）。
  **这件事的教训值得留在本册**：共用代码的成本不在「写两遍」，而在**「改一份忘一份」导致行为分叉**——
  本次是靠两处同时修改才没留下分叉；今后改 `:probe` 或等待循环，务必同步两个文件。

- **数据库层的职责边界**：`schema.sql` 是唯一的 DDL 来源（`ddl-auto: none`），`data.sql` 只做
  「不存在则插入」的基础数据初始化；业务数据的生命周期全部由 Java 服务控制，脚本不碰。
- **四条贯穿全库的设计决策**（也是答辩最爱问的）：
  ① 无外键 —— 幂等重跑、逻辑删除、批量写入三件事都要它让步，代价是**孤儿数据靠业务代码防**，
     删父行不会级联（例如删项目前要检查是否已产生结果，这是 Service 层的活，不是数据库的活）；
  ② `DECIMAL` 而非 `DOUBLE` —— 权重合计、CR 阈值边界、基准容差比对都要求十进制精确；
  ③ JSON 存 `TEXT` —— 换来跨库可移植与写入开销，代价是**不能按 JSON 内部字段查询**，
     所以「需要查询的字段必须落成独立列」（`ahp_consistency` 的四个数值列、`result_detail` 的行式明细就是这么来的）；
  ④ 字符串枚举 —— `status`/`algorithm`/`severity` 全部人可读，加取值不用改表。
- **容易误解的地方**：
  1. `sys_config` 里的 17 个参数**不等于**17 个生效开关。确切被代码读取的是
     `algorithm.allow.force`、`data.missing.policy`、`audit.retention.days`；`algorithm.cr.threshold`、
     `security.login.maxfail`、`security.login.lockmin` 等的真实来源是 `application.yml`
     （`ees.algorithm.ahp-cr-threshold`、`ees.security.max-login-fail`、`ees.security.lock-minutes`）。
  2. `data.sql` **不创建默认账号**——2 个账号（`admin`、`evaluator`）由 `AuthService.initDefaultUsers()` 在用户表为空时用
     BCrypt 现算哈希创建（带随机盐，没法写死在 SQL 里）。
  3. 权限在**登录时**从 `sys_role.permissions` 读进 JWT，**改权限必须重新登录**才生效。
  4. `QR-FORMAT` 的级别是 `BLOCK`，但它的语义是**按行阻断**：错误行被标记，同批有效行照常入库，
     这不是 bug 而是修过的真实缺陷（README 第四节第 5 条）。
  5. `QR-DIRECTION` 这条规则目前在批次校验里**没有读取点**（`severityByType` 只取 6 类），
     方向未确认的拦截发生在任务提交侧的 `DIRECTION_UNKNOWN` 错误码。
  6. `db/01_schema.sql`、`db/02_seed.sql` 是 jar 内资源的副本，**改了源码里那份必须整文件复制过来**，
     否则手工初始化的库会缺表或缺数据。
  7. **`build-all.bat` 现在会**把前端产物打进后端 jar（`backend/pom.xml` 的
     `copy-frontend-dist-into-jar`，绑定 `prepare-package`），所以**必须先构建前端、再构建后端**，
     交付口径也从「Nginx 托管 dist + 反代 /api」改成「**单 jar**：目标机器只要 JDK 21 + MySQL」。
     旧版本册写的「不会拷贝、用 Nginx」已作废（2.9 的易错点一节有完整解释）。
  8. **写死的本机绝对路径已全部删除（共三处）**：旧版 `start-all.bat` 里的 `call D:\DevEnv\start-mysql.bat` 与
     提示文案里的 `D:\DevEnv\mysqldata\mysql-error.log`、旧版 `stop-all.bat` 里的
     `call D:\DevEnv\stop-mysql.bat`，现在统一由「环境变量 `EES_MYSQL_START`/`EES_MYSQL_STOP` →
     `sc query` 探测服务名」两级方式处理，**探测不到只提示、不中断，也不会误停甲方 DBA 维护的库**。
     日志位置由后端配置决定（`application.yml` 的 `logging.file.name`），不再写在脚本提示里。
  9. **`:probe` 里那处 `%ERRORLEVEL%` 缺陷已经修复**（不再是「已知边界」）：上一版把 PowerShell 分支写在
     `if errorlevel 1 ( … )` 括号块内，块里的 `exit /b %ERRORLEVEL%` 因解析期展开恒取到「进块前」的值
     （`where curl` 的失败码 `1`），于是**没有 curl 的机器上探测恒定返回 1**——后端明明是活的，
     也要白等约 2 分钟并打误导性告警。现在两个脚本都改成 `goto probe_by_powershell` + **块外**
     `exit /b %ERRORLEVEL%`，A/B 对照实测由 `RESULT=1` 变为 `RESULT=0`（见 2.7.3、2.10.4）。
     顺带记一个容易记错的实测细节：curl 探活时**死掉的 URL 返回的是 `7`（连接失败）而不是 `1`**，
     HTTP ≥ 400 是 `22`，调用方只判「是否为 0」。
- **四个 `.bat` 的共同纪律**（都是踩过坑才有的写法）：保存为 **GBK(936) + CRLF**——编码错（UTF-8）
  会让中文乱码甚至把注释里的中文当命令执行，换行用 Windows 传统的 CRLF 是因为这些脚本大量依赖
  `call :label` / `goto` 与括号块，**CRLF 是最保守的选择**；**不写死任何本机绝对路径**
  （MySQL 用「环境变量 → `sc query` 服务名探测」两级方式，探测不到只提示、不中断）；
  用 `setlocal enabledelayedexpansion` 配合 `!VAR!` 读取循环内变化的变量（块内写 `%VAR%`
  拿到的永远是解析期的旧值）；**退出码这类「刚产生」的值干脆别放进括号块**——
  `exit /b %ERRORLEVEL%` 用 `goto` 分流到块外（本册实测过它写进块里的后果，见 2.7.3）；
  用 `where` 先查运行环境再动手、用 `ping -n` 代替会被重定向破坏的 `timeout`、
  用 `curl -s -f -o nul`（缺失时退回 PowerShell `Invoke-WebRequest`）探活而不是死等、
  用 `goto` 标签循环避开 cmd 延迟展开陷阱、
  停止时按端口 kill 而不只是关窗口（`mvn`/`npm` 的子进程会继续占着 8080/5173）、
  跨目录操作用 `pushd/popd` 成对、调用外部批处理一律加 `call`、
  需要指定工作目录时用 `start /D` 而不是往 `cmd /k` 里塞 `cd /d`（路径含空格也不会出错）。
- **样例数据的分工**：`指标体系样例.csv` 负责「正常路径」（6 指标 / 3 叶子 / 3 层，含 1 个负向指标）；
  `试验数据样例.csv` 负责「正常批次」（15 行 / 5 对象 / 指标全覆盖，可用于人工核对标准化值）；
  `试验数据（含错误行样例）.csv` 负责「异常路径」（按行错误 + 指标未覆盖阻断）；
  两个 JSON 分别负责「AHP 的 4 种矩阵形态」与「3 种算法的参数组合」。
  **每一个样例的预期结果都在 `docs/ACCEPTANCE.md` 里有对应的验收项**，样例不是随手写的演示文件，
  而是可执行验收单的输入。
