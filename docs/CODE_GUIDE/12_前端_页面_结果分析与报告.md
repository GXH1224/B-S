## 2. 逐文件详解

### 2.1 `frontend/src/views/result/ResultList.vue`

**作用**：评估结果列表页。按项目 / 任务 / 算法 / 评判等级 / 发布状态 / 对象编码六个条件检索结果，行双击进入结果分析页，并提供「复核」「发布」「导出 Excel / Word / PDF」三类行内操作。

**被谁使用**：
- `frontend/src/router/index.ts` 第 80-84 行以 `component: () => import('@/views/result/ResultList.vue')` 懒加载注册，路由 `results`，`meta.menu = 'result'`；
- 评估任务页通过 `#/results?taskId=…` 深链跳入（本页 `onMounted` 消费这三个 query）；
- 行内「查看分析」跳 `/results/{id}`，由本册 2.2 的 `ResultDetail.vue` 承接。

**关键设计点**：
1. **数值零加工**：所有分数、权重、等级直接取后端返回值，`fmtScore` 等只做「保留小数位 + 空值占位」，不做任何换算或重算，以保证列表、表格、图形三处数值同源（方案 7.3 结果一致性；对应 `docs/ACCEPTANCE.md` 1.7.13）。
2. **排序能力如实降级**：结果列表接口 `GET /api/evaluation-results`（`docs/API.md` §7）**没有 `sortBy` / `order` 参数**，所以页面用 Element Plus 的本地排序（`sortable`，非 `sortable="custom"`），并显式在页脚写明「排序作用于当前页数据」（第 181-183 行）。这与 2.2 的表格标签页（真实服务端排序）形成有意对照，属于「能力边界写清楚」而非隐藏缺陷。
3. **深链健壮性**：任务下拉只取 `page:1, size:100`，深链带来的 `taskId` 可能不在其中，于是 `ensureTaskOption()` 用 `taskApi.detail(taskId)` 单独取回该任务并插到下拉首位，避免「查询条件有值但下拉框显示空白」。

**为什么会出现这个现象（务必理解）**：`el-dropdown` 的根元素由 Element Plus 自带 `display: inline-flex` 与 `line-height: 1`。四个操作项平铺在同一个 inline 格式化上下文里时，浏览器按**基线（baseline）**对齐：`el-button` 的行盒由按钮自身的行高与内边距撑起，而 `el-dropdown` 的行盒高度只等于 `line-height: 1`，两者基线不一致，「导出」就被顶得整体下沉。本页操作列此前**没有任何布局约束**（`ResultList.vue` 里既没有包装容器、也没有相关样式），所以完全受 Element Plus 默认样式影响。

**为什么只有这一页有问题（本次改动的关键背景）**：项目里其余同类位置早就用 flex 容器约束过了，所以这是一次「补齐」而不是「发明新写法」：

- **数据接入三个页面的操作列本来就套了 `.op-cell`**，写法与本页现在完全一致：
  - `frontend/src/views/data/DataBatchList.vue`——模板第 91 行 `<div class="op-cell">`，样式第 1062-1071 行；
  - `frontend/src/views/data/DataSourceList.vue`——模板第 80 行，样式第 886-895 行；
  - `frontend/src/views/data/SnapshotList.vue`——模板第 92 行，样式第 728-737 行。
  三处的 `.op-cell` 都是 `display:flex; flex-wrap:wrap; align-items:center; gap:2px 6px`，并且都把 `el-button + el-button` 的左外边距归零。
- **页面头部操作区由公共组件兜底**：`frontend/src/components/PageHeader.vue` 第 7 行用 `.ees-page-actions` 包住 `#actions` 插槽，而该类的全局样式在 `frontend/src/styles/index.scss` 第 91-96 行就是 `display:flex; align-items:center; gap:8px; flex-wrap:wrap`。因此 `ResultDetail.vue` 页头（第 13-24 行）的「导出报告」下拉天然处在 flex 容器里，从不会出现这个对齐问题。

**结论**：本次改动属于**沿用项目既有约定**，未引入新写法。今后同类页面的操作列若新增下拉类控件（`el-dropdown`/`el-select`/`el-tooltip` 包按钮等），也应放进 `.op-cell`（或等价的 flex 容器）而不是直接平铺，否则会重复出现这次的下沉现象。

**易错点/注意**：
1. 第 311 行 `Object.entries(PUBLISH_LABEL)` 生成的 `value` 是**字符串**（`'DRAFT'`/`'PUBLISHED'`/`'ARCHIVED'`），与 `query.publishStatus` 的 `'' as string` 类型一致；但 `query.projectId`/`query.taskId` 是数字，二者不可混用同一下拉逻辑。
2. `ensureTaskOption()` 只在「任务不在前 100 条」时补项，如果系统里任务超过 100 条且用户**手工**在下拉里找不到较早的任务，需要改用任务搜索——当前实现只保证深链场景可用，这一点属已知边界。

**为什么 `full` 里已经有 `text` 还要单独调 `/text` 取 `improvements`？**

这是本页最容易被误解的一处，必须讲清楚：

1. `GET /api/evaluation-results/{id}`（完整视图）的 `text` 字段，后端放的是 `buildTextConclusion(...)` 的**结论对象本身**——`ResultService.fullView()` 第 114 行 `m.put("text", buildTextConclusion(r, details, task))`。该方法返回的 Map 里只有 `summary`、`weakIndicators`、`strongIndicators`、`level`、`score`、`algorithm`、`algorithmLabel`、`objectCode`、`generatedAt`（第 133-199 行），**没有 `improvements`**。
2. `GET /api/evaluation-results/{id}/text`（文本展示）返回的是**包装对象** `{ conclusion: {...}, warnings: [...], improvements: [...] }`（`ResultService.textView()` 第 122-131 行，第 129 行 `m.put("improvements", buildImprovements(details))`）。`improvements` 只在这一个出口存在。
3. 因此前端必须额外请求 `/text`，`loadTextView()`（第 811-818 行）就是为此而生，`improvements` 计算属性（第 731-734 行）优先取 `textView.improvements`，仅当它为空时才回退到 `full.text.improvements`——这个回退在当前后端实现下**永远不会命中**，属于对未来接口演进的防御性写法。

**为什么不能只显示最大隶属度对应的等级（方案 6.3 的要求）？**

- 模糊综合评判的信息量在于**向量的分布形态**，而不只是 argmax。例如向量 `[0.46, 0.31, 0.19, 0.04]`：最大隶属度 0.46 对应「优」，但「良」有 0.31，说明该对象在优与良之间，而不是稳稳的优。如果只显示「优」这个等级，读者会误以为结论非常确定。
- 只显示等级还**丧失可核验性**：评审或答辩时无法判断矩阵合成、权重归一化是否算对，也无法解释「两个对象等级相同但得分不同」的原因。完整向量是把算法过程摊开给使用者看，符合方案对「算法过程可追溯、结果可复核」的要求。
- 因此页面采用「表格（精确保留） + 进度条（直观对比） + 最大隶属标记（结论指向） + 原始向量（溯源）」四层展示，对应 `docs/ACCEPTANCE.md` 2.4「向量 [0.46,0.31,0.19,0.04]，等级「优」，得分 85.55」这条可执行验收。

**为什么散点图的轴选择器要显示「后端实际返回的组合」？**

`docs/API.md` §7（第 185 行）明确规定：`GET /api/evaluation-results/charts/{chartType}?taskId=&resultId=&projectId=` —— **只接受任务 / 结果 / 项目三个参数，没有横纵轴参数**。后端 `ResultService.scatterChart(taskId)` 的实现（第 425-453 行）固定取该任务全部指标编码列表的**前两个**（`codes.get(0)`、`codes.get(1)`）作为 X、Y 轴。

于是存在一个能力缺口：界面提供了轴选择器，但接口无法按选择返回数据。页面选择**如实告知**而不是假装可用，具体做法有三层：

1. **记录请求意图**：`refreshScatter()` 先 `scatterRequested.value = { x: scatterX.value, y: scatterY.value }`（第 910 行）保存用户点「应用」时的选择；
2. **回填实际结果**：请求回来后 `charts.scatter` 被替换，`syncScatterSelection()` 把选择器**重置为后端实际返回的轴**（第 877-885 行，同时更新 `scatterRequested`，避免把回填本身误判成用户选择）；
3. **动态文案解释**：`scatterHint`（第 895-905 行）三种分支：
   - 没有散点数据 → 「散点图数据尚未返回。」
   - 有 `emptyReason` → 「该图形数据不足，后端已给出原因。」
   - 用户没选过轴 → 「坐标轴由后端默认选择。」
   - 用户选择与后端返回一致 → 「已按所选指标组合展示。」
   - 用户选择与后端返回不一致 → 「**后端当前的散点图图形接口仅接受任务 / 结果 / 项目参数，实际返回的是下方所示坐标轴组合，如需其他组合请在评估时调整指标体系。**」

第 5 种是真实会走到的那条分支，它把「为什么我选了 X/Y 却没生效」和「怎样才能换组合」都讲清楚了，并把话题引向真正的解法（调整指标体系使目标指标排在编码前两位），而不是给用户一个无效的反复尝试循环。这就是「限制如实告知」的完整实现。

### 2.3 `frontend/src/views/report/ReportList.vue`

**作用**：报告导出页。检索已生成的报告记录（Excel / Word / PDF / JSON），查看状态与详情并下载；提供「生成报告」弹窗，按「选择任务 → 可选具体结果 → 选择格式」三步生成新报告，生成后立即询问是否下载。

**被谁使用**：
- 路由 `reports`（`router/index.ts` 第 92-96 行，`name: 'Reports'`，`meta.menu = 'report'`，图标 `Document`）；
- 结果列表页与结果分析页的「导出」操作实际也会落一条报表记录到这里（`POST /api/evaluation-results/{id}/exports` 内部复用同一套报表生成与登记逻辑），因此本页是**所有导出文件的统一台账**；
- 侧栏「报告导出」菜单。

**关键设计点**：
1. **导出走「先登记、后下载」**：所有导出都先在服务端生成文件并写一条报告记录，再通过 `GET /api/reports/{id}/download` 下载。这样「谁在什么时候导出了什么格式的哪个任务的报告」永远可查（验收 1.9.5），也让下载页成为导出的统一入口。
2. **状态三态显式呈现**：`GENERATING`（生成中）/ `READY`（可下载）/ `FAILED`（生成失败）三态各有颜色，且**失败态禁止下载**（按钮 `disabled`），失败原因在详情弹窗里以红色文本展示，避免用户反复点一个必然失败的按钮。
3. **详情弹窗「行数据先占位、再请求刷新」**：点击详情立即用列表行数据填充弹窗（无需等待），同时发起 `GET /api/reports/{id}` 补充 `filePath`、`errorMsg` 等列表里没有的字段；请求失败则保留行数据。这样弹窗永远不会空白，弱网体验更好。

### 2.4 `frontend/src/views/baseline/BaselineList.vue`

**作用**：算法基准测试页。列出全部基准样例（编号、名称、算法、绝对/相对容差、启用状态、最近运行时间与结果），支持「单个运行」（弹出逐字段比对明细）与「全部运行」（汇总「通过 X / Y」）。它是 `docs/ACCEPTANCE.md` 第二章「算法验收」的**直接验证入口**。

**被谁使用**：
- 路由 `baselines`（`router/index.ts` 第 98-102 行，`name: 'Baselines'`，`meta.menu = 'baseline'`，图标 `Compass`）；
- 侧栏「算法基准」菜单；
- 答辩 / 验收时由操作人手工触发（README「五分钟体验路径」第 7 步：点击「全部运行」，确认四个标准样例全部通过）。

**关键设计点**：
1. **容差判定完全交给后端**：页面只展示 `absTolerance`/`relTolerance` 与每项的 `passed`/`note`，前端不做任何数值比较。这样「浮点结果按绝对误差**或**相对误差判定，任一满足即通过」这条规则只在后端实现一处（界面上的说明文案两处重复了这条规则，但结论仍来自后端），避免出现「后端判 PASS、前端画出 FAIL」的分裂。
2. **所有差异都留下测试记录**：不仅显示结论，还逐字段列出期望值 / 实际值 / 判定 / 差异说明，并可展开完整的 `expected` 与 `actualRaw` JSON，满足「所有差异都有测试记录」的页面承诺（页面副标题原文）。
3. **颜色即结论**：`PASS` 绿、`FAIL`/`ERROR` 红（等宽字体加粗），大号判定标签用 `size="large" effect="dark"`，让「4/4 通过」在投影仪上也能一眼看清。

1. **顶部汇总告警是会话内状态**：`lastRunAll` 只存在内存里，刷新页面后 2.4.1 的 `el-alert` 消失，只剩列表里的「最近运行结果」列。演示或验收时如果要展示「通过 4 / 4」的告警，需要先点一次「全部运行」，不要刷新页面。

## 3. 本册小结

- 本册共覆盖 **4 个文件、2980 行**代码：`ResultList.vue`（621 行）、`ResultDetail.vue`（1370 行）、`ReportList.vue`（525 行）、`BaselineList.vue`（464 行），与分配清单完全一致（621 + 1370 + 525 + 464 = 2980）。
- **这一层的职责边界**：四个页面全是「展示 + 编排」，不含任何算法计算。所有数值（得分、权重、贡献值、隶属度、λmax/CI/RI/CR、标准化值）都直接来自后端结果数据集或基准运行结果；前端的 `computed` 只做「结构归一 + 单位换算 + 阈值着色」这类展示层处理，绝不重算。这是方案 7.3「结果一致性」在页面层的落实方式，也是验收 1.7.13（表格得分与柱状图数值完全一致）能够通过的根本原因。唯一需要留意的是 `vectorRows` 里 `value <= 1 ? value * 100 : value` 这一处换算——它处理的是「隶属度存储为 0~1 还是百分数」的两种可能，属于展示口径归一而非业务重算。
- **「三类展示」在代码里的锚点是三个 `el-tab-pane` 的 `name`**：`text` / `table` / `chart`，与 `docs/API.md` §7.1「三类展示形式」、`docs/ACCEPTANCE.md` 1.7.1~1.7.3 一一对应；三个标签页的数据分别来自 `full.text` + `/text`、`/details`、`/charts`，页面用 `onMounted` 里「一次串行 + 三次并行」的加载链把它们拼成一个整体。
- **容易被误解的三处**：
  1. `ResultDetail.vue` 必须**同时**请求 `/{id}`（full）和 `/{id}/text`——因为 `full.text` 放的是结论对象、**不含 `improvements`**，改进建议只在 `/text` 的返回体内（`ResultService` 第 114 行 vs 第 129 行）。`conclusion` 计算属性用「有 `conclusion` 就嵌套取、否则整体当结论」的写法兼容这两种结构。
  2. 两个页面的**排序能力不同**而且都是有意为之：结果列表页接口无排序参数，因此排序只作用于当前页并在页脚注明；结果明细接口支持 `sortBy`/`order`，因此表格列全部用 `sortable="custom"` 走真实服务端排序，合计行则始终按**全部明细**（`allDetails`）求和、不随翻页变化。
  3. `ResultDetail.vue` 图形标签页的 `lazy` 与散点图轴选择器的提示文案，都是**能力边界的显式表达**：前者避免 ECharts 在 `display:none` 容器里以 0 尺寸初始化；后者如实告知「`/charts/{type}` 只接受 taskId/resultId/projectId，不能指定轴」，并给出真正可行的替代路径（调整指标体系）。
- **操作列对齐是一条项目级的样式约定**：`ResultList.vue` 的操作列（模板第 154-177 行、样式第 566-583 行）与数据接入三个页面的操作列一样，用 `.op-cell`（`display:flex; align-items:center; gap:2px 6px`）包住全部操作项，并把 `el-button + el-button` 的默认外边距归零；页头操作区则由 `PageHeader.vue` 的 `.ees-page-actions`（`styles/index.scss` 第 91-96 行）兜底。原因是 `el-dropdown` 根元素自带 `display:inline-flex` 与 `line-height:1`，与 `el-button` 平铺在同一个 inline 流里时基线不一致，「导出」会整体下沉——这正是提交 `1f8f374` 修掉的缺陷（详见 2.1.10）。**新增页面或给操作列加下拉类控件时，必须沿用这个 flex 容器写法**。
- **本册涉及的关键权限码共 7 个**：`result:review`、`result:publish`、`result:export`（结果列表与结果分析页）、`report:create`、`report:download`（报告导出页）、`baseline:list`（算法基准页，查看与运行共用），以及结果分析页特有的一处**无权限码操作**——「打印 / 导出 PDF」走浏览器原生 `window.print()`，不产生服务端文件、不写导出审计，因此不设权限。前端的 `v-if` 只控制可见性，真正的拦截在后端方法级注解与统一响应拦截器（`request.ts` 第 95-98 行对 403 提示「无权访问该资源」）。
- **错误提示只有一处来源**：四个页面里所有 `catch` 块几乎都是空的（引 `// 统一响应拦截器已提示`），因为 `request.ts` 的响应拦截器已经统一 `ElMessage.error(body.message)`。这是本项目的重要约定——**新增页面时不要在 `catch` 里重复弹错**，否则用户会看到两条相同提示；反过来说，「已退回的结果不允许发布」这类业务规则提示之所以能原样出现在页面上，也正是因为它由后端抛出、由拦截器透传。
