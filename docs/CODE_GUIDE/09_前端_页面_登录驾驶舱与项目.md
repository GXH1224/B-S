## 2. 逐文件详解

### 2.1 `frontend/src/views/Login.vue`

**作用**：系统唯一入口页，负责收集用户名/密码、调用登录接口写入令牌、按 `redirect` 参数跳回用户原本想访问的页面，并顺带展示品牌标识（系统名 + 一句话定位）与两个默认演示账号。

**被谁使用**：
- `frontend/src/router/index.ts:10-13` 以 `() => import('@/views/Login.vue')` 懒加载，路径 `/login`，`meta.public = true`（免登录）；
- 路由守卫 `router/index.ts:199-202`（未登录）与 `207-211`（`/api/auth/me` 失败后 `resetLocal()`）都会 `next({ path: '/login', query: { redirect: to.fullPath } })`，因此本页是登录超时与未授权访问的统一落点；
- 令牌写入由 `stores/user.ts:44-51` 的 `login()` 完成，本页不直接操作 `sessionStorage` 里的令牌（`ees_token` 的唯一读写入口是 `api/request.ts`；其存储方式已由 `localStorage` 改为会话级 `sessionStorage`）。

**关键设计点**：
1. 左品牌 / 右表单**非对称双栏**（左侧深色渐变、右侧浅色卡片），对应方案 7.4「混合式 UI」中深色品牌感 + 浅色工作台的视觉基调，且 900px 以下自动改为上下单列（`417-442`）。
2. 本页是 `meta.public` 页面，**只调用一个不需要登录的接口** `/api/auth/login`（后端白名单见 `com/ees/config/EesProperties.java:28-30` 的 `security.permitPaths`）；原先还会调用 `/api/info` 填充底部页脚，页脚删除后该调用一并移除（接口本身保留作运维只读探针，`MainLayout` 侧栏的版本号也已随提交 `546ef92` 删除、前端已无调用方，见 07 分册 2.2），因此后端未启动时页面骨架仍可渲染。
3. 「记住用户名」采用 `localStorage` 键 `ees_remember_user`，**只存用户名、不存密码**；默认账号面板的密码写在源码里，属于演示便利而非凭据缓存（详见 2.1.2 后的设计取舍说明）。

**本次改动说明（登录页的三处变化，行号因此整体变化）**：

- **默认账号由五个减为两个**：`const accounts` 现在只有 `admin`（系统管理员）与 `evaluator`（评估人员）两项，`dataadmin`/`reviewer`/`viewer` 随角色精简一并删除（系统只保留 `SYSTEM_ADMIN` 与 `EVALUATOR` 两类角色）；账号说明条目的文案也由「系统预置五种角色的演示账号」改为「系统预置两类角色的演示账号」。
- **左侧品牌区原有的"四条系统介绍卡片"已整体删除**：模板里的 `<ul class="feature-list">` + `v-for="item in features"`（原第 19–29 行）、`<script setup>` 里的 `interface FeatureItem`（原 146–150 行）与 `const features: FeatureItem[] = [...]` 四项能力点（原 165–186 行）、以及 `.feature-list` / `.feature-item` / `.feature-icon` / `.feature-text` 等样式（原 396–444 行）均不再存在；品牌区现在只剩 `.brand-head`（EES 徽标 + 系统名 + 英文名）与 `.brand-slogan`（一句话定位文案）。
- **登录页底部的页脚已整体删除**（提交 `59aa33b`，需求即"删除登录界面底部这一行版本与架构信息"）：模板里的 `.login-foot` 区块（原第 115–121 行，3 个内容 `<span>` + 2 个 `.sep` 分隔点）、脚本里只为它服务的 `info`（reactive）、`algorithmCount`（ref）与 `algorithmText`（computed）、`onMounted` 中调用 `/api/info` 并逐字段兜底赋值的 `try/catch`（原第 228–241 行）、已无人使用的 `import { systemApi } from '@/api'` 与 vue 导入里的 `computed`、以及样式 `.login-foot` / `.login-foot .sep`（原第 446–459 行）全部移除；`onMounted` 因此不再需要 `async`，现在只剩「读取记住的用户名」一段。**`/api/info` 接口本身没有被删除**——`MainLayout` 的侧栏版本号（原 `layouts/MainLayout.vue:227` 取 `version` 渲染 `v1.0.0`）也已随提交 `546ef92` 删除，**前端已无任何调用方**，该接口保留作运维只读探针（见 07 分册 2.2）。

**设计取舍：为什么「记住用户名」不记住密码**

- 密码是敏感凭据。本系统认证链是「BCrypt 存哈希 + JWT（HS256）令牌」，服务端从不保存可逆密码（README 技术基线），前端若把明文密码写进 `localStorage`，等于把唯一可逆副本放到浏览器里，任何同源脚本、浏览器插件或共用终端都能直接读走，会架空整套密码策略。
- `localStorage` 无过期、无作用域隔离，且本系统面向**私有化 / 内网离线部署**（README 七）：终端常为多人共用的内网机，明文密码留存的风险远大于便利收益。
- 真正需要「免二次输入」时，正规做法是让浏览器密码管理器接管。表单因此显式声明 `autocomplete="username"` / `"current-password"`，把「要不要记住密码」的选择权交还给用户与其浏览器策略。
- 页面上给出的替代路径是「忘记密码请联系系统管理员重置」，配合后端登录失败 5 次锁定 15 分钟的防爆破策略。

- **空值 / 空数组保护**：
  - 表单三个字段（`157-161`）都不预填，用户名由 `onMounted`（`205-211`）视本地记录条件回填，读不到就保持空串，不会渲染出 `undefined`；

  - `fillAccount`、`submit` 都做了 `formRef.value` 存在性判断（`171`、`182`），避免实例未就绪时报错。

**易错点 / 注意**

1. `rules` 里没有校验「用户名去除空格后是否为空」——`required` 只判空串，输入纯空格会通过前端校验并由后端拒绝；这是有意的（把判定权交给后端），但如果要改前端行为，应在 `submit` 里 trim 后补充判断，而不是另加一条 `required`。

3. `@keyup.enter="submit"` 挂在 `el-form` 上，因此在密码框或用户名框内回车都会触发；如果将来在表单里加入下拉框或日期选择器，回车行为可能被其内部键盘处理抢占，需要改为在具体输入框上绑定。

### 2.2 `frontend/src/views/NotFound.vue`

**作用**：全局 404 兜底页。命中任何未注册路由时展示「页面不存在或已被移除」，并给出返回驾驶舱 / 返回上一页两个出口。

**被谁使用**：`frontend/src/router/index.ts:130-135` 的通配路由 `path: '/:pathMatch(.*)*'`，`meta.public = true`。它不是 `MainLayout` 的子路由，因此渲染时不带侧栏与顶栏，是整屏独立页面。

**关键设计点**：
1. `meta.public = true` 让 404 页**免登录**可见：地址写错时用户看到的是「页面不存在」而不是被守卫扔回登录页，避免把「路径错误」误报成「需要登录」。
2. 文案同时覆盖三类成因——地址失效、已被归档、**当前账号没有访问权限**；因为守卫对无菜单权限的访问是重定向到 `/dashboard`（`router/index.ts:221-230`），但历史地址或直接改 hash 仍可能落到这里，文案上先给出解释比只写「404」更贴合内网使用场景。
3. 双出口设计：`goDashboard()` 用 `push` 修复路径（推荐动作，主按钮），`goBack()` 用 `router.back()` 保留用户来路（次要动作，`plain` 按钮）。

**作用**：综合驾驶舱。以当前账号的授权范围为界，一屏汇总项目/任务/快照/结果指标、异常任务告警、任务趋势与等级分布图、最新评估结果、项目态势、算法使用情况与最近任务。「以当前账号的授权范围为界」不再只是页头的一句承诺：**提交 `747fec4` 之后，后端 `DashboardService.overview()` 真的按 `ProjectService.visibleProjectIds()` 过滤**（`null` = 管理员 / `ALL` 数据范围不限制，仍看全部项目；否则只统计可见项目），带 `?projectId=` 时先做可见性校验、不可见直接 **403**。本册 2.3.5 给出三种账号的实测对照表。

**被谁使用**：
- `router/index.ts:20-25` 注册为 `/dashboard`（`meta.menu = 'dashboard'`），是 `MainLayout` 的默认落地页（根路径 `redirect: '/dashboard'`，`router/index.ts:17-18`），也是无菜单权限时的兜底跳转目标（`222-229`）；

- 写入 `appStore.setCurrentProject(id)`，该上下文被 `EvaluationWorkbench.vue`（`604`、`724`、`1285` 行）与 `TaskList.vue`（`227` 行）读取，是跨页面的「当前项目」源头之一。

**关键设计点**：
1. **两个接口并行加载**：`Promise.all([systemApi.dashboard(projectId.value, from, to), taskApi.recent(8).catch(() => [])])`（`576-579`），总览与最近任务同时发出，避免串行等待；并且给 `recent()` 单独挂了 `.catch(() => [])`，让「最近任务」这一个子请求失败时不影响主总览。
2. **前端不做二次计算**：所有数字、图形数据、等级分布都直接来自后端评估数据集，页面只做格式化与取值兜底（页脚 `334` 行明确写出「前端不做二次计算」），这是方案 7.3 结果一致性要求的落点。
3. **两张图表的 option 手写在页面内**：`trendOption`（`419-473`）与 `levelOption`（`476-503`）没有放进 `utils/chartOptions.ts`，原因见本小节末尾的说明——它们不属于「评估结果八类图形」。
4. **页面不自行判断「哪些项目可见」，只负责不带着失效的项目 id 发请求**：可见性口径只存在于后端（`ProjectService.visibleProjectIds()` / `checkVisible()`），前端拿到的项目下拉本身就是可见项目列表。因此这里没有、也不该有「按角色过滤统计」的前端逻辑；前端要做的只有两件配套小事——**换人登录时清空项目上下文**（`stores/user.ts` 的 `login`/`logout`/`resetLocal`，见 08 分册 2.11）与**下拉回来后校验本地 id 是否仍然有效**（`loadProjects()` 第 596-602 行的安全网）。两者的共同目的都是：**绝不带着一个无权或已失效的 `projectId` 去打 `/api/dashboard/overview`**，因为在 `747fec4` 之后那会得到 403 而不是一份空数据。
5. **统计区间只驱动两张图，指标卡刻意不跟着变（提交 `5f8ba79`）**：页面把 `dateRange`（`[from, to]` 两个 `YYYY-MM-DD` 字符串）作为**唯一的区间状态**，`load()`（`572-588`）把它透传给 `systemApi.dashboard()`，后端据此重算「任务趋势」与「评判等级分布」；而上方六张指标卡（项目数/评估任务/数据快照/评估结果/平均得分/可用算法）读的是同一响应里的**总量字段，不随区间变化**。因此用户在「近一周」与「近一年」之间切换时，只会看到两张图和它们的标题/副标题/空态文案变化，指标卡纹丝不动——**这是刻意的口径划分，不是漏传参数**。详见 2.3.6。

**本次改动说明（提交 `da6af44`：修复「任务趋势」图 y 轴名称「任务数」显示不全）**：

页面表现是「任务趋势」折线图左上角的 y 轴名称「任务数」只露出下半截、上半截被画布顶边裁掉。原因在 ECharts 的坐标轴名称定位规则：`yAxis.name` **默认画在网格（grid）上沿之上**，并且还要再往上偏移一个 `nameGap`（默认 15px），也就是说名称实际占用的高度是「`grid.top` 之上、再往上 15px 左右」。原先 `grid.top` 只有 26，减去 `nameGap` 的 15 后留给名称本身的只有约 11px，而 12px 字号的「任务数」需要约 16px，因此名称的上半截落到了画布外被裁掉——它并不是「没渲染」，而是**被画布裁掉了**。改动只有三处（都在 `trendOption` 内，见 2.3.2 的 `423-446` 行）：

- **`grid.top` 由 26 改为 46**（第 `427` 行）：把网格上沿整体下移 20px，为「名称 + nameGap」腾出真实高度，这是本次修复的关键；`left`/`right`/`bottom` 不动，折线绘图区只是略微变矮，不影响 7 天刻度的可读性。
- **`yAxis` 新增 `nameGap: 10`**（第 `441` 行）：名称与网格上沿的默认间距是 15px，偏大且与 `name` 字号（12px）不成比例；收紧到 10px 后，名称与网格之间只留一条窄缝，等效于把「名称 + 间距」的总高度压到 `grid.top` 的 46px 之内，避免为修一处裁切而把网格压得过低。
- **`grid` 上方新增 3 行注释**（第 `424-426` 行）：把上面这条推导写在代码旁——「名称默认画在网格上沿之上、且再往上偏移 nameGap（默认 15）」「原先 top 只有 26，名称顶到画布外，上半截被裁掉」「这里给到 46 并收紧 nameGap」。之所以必须留注释：`top: 46` 这个数字**本身看不出理由**，后来者很容易把它当成随手调大的边距又改回 26，从而复现同一个裁切缺陷。

**为什么 `top` 不能只留 26**：这 26px 同时要装下「y 轴名称文本高度」与「`nameGap` 间距」两项，而二者都由 ECharts 在网格之外绘制，不参与绘图区计算，也就不会被自动避让。只要 `top < nameGap + 名称行高`（默认约 15 + 16 = 31），名称就必然有一部分被画布裁掉；26 恰好落在这个阈值之下，因此在默认 `nameGap` 下**任何**名称较长的 y 轴（「任务数」三字已足够）都会显示不全。若把 `nameGap` 调大而不动 `top`，裁切只会更严重——这两个值是绑在一起的，改一个必须同时核对另一个。

**验证与影响面**：改动后 `npm run build`（含 `vue-tsc` 类型检查）与后端重新打包均通过；无头浏览器截图确认「任务数」三字完整显示，折线、坐标轴刻度与其余部分未受影响。本页只有两张图，另一张「评判等级分布」是饼图、**没有坐标轴名称**，所以只有 `trendOption` 需要改；`levelOption` 的行号虽然因本次插入而后移（`445-472` → `449-476`；提交 `5f8ba79` 之后进一步变为 `476-503`），内容一字未动。

**为什么两张图的 option 不放进 `utils/chartOptions.ts`**

- `chartOptions.ts` 的定位是**评估结果（方案 7.1/7.2）的八类图形渲染器**：`buildChartOption()` 是 `switch (chart.chartType)` 分派，入参类型是 `ChartData`（`api/index.ts:165-173`），带 `chartType / title / unit / description / dataSource / emptyReason` 等后端契约字段，八类图形分别是柱状、折线、饼/环形、雷达、散点、热力、箱线、排名条形。
- 驾驶舱这两张图**不属于这八类**：它们的数据源是 `GET /api/dashboard/overview` 里的 `taskTrend`（`{date, taskCount}`）与 `levelDistribution`（`{level, count}`），既没有 `ChartData` 的字段结构，也不参与结果导出与图形一致性核对。硬塞进 `chartOptions.ts` 会让那个文件同时承担「结果图形渲染」与「驾驶舱统计图」两种职责，并迫使 `buildChartOption` 增加两个非 `chartType` 的分支。**提交 `5f8ba79` 给趋势图加的统计区间交互进一步印证了这个划分**：区间状态、快捷区间下拉、366 天截断都是「这一页的交互」，与八类图形的渲染器毫无关系，留在页面内才不会污染那个共用文件。
- 于是采用「**数据形状不同的图留在页面内、可复用的视觉常量抽出去**」的折中：颜色、坐标轴样式等在本页内联（趋势图的 `xAxis`/`yAxis`/`series` 在 `428-471`，等级图的 `tooltip`/`legend`/`series` 在 `487-501`），唯一跨页复用的是 `GRADE_COLOR`（`349`、`484`），确保驾驶舱的等级配色与结果页 `LevelTag`、排名条形图分毫不差。
- 反过来说，如果将来驾驶舱需要新增图形，判断标准很简单：**数据来自 `/api/evaluation-results/charts` 就走 `chartOptions.ts`，来自 `/api/dashboard/overview` 就留在本页**。

#### 2.3.4 数据加载、失败处理、loading 与空值保护

- **进入时加载**：`onMounted`（`643-647`）——① 从 `appStore.currentProjectId` 恢复项目筛选（该值源于 `localStorage: ees_project_id`）；② `projectApi.options()` 取项目下拉；③ `load()` 并行请求 `GET /api/dashboard/overview?projectId=&from=&to=` 与 `GET /api/evaluation-tasks/recent?limit=8`（提交 `5f8ba79` 起总览请求会带上当前统计区间的起止日期；项目切换、快捷区间切换、手动改日期都只重跑 `load()`，项目下拉本身不变、无需重取）。
- **`projectId` 安全网（提交 `747fec4`，`596-602`）**：`loadProjects()` 在拿到可见项目列表后做一次存在性校验——本地保存的 `projectId` 若不在列表中（项目被删除/归档，或换人后权限不同），就把它与 `appStore` 一起重置为 `undefined`，即回退到「全部项目」。**为什么必须要有**：后端 `DashboardService.overview()` 现在会先对 `?projectId=` 做可见性校验（`ProjectService.checkVisible`），不可见直接返回 **403**；带着一个失效 id 请求不再得到「空数据」而是「加载失败」，整页统计会进空态。它同时也是「换人后权限不同」这一场景的最后一层兜底（`stores/user.ts` 的登录/登出清理是第一层，见 08 分册 2.11）。
- **加载失败如何处理**：
  - `overview` 失败 → 命中 `582-584` 的 `catch`，`raw` 清空为 `{}`、`recentTasks` 清空为 `[]`，页面整体进入空态；具体的错误提示（业务码弹 `message`、403 提示无权访问、超时提示重试）由响应拦截器统一给出。**提交 `5f8ba79` 给这个分支增加了一个真实触发路径**：若区间参数被后端判为非法（`PARAM_INVALID`），走的就是这里——整页卡片与表格一起被清空，这正是 `onRangePick` 要在前端先截断 366 天的原因（见 2.3.6）。
  - `recent` 单独失败 → 被 `578` 行的 `.catch(() => [])` 吞掉，只有「最近评估任务」卡变空，其余统计照常展示，这是「非核心子请求降级」的处理方式。
  - `projectApi.options()` 失败 → `loadProjects()` 的 `catch`（`593-595`）把下拉置空；此时顶部下拉点开无选项，但清空 / 刷新仍可用。
- **loading 状态**：只有一个全局 `loading`（`364`），同时驱动根节点 `v-loading`（`2`）与刷新按钮 `:loading`（`26`）；`loadProjects()` 无独立加载态（下拉选项的加载不值得阻塞界面）。区间切换也复用它，因此点「近一年」时整页会出现一次遮罩——这是有意为之：区间变化会同时影响两张图与两个空态文案，局部 loading 反而会让人以为只有一张图在变。
- **空数据 / 空数组保护**：
  - `arr()`（`373-375`）统一把 `alerts / latestResults / projects / algorithmUsage / taskTrend / levelDistribution` 收敛为数组（`395-400`），`el-table :data` 永远不会收到 `null`；
  - `num()`（`378-381`）兜住所有数值展示（指标卡、任务数、结果数、折线数据点），非法值显示 0 而非 `NaN`；
  - 两张图表用 `if (!rows.length) return null` + 模板 `v-if/v-else` 显式渲染**带原因的空态**（`152-156`、`167-171`），空态文案里的「近 7 天」在提交 `5f8ba79` 后改为随区间变化的 `{{ rangeTitle }}`；
  - 四张表格都提供 `#empty` 插槽（`221-223`、`267-269`、`294-296`、`326-328`），文案分别是「暂无评估结果 / 暂无可见项目 / 暂无算法使用记录 / 暂无评估任务」；
  - 告警卡整体 `v-if="alerts.length"`（`75`），没有异常任务时整块不渲染；
  - 单元格层面统一 `row?.xxx || '-'` 兜底，`ranking` 用 `??` 以免 0 被判为空。

#### 2.3.5 数据权限口径与实测（提交 `747fec4`）

**页头的承诺与后端实现**：`PageHeader` 的 `desc`（第 5 行）写着「数据来自当前账号的授权范围：项目、任务、快照与结果均按数据权限过滤，仅展示可见的汇总信息」。这句话在 `747fec4` 之前**名不副实**——实现只对「项目数」做了过滤，任务/快照/批次/结果仍是全库统计，一个可见项目为 0 的评估人员照样能看到 15 个任务、48 条结果的汇总。改动后后端统一了口径，页头文案才真正成立：

- `DashboardService.overview()` 取 `visibleProjectIds()`：**`null` = 不限制**（管理员 / `ALL` 数据范围，仍看全部项目统计），否则是可见项目 ID 集合（**可能为空**）。
- 带 `?projectId=` 时先调 `ProjectService.checkVisible(projectId)`，不可见**直接 403**（与 `ProjectService.get(id)` 同一口径），而不是返回一份空数据。
- 由项目派生的统计全部按该范围取数：项目数、进行中/已归档、任务各项、快照、批次、结果、已发布、平均得分、等级分布、算法使用、最新结果、告警、任务趋势、项目态势；可见集合为空时直接返回 0 / 空数组。
- **不属于项目数据的能力不受影响**：「可用算法」是系统级能力，仍显示 4。

**前端为什么必须配合**：既然「不可见项目 → 403」，前端就不能再带着「上一个账号选的项目」或「已被删除/归档的项目」去请求，否则驾驶舱整页加载失败。本册 2.3.2 的 `loadProjects()` 安全网（`596-602`）与 08 分册 2.11 的 `login`/`logout`/`resetLocal` 三处清理就是为此而加，二者共同保证请求里的 `projectId` 要么为空（全部项目）、要么确实可见。

#### 2.3.6 图表统计区间联动（提交 `5f8ba79`）

**需求**：「任务趋势」默认仍统计近 7 天，但允许用户选起止日期或快捷区间（近一周 / 近一个月 / 近一年）；右侧「评判等级分布」必须与它**统计同一区间、同步变化**。

**数据流一句话**：`rangePreset` + `dateRange`（页面唯一区间状态）→ `rangeTitle`（标题显示）与 `load()`（请求参数）→ `systemApi.dashboard(projectId, from, to)` → 后端按区间重算 `taskTrend` 与 `levelDistribution` → 两张图与两个空态文案一起更新。**指标卡不在这个链路上**。

**两个入口的分工**：

| 入口 | 触发 | 处理函数 | 关键点 |
|---|---|---|---|
| 快捷区间下拉 | `el-select @change` | `onPresetChange`（`540-546`） | 反查 `days` → `buildRange` 算出闭区间 → 写回 `dateRange` → `load()`。选中「自定义」时**直接返回**，只切下拉态、不动日期，等用户去挑具体区间 |
| 起止日期选择器 | `el-date-picker @change` | `onRangePick`（`548-570`） | ① 未选全则忽略；② 超过 366 天自动按结束日期往前截断 + `ElMessage.warning`；③ **忽略由快捷区间程序化写入触发的多余 change**（新值与 `buildRange(hit.days)` 完全相同时 `return`）；④ 真正的手动改期才把 `rangePreset` 标为 `'CUSTOM'` 并刷新 |

**交互细节与为什么这样做**：

1. **为什么必须识别并忽略「程序化触发」的 change**：`onPresetChange` 是把新日期**写进 `dateRange`**，而 `dateRange` 正是 `el-date-picker` 的 `v-model`——写值必然触发一次 `@change`。如果不加判断，就会发生两件坏事：**重复请求**（一次选择发两个总览请求），以及 **`rangePreset` 被立刻改写成 `'CUSTOM'`**（因为 `onRangePick` 最后一行会把下拉标成自定义），表现为「刚选了『近一个月』，下拉马上跳回『自定义』、标题也从『近一个月』变成一串日期」。判断方式是**比较新值与快捷区间应得的日期是否完全一致**（`pf === f && pt === t`），一致就说明这次 change 是程序化写入的回声，直接返回。这比用 `isProgrammatic` 之类的布尔标志更稳——标志需要成对维护（设值/清值），一旦某条路径忘了清就会漏掉后续真实的手动选择。
2. **为什么超过 366 天要前端截断**：后端对区间上限的拒绝方式与项目权限一样是「业务异常」——HTTP 200 + 错误码，**不是部分失败而是整个 `/api/dashboard/overview` 失败**。区间参数和指标卡在同一个接口里，所以一次越界就等于整页清空（`582-584` 的 `catch` 把 `raw` 与 `recentTasks` 一起置空），用户看到的是「我只是把范围拉大了一点，整个驾驶舱都空了」。前端截断把这种「越界即全空」的放大效应**消灭在请求发出之前**，并用 `ElMessage.warning` 明确告知「已自动调整为该日期往前 366 天」——用户知道数据被改过口径，而不是以为系统算错。注意 `spanDays` 的计算是 `天数差 + 1`（含首尾两天），与后端同一口径，否则会差一天。
3. **为什么标题和空态文案都要跟着区间变**：两张图共用一个区间，但它们在视觉上分处左右两栏，很容易被理解为两张独立的图。把区间写进标题（`任务趋势（近一周）`）、写进饼图副标题（`近一周内全部评估结果按评判等级统计`），并在趋势图副标题里明写「与右侧等级分布同区间」，等于**在界面上把「这两张图是一组、同一口径」这件事讲清楚**；空态文案同理（`{{ rangeTitle }}内没有评估任务记录`）——否则用户把区间改成近一年后看到「近 7 天内没有评估任务记录」，会以为空态文案是错的。命中快捷区间显示名称、手动改过之后显示具体日期（`2026-09-01 ~ 2026-09-30`），用户据此知道当前到底在看哪一段。
4. **为什么 `:clearable="false"`**：日期选择器默认允许清空，清空后 `dateRange` 变成 `null`、`rangeTitle` 退化成「近期」，请求则变成「不传区间」由后端回落近 7 天——**界面显示与后端口径会悄悄错开**。禁掉清空后，「页面上始终有一个明确的区间」这条不变量成立，标题与请求永远一致；要回到近 7 天，选下拉里的「近一周」即可，语义也更清楚。
5. **为什么「近一年」要点开 `hideOverlap`**：快捷区间把点数从 7 个拉到 365 个，`xAxis.axisLabel` 若不抽稀，`MM-DD` 标签会重叠成一团黑。`hideOverlap: true` 交给 ECharts 自动隐藏重叠标签（第 432 行的注释就写在这里），7 个点的默认视图看不出差别，但近一年视图的可读性完全靠它。
6. **区间与项目筛选是正交的两个维度**：`projectId`、`from`、`to` 三者一起进同一个请求，切换任一个都只调一次 `load()`。**注意「最近评估任务」表不受区间影响**（它来自独立的 `taskApi.recent(8)`），所以把区间改成近一年后，该表里的任务可能落在区间之外——这不是缺陷，它本来就是「最近 8 条任务」而非「区间内任务」。

**与后端契约的对应**：`from`/`to` 为 `YYYY-MM-DD` 字符串（`LocalDate`，含首尾两天），只影响「任务趋势」与「评判等级分布」两张图；两者都不传时后端按近 7 天处理。接口层与前端封装的逐行说明分别见 07 分册 2.12 与 08 分册 2.14。

**易错点 / 注意**

1. 项目状态 tag 配色与 `ProjectList.vue` **不一致**：本页（`391`）是 `DRAFT→info、ARCHIVED→warning`，而 `ProjectList.vue:348-353` 是 `DRAFT→warning、ARCHIVED→info`。两处都是「同一状态、不同颜色」，验收走查界面时应确认以哪一套为准，建议后续统一收敛到 `utils/format.ts`。
2. 告警表既给「任务编号」加了 `<a href="#/tasks/{id}">`，又给整行绑了 `@row-click="openAlertTask"`（`82`、`85-89`）。点击编号时两个导航目标相同，`vue-router` 对重复导航不会产生副作用，但属于冗余；若要精简，应保留行点击、把 `<a>` 换成 `<span>` 加样式，或反之。
3. `taskApi.recent(8)` 与总览里的 `latestResults` 是**两个不同维度的数据**：前者是任务（含失败/运行中），后者是评估结果（按结果记录）。不要用其中一张表代替另一张来判断「系统是否在跑任务」。**补充（提交 `5f8ba79`）**：`recent(8)` 还**不受统计区间约束**，「最近评估任务」表与两张统计图的口径天生不同，走查时不要把它当成「区间内任务数」的对照。
4. `:current-row-key="projectId"` 只有在同时设置 `row-key="id"` 时才生效（`237`、`238`）——Element Plus 需要行键才能匹配当前行；若将来删掉 `row-key`，高亮会静默失效而不报错。
5. **`dateRange` 的格式必须始终是 `YYYY-MM-DD` 字符串**（提交 `5f8ba79`）：`el-date-picker` 靠 `value-format="YYYY-MM-DD"` 保证，`buildRange`/`fmtDate` 也手工拼同一格式，后端接收 `LocalDate`。**唯一容易破坏这条不变量的写法是把 `dateRange` 改成 `Date` 对象**（例如去掉 `value-format`）——那样 `api/index.ts` 的 `if (from)` 仍会通过，但请求会带上一串时间戳，后端绑定失败返回 1001，表现为「选完日期整页数据消失」。这也是 2.3.4 里「`overview` 失败 → 整页进空态」那条兜底在本次改动后最可能的真实触发场景。
6. **区间上限 366 天是前后端两处独立维护的同一个数字**（提交 `5f8ba79`）：前端在 `onRangePick` 里判断 `spanDays > 366`（`553`），后端在 `DashboardService.overview` 里也拒绝超过 366 天的区间。**改一处必须同时核对另一处**：只改后端会让用户先看到一个「整页清空」，只改前端则用户能通过手工构造请求绕过。这与本册反复出现的「同一数值两处维护」属同一类已知重复（另见 08 分册 2.17 关于 `--ees-sidebar-width` 的易错点）。

### 2.4 `frontend/src/views/project/ProjectList.vue`

**作用**：评估项目的维护入口。提供关键字/状态筛选与分页列表、按钮级权限控制、新建与编辑（含编码留空自动生成、负责人下拉与**默认预填当前登录用户**、起止日期校验）、项目成员配置（覆盖保存）、项目统计查看，以及归档/启用与删除（已产生评估结果的项目只能归档）；列表为空时还会**按数据范围解释原因**（见关键设计点 4）。

**被谁使用**：
- `router/index.ts:26-31` 注册为 `/projects`（`meta.menu = 'project'`），菜单级授权由守卫按 `meta.menu` 判定；
- 依赖 `projectApi`（list/statistics/create/update/archive/activate/remove/members/saveMembers）、`taskApi.list`、`userApi.options`；
- 权限码 `project:create` / `project:update` / `project:member` 来自后端角色权限（`backend/src/main/resources/db/data.sql:12` 中 EVALUATOR 角色即含这三个码；SYSTEM_ADMIN 为 `["*"]`），经 `stores/user.ts:30-36` 的 `has()` 判定。

**关键设计点**：
1. **按钮级权限**：三个 `computed`（`348-350`）把 `userStore.has('project:xxx')` 包成响应式布尔值，模板用 `v-if` 控制 新建/编辑/归档/成员配置/删除。`has()` 对超级管理员与通配符 `*` 直接放行，因此 admin 永远看得到全部按钮。
2. **删除 vs 归档**：删除是「已产生结果就拒绝」的硬约束（后端 `ProjectService.delete`：`results > 0` 时抛「该项目已产生 N 条评估结果，不允许删除，请改用归档」），前端在确认框文案里就预先告知，并在被拒时用弹窗把后端原文或兜底文案讲清楚。
3. **成员配置是覆盖保存**：后端 `ProjectService.saveMembers` 先 `deleteByProjectId` 再逐条插入，因此前端提交的必须是**完整成员列表**——弹窗里「移除」只是删本地行，只有点「保存成员」才会真正生效，这一点通过按钮文案与流程设计传达给用户。
4. **列表为空时按数据范围解释原因（`scopeRestricted`，第 352-360 行）**：非超管且 `dataScope !== 'ALL'` 的角色（如评估人员）只能看到"本人负责或参与"的项目，**新建完项目若负责人没落成自己人，列表就是空的**。因此主表格的空态改用 `#empty` 插槽（第 44-57 行）分支渲染：受限时展示「暂无可见项目」+ 具体原因（当前角色名、数据范围含义、找管理员加成员或自行新建，并说明创建者与负责人会自动成为成员），不受限时才退回「暂无项目数据」这一句。这让"空列表"从疑似故障变成可自解的操作指引。

#### 2.4.4 数据加载、失败处理、loading 与空值保护

- **进入时加载**：`onMounted`（`780-783`）依次 `loadUserOptions()`（`GET /api/users/options`）与 `load()`（`GET /api/projects`）。弹窗数据按需加载：编辑/新建不需要额外请求（负责人下拉已就绪）；`openMembers` 时请求 `GET /api/projects/{id}/members`；`openStatistics` 时请求 `GET /api/projects/{id}/statistics` 与 `GET /api/evaluation-tasks?projectId=&page=1&size=10`。切换筛选、翻页、增删改归档后都重新 `load()`。
- **加载失败如何处理**：
  - 列表失败（`403-405`）→ 清空 `rows` 与 `total`，页面进入空态，错误提示由拦截器给出；
  - 用户下拉失败（`501-503`）→ `userOptions = []`，负责人下拉变空但仍可提交（`ownerId` 为 `null`）；
  - 成员加载失败（`694-696`）→ `memberRows = []`，弹窗提示「暂无成员，请添加」；
  - 保存/归档/删除失败 → 全部交给拦截器（业务码弹 `message`、403 提示无权访问），**例外是删除**：`642-648` 会把「已产生评估结果」这一类拒绝单独识别，用弹窗展示后端原文或兜底文案，因为这类失败需要用户改变做法（改用归档），一句 toast 不足以说明。
- **loading 状态**：共 5 个——`loading`（主列表表格 + 刷新按钮）、`saving`（表单保存按钮）、`memberLoading`（成员表格）、`memberSaving`（保存成员按钮）、`statLoading` + `taskLoading`（统计弹窗的两块区域，二者独立）。分而治之的好处是任一区域在加载时，其它区域仍可读可操作。
- **空数据 / 空数组保护**：
  - 列表：`Array.isArray(res?.records) ? ... : []`（`401`）+ 主表格的 `#empty` 插槽（`44-57`）——不受限时显示「暂无项目数据」，**受限（`scopeRestricted`）时改为显示「暂无可见项目」+ 原因与操作指引**；`total` 经 `Number(res?.total ?? 0)` 兜底（`402`）；
  - 用户下拉：`Array.isArray(list) ? ... : []`（`500`）；
  - 成员列表：`Array.isArray(list) ? ... : []`（`683`）+ `userId` 三级取值 `m?.userId ?? m?.id ?? 0`（`685`）+ `memberRole` 默认 `VIEWER`（`691`）；
  - 统计任务：`Array.isArray(res?.records) ? res.records : []`（`772`）+ `empty-text="该项目暂无评估任务"`；
  - 统计卡：全部 `stat?.xxx ?? 0`，未加载完成或加载失败时显示 0（`250-254`）；
  - 单元格：统一 `row?.xxx || '-'`，`resultCount` 用 `?? 0` 保留 0 的语义（`280`）；
  - 可添加用户：`addableUsers` 过滤后可能为空（全部用户都已是成员），此时下拉无选项，`添加成员` 按钮因 `newMemberUserId === null` 保持禁用（`237`），不会产生无效操作。

**易错点 / 注意**

1. **状态 tag 配色与驾驶舱不一致**：本页 `statusTagType`（`372-377`）是 `DRAFT→warning、ARCHIVED→info`，而 `Dashboard.vue:391` 是 `DRAFT→info、ARCHIVED→warning`。同一状态在两页颜色相反，走查/答辩时容易被质疑，建议把映射收敛到 `utils/format.ts`（例如新增 `PROJECT_STATUS_TYPE`）后两处引用。
2. **成员加载失败后直接保存会清空成员**：后端 `saveMembers` 是覆盖式实现（先删后插）。若 `members()` 请求失败，`memberRows` 为空数组，此时点「保存成员」会提交空列表并把该项目成员全部删除。当前实现只依赖用户自行察觉「暂无成员，请添加」。若要加固，应在 `openMembers` 的 `catch` 中记录失败标记并禁用「保存成员」按钮。
3. **起止日期校验是单向的**：`endDate` 的 validator（`476-488`）只在结束日期自身变化时触发，`startDate` 没有对应规则。先填结束日期、后把开始日期改到更晚，不会立即报错（提交时因为 `endDate` 未再变化也不会重校验），存在提交出「结束早于开始」数据的可能。稳妥做法是给 `startDate` 也加一条同样的 validator，或在 `submitForm` 里做一次提交前交叉校验。
4. **统计弹窗两个请求串行**：`openStatistics`（`762-777`）两段 `try` 顺序执行，弹窗停留时间等于两者之和。若后端任一接口较慢，可改为 `Promise.all` 并各自 `catch`，但要注意保持两个 `loading` 的独立语义。
5. **按钮隐藏不等于接口不可访问**：`canCreate/canUpdate/canMember` 只控制按钮渲染，是体验层措施；真正的权限拦截在后端方法级校验与 `request.ts:95-98` 的 403 分支。不要因为前端看不到按钮就认为该接口安全。
6. **前端未做「编码唯一性」预校验**：编码重复依赖后端返回 `DATA_CONFLICT` 并由拦截器提示（`585-587`）。如果后续要在前端提前拦截，应新增 `projectApi` 侧的查询接口，而不是在本地列表里比对（列表只含当前页数据）。
7. **`scopeRestricted` 只是一段界面文案的判据，不是权限边界**：它读的是 `/api/auth/me` 返回的 `dataScope`，只决定空列表时显示哪段说明；真正的数据过滤在后端 `ProjectService`（按 `project_member` 与 `owner_id` 算可见项目 id 集合）。因此不要把「列表有数据」当成授权依据，反之亦然。
