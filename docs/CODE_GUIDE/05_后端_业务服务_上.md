## 2. 逐文件详解

### 2.1 `backend/src/main/java/com/ees/service/AuthService.java`

**作用**：系统的认证与用户维护入口——登录、登出、改密、用户新增/修改，以及首次启动时的默认账号初始化。
**被谁使用**：`AuthController`（`/api/auth/login`、`/logout`、`/change-password` 注入本服务）、
`UserController`（`/api/users` 新增/修改/重置密码均走 `saveUser`）、`DataInitializer`（启动时调用 `initDefaultUsers`）；
权限码经 `LoginUser` → `JwtService.generate`（写入 `perms`/`scope` 声明）下发，后续请求由 JWT 过滤器还原。
**关键设计点**：
1. 登录是**顺序判定链**：用户不存在 → 已停用 → 锁定中 → 密码不符 → 成功。前四个分支一律"先写审计、再抛异常"，
   对应方案 9.2「登录纳入审计」；成功分支记录最后登录时间与 IP，对应方案 9.2 可追溯要求。
2. 失败计数采用"累计到阈值即置 `LOCKED` 并写 `lockedUntil`"，阈值与锁定时长来自 `EesProperties.Security`
   （`max-login-fail=5`、`lock-minutes=15`），不在代码里写死。
3. 权限（按钮级）、数据范围、菜单（可见性）三件事分别由 `permissionsOf` / `dataScopeOf` / `menusOf` 提供，
   且只在登录响应中随用户信息一起下发。
4. **初始口令的输出按档位分级，这是合规要求而非可选项**：默认账号必须让使用者知道怎么登录，方案 9.1 又要求
   "日志不得打印密码和敏感配置"，两者只能在"档位"上折中——dev 档打印口令便于本地调试，非 dev 档只打印账号名
   （`initDefaultUsers()` 249-254 行）。档位判断统一收在 `isDevProfile()`（257-265 行）一处，读的是运行时真实的
   `Environment.getActiveProfiles()`，而不是散落各处去读 `spring.profiles.active` 属性（该属性在多文档 YAML、
   命令行覆盖、profile group 等场景下并不可靠，容易误判成"非 dev"或漏判）。

**为什么 `initDefaultUsers()` 要把日志内容按档位区分**：技术方案 9.1 明确要求「生产环境关闭调试接口和详细异常堆栈，**日志不得打印密码和敏感配置**」。整改前该方法在建号完成后**无条件**把当时全部（5 个）默认口令一次性打进日志，与本项目先前已修复的 Spring Security 明文密码问题属同一类缺陷：默认口令长期不变，而启动日志会被控制台、`logs/` 目录、运维采集与截图答辩等多种途径留存，等于把可用凭据随手散出去。整改后改为分档输出（249-254 行）：

| 档位 | 输出内容 | 取舍理由 |
|---|---|---|
| `dev`（本项目默认档） | `admin/admin123, evaluator/eval123`，并追加 `log.warn("以上为初始口令，首次登录后请立即修改。")` | **便利优先**：本地开发、联调、演示答辩时不必翻文档就能登录，且 WARN 明确提醒改密 |

**易错点/注意**：
1. 失败分支在 `throw new BizException(...)` 之前执行了 `setLoginFailCount(...)` 与 `userRepository.save(user)`，但 `login` 方法自身带 `@Transactional`、`BizException` 又是 `RuntimeException`（`BizException extends RuntimeException`），按 Spring 默认回滚规则，**这两个写入会随外层事务一起回滚**（审计日志因为 `recordSync` 使用 `REQUIRES_NEW` 才得以保留）。也就是说"连续失败 5 次锁定"（验收 1.1.5）是否真正落库需要实测确认；若确认未落库，修法是让失败计数的更新走一个 `REQUIRES_NEW` 的独立事务（或去掉 `login` 上的 `@Transactional`），而不是只调整审计。
2. 分支三只检查 `lockedUntil` 是否过期，**不检查状态是否为 `LOCKED`**；因此锁定期满后即使没人解锁也能登录成功，并在 116-118 行被复位为 `ENABLED`（这是设计意图：锁定是临时措施）；但 `DISABLED` 与之不同，必须由管理员在用户管理页改回。
3. **`menus` 必须由登录响应与 `GET /api/auth/me` 两处一起下发，且两处只能来自同一个 `menusOf()`**：`/me`（`AuthController` 56-70 行，其中第 67 行 `m.put("menus", authService.menusOf(u.getRoleCode()))`）与登录响应现在都会带上 `menus`。这是本项目修过的一个真实缺陷：早先 `/me` 只返回 `dataScope`/`permissions`、不含 `menus`，而前端刷新页面（F5）时不再调登录接口、走的是 `userStore.loadUser()` → `/me`，于是 `hasMenu()` 对**非超管**角色因 `menus` 为空而全部返回 false——`MainLayout.visibleMenus` 过滤掉所有侧栏项、路由守卫又把带 `meta.menu` 的路由（含驾驶舱自身）全部跳回 `/dashboard`，形成无限重定向、整页白屏；超管因 `isSuperAdmin` 短路不受影响。因此新增菜单只需要改 `menusOf()` 一处，两个调用点自动同步，**不要在 Controller 里另写一份菜单数组**。
4. **注入项已由 6 个变为 7 个，手工 `new` 会编译失败**：为拿到档位信息，`AuthService` 新增了 `Environment` 依赖（41-47 行字段、49-60 行构造器）。Spring 容器按类型自动注入，正常启动无需任何配置改动；但任何**手工 `new AuthService(...)`** 的地方（测试替身、旧示例代码、按旧签名写的反射/工厂）都会因为少传第 7 个参数而**编译失败或运行期抛错**，必须补齐 `Environment`（测试里可用 `MockEnvironment` / `new StandardEnvironment()`；由于它没有激活任何档位，`isDevProfile()` 会返回 `false`，即测试环境默认走"不打口令"的合规分支）。同理，若把该字段改成可空或手动置 null，`isDevProfile()` 第 259 行会在 `environment.getActiveProfiles()` 上抛 NPE。

### 2.2 `backend/src/main/java/com/ees/service/AuditService.java`

**作用**：审计日志的唯一写入口与查询/清理入口，落实方案 9.2「导出、发布、数据源测试、权限变更、算法参数变更全部纳入审计，日志不得由普通用户删除」。
**被谁使用**：`AuditFilter`（对 `POST/PUT/DELETE/PATCH` 自动登记，调用异步 `record` 并传入 `RequestInfo.of(request)`）、
`AuthService`（登录/登出/改密，调用同步 `recordSync`）、其他业务服务通过 `record` 追加关键动作、
`SystemController`（`/api/audit-logs` 查询、`/api/audit-logs/purge` 清理）。
**关键设计点**：
1. 两种写法对应两种场景：`record` 异步（`@Async("ioExecutor")`）用于量大、非关键的自动审计；`recordSync` 同步用于登录等关键安全事件。
2. 两者都用 `Propagation.REQUIRES_NEW`：日志必须独立于业务事务提交，业务回滚不能带走日志、日志写失败也不能带崩业务。
3. `record` 的签名传 `RequestInfo` **值对象**而非 `HttpServletRequest`——这是本项目修过的一个真实缺陷，详见下面对 42-46 行与 72-90 行的说明。

### 2.3 `backend/src/main/java/com/ees/service/CodeService.java`

**作用**：统一生成业务编号，格式 `PREFIX-yyyyMMdd-####`（如 `TASK-20260922-0001`、`SNAP-20260922-0003`、`BATCH-20260922-0007`）。
**被谁使用**：`ProjectService`（`PRJ` / `project` / `project_code`）、`DataSourceService`（`DS` / `data_source` / `source_code`）、
`DataBatchService`（`BATCH` / `data_batch` / `batch_code`）、`SnapshotService`（`SNAP` / `data_snapshot` / `snapshot_code`）、
`TaskService`（`TASK` / `evaluation_task` / `task_code`）、`ReportService`（`RPT` / `report_record` / `report_code`）。
**关键设计点**：
1. 流水号**由数据库当天已有编号的最大值推导**，而不是用进程内自增计数器——进程内计数器在服务重启后会从 0 开始，生成重复编号并撞唯一键，这是本项目修过的真实缺陷（类注释 20-21 行明确写了"服务重启后不会重复"）。
2. `REQUIRES_NEW` 让编号生成不依赖调用方事务：调用方（创建任务/导入批次）回滚时，编号事务已独立提交，编号只会"跳号"而不会"重用"。
3. 回绕（`MAX_SEQ` 到顶回到 1）后用 `exists` 逐个探测，配合 `queryMaxSeq` 的异常降级，保证即使库查询失败也不会生成重复编号。

**易错点/注意**：
1. `next` 的"读预占—自增—写预占"（47-54 行）不是原子操作，`ConcurrentHashMap` 只保证单个 `get`/`put` 线程安全。多线程并发首次调用同一 `key` 时（缓存未命中），两个线程可能从库里读到同一个基准值并各自 +1 → 得到同一编号。兜底手段是各业务表的编号列上建了唯一约束，冲突时会抛数据库异常；使用方（如 `TaskService`）也在事务中调用。若需要彻底消除该窗口，应改为 `reserved.merge(key, 1, Integer::sum)` / `compute` 原子更新，或对 `key` 加锁。
2. 降级种子 `秒*100+分` 可能超过 `MAX_SEQ`（例如 59×100+59=5959 尚可，但 秒=59、分=59 时为 5959，仍小于 9999；真正越界只可能出现在分钟>99，实际不会）。即便如此，`%04d` 对大于四位的数**不会截断**，会输出 5 位数字——编号仍唯一，但宽度与模板不一致；因此降级分支只应视为临时兜底，运维应关注其对应日志。
3. `table`/`column` 参与原生 SQL 字符串拼接，之所以没有注入风险，是因为它们**只由服务内部以字面量传入**（`"evaluation_task"`、`"task_code"` 等），不接受任何前端参数。若将来把 `next(prefix, table, column)` 暴露成外部可控参数（例如可配置前缀表），必须补一层白名单校验。

1. 缓存没有过期时间、也没有跨节点失效机制：`ConcurrentHashMap` 是进程内的，多实例部署时 A 节点改参数、B 节点仍读旧值直到重启。本项目为私有化单机部署（README 第一节），该取舍可以接受；若改为集群部署，需要引入共享缓存或消息通知。
2. `update` / `updateBatch` 都接收 `operator` 参数但**未使用**（没有写 `updated_by`）。若审计需要"谁改了什么"，目前只能依赖 `AuditFilter` 自动登记的 `PUT /api/configs` 记录，而不是参数行上的修改人。
3. `getInt`/`getDouble` 在参数值非法时静默回落默认值，且不会写入缓存（因为 `get` 返回的是 `def`，非 null 会被缓存——注意：`get` 会把默认值缓存起来，而 `getInt` 的解析失败发生在缓存之后的转换环节，因此不影响下次读取）。真正需要留意的是：**一旦某键首次以默认值被缓存，之后即使库中补上了该参数，也不会自动生效**，除非调用过 `update` 刷新缓存或重启服务。

### 2.5 `backend/src/main/java/com/ees/service/IndicatorService.java`

**作用**：指标体系接入（方案 4.3 / 2.2）——导入 Excel/CSV、逐行校验与告警、层级与循环引用检查、层级路径与叶子标记推导、版本化（`IND-yyyy-NNN`）、重新校验、发布/归档/删除、指标树组装。提交 `e295085` 起，版本列表、版本详情、指标清单、指标树、导入批次五类读接口与导入入口**全部按数据权限过滤**。
**被谁使用**：`IndicatorController`（`/api/indicator-versions` 全部接口，含 `/tree`、`/import`、`/revalidate`、`/publish`、`/archive`、`DELETE /{id}`、`/import-batches`）、

`SnapshotService`（`get` / `indicators` 校验版本可用性与指标清单）、`TaskService`（`get` / `indicators` 取版本与指标）、
`ExcelTemplateWriter`（引用 `TEMPLATE_COLUMNS` 生成导入模板）。
**它依赖谁**（提交 `e295085` 新增）：`ProjectService` —— 数据权限修复后本类反过来注入它，用 `visibleProjectIds()` 取可见项目集合做列表过滤，用 `checkVisible(projectId)` 做按 id 直读与导入目标项目的越权拦截。
**关键设计点**：
1. **只导入、不设计**：系统不负责重新设计指标体系，导入后的原始版本只读保存，校验结果单独存在 `validate_result` 里（类注释 38-39 行），这与 `revalidate` "只读不修改原始指标"的设计互为印证。
2. 校验分三层：**行级**（编码/名称/方向/权重/上下界/JSON）→ **表级**（层级存在性、循环引用、方向缺失统计、同层权重和）→ **短路**（全部失败不建版本）。
3. 版本化与可追溯：文件哈希、文件名、导入批次、校验结果全部落库，对应方案 5.4 可追溯要求与验收 1.3.9。
4. **数据权限（提交 `e295085`）**：`search` 把可见项目集合传进仓储；`get` 对公共版本放行、对其余版本校验项目可见性；新增私有守卫 `requireVersionVisible(versionId)` 覆盖 指标清单 / 指标树 / 导入批次；`publish` / `archive` / `revalidate` / `delete` **本就走 `get(versionId)`，因此自动被守卫**，不需要逐个补校验；`importFromFile` 额外校验目标项目可见（只能往自己可见的项目导入）。**一处必须记住的例外**：可见集合为**空**时 `search` 也**不返回空页**，因为公共版本（`projectId` 为空）对所有项目可见。

三条必须记住的策略（其余四个列表/详情同此口径）：

1. **列表查询用「取交集」**：传入不可见的 `projectId` 时返回**空列表**而不是报错。原因是历史遗留的项目上下文（前端 `localStorage['ees_project_id']` 里可能存着一个早已被移出成员的项目）会把页面打成错误页；取交集只会让用户看到"0 条"，界面仍然可用。本类的"交集"由仓储 `search` 的 `:ids` 条件完成（用户选的 `projectId` 与账号可见的 `ids` 同时生效）。
2. **按 id 直读直接 403**：那属于用户主动构造 id 的明确越权行为，因此 `get` / `requireVersionVisible` / `importFromFile` 一律抛 `FORBIDDEN(2003)`，不做"返回空对象"的软化处理。
3. **空集合例外只在本类**：任务 / 结果 / 批次 / 快照四个列表在可见集合为空时由各自 service 直接返回空页（`in ()` 不能进 SQL），本类的 `search` 不能这么做 —— 见关键设计点 4 与 03 分册分组说明（10）。

**易错点/注意**：
1. 区分 `success` 与 `versionId`：`success` 只在**零错误**时为 true；部分成功时 `success=false` 但已经建了 `DRAFT` 版本并落了指标与批次。任何调用方（前端、自动化脚本）都应以 `versionId != null` 作为"是否产生了版本"的依据。
2. 方向"缺省即正向"（542 行）意味着**漏填方向不会报错**：291-295 行的"方向缺失"表级告警在本方法的流程里几乎不可能触发，真正的方向问题只能靠 `revalidate`（对库中数据检查 `direction == null || isBlank`）发现。若业务要求"必须显式填写方向"，应把 `normalizeDirection` 的 null/空白分支改为返回 null。
3. `delete` 会**物理删除** `indicator` 明细行，而被删除版本的 `versionId` 可能已被历史 `evaluation_task`/`evaluation_result` 引用（任务侧保存的是 `indicatorVersionCode` 文本，明细则通过 `snapshot` 留存）。因此删除前应确认该版本尚无任务引用；当前实现只拦"已发布"，`ARCHIVED`/`DRAFT` 版本一旦被历史任务用过，删除后这些任务的指标明细将无法再按版本还原。
4. **可见项目集合为空时 `search` 的行为与其余四个列表不同，改动前务必先读这一条**：任务 / 结果 / 批次 / 快照的列表在可见集合为空时由各自 service 直接返回空页（因为 `in ()` 不能进 SQL）；`IndicatorService.search` **不能**这么做 —— 公共版本（`projectId` 为空）对所有项目可见，若在这里短路返回空页，系统级的公共版本就会从项目级用户的列表里凭空消失。因此本例把空的 `ids` 原样传进仓储，由 `:ids is null or v.projectId is null or v.projectId in :ids` 判定（空集合只命中"公共版本"这一支）。同理 `get` 与 `requireVersionVisible` 也是先判断 `projectId != null` 再校验，而不是直接 `checkVisible(null)`。

### 2.6 `backend/src/main/java/com/ees/service/ProjectService.java`

**作用**：项目管理（方案 4.2）——按数据范围过滤的项目查询、项目保存（编码唯一 + 负责人自动入成员）、归档/启用、逻辑删除（有结果时拒绝）、成员覆盖保存、项目统计聚合、下拉选项。

1. 数据范围用"**返回 null 表示不限制**"的约定表达，而不是返回全量 ID 列表：既避免了 `IN (...)` 的超长参数列表，也让仓储层可以直接表达 `(:ids is null or p.id in :ids)`。

3. 删除是"有约束的逻辑删除"：已产生评估结果的项目只能归档，保留项目操作记录与历史结果的可查询性（方案 4.2）。

- **日志里不许出现口令（方案 9.1）在本册的落点是 `AuthService.initDefaultUsers()`**：默认账号（只有 `admin` 与 `evaluator` 两个）的口令只在该 Bean 判定为 `dev` 档时打印，非 dev 档只打印账号名并指向交付文档；档位由 `Environment.getActiveProfiles()` 判定（`isDevProfile()`，257-265 行），`application.yml` 缺省 `dev` 使本地开发仍便利。整改后以 `prod` 档实测，启动日志中 2 个初始口令出现 0 次。这条约定的推广含义是：**任何新增的"输出初始凭据 / 敏感配置"的日志（含启动横幅、异常堆栈、配置回显）都必须先判档位**，不能依赖"生产环境应该没人看日志"的假设。
- **审计是旁路能力**：`AuditService` 两种写法（异步 `record` + 同步 `recordSync`）都用 `REQUIRES_NEW`，保证"业务回滚不带走日志、日志失败不阻断业务"。异步路径必须传 `RequestInfo` **值对象**（发起线程采集），因为 `@Async` 线程既没有 `SecurityContext`，也无法安全访问已回收的 `HttpServletRequest`——这是本项目修过的一个真实缺陷，后续任何新增异步审计都必须遵守同一约定。
- **编号必须是"数据库推导 + 进程内预占 + 冲突探测"三重保险**：`CodeService` 放弃进程内计数器（重启后会重复并撞唯一键，本项目修过的真实缺陷），改为以当天库中最大编号为基准；`IndicatorService.nextVersionCode()` 用 `synchronized` + 存在性检查实现同类语义。编号生成用 `REQUIRES_NEW` 独立事务，业务回滚只会跳号，不会重号。
- **配置与数据的边界很清楚**：`ConfigService` 管"少量、读多写极少、可页面维护"的策略参数（缺失值策略、CR 阈值、保留天数），并用 `editable=false` 保护 `system.offline`、`system.version` 这类部署基线；不可在页面上改的东西一律标 `editable=0`。缓存是进程内的、写后刷新、无过期，因此改参数后立即生效但**不支持多实例共享**。
- **指标体系导入是本册最重的逻辑**，其核心不是"读表格"而是"**分层校验 + 只读存档**"：15 条规则分文件级/行级/表级三层，错误剔除行、告警保留行，全部失败时短路不建版本；循环引用用 `visited` 上溯检测，层级路径用父链回填（带 `guard` 死循环保护），叶子标记靠"反向标记父节点"两遍扫描得到，同层权重和按 `parentKey` 归并告警。`revalidate` 只更新校验结果与状态、**绝不修改原始指标数据**，这是方案 4.3"导入后的原始版本只读"的直接落地。
- **数据权限在本册分两处落地**：① `ProjectService.visibleProjectIds()` / `checkVisible` 是唯一的数据范围判据（`null` = 不限制、集合 = 成员 ∪ 负责人、`checkVisible` 抛 `FORBIDDEN(2003)`）；② 各业务服务用它过滤列表与拦截按 id 直读。**列表用「取交集」返回空列表**，避免历史遗留的项目上下文（`localStorage['ees_project_id']`）把页面打成错误页；**按 id 直读直接 403**，因为那是明确的越权访问。提交 `e295085` 把这一口径补到了任务/结果/批次/快照/指标体系的列表与详情上（实测：可见项目为 0 的评估人员五个列表全部由 15/48/6/6/4 条变为 **0 条**，任务详情/结果详情/批次记录由 200 变为 **403**，管理员不受影响）；**指标体系是唯一例外** —— 公共版本（`projectId` 为空）对所有项目可见，因此 `IndicatorService.search` 在可见集合为空时不短路，而是把空集合交给 SQL 的 `v.projectId is null` 分支处理。
