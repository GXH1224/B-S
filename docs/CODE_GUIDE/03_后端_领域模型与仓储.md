## 2. 逐文件详解

#### 分组零 · 公共审计基类：`BaseEntity` 与"每张表的公共列"

这一组只有一个文件，但它决定了另外 24 个实体的写法，所以单独成组。

`db/schema.sql` 里共有 **24 张业务表**，加上 `BaseEntity` 这个 `@MappedSuperclass` 基类，`domain` 包正好 25 个文件。全部表共享三类公共列，本册后文一律不再重复：

| 公共列族 | 出现的表 | 语义 |
|---|---|---|
| `created_at` / `updated_at` | `sys_role`、`sys_user`、`sys_config`、`project`、`indicator_version`、`indicator`、`evaluation_task`、`evaluation_result`、`data_quality_rule`、`algorithm_baseline`、`data_source` | 审计时间。分成两种处理方式：**继承 `BaseEntity` 的实体**交给 Spring Data JPA 审计自动填充；**不继承的实体**（如 `data_batch`、`report_record`）在 service 里显式 `setCreatedAt(LocalDateTime.now())` |
| `created_by` / `updated_by` | `sys_user`、`project`、`indicator_version`、`evaluation_task`、`data_source` 等 | 记录**操作者登录名字符串**（不是用户 id）。存字符串是为了审计可读性与"用户被删后仍可追溯"，因此表里没有指向 `sys_user` 的外键 |
| `deleted`（`TINYINT(1)`，默认 0） | `sys_user`、`project`、`indicator_version`、`data_source`、`data_batch`、`evaluation_task` | 逻辑删除标记。所有对外查询都以 `AndDeletedFalse` 收尾，物理删除只出现在"任务重跑前清理派生数据"这类场景 |

两个必须知道的工程前提（它们解释了本册大量"为什么这样写"）：

1. `application.yml` 中 `spring.jpa.hibernate.ddl-auto: none`，建表完全由 `db/schema.sql` 负责（`spring.sql.init.mode: always`，幂等）。所以**实体注解是"跟着建表语句走"的**，本册每个实体的 `@Column` 都与 `schema.sql` 的列名、长度、`nullable`、精度一一对齐解释；一旦某列写错，Hibernate 不会帮忙改表，只会在运行时报 SQL 错误。
2. `spring.jpa.open-in-view: false`，session 在事务结束即关闭。这正是**实体之间一律不使用 JPA 关联注解**的根本原因（详见 2.1 与仓储层总述）。

### 2.1 `backend/src/main/java/com/ees/domain/BaseEntity.java`

**作用**：所有需要自动维护审计时间的实体的公共父类，只提供 `createdAt` / `updatedAt` 两个字段及其访问器。
**被谁使用**：`SysRole`、`SysUser`、`SysConfig`、`Project`、`IndicatorVersion`、`Indicator`、`DataSourceEntity`、`EvaluationTask`、`EvaluationResult`、`DataQualityRule`、`AlgorithmBaseline` 共 11 个实体 `extends BaseEntity`。
**关键设计点**：
1. `@MappedSuperclass` 表示"我不是一张表"，JPA 会把本类的字段**映射到每个具体子类的表里**，因此子类表各自拥有 `created_at` / `updated_at`，而不会多出一张 `base_entity` 表 —— 与 `schema.sql` 中"审计列分散在各表"的写法完全一致。
2. `@EntityListeners(AuditingEntityListener.class)` 注册 Spring Data 的审计监听器；它只在**启动类带有 `@EnableJpaAuditing` 时真正生效**（见下方与 2.1 的配合说明）。两者缺一不可：少了 `@EnableJpaAuditing`，监听器不会被装配，`@CreatedDate` / `@LastModifiedDate` 就永远是 `null`，写库时 `created_at` 为 NULL。
3. 字段是**手写 getter/setter 而不是 Lombok**：本类是抽象基类，手写可以避免 Lombok 在继承体系里生成的 `equals/hashCode` 干扰 JPA 的实体标识判断，也让"基类只有两个字段"这件事在 IDE 里一眼可见。

| 行号 | 代码 | 说明 |
|---|---|---|
| 1-11 | `package com.ees.domain;` / `import ...JsonFormat / Column / EntityListeners / MappedSuperclass / CreatedDate / LastModifiedDate / AuditingEntityListener / LocalDateTime` | 导入分成三组：Jackson 的 `@JsonFormat` 负责把时间序列化成前端要的字符串格式；`jakarta.persistence.*` 是 JPA 标准注解；`org.springframework.data.annotation.*` 与 `AuditingEntityListener` 是 Spring Data 审计注解，注意 `@CreatedDate` 来自 Spring Data 而不是 JPA |
| 13-15 | `/** 通用审计字段基类。 */` | 类职责声明，同时提示"只放审计字段"，业务字段一概不放 |
| 16 | `@MappedSuperclass` | 关键：不生成独立表，字段下沉到 11 个子类表中 |
| 17 | `@EntityListeners(AuditingEntityListener.class)` | 关键：注册审计监听器。它监听 `@PrePersist` / `@PreUpdate` 生命周期，在插入/更新前把当前时间写进被 `@CreatedDate` / `@LastModifiedDate` 标注的字段 |
| 18 | `public abstract class BaseEntity {` | 抽象类，禁止直接实例化（它没有对应的表，实例化没有意义） |
| 20-23 | `@CreatedDate` / `@Column(name = "created_at", updatable = false)` / `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")` / `private LocalDateTime createdAt;` | 三个注解各司其职：`@CreatedDate` 让监听器在**首次持久化时**填值；`updatable = false` 让 Hibernate 生成的 UPDATE 语句永远不带 `created_at`，从数据库层面保证"创建时间不可篡改"；`@JsonFormat` 让接口返回 `2026-09-22 10:30:00` 而不是 Jackson 默认的 ISO 数组/带 T 的格式，前端表格无需再格式化 |
| 25-28 | `@LastModifiedDate` / `@Column(name = "updated_at")` / `@JsonFormat(...)` / `private LocalDateTime updatedAt;` | 与上行对称：`@LastModifiedDate` 在**每次更新时**刷新；不加 `updatable = false`，因为它本来就要被改写 |
| 30-36 | `getCreatedAt()` / `setCreatedAt(...)` | 保留 setter，因为不继承 `BaseEntity` 的实体与 DTO 转换、反序列化场景仍可能手工赋值（例如导入历史数据） |
| 38-44 | `getUpdatedAt()` / `setUpdatedAt(...)` | 同上 |

**易错点/注意**：
- `@CreatedDate` 只在 `AuditingEntityListener` 生效时工作。启动类 `EesApplication` 第 15 行的 `@EnableJpaAuditing` 就是它的开关；如果把实体单独搬到一个不带该注解的测试上下文里，`createdAt` 会是 `null`，而 `SysAuditLog` 等**自己 `new LocalDateTime.now()` 的实体不受影响**——这解释了为什么两种写法在同一个项目里并存。
- `created_at` 在 `sys_audit_log`、`task_status_history` 两张表中是 `NOT NULL`，而这两张表对应的实体**没有**继承 `BaseEntity`，它们用字段默认值 `= LocalDateTime.now()` 保证非空（见 2.4、2.19）。

#### 分组一 · 账号权限：`sys_role` / `sys_user` / `sys_audit_log` / `sys_config`

**这组表解决什么问题**：这是整个系统的"平台层"，不参与任何评估计算，但决定了"谁能进系统、能看哪些项目、做了什么操作、系统运行参数是多少"。四张表的关系是**弱关联**：

- `sys_role` → `sys_user`：通过 `role_code` 字符串关联，而**不是** `role_id`。原因是角色是"配置型字典"（方案 4.1 的角色字典；系统现已精简为 `SYSTEM_ADMIN` 系统管理员与 `EVALUATOR` 评估人员**两类**，`DATA_ADMIN`/`REVIEWER`/`VIEWER` 已删除），用编码关联让 `sys_user` 表可读（`evaluator` 一眼可懂）、也让 JWT 里可以直接放编码，不必每次查角色表；`schema.sql` 只在 `sys_user.role_code` 上建了普通索引 `idx_user_role`，没有外键约束。
- `sys_user` ↔ `project_member`：多对多授权走中间表（见分组二）。
- `sys_audit_log`：只记 `user_id` + `username` 冗余，不建外键，避免用户删除后审计记录被连带影响。
- `sys_config`：与业务表完全解耦的键值对，供 `ConfigService` 运行期读取（如 `data.missing.policy`、`algorithm.allow.force`）。

四张表都**不参与评估结果的追溯链**，因此只有 `sys_user` 带 `deleted` 逻辑删除列；`sys_role` 靠 `built_in` 内置标志保护、`sys_audit_log` 靠保留天数清理、`sys_config` 靠 `editable` 标志限制修改。

### 2.2 `backend/src/main/java/com/ees/domain/SysRole.java`

**作用**：角色定义实体，保存权限编码集合、数据范围与排序，对应 `schema.sql` 第 15-28 行的 `sys_role`。
**被谁使用**：`AuthService`（登录时按 `role_code` 取权限与数据范围）、`UserController`（角色列表含用户数）、`DataInitializer`/`data.sql`（内置角色字典，现只有 `SYSTEM_ADMIN` 与 `EVALUATOR` 两条记录）。
**关键设计点**：
1. `permissions` 不做成 `sys_permission` 关联表，而是**一个 TEXT 列存 JSON 数组**：权限字典在代码里是固定的（见 `/api/permissions` 接口），角色数量只有个位数，拆表带来的连接与维护成本高于收益；`RoleContext` 解析一次即可缓存。

#### 分组二 · 项目：`project` / `project_member`

**这组表解决什么问题**：项目是**全部业务数据的归属与授权边界**。指标体系版本、数据批次、数据快照、评估任务、评估结果都带 `project_id` 或 `project_code`，`ProjectService.checkVisible(projectId)` 是所有写操作的入口校验。两张表分工如下：

- `project`：项目主数据（编码、名称、类型、负责人、起止日期、状态机 `DRAFT/ACTIVE/ARCHIVED`）。
- `project_member`：项目级授权明细，与 `sys_user` 组成多对多；`member_role` 比全局角色更细（`MANAGER` 可管成员）。唯一键 `uk_project_member(project_id, user_id)` 保证同一用户在同一项目只有一条成员记录。

#### 分组三 · 指标体系：`indicator_version` / `indicator` / `indicator_import_batch`

**这组表解决什么问题**：指标体系是评估的"标尺"。三个层次：

- `indicator_version`：**版本**。方案要求"原始版本只读、绑定版本号"，所以指标一旦发布就不再原地修改，新的调整产生新版本；`source_hash`（原始文件 SHA256）与 `import_batch_id` 让"这份指标从哪个文件、哪次导入来的"可追溯。
- `indicator`：**指标明细**，挂在版本下（`version_id`）。层级用 `parent_code` + `level` + `level_path` 表达，**用编码而不是 id 关联父子**，因为导入文件里天然只有编码（`parent_code` 列），用编码关联可以"先按文件建树、再落库"，不必维护 id 映射。
- `indicator_import_batch`：**导入批次**，记录文件名、大小、哈希、总行数/成功行数/错误行数与错误明细 JSON，是导入失败的排查入口。

三张表都**没有外键**：删除版本时由 `IndicatorService` 依次 `indicatorRepository.deleteByVersionId`（派生删除）清理明细，导入批次则保留作为历史留痕。`indicator` 上的三个复合索引 `idx_ind_code(version_id, indicator_code)`、`idx_ind_parent(version_id, parent_code)` 正好覆盖"按版本查编码""按版本查子节点"两个最常用查询。

### 2.9 `backend/src/main/java/com/ees/domain/Indicator.java`

**作用**：指标定义实体，对应 `indicator`；一个版本下的一个指标节点，含层级、方向、单位、本地权重与各类阈值。
**被谁使用**：`IndicatorService`（解析导入文件、建树、校验、发布）、`TaskService`（装配算法输入的指标元数据）、`SnapshotService`（`ScoringSupport.Range` 的极值来源）。
**关键设计点**：
1. `direction`（`POSITIVE` / `NEGATIVE` / `INTERVAL`）**直接改变标准化公式**，是最容易出错、也最需要讲清的字段。判据在 `MathSupport.normalize`（算法分册详解），三种取值的效果是：
   - `POSITIVE`（正向/效益型，越大越好）：`r = (value - min) / (max - min)`，值越大标准化结果越接近 1（如"命中率""效能值"）。
   - `NEGATIVE`（负向/成本型，越小越好）：`r = (max - value) / (max - min)`，值越小越接近 1（如"响应时间""故障率"）。
   - `INTERVAL`（区间型，落在区间内最好）：区间 `[intervalLower, intervalUpper]` 内 `r = 1`；低于下界按 `1 - (lower - value)/(lower - min)` 衰减到 0，高于上界按 `1 - (value - upper)/(max - upper)` 衰减到 0（如"最佳温度区间""最佳射程"）。
   因此 `minValue` / `maxValue` 对 `NEGATIVE` 与 `INTERVAL` 是**必填**（作为归一化分母），这也是导入校验会告警的项。
2. `leaf`（列名 `is_leaf`）决定该指标是否参与计算。**字段名故意叫 `leaf` 而不是 `isLeaf`**：JavaBean 命名下 `Boolean isLeaf` 的 getter 是 `isLeaf()`，Jackson 序列化会得到 `leaf`（Boolean 包装类型时 Lombok 生成 `getLeaf()`，可能产生 `isLeaf`/`leaf` 两种字段名，前端不好对）；直接用 `leaf` 字段名，`getLeaf()` 序列化结果稳定为 `leaf`。API.md 的指标树响应字段正是 `leaf`、`isLeaf` 的反例不会出现。
3. `weight` 是**本地权重**（当前节点在其兄弟中的权重），可为空：若指标体系未提供权重，则由 AHP 判断矩阵或加权平均法参数提供；两处都缺失时算法会按等权处理并给出告警。
4. `scoreRule` 存评分规则 JSON（分段函数等），`dataType` 预留 `NUMBER` 之外的类型（如 `TEXT`、`DATE`），当前导入以数值型为主。

#### 分组四 · 数据接入：`data_source` / `data_source_field` / `data_batch` / `raw_data_record` / `field_mapping`

**这组表解决什么问题**：把"甲方业务库/文件里的原始数据"变成"可供算法计算的规范化数值"，对应方案 5.1-5.5 的数据接入与质量要求。两条接入路径共用一套下游结构：

- **文件导入**：直接生成 `data_batch` + `raw_data_record`（`source_type = FILE`）。
- `field_mapping`：声明来源列与标准字段的对应关系及转换规则，属于映射能力的表结构支撑。

### 2.11 `backend/src/main/java/com/ees/domain/DataSourceEntity.java`

**作用**：外部数据源实体，对应 `data_source`；保存 JDBC 连接配置与只读限制参数。
**被谁使用**：`DataSourceService`（增删改查、连接测试、表清单、字段预览、SQL 抽取）、`DataBatchService`（抽取时读连接信息）。

1. **类名叫 `DataSourceEntity` 而不是 `DataSource`**：`javax.sql.DataSource` 是 JDBC 标准接口名，Spring 配置里也大量出现；加 `Entity` 后缀避免与标准接口重名导致的导入歧义 —— 这是"命名服从工程可读性"的例子。

### 2.13 `backend/src/main/java/com/ees/domain/DataBatch.java`

**作用**：数据批次实体，对应 `data_batch`；一次文件导入或一次数据库抽取 = 一个批次，批次是快照的输入。
**被谁使用**：`DataBatchService`（导入、校验、质量报告、删除、导出错误明细）、`SnapshotService`（按批次生成快照）、`DashboardService`（批次计数）、`ProjectService`（项目统计中的 `batchCount`）。
**关键设计点**：
1. 批次同时保存**来源描述**（`sourceType`、`sourceRef`、`dataSourceId`、`querySql`）与**文件描述**（`fileName`、`fileHash`、`storedPath`）：文件导入与数据库抽取共用一张表，靠 `sourceType` 区分。`querySql` 只在 `DATABASE` 来源时有值，这是"抽取过程可复现"的关键——保留 SQL 才能重新取一遍数据。

4. `objectCount` / `indicatorCount` 是**冗余的聚合结果**：分别等于该批次内 `distinct object_code` 与 `distinct indicator_code` 的数量，在导入结束时算好，列表页不必再扫明细表。

### 2.14 `backend/src/main/java/com/ees/domain/RawDataRecord.java`

**作用**：原始数据记录实体，对应 `raw_data_record`；窄表形态保存导入的原始数据，一行 = 一个"对象 + 指标 + 值"。
**被谁使用**：`DataBatchService`（写入、错误明细查询）、`SnapshotService`（读取并标准化生成 `SnapshotValue`）、`RawDataRecordRepository`（取对象/指标编码集合）。
**关键设计点**：
1. 类注释写明"**保存原始数据，标准化数据另存快照**"——这是方案 5.4"原始与标准化数据分别保存"在代码层的落点：本表的值**永不修改**（`indicator_value` 就是文件里的数），标准化结果写进 `snapshot_value.normalized_value`。这样"原始数据可复查、标准化过程可重算"。

#### 分组五 · 数据快照：`data_snapshot` / `snapshot_value`

**这组表解决什么问题**：快照是**评估的输入契约**，也是"评估结果可复现"的保证。方案 5.4 要求"原始数据与标准化数据分别保存"、方案要求"快照生成后不可变"，所以设计成两张表：

- `data_snapshot`：一次快照的**元数据**（编号、批次、指标体系版本、条数统计、校验值 `checksum`、质量报告、状态、存储路径）。
- `snapshot_value`：**展开后的矩阵**，一行 = "一个对象 × 一个指标"，同时保存 `raw_value` 与 `normalized_value`。

生命周期：`GENERATED`（已生成）→ `USED`（已被评估任务使用，由 `SnapshotService.markUsed` 置位并累加 `used_count`）；`INVALID` 表示内容已不可信。**被任务引用后不允许删除**（API.md §5.3 明确"删除（已被任务使用则拒绝）"），这是可追溯性的硬约束。

关键取舍：快照把结果**物化**下来，虽然占空间（`record_count` = 对象数 × 指标数，写入时按 1000 条分批），但换来两个好处——算法输入一次读表即可装配（`TaskService.buildRequest` 直接遍历 `findBySnapshotIdOrderByObjectCodeAscIndicatorCodeAsc`），以及"当时用的是哪份数据"永远可查。

### 2.17 `backend/src/main/java/com/ees/domain/SnapshotValue.java`

**作用**：快照指标值实体，对应 `snapshot_value`；一行 = 一个"对象 × 指标"，是算法直接输入的数据单元。
**被谁使用**：`SnapshotService`（写入）、`TaskService.buildRequest`（装配算法输入，取 `rawValue` 与 `missing` 标志）、`ResultService`（追溯面板展示原始/标准化值）。
**关键设计点**：
1. **为什么同时存 `rawValue` 和 `normalizedValue`**：这正是方案 5.4"原始数据与标准化数据分别保存"的落点，四个具体理由：
   - 追溯要求：结果分析页要能回答"这个 87.5 分是怎么来的"，必须给出原始值 → 标准化值 → 权重 → 贡献值的完整链路；只有标准化值就丢了原始口径。
   - 重算要求：算法版本升级或指标方向改判后需要重算，原始值在手才能重新标准化，否则必须先回头找批次甚至原始文件。
   - 审计要求：原始值是"事实"，标准化值是"处理结果"，两者混存会让人无法判断差异来自数据还是来自处理规则。
   - 粒度差异：`raw_value` 是 `DECIMAL(24,8)`（与 `indicator`/`raw_data_record` 一致，可容纳大数值），`normalized_value` 是 `DECIMAL(18,8)`（标准化到 [0,1] 区间，18 位足够）。
2. `normalized`（布尔）与 `normalizedValue`（数值）**不是重复**：当指标缺失时，`normalizedValue` 为 NULL 且 `normalized = false`（表示"未做标准化"）；当标准化结果本身就是 0 时，`normalizedValue = 0` 且 `normalized = true`。二者语义不同，缺了布尔位就无法区分"值是 0"和"没算"。
3. `missing` / `outlier` / `valid` 三个标志的分工：`missing` 表示该对象缺这个指标的数据（`SnapshotService` 会为每个"对象 × 指标"组合都生成一行，缺的那行标记 `missing = true` 并写 `remark = "该对象缺少此指标数据"`）；`outlier` 表示值超出指标体系上下界；`valid` 表示该值是否可用于计算。**用"补全占位行"而不是"少一行"**，使得快照矩阵始终是完整的笛卡尔积，算法端不必判断"哪一格不存在"，也便于热力图这类二维图直接铺格子。

#### 分组六 · 评估任务：`evaluation_task` / `task_status_history`

**这组表解决什么问题**：任务表是"算法执行"的载体，历史表是"状态变更"的流水，两者共同支撑方案 8.3 的任务状态机与"失败可查、可重试、可审计"的要求。

- `evaluation_task`：一次评估的**输入契约 + 执行状态**。输入部分由 `project_id` + `indicator_version_id` + `snapshot_id` 三元组锁定（缺一不可，且快照必须与版本绑定一致），算法部分由 `algorithm` + `parameters` + `combo_flow` 描述，执行部分由 `status` + `progress` + 时间列 + 错误列描述。
- `task_status_history`：**每一行是一次状态迁移**（`from_status` → `to_status`），含原因与操作者。`TaskService.transition` 在改状态的同时一定插一行历史，所以两者永远不会脱节。

任务状态机（对应方案 8.3）在 `evaluation_task.status` 注释与 API.md 中列全：

| 状态 | 含义 | 进入方式 |
|---|---|---|
| `DRAFT` | 草稿，尚未提交执行 | 实体默认值；`TaskService.create` 里先落库再改状态 |
| `VALIDATING` | 参数/数据前置校验中 | 提交后立即进入，校验失败转 `FAILED` |
| `QUEUED` | 已入队等待执行 | 校验通过后入队（`queuedAt` 记录时刻） |
| `RUNNING` | 算法执行中 | `startedAt` 记录开始时刻，`progress`/`currentStep` 持续更新 |
| `SUCCESS` | 执行成功 | `progress = 100`、`finishedAt`、`durationMs` 落定，随后 `markUsed(snapshotId)` |
| `FAILED` | 执行失败 | 写入 `errorCode`/`errorMsg`/`stackTrace`，可被"重试" |
| `CANCELED` | 用户取消 | 只允许从 `QUEUED`/`RUNNING`/`VALIDATING`/`DRAFT` 转入（`TaskService.cancel` 校验） |
| `TIMEOUT` | 超时终止 | 与 `FAILED` 一样可重试（`retry` 允许 `FAILED`/`CANCELED`/`TIMEOUT`） |
| `PENDING_REVIEW` | 结果待复核 | 结果提交复核后，任务层同步该状态 |
| `PUBLISHED` | 结果已发布 | 审核通过并发布 |
| `ARCHIVED` | 结果归档 | 归档只读 |

### 2.18 `backend/src/main/java/com/ees/domain/EvaluationTask.java`

**作用**：评估任务实体，对应 `evaluation_task`；承载算法选择、参数、状态机、进度与执行错误。
**被谁使用**：`TaskService`（创建、异步执行、状态迁移、取消、重试、查询）、`ResultService`/`ReportService`（按任务取结果与报告）、`DashboardService`（任务统计与告警）、`ProjectService`（项目统计中的 `taskCount`）。
**关键设计点**：
1. `algorithm` 取值 `AHP` / `FUZZY` / `WEIGHTED` / `COMBO`，配合 `algorithmVersion`（如 `java-weighted-1.0.0`）实现"算法可替换"：README 决策表写明切换 `ees.algorithm.engine=CPP_ENGINE` 走 C++ 服务时只需换配置。**版本必须随任务保存**，否则日后算法升级后无法解释历史结果。
2. `parameters`（算法参数 JSON）与 `comboFlow`（组合流程 JSON）分开存：`parameters` 是所有算法共用的参数字段（等级名/阈值/评分/算子/判断矩阵），`comboFlow` 只在 `COMBO` 算法时记录阶段顺序（如 `["AHP","WEIGHTED"]`）。分开存让"哪些是通用参数、哪些是流程编排"一目了然，重试时也更容易复用。
3. `inputSummary` 记录**输入摘要** JSON（对象数、指标数、快照编号、缺失值数等）：任务详情页与报告封面需要一段"这次评估用了什么"的快照说明，与其每次重算，不如提交时固化。它也是"结果可追溯"的证据链一环。
4. 时间列四件套 `queuedAt` / `startedAt` / `finishedAt` / `durationMs`：`durationMs` 是**冗余的计算结果**（`finishedAt - 开始时刻` 的毫秒差），存下来便于排序与统计，避免每次用 SQL 做时间差。
5. `retryOf` + `retryCount`：重试**不覆盖原任务**，而是新建一条任务并指向原任务 id（`TaskService.retry` 新建 `EvaluationTask`，`taskCode` 新生成、`retryOf = origin.getId()`、`retryCount = 原值 + 1`）。这样失败记录永久保留，符合审计要求；`retryCount` 用于防止无限重试。

#### 分组七 · 评估结果：`evaluation_result` / `result_detail` / `ahp_consistency`

**这组表解决什么问题**：把算法输出变成"可展示、可复核、可导出、可追溯"的结果数据。三张表的分工是**"宽表存整体 + 窄表存明细 + 专表存过程"**：

- `evaluation_result`：每个被评估对象一条，存综合结论（`total_score`、`level`、`vector`）+ 若干 JSON 大字段（权重、贡献、明细、告警、中间结果）+ 复核与发布状态。它是**结论表**。
- `result_detail`：行式明细，一个结果 × 一个指标一行。它是**明细表**，存在的理由是表格展示需要"按列排序 + 分页 + 关键字筛选 + 导出"，这些操作对 JSON 数组做不了（见 2.21）。
- `ahp_consistency`：AHP 一致性检验的过程留痕，一次任务可能有多个判断矩阵（多层 AHP 每个非叶子节点一个）。

为什么 `evaluation_result` 里已经有一个 `details` JSON，还要再建 `result_detail` 表？因为两者服务的目标不同：`details` JSON 是**算法输出原样留档**（保证"算法算出来的东西一字不改地留下来了"，导出与对比时可直接用），`result_detail` 是**为查询优化的投影**（可索引、可排序、可分页）。这是典型的"原始留档 + 检索副本"双写策略，代价是存储冗余，收益是查询能力与可追溯性兼得。

三张表都带 `task_id`，删除/重跑任务时按 `task_id` 清理（`TaskService` 在重跑前先 `detailRepository.deleteByTaskId` → `resultRepository.deleteAll(findByTaskIdOrderByTotalScoreDesc)` → `ahpRepository.deleteByTaskId`，顺序体现了"先明细后主表"）。

### 2.20 `backend/src/main/java/com/ees/domain/EvaluationResult.java`

**作用**：评估结果实体，对应 `evaluation_result`；一个被评估对象的综合结论、完整评判向量、复核与发布状态。
**被谁使用**：`TaskService.saveResults`（写入）、`ResultService`（结果列表/详情/文本/表格/图形/对比/复核/发布）、`ReportService`（导出）、`DashboardService`（等级分布、平均分、最新结果）。
**关键设计点**：
1. **`vector` 必须保存完整模糊评判向量，而不是只存等级**（对应方案 6.3）。原因有四条：
   - 模糊综合评判的结论是一个**隶属度分布**（如 `[0.12, 0.63, 0.20, 0.05]` 对应"优/良/中/差"），"良"只是取最大值后的**降维结论**；只存 `level = 良` 会把"良 0.63 还是良 0.99"这个关键信息丢掉，而这两者的管理含义完全不同。
   - 展示需要：结果分析页要用它画**等级分布饼图/柱状图**（`levelPie` 数据源就是向量各分量），也要在文本结论里写"以 63% 的隶属度属于良"。
   - 复核需要：审核人员可能不同意"按最大隶属度定级"，需要看到完整向量的第二、第三候选，才能判断"这次定级是否稳健"。
   - 追溯需要：算法参数或算子（`M_PLUS` / `M_MIN_MAX` 等）变化时，必须能对比"同一份数据在不同算子下的向量差异"，只存等级无法对比。
   同理 `weights`、`contributions`、`details` 也一并存 JSON：权重要支撑"权重饼图"和复核时的定权质疑；贡献值（`weight × normalized`）要支撑"哪些指标拉低了得分"的排序；`details` 要支撑导出与逐指标核对。
2. `reviewed`（`NONE`/`PENDING`/`APPROVED`/`REJECTED`）与 `publish_status`（`DRAFT`/`PUBLISHED`/`ARCHIVED`）是**两条独立的状态线**：复核是"内容对不对"，发布是"能不能对外"。审核通过但未发布，查看人员看不到；发布后归档则转为只读。API.md 的 `/review`、`/publish`、`/archive` 三个接口分别驱动它们。
3. `ranking` 在 `saveResults` 里按 `total_score` 降序计算，**得分相同则并列名次**（`Math.abs(prev - cur) > 1e-9` 才递增名次）：这是"排名条形图"与结果表格的排序依据。
4. 注意本类的 `reviewedAt` / `publishedAt` 用的是**全限定名 `java.time.LocalDateTime`**（第 91、98 行），且**没有 `@JsonFormat`**：与其他实体不同。读代码时不要以为字段"没写类型"；这也意味着这两个时间字段的 JSON 格式与 `created_at`（来自 `BaseEntity`，有 `@JsonFormat`）不一致，前端若要统一展示需自行格式化。

### 2.21 `backend/src/main/java/com/ees/domain/ResultDetail.java`

**作用**：结果指标明细实体，对应 `result_detail`；一个结果 × 一个指标一行，是"表格展示"与导出的数据源。
**被谁使用**：`TaskService.saveResults`（批量写入，`rankNo` 按写入顺序编号）、`ResultService`（`/details` 分页排序、图形模块的雷达图/热力图/箱线图取数）、`ReportService`（Excel/Word/PDF 明细表）。
**关键设计点**：
1. **为什么要把明细拆成行式表**（建表语句注释原文："行式存储，支撑表格分页/排序与导出"）：API.md 的 `/details` 接口支持 `sortBy ∈ indicatorCode/weight/score/contribution/normalizedValue/rawValue` 与 `order`、`keyword`、分页。若明细只存在 `evaluation_result.details` 这个 JSON 字符串里，排序和分页就必须"全量取出 → 内存排序 → 手动切片"，指标数一多就不可接受。行式表让这些都变成标准 SQL。
2. `weight` / `contribution` / `score` 三个数值列**语义要分清**：`score` 是该指标的**得分**（0-100 或按 `scoreScale`），`weight` 是该指标的**最终权重**（可能是指标体系给的、也可能是 AHP 算出来的），`contribution = weight × normalizedValue` 是它对总分的**贡献值**。`contribution` 之所以单独存而不是读取时相乘，是因为"算法实际用的贡献值"可能与"权重 × 标准化值"存在舍入差异，留档才能对账。

5. `indicator_level` / `parent_code` / `direction` 冗余自指标定义：表格要按层级缩进展示、要显示"正向/负向"，冗余后无需回查 `indicator`（而且历史结果展示的是**当时**的层级与方向）。

### 2.22 `backend/src/main/java/com/ees/domain/AhpConsistency.java`

**作用**：AHP 一致性检验记录实体，对应 `ahp_consistency`；保存每个判断矩阵及其 λmax、CI、RI、CR 与是否通过。
**被谁使用**：`TaskService.saveConsistency`（从算法输出的 `extra.consistency` 提取后落库）、`TaskService.detail`（任务详情页"一致性检验"区块）、`ResultService`（追溯信息中的一致性证据）。
**关键设计点：四个数学量的含义**（这是本册最需要讲清的部分，直接对应方案 6.2 的一致性检验要求）：

| 字段 | 数学含义 | 计算方式与用途 |
|---|---|---|
| `lambdaMax`（λmax） | 判断矩阵的**最大特征值** | `MathSupport.lambdaMax` 用 `λmax = mean((Aw)_i / w_i)` 计算（`w` 是幂法求出的主特征向量）。理想一致矩阵有 `λmax = n`（矩阵阶数）；`λmax` 越大于 `n`，说明专家打分前后矛盾越多 |
| `ci`（CI） | **一致性指标** | `CI = (λmax - n) / (n - 1)`，其中 `n = matrixSize`。CI 是"偏离一致性"的绝对量：完全一致时为 0。`n ≤ 2` 时 CI 无意义（一阶、二阶矩阵必然一致） |
| `ri`（RI） | **随机一致性指标** | 由 Saaty 随机指标表按阶数取常数（`MathSupport.RI_TABLE`：n=3 → 0.58，n=4 → 0.90，n=5 → 1.12 …，n=15 → 1.59，n>15 按 `1.59 + (n-15) × 0.01` 外推）。它的作用是**把 CI 按阶数标准化**——阶数越大，随机打分就越容易不一致，必须除以对应的基准 |
| `cr`（CR） | **一致性比率** | `CR = CI / RI`。判据是 `CR < 0.1`（阈值来自 `ees.algorithm.ahp-cr-threshold`，默认 `0.1`；`AlgorithmRequest.crThreshold` 与 `BaselineService` 均取 0.1）。`CR < 0.1` 时认为判断矩阵的一致性可以接受 |
| `passed` | 检验结论 | `CR < crThreshold` 为 `true`；`false` 时 `TaskService` 写入 `warning = "CR=%.4f 未通过一致性检验"`。方案 6.2 要求"一致性不通过时阻止正式评估"，因此算法层在 `passed = false` 且未开启 `allowForceOnCrFail` 时会返回失败（错误码 4003），任务随之进入 `FAILED` 并把原因写进状态历史 |

其余设计要点：
1. **一次任务可能有多行**：多层 AHP 的每个非叶子节点都有一个判断矩阵，因此用 `node_code`/`node_name` 标明"这个矩阵是谁的判断矩阵"（如 `ROOT`、`A1`），`matrix_size` 记录阶数。单层 AHP 只有一行。
2. `matrixData`（判断矩阵 JSON）与 `eigenVector`（权重向量 JSON）都要存：只存 CR 等于"只存结论不存过程"，审核人员无法复算；存了矩阵，任何人在任何时间都能重新算一遍验证。
3. `resultId` 与 `objectCode` 可空：AHP 的权重通常由指标体系决定，**与具体被评估对象无关**，因此一致性检验记录往往只在任务级（`resultId = NULL`）；只有"逐对象判断矩阵"的用法才填这两个字段。这是本表允许它们为空的原因。

### 2.25 `backend/src/main/java/com/ees/domain/AlgorithmBaseline.java`

**作用**：算法基准样例实体，对应 `algorithm_baseline`；保存"输入 JSON + 期望输出 JSON + 容差"，用于算法回归验证。

#### 仓储层分组说明：24 个 `*Repository` 的公共约定

后面 24 个小节都是"接口 + 方法签名"，如果逐个复述方法名会变成流水账。这一节先把**机制**讲清，后面每个小节只讲"这个仓储特有的取舍"。

**（1）这一层是什么**：24 个接口全部只有一句 `extends JpaRepository<实体, Long>`，**没有任何实现类**。Spring Data JPA 在启动时扫描 `com.ees.repository` 包，为每个接口生成基于 JDK 动态代理的实现：把方法名解析成 JPQL、把 `Pageable` 拼成 `limit/offset`、把 `@Query` 里的脚本交给 Hibernate 编译。所以"改一个方法名就能改 SQL"是这一层最大的特征，也是最大的坑（拼错属性名会在**启动时**直接抛 `PropertyReferenceException`）。

**（2）为什么所有实体都用 `Long` 主键 id、且属性路径永远只有一级**：因为实体之间**没有使用任何 JPA 关联注解**（全 25 个实体中没有一个 `@ManyToOne`/`@OneToMany`/`@JoinColumn`）。带来四个直接好处：

- **不会懒加载**：`spring.jpa.open-in-view: false` 时 session 在事务结束即关闭，若存在懒加载关联，Controller 层序列化时就会抛 `LazyInitializationException`。用 id 关联后，查询只返回本表字段，一步到位。
- **不会循环序列化**：`Project ↔ ProjectMember`、`EvaluationTask ↔ EvaluationResult` 这类双向关系若用对象引用，Jackson 序列化时会无限递归（需靠 `@JsonIgnore`/`@JsonManagedReference` 打补丁）；用 id 关联则天然无此问题。
- **分页与排序可控**：`Page<Project> search(...)` 生成的是单表 `select ... from project where ... limit ?, ?`，没有 `join` 造成的行数膨胀与 `distinct` 陷阱。
- **便于审计与追溯**：审计表、状态历史表都要在**实体被删除后**依然可读，用 id + 名称/编码冗余（`username`、`project_name`、`task_code`）比外键更能保住历史。

代价也很明确，交接时必须知道：**"跨表取名字"要靠 service 层显式再查一次**（例如任务列表要显示负责人姓名，就冗余 `owner_name`；结果表要显示项目名，就冗余 `project_name`）。本项目选择"在写入时冗余关键名称"来规避这个问题，所以你会看到大量 `*_code` / `*_name` 成对出现的列。

**（3）派生查询（Derived Query）命名规则**：Spring Data 按"前缀 + 属性表达式 + 排序/限制"三段解析。本册用到的片段如下：

| 方法名片段 | Spring Data 解析结果 |
|---|---|
| `findBy` | 生成 `select` 查询，返回 `List` / `Optional` / 实体 |
| `findByUsername` | `where username = ?1`。**属性名必须是实体字段名**，不是列名 —— 所以是 `findByVersionId`（字段 `versionId`）而不是 `findByVersion_Id`；`findByVersionIdAndLeafTrue` 里的 `Leaf` 对应字段 `leaf`，落到数据库列是 `is_leaf`（见 2.9） |
| `AndDeletedFalse` | `and deleted = false`，逻辑删除过滤。本项目把它作为一切对外查询的收尾，例如 `findByUsernameAndDeletedFalse` |
| `findTop20By…` / `findFirstBy…` | 加 `limit 20` / `limit 1`。`findTop20ByDeletedFalseOrderByIdDesc()` = "未删除的最近 20 条任务（按 id 倒序）"，`findFirstByTaskIdOrderByTotalScoreDesc()` = "某任务的最高分结果" |
| `OrderBy…Asc` / `…Desc` | `order by` 子句，可串联多个键，如 `findByDataSourceIdOrderByTableNameAscOrdinalPositionAsc`（先表名、再列序号） |
| `existsBy…` | 生成 `select count(*) > 0`，返回 `boolean`，用于"编码/用户名是否已被占用"的轻量校验（比查实体再判空省一次对象构造） |
| `countBy…` | 生成 `select count(...)`，返回 `long`，用于驾驶舱统计（`countByStatusAndDeletedFalse`、`countByAlgorithmAndDeletedFalse`…） |
| `deleteBy…` | 见下文第（6）点：**派生删除是"先查后删"**，不是一条 `DELETE` 语句 |
| `IsNull` | `is null`，如 `findByProjectIdIsNullOrProjectIdOrderByIdAsc` = "全局规则或本项目规则"（见 2.48） |
| `In` | `in (...)`，如 `findByStatusIn(List<String>)` |
| `True` / `False` | 布尔字段简写，如 `findByEnabledTrueOrderByIdAsc`、`findByMissingTrue`（对应字段 `missing`） |

**（4）`@Query` 中的"可选条件"写法 `(:param is null or …)`**：这是本项目所有列表筛选的统一写法，例如

```
select u from SysUser u where u.deleted = false
  and (:keyword is null or u.username like %:keyword% or u.realName like %:keyword% or u.orgName like %:keyword%)
  and (:roleCode is null or u.roleCode = :roleCode)
```

它的作用是**用一条 JPQL 覆盖所有筛选组合**（关键字 / 角色 / 状态任意子集），不需要写 2³ = 8 个方法、也不需要 Criteria API 拼条件。机制是：当参数为 `null` 时，`(:param is null or ...)` 的第一个分支为真，整段条件被短路成 `true`，等价于"这个条件不存在"。

**（5）为什么参数为 `null` 时要显式 `blankToNull`**：Web 表单"清空搜索框"后提交的是**空串**（`?keyword=`）而不是"不传这个参数"，于是 controller 拿到的 `keyword = ""`。空串在 SQL 里与 `null` 完全不是一回事：

- 对**等值条件**（`:roleCode is null or u.roleCode = :roleCode`），空串变成 `u.roleCode = ''`，**一行都匹配不到** —— 用户清空筛选后看到"0 条记录"，会以为数据丢了，这是最典型的线上 Bug。
- 对 **LIKE 条件**，空串变成 `like '%%'`，退化成"匹配所有非 NULL 值"，语义上碰巧对，但一旦某个条件改为等值就会立刻出错。

因此 8 个 service 各自持有一个私有静态方法 `blankToNull(String)`（`(s == null || s.isBlank()) ? null : s.trim()`），在**调用仓储之前**统一做归一化：`null` 保持 `null`、空串与纯空格变 `null`、正常值顺手 `trim()`（避免用户从 Excel 粘贴的编码带首尾空格导致精确匹配失败）。`TaskService.search`、`ResultService.search`、`AuditService.search` 等处都能看到这一行。

**（6）`@Modifying` 的删除方法为什么必须配 `@Transactional`**：删除分两种写法，本册都有：

- **派生删除**（`deleteByBatchId` 之外的 `deleteByProjectId`、`deleteByVersionId`、`deleteByTaskId`、`deleteByResultId`、`deleteByDataSourceId`…）：Spring Data 生成的实现是**先 `select` 出实体、再逐个 `delete`**，会触发实体生命周期回调，语义安全但在大数据量下会逐条跑 SQL。
- **`@Modifying` + `@Query` 的批量删除**（只在两处使用：`RawDataRecordRepository.deleteByBatchId` 与 `SnapshotValueRepository.deleteBySnapshotId`）：`@Modifying` 告诉 Spring Data"这不是 SELECT"，改用 `Query.executeUpdate()` 执行，从而生成**一条 `delete from 表 where 条件`**。这两处正是数据量最大的两张表（原始记录、快照值），逐条删除不可接受。

`@Modifying` 本身**不开启事务**：`JpaRepository` 只给内置 CRUD 方法加了默认事务，自定义的 `@Modifying @Query` 方法必须有外部事务，否则 Hibernate 会抛 `TransactionRequiredException: Executing an update/delete query`。本项目的做法是**在调用方 service 方法上声明 `@Transactional`**，例如 `DataBatchService` 重新校验批次（`revalidate`，第 525 行起，内部第 547 行）与删除批次（`delete`，第 565 行起，内部第 568 行）里调用 `rawRepository.deleteByBatchId(batchId)`、`SnapshotService` 删除快照（`delete`，第 330 行起，内部第 336 行）里调用 `valueRepository.deleteBySnapshotId(id)`、`TaskService` 重跑任务（第 291 行的 `@Transactional(propagation = REQUIRES_NEW)`）里调用三个清理方法、`AuditService.purge`（第 136 行）里调用 `deleteByCreatedAtBefore`。**这些调用一旦脱离事务（例如被一个没有 `@Transactional` 的新 service 复用）就会报错**，是二次开发最容易踩的坑。

**（8）`EvaluationResultRepository` 为什么同时有两条"按项目取结果"的方法**：

- `findByProjectIdOrderByIdAsc(projectId)` —— **升序**，服务于**趋势折线图**（`ResultService.lineChart`，第 305 行）。折线图要按时间从早到晚排列，`id` 是自增主键、天然单调递增，等价于时间序；升序取出后还在内存里按 `createdAt` 二次排序（`Comparator.nullsLast`），确保并列时顺序稳定。
- `findTop10ByProjectIdOrderByIdDesc(projectId)` —— **倒序 + 限 10 条**，服务于**最新结果列表**（`DashboardService` 第 186-213 行的 `latestResults` 取数：管理员走全表 `findAll`，受限范围走第 195 行的 `findTop10ByProjectIdInOrderByIdDesc(ids)`）与**横向对比**（`ResultService.compare` 第 671 行：未指定 `taskId` 时取该项目最近 10 条结果对比）。

两者不可互换：趋势图如果只用最近 10 条，就看不出完整走势；最新列表如果用全量升序，就必须把整个项目的历史结果全部查出来再在内存里取尾部 —— 既慢又浪费。这正是"同表不同访问路径各建一个方法"的典型理由。

**（9）数据权限过滤：为什么每个"统计查询"都要有一个 `…In`（按可见项目集合）的版本**

驾驶舱页面写着「项目、任务、快照与结果均按数据权限过滤」，但 `ProjectService.visibleProjectIds()` 给出的可见范围是**一个项目 id 集合（可能为空）**，而 `count()`、`countByStatusAndDeletedFalse(...)`、`countGroupByAlgorithm()`、`avgScoreAll()` 这类方法**只认全库口径**：它们既不接收范围参数，也无法表达"只统计其中某几个项目"。

因此提交 `747fec4` 在 6 个仓储里各补了一组 `…In` / `…ProjectIdIn` 查询，作为驾驶舱的**受限口径**（管理员保持全量口径，两套并存）：

| 仓储 | 新增的受限口径方法 | 服务驾驶舱的哪个字段 |
|---|---|---|
| `ProjectRepository` | `countByStatusAndDeletedFalseAndIdIn(status, ids)` | `activeProjectCount` / `archivedProjectCount` |
| `EvaluationTaskRepository` | `countByProjectIdInAndDeletedFalse` / `…AndStatus…` / `…AndCreatedAtAfter…` / `findTop20ByProjectIdInAndDeletedFalseOrderByIdDesc` / `findForTrend(ids, from, to)` | `taskTotal` / 各状态任务数 / `taskToday` / `alerts` / **`taskTrend`**（`5f8ba79` 起趋势改由 `findForTrend` 按区间直查，不再复用「最近 20 条」） |
| `DataBatchRepository` | `countByProjectIdInAndDeletedFalse(ids)` | `batchCount` |
| `DataSnapshotRepository` | `countByProjectIdIn(ids)` | `snapshotCount` |
| `EvaluationResultRepository` | `countByProjectIdIn` / `countByProjectIdInAndPublishStatus` / `avgScoreByProjects` / `countGroupByLevelInRange` / `countGroupByAlgorithmIn` / `findTop10ByProjectIdInOrderByIdDesc` | `resultCount` / `publishedResultCount` / `avgScore` / `levelDistribution` / `algorithmUsage` / `latestResults`（其中 `levelDistribution` 用的 `countGroupByLevelInRange` **同时**带时间区间，两个范围共用同一条查询） |
| `IndicatorVersionRepository` | `countVisibleByStatus(status, projectIds)` / `countByProjectIdIsNullAndStatusAndDeletedFalse(status)` | `indicatorVersionCount` |

三条必须记住的约定：

1. **管理员不走这些方法**：`visibleProjectIds()` 对超级管理员（`SYSTEM_ADMIN`）/ `dataScope = ALL` 返回 `null`（表示"不限制"），`DashboardService` 此时继续调用原有的全量方法（`count()`、`countGroupByAlgorithm()`…）。项目级用户（`EVALUATOR` 评估人员 / 「项目成员」角色）拿到的是可见项目集合，才走 `…In` 版本。所以 `…In` 版本是**补充**而不是替换 —— 这也是"为什么要新增方法，而不是给老方法加一个可空参数"的答案：老方法的名字与语义（全库）已经被多处调用（项目统计、列表接口），加可空参数会让"传 null 到底是全库还是空集合"变成新的歧义源。
2. **空集合不允许传进 `In` 查询**：`in ()` 在部分数据库上是语法错误（其余库上恒假），因此调用方在可见集合为空时必须**短路返回 0 / 空数组、根本不发查询**。`DashboardService.overview()` 用 `none` 分支统一负责这件事（见 06 分册 2.7.2）。提交 `e295085` 之后这条约束同样适用于**列表查询**：可见集合会被传进 5 个 `search`（见（10）），其中任务/结果/批次/快照四个列表由各自 service 在可见集合为空时直接返回空页。
3. **`In` 后缀同时用于派生方法与 `@Query` 方法**：能派生的（`countByProjectIdIn…`）用方法名派生；需要 `group by` / `avg()` / 时间区间的（`avgScoreByProjects`、`countGroupByLevelInRange`、`countGroupByAlgorithmIn`、`countVisibleByStatus`、`findForTrend`）必须写 `@Query` + `@Param`，并在方法名或注释上明确它与全量版本的配对关系（`countGroupByAlgorithm` ↔ `countGroupByAlgorithmIn`、`countByPublishStatus` ↔ `countByProjectIdInAndPublishStatus`、`findTop20ByDeletedFalseOrderByIdDesc` ↔ `findTop20ByProjectIdInAndDeletedFalseOrderByIdDesc`；`avgScoreAll` 的配对见下一条）。**注意 `countGroupByLevelInRange` 没有"全量孪生兄弟"**：它把可见集合与时间区间两个维度合并在一条查询里，而它取代的 `countGroupByLevel` / `countGroupByLevelIn` 已被删除（见 2.44 关键设计点 8）。

还有两处**不是简单对称**的地方，交接时必须知道：

- `avgScoreByProjects(ids)` 没有同名的"全量孪生兄弟"，它对的全量版本是已有的 `avgScoreAll()`（`select avg(r.totalScore) from EvaluationResult r`，无 `where`）。命名不一致是因为 `avgScoreAll` 是上一轮修复（提交 `c05676e`）先落地的，本次沿用旧名以免影响已同步的 06 分册。
- `IndicatorVersionRepository` 多一条特例：指标体系版本允许 `project_id` 为空表示**公共版本**，它对所有项目可见。因此可见集合为空时不能直接返回 0，而要退化成"只数公共版本"（`countByProjectIdIsNullAndStatusAndDeletedFalse`）；`@Query` 版本的可见性条件也必须写成 `(v.projectId is null or v.projectId in :projectIds)` —— 与同仓储 `search` 里承载可见集合的那个条件完全同口径（提交 `e295085` 后它排在 `keyword`/`status`/`projectId` 之后，是 `search` 的第四个条件），否则公共版本会在受限视图里凭空消失。

2.26 之后的每个仓储小节都会重复一遍"这个仓储加了哪些 `In` 方法、对应哪个统计字段"，阅读时以小节为准。

**（10）列表分页与"按 id 直读"的数据权限（提交 `e295085`）**

第（9）点讲的是**驾驶舱统计**的受限口径；同一条修复线的续篇（提交 `e295085`）把同一套判据补到了**列表分页**上 —— 修复前 5 个列表接口对项目级用户完全不设防：实测一个可见项目为 0 的评估人员账号能看到 15 个任务、48 条结果、6 个批次、6 个快照、4 个指标版本，而且知道 id 就能直读别人的详情（任务详情 / 结果详情 / 批次记录均返回 200）。

做法与 `ProjectRepository.search`（2.30）完全一致：在**已经存在的** `search` 查询里加一个可见集合条件，参数语义沿用 `(:ids is null or … in :ids)` —— **`null` = 不限制（管理员 / `dataScope = ALL`）**，非 null 集合 = 只取集合内的项目：

| 仓储 | 新增条件所在行 | 条件原文 |
|---|---|---|
| `EvaluationTaskRepository` | 61（方法签名第 69 行加 `@Param("ids") Collection<Long> ids`） | `and (:ids is null or t.projectId in :ids)` |
| `EvaluationResultRepository` | 37（签名第 45 行） | `and (:ids is null or r.projectId in :ids)` |
| `DataBatchRepository` | 25（签名第 31 行） | `and (:ids is null or b.projectId in :ids)` |
| `DataSnapshotRepository` | 27（签名第 32 行） | `and (:ids is null or s.projectId in :ids)` |
| `IndicatorVersionRepository` | 29（签名第 34 行） | `and (:ids is null or v.projectId is null or v.projectId in :ids)`（**多一个"公共版本"分支**） |

**为什么加在 `search` 里，而不是另立一个方法**：这个条件与原有的 `projectId` 条件不是一回事 —— `projectId` 是用户在页面上**主动选的**项目，`ids` 是**服务端按当前账号算出的可见范围**，两者必须同时生效（取交集）。把它作为 `search` 的一个可选参数，可以让"筛选项"与"数据权限"共用同一条 SQL，不必把 6 条件 / 7 条件的 `@Query` 再复制一份（这也正是（9）里"为什么不给全量方法加可空参数"的同一个理由，只不过 `search` 本来就是带全部可选条件的唯一入口）。

四条必须记住的约定：

1. **列表查询取交集，返回空列表而不是报错**：用户在页面上选了一个自己看不见的项目（典型来源是历史遗留的项目上下文，例如前端 `localStorage['ees_project_id']` 里存着早已被移出成员的项目）时，结果只是"0 条"，页面不会变成错误页。
2. **按 id 直读直接 403**：`/api/evaluation-tasks/{id}`、`/api/evaluation-results/{id}`、`/api/data-batches/{id}` 这类接口由 service 调 `ProjectService.checkVisible(该条数据所属项目)`，越权即抛 `FORBIDDEN(2003)`「无权访问该项目」（实测由 200 变为 403 —— 任务详情 / 结果详情 / 批次记录）。理由是那是用户主动构造 id 的明确越权行为，不能软化处理。
3. **空集合不能进 `in ()`**：可见项目为 0 时，任务 / 结果 / 批次 / 快照四个 `search` 的调用方（`TaskService` / `ResultService` / `DataBatchService` / `SnapshotService`，见 06 分册）直接返回空页、根本不发 SQL；**`IndicatorVersionRepository.search` 是唯一的例外** —— 公共版本（`projectId` 为空）对所有项目可见，因此空的 `ids` 也要照常传进去，由 `v.projectId is null` 这一支命中（见 2.32 关键设计点 4 与 05 分册 2.5）。
4. **`null` 与空集合的差别就是越权的差别**：`ids = null` 走"不限制"，`ids = []` 走"一个都不可见"；`ProjectService.visibleProjectIds()` 只对超级管理员 / `ALL` 范围返回 `null`（见 2.30 的易错点）。

## 3. 本册小结

- 本册共覆盖 **49 个文件、2595 行代码**：`domain` 包 25 个文件 1833 行（24 张业务表 + 1 个 `@MappedSuperclass` 基类；其中 `SysRole.java` 因类注释由 3 行扩为 7 行、说明两类角色，由 107 行增至 111 行），`repository` 包 24 个文件 **762 行**（较上一版 662 行 +82：提交 `747fec4` 为「驾驶舱统计按数据权限过滤」在 6 个仓储新增"按可见项目集合"的查询 —— `EvaluationResultRepository` 76→108（+32）、`EvaluationTaskRepository` 48→59（+11）、`IndicatorVersionRepository` 35→52（+17）、`ProjectRepository` / `DataBatchRepository` / `DataSnapshotRepository` 各 35→39（各 +4），其余仓储不变；此前 `EvaluationResultRepository` 还因新增全库均分与发布状态计数两个查询由 64 行增至 76 行；提交 `e295085`（列表与按 id 直读的数据权限）再给 5 个 `search` 各加 2 行（一行可见集合条件 + 一行 `@Param("ids")` 参数）—— `EvaluationTaskRepository` 59→61、`EvaluationResultRepository` 108→110、`DataBatchRepository` 39→41、`DataSnapshotRepository` 39→41、`IndicatorVersionRepository` 52→54，其余仓储不变；**本次提交 `5f8ba79`（驾驶舱图表支持自定义统计区间）再加 18 行** —— `EvaluationTaskRepository` 61→**76**（+15：新增 `findForTrend(ids, from, to)` 的 Javadoc、`@Query` 与方法签名）、`EvaluationResultRepository` 110→**113**（+3：新增 `countGroupByLevelInRange` 的 Javadoc/`@Query`/签名共 16 行、新增 `java.time.LocalDateTime` 导入 1 行，减去被它取代并删除的 `countGroupByLevelIn` 与 `countGroupByLevel` 及其分隔空行共 14 行），其余 22 个仓储不变）。按表分组共 **9 个分组**（公共基类组 + 8 个业务表组）与 1 个仓储层公共约定组。
- **实体层只做三件事**：映射表结构（字段名/类型/约束与 `db/schema.sql` 严格对齐，因为 `ddl-auto: none`，实体不会改表）、声明业务枚举的取值范围（全部用字符串列，注释里列全取值）、用 JSON 大字段收纳"结构不固定但必须留档"的算法数据（`vector`/`weights`/`contributions`/`details`/`extra`/`quality_report`/`matrix_data`…）。业务规则一律不写在实体里，实体甚至没有校验注解（校验在 service 与 DTO 层）。
- **两类实体的分界必须记住**：继承 `BaseEntity` 的 11 个实体由 Spring Data 审计（配合启动类 `@EnableJpaAuditing`）自动填 `created_at`/`updated_at`；其余 14 个实体按表结构自行处理时间列（有的用字段初值 `LocalDateTime.now()`，有的由 service 显式赋值）。判断标准只有一个：**看建表语句里到底有哪些审计列**。
- **实体之间没有任何 JPA 关联注解，全部用外键 id（`Long`）+ 编码/名称冗余关联**。这是为了适配 `open-in-view: false`（避免懒加载异常）、避免双向关系序列化递归、让分页查询保持单表、并让审计与历史数据不被级联删除影响。代价是跨表展示依赖写入时冗余的 `*_code`/`*_name`，`repository` 层的 JPQL 属性路径也因此永远是单级标量字段。
- **仓储层没有一行实现代码，全部由方法名与 `@Query` 驱动**。三条最容易踩坑的规则：`(:param is null or …)` 的可选条件要求参数**必须是 null 而不是空串**（所以每个 service 都有 `blankToNull`）；`@Modifying` 的批量删除**必须有外部事务**（由调用方 service 的 `@Transactional` 提供）；派生删除是"先查后删"，大数据量表（`raw_data_record`、`snapshot_value`）改用 `@Modifying` 一条语句删除。
- **同一项统计在仓储层有"全库"与"可见范围"两套方法，这是数据权限的落地方式**（提交 `747fec4`，见分组说明（9））：管理员 / `dataScope = ALL` 的用户在 `ProjectService.visibleProjectIds()` 拿到的是 `null`（不限制），驾驶舱继续走 `count()`、`countByStatusAndDeletedFalse`、`countGroupByAlgorithm`、`avgScoreAll` 这类**全库**方法；项目级用户拿到的是一个可能为空的 id 集合，改走 6 个仓储里新增的 `…In` / `…ProjectIdIn` 方法（`countByProjectIdInAndDeletedFalse`、`countByStatusAndDeletedFalseAndIdIn`、`avgScoreByProjects`、`countGroupByLevelInRange`、`countGroupByAlgorithmIn`、`findTop10ByProjectIdInOrderByIdDesc`、`countVisibleByStatus` 等）。三个必须记住的点：①**空集合绝不能传进 `In` 查询**（`in ()` 在部分数据库是语法错误），调用方短路返回 0 / 空数组；②`data_snapshot` / `evaluation_result` 没有 `deleted` 列，所以对应的 `In` 方法名里也不带 `DeletedFalse`；③`indicator_version` 的"公共版本"（`project_id` 为空）对所有项目可见，是"空集合短路"的**唯一例外** —— 可见项目为 0 时仍要数公共版本（`countByProjectIdIsNullAndStatusAndDeletedFalse`）。提交 `e295085` 把这套口径从**统计**扩展到了**列表与按 id 直读**（见分组说明（10））：5 个 `search` 各加一个 `(:ids is null or x.projectId in :ids)` 条件，列表按"取交集"返回空列表（避免历史遗留的项目上下文把页面打成错误页），按 id 直读则由 service 的 `checkVisible` 抛 `FORBIDDEN(2003)`（实测 200 → 403）。**提交 `5f8ba79` 又补上了第三个维度 —— 统计区间**：「评判等级分布」与「任务趋势」必须落在同一个 `[from, to)` 内，因此 `countGroupByLevelInRange(projectIds, from, to)`（2.44）与 `findForTrend(ids, from, to)`（2.42）把区间作为**必填参数**写进 `@Query`（而不再是"最近 20 条"这类隐式窗口），区间由 `DashboardService` 解析、校验（开始不得晚于结束、最长 366 天）后换算成左闭右开时间戳（见 06 分册 2.7.1 与 2.7.6）。
- **几个"看似重复"的字段与方法都有明确理由**：`SnapshotValue` 同时存原始值与标准化值（方案 5.4 可追溯 + 可重算）；`EvaluationResult.vector` 保存完整模糊评判向量而不只存等级（方案 6.3，只存等级会丢掉"以多大隶属度属于该等级"这一关键信息）；`EvaluationResult` 同时有升序全量（趋势折线图）与倒序 Top10（最新结果/横向对比）两条取数路径；`evaluation_result.details`（JSON 留档）与 `result_detail`（行式检索副本）双写，换取"算法输出原样可查"与"明细可排序分页"两种能力；`EvaluationResultRepository` 同时提供**全库均分** `avgScoreAll()` 与**按项目均分** `avgScoreByProject(projectId)`（同理还有 `countByPublishStatus` 与 `countByProjectIdAndPublishStatus`），一一对应驾驶舱「全部项目」与「选中项目」两个视图，**缺哪一条，哪个视图就会恒显示 0 或 "-"**（这正是提交 `c05676e` 修掉的缺陷）。
- **一致性检验是本册唯一的数学实体**：`AhpConsistency` 用 `lambdaMax` → `CI = (λmax - n)/(n - 1)` → `RI`（Saaty 表按阶数取常数）→ `CR = CI / RI` 四步完成判据，`passed = CR < crThreshold`（默认 0.1，可配），并通过 `matrix_data` 与 `eigen_vector` 把矩阵和权重向量一起留档，使任何一次检验都可以被独立复算——这比"只存一个通过/不通过"更能支撑评审与答辩。
