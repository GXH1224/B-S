### 1.2 权限模型与 `data.sql` 角色对照（全册前置）

`db/data.sql` 第 10-12 行一次性插入两个内置角色（`SYSTEM_ADMIN` 与 `EVALUATOR`，角色精简后系统只保留这两类），`permissions` 字段是 JSON 数组字符串；`SYSTEM_ADMIN` 写的是 `["*"]`，`LoginUser.isSuperAdmin()` 据此对其放行一切，因此**本册所有 `@PreAuthorize` 都额外挂了 `or hasRole('SYSTEM_ADMIN')`**，与 `*` 形成双保险（即使某天 `*` 语义被改，管理员仍可用）。`EVALUATOR` 则是逐个列举的 **29 项**显式授权（上一轮提交补上 `result:review`、`result:publish`、`result:compare` 并移除 `data:source:list` 后为 27 项；提交 `ce6c264` 又把 `report:list`、`report:create`、`report:download` 三项移除，27 → 24 项；本轮提交 `2a3d1d9` 为开放「数据库接入」补上 `data:source:list`/`data:source:create`/`data:source:update`/`data:source:test`/`data:source:extract` 五项，24 → **29 项**），因此报告模块的**列表与生成**接口对评估人员关闭；只有下载接口额外放行了 `result:export`（原因见 1.2 表与 2.11）。本轮起「数据源管理」的**五个权限码全部由 `EVALUATOR` 显式持有**（配套 `menusOf()` 给它补上 `dataSource` 菜单，见 05 分册），数据源端点不再只有管理员可用；此前那条 `data:source:list` 曾被移除、理由正是「没有对应菜单、属死权限」，本轮补菜单的同时把整条链路的五个码一并补齐，它不再是死权限（种子脚本是 `INSERT IGNORE`、不会覆盖已存在的行，所以每次改权限的提交都同时对运行库的 `EVALUATOR` 行执行了显式 `UPDATE`）。

## 2. 逐文件详解

### 2.1 `backend/src/main/java/com/ees/controller/AuthController.java`

**作用**：认证入口，只做四件事——登录发令牌、登出记审计、回显当前用户、改本人密码；不承载任何用户管理逻辑。
**被谁使用**：前端 `frontend/src/api/auth.ts` 及登录/改密页面；`AuthService`（构造器注入）承担全部校验与令牌签发；`SecurityUtils` 提供当前用户上下文。
**关键设计点**：
1. **本类是全项目唯一「免认证 + 需认证」混编的 Controller**：`/api/auth/login` 写在 `application.yml` 的 `ees.security.permit-paths`（第 76 行）里，其余三个方法没有 `@PreAuthorize`，靠 `SecurityConfig` 的 `anyRequest().authenticated()` 兜住——这样做的代价是「注释即契约」，没有注解直观，见「易错点」。
2. **四个方法都从 `SecurityUtils` 而非请求体取当前用户**：`/me` 用 `require()`（未登录直接抛 2001 未登录异常），`/change-password` 用 `require().getUsername()`，`/logout` 把 `HttpServletRequest` 透传给 service 只为让审计能记录客户端 IP。这样前端**永远无法通过伪造请求体来修改他人密码**（`ChangePasswordRequest` 里根本没有 `username` 字段）。
3. **`login` 把 `HttpServletRequest` 一并下传**，是因为审计日志需要 `AuditService.clientIp(request)`（登录成功/失败/锁定三处都记 IP），接口层不解析 IP，只做透传，保持职责单一。

### 2.2 `backend/src/main/java/com/ees/controller/HealthController.java`

**作用**：两个只读探针——`/api/health` 报告数据库、算法、存储三个组件的状态（前端主布局顶栏的健康标签每 60 秒轮询它）；`/api/info` 报告系统名称、版本、架构、离线标志与可用算法，**前端已无调用方**，现仅作运维只读探针。
**被谁使用**：`scripts/start-all.bat` 与 `docs/ACCEPTANCE.md` 的启动自检（curl `/api/health`）；`frontend/src/layouts/MainLayout.vue` 的 `loadHealth()`（第 54-57 行标签、第 207-219 行轮询）消费 `/api/health`。**`/api/info` 前端已无任何调用方**：登录页页脚曾调用它、该页脚已随提交 `59aa33b` 删除；主布局侧栏底部的版本号（原 `MainLayout.vue:227` 取 `version` 渲染 `v{{ version }}`）也已随提交 `546ef92` 删除，全项目 grep `systemApi.info` 无命中、`scripts/*.bat` 也不调用它，因此它现在**只剩「运维只读探针」这一个用途**（运维可直接 curl 或浏览器访问核对部署版本）；`EesProperties` 提供配置值，`AlgorithmRegistry` 提供算法清单，`javax.sql.DataSource` 用于真实探测数据库。
**关键设计点**：
1. **两个端点仍登记为免登录，但 `/api/info` 的免登录理由已经不成立**：`/api/health` 供运维脚本与前端顶栏健康标签在无人登录时探活，理由充分；`/api/info` 当初放进白名单，是因为**登录页要在拿到令牌之前用它渲染底部页脚**（系统名称、版本、算法清单），而该页脚已随提交 `59aa33b` 删除，随后主布局侧栏的版本号又随提交 `546ef92` 删除——**前端已无任何调用方，「免登录」这个设定已不再有前端需求支撑**。它现在只剩运维只读探针这一个用途，返回字段（`name`/`version`/`architecture`/`offline`/`algorithms`/`algorithmMode`/`serverTime`）**没有任何敏感信息**，因此留在白名单不会造成信息泄露。**是否要收紧为需鉴权属于待定事项，本次未改**：两者仍登记在 `application.yml` 的 `ees.security.permit-paths`（`/api/health`、`/api/health/**`、`/api/info`）中，由 `SecurityConfig` 第 49/57 行读取并放行。
2. **`/api/health` 的数据库探测是「真探测」**：通过注入的 `DataSource` 取连接并调用 `conn.isValid(3)`（3 秒超时），成功时连产品名与版本一起回显；异常被就地捕获，转成 `dbOk=false` + 异常消息，**不让健康检查自己抛异常**——健康检查一旦抛异常就失去了「报告不健康」的意义。
3. **算法与存储只做「配置回显」，不做深度自检**：算法组件恒为 `UP`（只说明注册表里有引擎、当前引擎模式是什么），存储组件恒为 `UP`（只回显 `root` 路径，不测写权限）。这是本类的诚实边界，见「易错点」。

1. 算法与存储组件的 `UP` 是**静态结论**：算法只证明注册表非空，存储只回显配置路径，都**不检查目录可写、不检查 C++ 引擎连通性**。要做真实的 C++ 引擎探活，需要在此处对 `ees.algorithm.cpp-engine-url` 发一次带超时的 HTTP 请求（当前未实现）。

### 2.3 `backend/src/main/java/com/ees/controller/UserController.java`

**作用**：用户与角色的管理接口，外加一份前端用的权限字典；是本册唯一**直接注入 Repository**（`SysUserRepository`、`SysRoleRepository`）的 Controller。
**被谁使用**：前端 `/system/users`、`/system/roles` 两个页面与 `frontend/src/api/system.ts`；`AuthService.saveUser` 复用于新增/修改/重置密码三条路径。
**关键设计点**：
1. **本类是「Controller 直连 Repository」的例外实现**：用户管理只有查询组装与少量字段修补，没有跨表业务规则，因此省掉一层 service；代价是事务边界变弱（本类方法**没有 `@Transactional`**，`changeStatus`/`delete` 各自一次 `save`，天然原子），以及未来若要加「改角色需级联清理成员关系」这类规则时需重构。
2. **重置密码是「伪更新」**：`resetPassword` 不复用任何 DTO，而是先把库里用户逐字段读出来塞进一个 `UserSaveRequest`（第 99-109 行），只替换密码，再调用 `authService.saveUser`。这样做的好处是**密码加密与审计逻辑只有一份**（在 `AuthService` 里），不会因为「重置密码」这条捷径绕过 BCrypt 编码。
3. **`/api/permissions` 的权限字典与 `data.sql` 的角色权限刻意解耦**：字典是给前端做按钮级控制与角色页展示用的静态清单，不是鉴权数据源。代价是两处会漂移——字典里**缺少**若干实际在用的权限码（本轮补齐 `data:source:create`/`data:source:update` 后由 8 个减为 6 个，见「易错点」）。

**易错点/注意**：
1. **权限字典与 `data.sql` 漂移**：`/api/permissions` 的 **35 项**里**没有** `data:batch:delete`、`data:rule:manage`、`system:user:create/update/delete`、`system:role:list` 这 **6 个仍写在 `@PreAuthorize` 里**的码（例如 `DELETE /api/data-batches/{id}` 用的是 `data:batch:delete`）。本轮提交 `2a3d1d9` 把 `data:source:create`、`data:source:update` 补进字典（第 189、190 行），此前它们正属于「接口在用、字典里没有」之列——这也正是「新授予评估人员的权限在角色权限页看不到」的**历史缺口**，现补齐后该缺口消除；更早一轮已把 `result:compare` 补进字典（现为第 199 行），所以它也不在此列；`result:archive` 则属于另一种情况——**字典与 `data.sql` 里都没有这个码，也没有任何接口在读它**（归档接口读的是 `result:publish`，实测 grep 全项目无 `result:archive`）。对这 6 个码而言，当前 `data.sql` 中只有 `SYSTEM_ADMIN` 与 `EVALUATOR` 两个角色，`EVALUATOR` 的权限数组里没有它们，因此实际只有 `SYSTEM_ADMIN` 通过 `["*"]`（以及注解里的 `or hasRole('SYSTEM_ADMIN')`）可用。角色权限页若依据该字典渲染勾选框，这 6 个码仍会出现「接口在用、页面上看不到」的情况。
2. `get(@PathVariable Long id)` 查不到用户时返回 `code=0, data=null`，而 `resetPassword`/`changeStatus`/`delete` 查不到时返回 `fail("用户不存在")`。**同一个类里两种「查不到」的返回风格不统一**，前端不能一律按 `code!=0` 判错。

4. `search` 的 `size` 没有上限校验，传 `size=100000` 可一次性拉全表；同类风险在 `options`（全量用户）与 `/api/permissions` 上同样存在。

### 2.4 `backend/src/main/java/com/ees/controller/ProjectController.java`

**作用**：项目（评估对象载体）的增删改查、归档/启用、成员管理三个接口组；权限过滤与数据范围判定全部下沉到 `ProjectService`。
**被谁使用**：前端 `/projects` 页面、项目上下文切换器（`stores/project.ts` 调用 `options`/`all`）；`ProjectService` 提供全部业务实现，`SecurityUtils` 提供操作人。
**关键设计点**：
1. **本类是「薄 Controller」的样板**：每个方法都是一行 `ApiResponse.ok(projectService.xxx(...))`，请求体直接绑定领域实体 `Project`（而非专门 DTO），业务校验（编码唯一、已产生结果不许删、数据范围过滤）都在 service 内。这样接口层只负责「路径/参数/权限/响应包装」四件事。
2. **`create`/`update` 用 `id` 覆盖法区分新增与修改**：`create` 把 `id` 置 `null`（强制新增），`update` 把路径 `id` 写入实体（强制改指定记录），与 `UserController` 完全同构，是项目内一致的安全习惯。
3. **成员接口是「覆盖式保存」**：`POST /projects/{id}/members` 接收整个成员数组，由 service 做「先清后插」，而不是提供增删两个接口。这样前端只需维护一份完整列表，避免并发下的增量不一致。

### 2.5 `backend/src/main/java/com/ees/controller/IndicatorController.java`

**作用**：指标体系版本的接入接口（方案 4.3）——导入、校验、查询（平铺/树/下拉）、发布、归档、删除、导入批次查询，以及**模板 xlsx 下载**。系统只负责「导入与使用」指标体系，不负责设计指标体系（类注释已明确这一职责边界）。
**被谁使用**：前端 `/indicators` 页面（导入向导、指标树、校验结果、发布按钮）；`IndicatorService` 承担解析与校验，`ExcelTemplateWriter` 生成模板字节，`SecurityUtils` 提供操作人。
**关键设计点**：
1. **模板下载不用「响应包装类」而是直接写字节流**：`template()` 返回 `ResponseEntity<Resource>`，把 `ExcelTemplateWriter.indicatorTemplate()` 生成的 `byte[]` 包成 `ByteArrayResource` 交给 Spring 写响应体。这样浏览器拿到的是**文件而不是 JSON**——下载类接口必须绕过 `ApiResponse` 统一结构，否则前端会下到一个 JSON 文本。
2. **中文文件名双写 `filename` + `filename*`**：`Content-Disposition` 同时给出 `filename="URL编码后的名字"` 与 `filename*=UTF-8''编码后的名字`（`download` 私有方法第 138-141 行）。老浏览器/旧代理只认 `filename`，现代浏览器按 RFC 5987 优先读 `filename*`，两份都写才不会出现「指标体系导入模板.xlsx」变成乱码或 `download`（无扩展名）的情况。
3. **导入结果的提示语随业务结果变化**（第 93 行）：`success=true` 时提示「导入成功」，否则提示「导入完成，存在错误行」——HTTP 层与 `code` 仍是成功（`code=0`），因为「文件读到了、行级错误已收集」不是接口失败而是业务结果；前端据此决定弹绿色还是黄色提示。

### 2.6 `backend/src/main/java/com/ees/controller/DataSourceController.java`

**作用**：甲方业务库的**只读**接入接口——数据源增删改查、连接测试、表清单、字段预览、受限 SELECT 抽取、抽取前 SQL 只读校验，以及可接入数据库类型字典（方案 4.2「数据库接入」）。
**被谁使用**：前端 `/data-sources` 页面的数据源表格与「连接测试 / 表清单 / 字段预览 / 抽取」向导；`DataSourceService` 承担 JDBC 连接、白名单校验与抽取落库；`SecurityUtils` 提供操作人。
**关键设计点**：
1. **密码永不回显，靠「服务层脱敏 + 接口层补掩码」双保险**：详情走 `dataSourceService.getMasked(id)`，服务内把非空密码替换为 `"******"`（`DataSourceService` 第 94-98 行）；而 `create`/`update` 保存后**接口层再手工 `saved.setDbPassword("******")`**（第 73、82 行），因为 `save` 返回的是刚写入的实体、密码字段是密文，必须再盖一层。列表查询则在服务内把密码置 `null`（`search` 第 81 行），**连掩码都不返回**——三种读路径三种脱敏强度，前端因此在列表页拿不到 `dbPassword`，在表单页只能拿到 `******`。
2. **保存时对掩码的保留逻辑是「编辑不丢密码」的关键**：前端编辑数据源时表单里显示的是 `******`，用户不改密码就原样提交。服务端 `save` 判断「非空且不等于 `******`」才重新加密写入，否则保持库中原密文；若是全新数据源（原密文为 `null`）又没填密码，则抛「请填写数据源密码」（`DataSourceService` 第 126-132 行）。若没有这条判断，用户每次改备注都会把密码覆盖成 `******` 的密文，导致连接测试全部失败。
3. **`db-types` 列出「能配的」而不是「已装驱动的」**：字典硬编码 7 类（MySQL、PostgreSQL、Oracle、SQL Server、达梦、人大金仓、通用 JDBC），每项给出 `driverClass` 与 `urlExample`。离线内网环境下驱动是**可插拔**的（对应 README 第九节「可插拔 JDBC 连接器」），如果只列已加载的驱动，运维换 jar 包前页面上就没有可选项、无法提前保存配置；给出 `urlExample` 则解决了「达梦的 JDBC URL 长什么样」这类现场高频问题。实际连通性由 `/test` 接口暴露，不靠字典猜测。

**易错点/注意**：
1. **`getMasked` 与 `get` 只差一个方法名，后果却是「泄密」与「安全」的差别**。新增读接口时若图省事写了 `dataSourceService.get(id)`，返回体里就会出现 `dbPassword` 密文字段。`create`/`update` 之所以要在接口层再补一次 `setDbPassword("******")`，也正是因为 `save` 返回的是 `get` 系实体。
2. `db-types` 的 7 类里，达梦（`dm.jdbc.driver.DmDriver`）、人大金仓（`com.kingbase8.Driver`）等驱动**默认不在 `pom.xml` 中**（仅 MySQL 内置）。选择这些类型保存配置没问题，但 `/test` 会报「驱动未找到」——这是预期行为（驱动由现场按需补 jar），不是 Bug。
3. `search` 把密码置 `null`，而 `getMasked` 置 `******`：前端从列表进入编辑页时若直接复用列表行数据，密码框会是**空**而不是 `******`。此时保存仍然是安全的（服务端只认「非空且不等于 `******`」为改密码，空值在库中已有密文时保留原值），但界面上看不到「已配置密码」的提示，用户容易误以为密码丢了而重填。
4. 请求体用 `Map<String,Object>` 的三个接口（`extract`、`validateSql`，以及其它类的创建/保存接口）**没有参数校验注解**，字段缺失只会在服务层报中文错误；`asLong` 遇到非数字返回 `null`，会把「传错类型」降级成「没传」。
5. **`data:source:update` 同时管着「编辑」与「删除」——开放数据库接入后，评估人员因此可以删除数据源**（第 86-91 行的 `DELETE /api/data-sources/{id}` 用的就是 `data:source:update`，字典里没有独立的 `data:source:delete`）。这是本轮授权必须一并说明的**副作用**：只授予"能改配置"就等于同时授予"能删配置"，且删除是逻辑删除（服务层记审计），页面上没有额外的前端白名单拦截。若业务上要求"可编辑但不可删除"，正确做法是**新增一个 `data:source:delete` 码**、把 `delete` 方法的注解换掉、再在两份种子与权限字典里同步（只改其中一处会出现「有权限码但字典里查不到」或反之的漂移）。**数据源密码的防护本次未改动**：密码以加密形式保存，接口一律不回显——列表把 `dbPassword` 置 `null`、详情与保存后的返回值用 `******` 掩码（`getMasked`，见「关键设计点」1），因此删除风险不涉及口令外泄。

### 2.7 `backend/src/main/java/com/ees/controller/DataBatchController.java`

**作用**：数据批次（文件导入 + 数据库抽取结果）的管理接口——分页/详情、上传导入、原始记录、错误行、质量报告、重新校验、删除，以及**两个下载接口**（数据导入模板 xlsx、指定批次的错误明细 xlsx）。
**被谁使用**：前端 `/data-batches` 页面（上传向导、质量报告卡片、错误明细表、导出按钮）；`DataBatchService` 负责解析文件、逐行校验与落库，`ExcelTemplateWriter` 负责两类 xlsx 生成，`SecurityUtils` 提供操作人。
**关键设计点**：
1. **模板与错误明细都是「内存生成 → 字节数组 → 直接写响应流」**：`template()` 调 `ExcelTemplateWriter.dataTemplate()` 拿 `byte[]`，`exportErrors()` 用 `ExcelTemplateWriter.errorDetail(rows, headers)` 生成 `byte[]`，两者共用私有 `download(...)` 把字节包成 `ByteArrayResource`。全过程**不落盘**，因此没有临时文件清理问题，也不产生额外的存储路径依赖；缺点是每次下载都要现场生成（模板很小，可接受）。
2. **错误明细与页面表格同源**：`exportErrors` 先调 `dataBatchService.errorRows(id)` 拿**与 `/errors` 接口完全相同的** JSON 结构，再逐行映射成中文表头的 Map 交给 POI。这保证「屏幕上看到的错误」与「导出的 Excel」永远一致（方案 5.4 可追溯要求），不会出现两套查询逻辑导致的数字对不上。
3. **批量导入的成功提示取决于「是否阻断」**（第 64 行）：`blocking=true` 时提示「导入完成，存在阻断级错误」，否则「导入成功」。这与质量报告里的 `blocking`/`blockingReasons[]` 字段呼应——阻断级错误意味着该批次不能用于生成快照，前端据此把后续步骤置灰。

### 2.8 `backend/src/main/java/com/ees/controller/SnapshotController.java`

**作用**：数据快照接口（方案 5.2）——分页、详情、总览、全部快照值、由数据批次生成快照、删除。快照一旦生成即冻结，任务执行后保持不变（类注释即此约束）。
**被谁使用**：前端 `/snapshots` 页面与评估工作台第 3 步（选快照）；`SnapshotService` 负责生成与冻结逻辑，`SecurityUtils` 提供操作人。
**关键设计点**：
1. **「生成快照」是 POST 到集合路径并只用 `Map` 传三个字段**：`create` 用 `@RequestBody Map<String,Object> body` 而非 DTO，因为请求体只有 `batchId`、`indicatorVersionId`、`remark` 三个短字段，且 `indicatorVersionId` 允许缺省（服务会取批次绑定的版本）。与 `TaskController.create` 用 Map 的理由不同（那里是**参数结构差异极大**），这里是**参数极少**。
2. **删除快照复用 `data:snapshot:create` 权限码**：快照没有独立的 `delete` 权限码，因为「能造就能删」——快照是评估中间产物，且只读地服务于任务；真正需要保护的是「已被任务使用的快照不许删」，该规则在 `SnapshotService.delete` 内（对应 API.md §5.3「已被任务使用则拒绝」）。
3. **`overview` 与 `values` 分工**：`overview` 给页面的矩阵视图（`maxObjects` 限制对象数，默认 20，返回 `{snapshot,objects[],indicators[],missingCount,outlierCount,recordCount,values[]}`）；`values` 给完整取值（供导出/算法核对）。分开的原因是矩阵视图是「抽稀展示」、全量取值是「数据核对」，二者体量差三个数量级。

### 2.9 `backend/src/main/java/com/ees/controller/TaskController.java`

**作用**：评估任务的接口（方案 4.5 / 8.1）——分页、最近任务、**创建并异步执行**、详情、状态轮询、状态历史、取消、重试。算法编码与参数校验全部下沉到 `TaskService`。
**被谁使用**：前端 `/tasks`、`/workbench`（分步向导的提交步骤）与 `/tasks/:id`（状态机与进度轮询）；`TaskService` 负责状态迁移与异步调度，`SecurityUtils` 同时提供**用户名与用户 id**（任务表两个字段都要）。
**关键设计点**：
1. **创建接口刻意接收 `Map<String,Object>` 而不是强类型 DTO**：四种算法的 `parameters` 子对象结构差异极大——`WEIGHTED` 是 `{gradeNames,gradeThresholds}`，`FUZZY` 是 `{gradeNames,gradeScores,operator}`，`AHP` 单层是 `{criteria,matrix,gradeThresholds}`、多层是 `{nodes:[{nodeCode,nodeName,criteria,matrix}]}`，`COMBO` 是 `{comboFlow,matrix,...}`（详见 API.md §6）。若为每种算法写一个 DTO，要么写四个类 + 一个带 `@JsonSubTypes` 的多态基类，要么写一个装着所有可能字段的「胖 DTO」（大量字段对多数算法无意义）；`TaskService.create` 里只需把 `parameters` 原样转成 JSON 存进任务表（第 200 行 `task.setParameters(JsonUtils.toJson(parameters))`），因此**用 Map 透传、由服务按算法类型逐项校验**是最省代码的写法。
   **代价**：① 接口层没有任何编译期/声明期校验，字段名写错（`gradeThresolds`）只能在服务层运行时暴露；② OpenAPI/接口文档无法从签名自动生成参数结构，只能靠 API.md 人工维护；③ 请求体里 `projectId` 等字段也变成弱类型，需要 `asLong`/`asString` 逐个容错；④ 参数结构变更不会引起编译错误，回归全靠测试与基准样例。
2. **`status` 接口单独造了一个轻量 Map 而不是复用 `detail`**：任务详情页每 1~2 秒轮询一次状态，而 `detail` 要带 `parameters`、`inputSummary`、`history[]`、`resultCount`、`consistency[]`（见 API.md §6）——那些字段体积大且不变化。因此 `status` 只回 11 个标量字段（状态、进度、当前步骤、错误码/信息、结果数、耗时、起止时间），把轮询的响应体压到最小。
3. **时间筛选用 `@DateTimeFormat(iso = ISO.DATE_TIME)`**：`from`/`to` 是 `LocalDateTime`，Spring 默认无法把查询串转成它，必须显式声明 ISO 格式（如 `2026-09-22T00:00:00`）；两个参数都可选，从而支持「按时间区间查任务」而不过滤时用 `null`。

**易错点/注意**：
1. 创建接口的请求体**没有任何校验注解**，字段类型也宽松：`projectId` 传 `"abc"` 会被 `asLong` 变成 `null`，服务层的提示会是「请选择项目」而不是「参数格式错误」。前端表单应承担格式校验。
2. `Map<String,Object>` 请求体的字段名（`projectId`、`snapshotId`、`indicatorVersionId`、`algorithm`、`taskName`、`parameters`）是**隐式契约**，散落在 API.md、`TaskService.create` 的取值语句与前端表单三处，改名需要三处同改。
3. `/recent` 无 `@PreAuthorize` 且不分页：它会把最近 N 条任务返回给**任何登录用户**（当前 `SYSTEM_ADMIN` / `EVALUATOR` 两类角色都能看到其他项目的最新任务标题）。若需严格隔离，应加 `task:list` 并在服务内做数据范围过滤。
4. `status` 手工拼 11 个字段，与 `detail` 存在**部分字段重复**（`task`、`resultCount`）。若新增需要展示的标量字段（如 `queuePosition`），必须同时改 `EvaluationTask`、`status` 方法与本册表格。

### 2.10 `backend/src/main/java/com/ees/controller/ResultController.java`

**作用**：评估结果接口（方案 7.1 三类展示、7.2 八类图表）——分页、按任务取结果、完整视图、文本/表格/图形三种展示、横向对比、复核、发布、归档、生成导出文件。是本册**唯一注入两个 service** 的 Controller。
**被谁使用**：前端 `/results`、`/results/:id`（三标签页 + 追溯信息 + 导出按钮）；`ResultService` 提供结果与图表数据，`ReportService` 提供导出文件生成（`/exports` 走的正是它）。
**关键设计点**：
1. **`/charts` 与 `/charts/{chartType}` 是一对「全集」与「单取」的接口，`charts` 的 `chartType` 默认 `all`**：
   - `GET /charts`（第 81 行）带 `chartType` 参数，**默认 `all`**，返回八类图形的**全集对象** `{bar,line,pie,radar,scatter,heatmap,boxplot,rankBar}`（每类都含 `chartType,title,unit,description,dataSource,generatedAt`，数据不足时含 `emptyReason`）。为什么要有全集？因为结果分析页一屏内可能同时渲染多张图，**一次拉齐**能保证八张图与下方表格来自**同一次查询、同一份明细数据**（`ResultService.buildAllCharts` 注释即「一次返回全部图形数据，保证与表格同源」），避免逐图请求之间数据被改动导致图表互相矛盾；同时 `fullView`（第 53 行）内嵌的 `charts{}` 也是同一份全集，页面首屏一个请求就能拿到文本+表格+图形。
   - `GET /charts/{chartType}`（第 102 行）是「单图直达」形式，路径风格更符合「资源定位」，适合前端在图表组件懒加载或需要单独刷新某一张图时使用（也可被导出/截图工具按名调用）。
   - 两者的实现是**同一个服务方法**：都先调 `resultService.buildAllCharts(...)` 拿到全集，再按需取出其中一项（第 87-92 行、第 108-114 行）。`charts` 在 `chartType` 不认识时回一个带支持列表的中文错误（第 94 行），`charts/{chartType}` 的错误提示较短（第 111 行）——两处提示文案不一致。
2. **`chartType=all` 返回八类全集是有意为之，代价是「单图请求也要算八张图」**：因为服务先把八类全部算完再挑一项，所以调 `/charts/bar` 的开销与调 `/charts?chartType=all` 相同（都用同一份 `details` 数据，实际额外开销主要是内存与少量遍历）。这个取舍换来了**代码极简与绝对同源**——不存在「单图路径」与「全集路径」两套算法实现导致数值不一致的风险。
3. **`/exports` 不在本类里生成文件，而是委托 `ReportService.generate` 并把 `downloadUrl` 指回 `ReportController`**（第 156-163 行）：导出是一个「生成记录 + 落盘 + 可再次下载」的完整流程，与 `/api/reports` 模块天然重合，因此结果页导出复用报告模块，只回一个 `{reportId,reportCode,fileName,downloadUrl}`，**下载一律走 `GET /api/reports/{id}/download`**（那里才有 `Content-Disposition` 中文文件名处理与下载计数，见 2.11）。这样避免了在本类里再写一份下载逻辑。

**易错点/注意**：
1. `/charts` 与 `/charts/{chartType}` 的**非法类型提示不一致**（前者列出全部可选值，后者只说「不支持的图形类型」）。前端若要统一展示错误，应统一走其中一个。

5. `fullView` 内嵌的 `charts{}` 与 `GET /charts` 返回的是同一份八类数据，但前者按 `resultId + taskId` 取、后者还支持仅按 `projectId` 取上下文（如项目级折线）。若两个入口传参不同，同一张图的数据**可能不同**——这是特性（不同上下文），也是排障时的常见困惑点。

### 2.11 `backend/src/main/java/com/ees/controller/ReportController.java`

**作用**：报告与导出接口（API.md §8）——报告记录分页、按任务生成报告（EXCEL/WORD/PDF，另支持 JSON）、**报告文件下载**、报告详情。是数据面里唯一返回磁盘文件流的 Controller。
**被谁使用**：前端 `/reports` 页面（仅系统管理员可见，本轮提交 `ce6c264` 已把 `report` 菜单从 `EVALUATOR` 的菜单数组中去掉）、结果分析页的导出按钮（先调 `POST /api/evaluation-results/{id}/exports`，再跳转本类的下载地址，该按钮由 `result:export` 授权，也是下载接口放行 `result:export` 的原因）；`ReportService` 提供文件生成、路径解析与下载计数，`SecurityUtils` 提供操作人。
**关键设计点**：
1. **下载用 `ResponseEntity<Resource>` + `FileSystemResource`（而不是 `ByteArrayResource`）**：报告是已经落盘的 Excel/Word/PDF（存放在 `ees.storage.root/report/<日期>/` 下），文件可能几十 MB，用 `FileSystemResource` 让 Spring 以流方式写响应，**不需要先把整个文件读进内存**；这也是它与 `IndicatorController`/`DataBatchController` 那两处「内存字节」下载的本质区别（那两个文件小、且是现场生成、没有磁盘副本，因此用 `ByteArrayResource`）。
2. **`Content-Disposition` 的 `filename` + `filename*=UTF-8''` 双写**（第 78-81 行）：报告文件名形如「方案对比评估 评估报告_20260922.xlsx」，含中文与空格。`URLEncoder.encode(name, UTF_8)` 先把中文转成 percent-encoding，**再用 `.replace("+", "%20")` 把空格还原**（`URLEncoder` 按 `application/x-www-form-urlencoded` 规则把空格编成 `+`，而 `filename*` 的值里 `+` 是字面加号）；随后同一串既填 `filename="..."`（老浏览器/旧代理的 ASCII 回退，虽然内容是 percent-encoding，但足以得到可用的文件名）又填 `filename*=UTF-8''...`（RFC 5987，现代浏览器优先采用，得到正确中文）。**两份都写**是兼容性的关键：只写 `filename*` 时部分老环境会退化成 URL 末段（如 `download`）或出现乱码。
3. **`markDownloaded` 是下载这一动作唯一的持久留痕**：项目里的审计由 `AuditFilter` 按 `ees.audit.methods = POST,PUT,DELETE,PATCH` 自动登记（另见 `application.yml` 第 134 行），**GET 请求不写审计**；而报告下载恰好是 GET。因此 `reportService.markDownloaded(id)`（把 `downloadCount` 加一并落库）成为「这份报告被取走过几次」的唯一数据来源，配合报告记录上的操作人/生成时间，满足方案 5.4 对**交付物去向**的可追溯要求。注意它记录的是**次数而非明细**：谁在哪一刻下载的，需要靠 `ReportRecord` 上的生成信息 + 访问日志（`data/logs/evaluation-backend.log`）回溯。
4. **下载接口的鉴权是「`report:download` 或 `result:export` 或 SYSTEM_ADMIN」——这是本轮提交 `ce6c264` 报告导出收紧后的必要联动**（第 72-73 行）。提交把 `report:list`/`report:create`/`report:download` 从 `EVALUATOR` 的权限数组中去掉、并把 `report` 菜单从 `menusOf()` 的 `EVALUATOR` 分支里删掉（当时 27 → 24 项、9 → 8 个菜单；权限数在本轮提交 `2a3d1d9` 因补入五个 `data:source:*` 变为 29 项，菜单数也因补入 `dataSource` 回到 9 个，但 `report` 相关权限与菜单至今未回归），报告模块的列表与生成由此只对系统管理员开放。但「评估结果」页的导出是一条**两步链路**：先 `POST /api/evaluation-results/{id}/exports`（需要 `result:export`）生成报告，再 `GET /api/reports/{id}/download` 取回刚生成的文件；该按钮归 `result:export` 管，与报告模块无关。如果下载仍只认 `report:download`，评估人员在第二步就会拿到 **403**——第一步明明成功、文件也已落盘，导出却在取回时断掉。因此下载接口改为接受生成侧所用的权限：**用哪个权限生成的就用哪个权限取回**。这条放行不会让评估人员拿到额外能力：`GET /api/reports`（列表，`report:list`）与 `POST /api/reports`（生成，`report:create`）都保持只认 `report:*`，评估人员既不能浏览报告记录、也不能自行生成报告（前端 `TaskDetail.vue` 的「导出报告」按钮也改为按 `report:create` 判权，评估人员不再显示）。

1. **下载类接口不能用 `?token=` 之外的认证方式**：前端若用 `window.open(downloadUrl)` 或 `<a href>` 打开新窗口，浏览器**不会**带上 `Authorization` 头，因此必须在 URL 上追加 `?token=<jwt>`（API.md §8 已注明）。这个能力由 `JwtAuthenticationFilter` 第 54-58 行支持（依次尝试 `Authorization` → `X-Token` → 查询参数 `token`），Controller 本身不解析令牌。
2. 前端若要读取文件名，需要跨域场景下服务端暴露该响应头：`SecurityConfig` 已把 `Content-Disposition` 放进 `cfg.setExposedHeaders(...)`（第 92 行）。若用 Nginx 反代，注意不要在反代层丢掉该响应头。
3. `markDownloaded` 在文件流写出之前调用，下载被取消也会计数；同时 GET 不进审计——**「谁下载了」只能靠服务器访问日志**。若审计要求更严，应把下载改成 `POST`（可被 `AuditFilter` 捕获）或在 `markDownloaded` 里写一条显式审计。
4. `search` 的筛选字段是 `projectId/reportType/taskId`，**没有 `keyword`**；前端若照抄其它列表页的关键字搜索框，会得到一个被静默忽略的参数。

### 2.12 `backend/src/main/java/com/ees/controller/SystemController.java`

**作用**：一个类承载**五类系统级接口**（用分隔注释分块）：综合驾驶舱（`/dashboard/overview`）、算法基准（`/baselines`）、审计日志（`/audit-logs`）、系统参数（`/configs`）、数据质量规则（`/quality-rules`）。
**被谁使用**：前端 `/dashboard`、`/baselines`、`/system/audit`、`/system/config` 四个页面，以及数据接入页读取质量规则；`DashboardService`、`BaselineService`、`AuditService`、`ConfigService` 四个服务 + `DataQualityRuleRepository` 一个仓储由构造器注入（本册注入依赖最多的 Controller）。
**关键设计点**：
1. **为什么五类接口合成一个类**：这五组都是「平台运维面」能力而不是业务闭环里的一环——它们共同的路径前缀就是 `/api`（而不是某一个业务资源），都不属于任何单一业务对象，且单个页面所需的方法很少（驾驶舱 1 个、基准 3 个、审计 3 个、参数 3 个、质量规则 2 个）。合在一个类里可以共用 `@RequestMapping("/api")` 前缀与构造器注入，减少 4 个文件与 4 段样板；作者还用注释分隔线（第 48、60、83、108、131 行）把类内分区，保持可读性。
   **代价**：① 类变成 172 行（提交 `5f8ba79` 为驾驶舱补统计区间参数后由 167 行增至 172 行）、12 个方法，是全册最长的类，按业务查找时要靠注释跳转；② **权限边界混杂**——同一类里既有「任何登录用户可读」的接口（`/quality-rules`、`/dashboard/overview` 之外还有 `/configs` 需权限），又有**仅限管理员的写接口**（`/configs/{key}`、`/audit-logs/purge` 都是光秃秃的 `hasRole('SYSTEM_ADMIN')`，连细粒度权限码都没有）；审阅者必须逐个方法看注解，无法靠「类注释」判断整个类的安全级别；③ 五组接口的鉴权策略若要统一调整（例如给质量规则加读写分离），改动会集中在一个大文件里，不利于多人并行修改。
2. **`/audit-logs/purge` 与 `/configs` 的写操作只认 `SYSTEM_ADMIN` 角色**：这三个方法（第 99-105、116-122、124-129 行）的 `@PreAuthorize` 里**没有 `hasAuthority(...)`**，因为「清理审计日志」「改系统参数」属于平台级动作，权限字典里也没有对应码（`/api/permissions` 只提供了 `system:config:list` 这一读权限）。这形成了一条清晰的规则：**能看参数的角色可以更多，能改参数的只能是系统管理员**。
3. **质量规则直接注入 `DataQualityRuleRepository`**（与 `UserController` 直连仓储属同一类例外）：规则只有「列出」与「改三个字段」两种操作，没有跨表规则，因此省掉 service 层；`updateQualityRule` 在方法内做了**字段级部分更新**（哪个字段非 `null` 就改哪个），实现「只改严重级别」或「只启停」这类局部操作。
4. **驾驶舱的两个统计区间参数只影响两张图（提交 `5f8ba79`）**：`overview(...)` 新增 `from` / `to` 两个**可选** `LocalDate` 参数（`@DateTimeFormat(iso = ISO.DATE)`，ISO 日期、**含首尾两天**），转调 `dashboardService.overview(projectId, from, to)`。**它们只作用于「任务趋势」与「评判等级分布」两张图**：前者按区间逐日分桶，后者改为按结果创建时间落在同一区间内统计，从而实现「两张图同区间联动」；**上方六张指标卡（项目数 / 评估任务 / 数据快照 / 评估结果 / 平均得分 / 可用算法）始终是「当前总量」，不随区间变化**。两个参数都为空时，服务层把 `to` 取今天、`from` 取 `to` 往前 6 天，即**行为与改动前的「近 7 天」完全一致**；开始晚于结束或区间超过 366 天则由服务层抛 `BizException(PARAM_INVALID)`（HTTP 200 + 错误码，见 06 分册）。接口层在这里**不做任何区间校验**，只负责按 ISO 格式把字符串绑成 `LocalDate` 并透传——边界值规则（含首尾、366 天上限）属于业务规则，对应方案的分层要求。

**易错点/注意**：
1. `qualityRules` 的 `projectId` 语义容易误解：**不传时只返回已启用规则**（`findByEnabledTrueOrderByIdAsc`），因此「关闭的规则」在默认视图里查不到；要查看被停用的全局规则，当前接口没有提供入口（只能改库）。前端「全部规则」页若直接调本接口，会看不到已停用项。
2. `enabled` 的 `Boolean.valueOf(String.valueOf(x))` 语义：「非空且等于 `true`（忽略大小写）」才是 `true`，**其余一律 `false`**。前端必须发真正的布尔 `true/false` 或字符串 `"true"/"false"`，发 `1`/`0` 会得到错误结果且不报错。
3. `/configs`、`/configs/{key}`、`/audit-logs/purge` 三个写接口**没有细粒度权限码作兜底**：一旦 `SYSTEM_ADMIN` 角色的定义被改动（例如把 `*` 换成显式列表），这三处仍只认角色码 `SYSTEM_ADMIN`；反之若产品要求「运维角色可改参数」，必须改代码而不能只改 `data.sql`。
4. `/baselines/{id}/run`、`/baselines/run-all`、`/audit-logs/{id}` 三个接口都返回 `code=0` 而不论业务成败（基准失败、审计记录不存在除外），前端**一律要读 `data` 里的 `passed` 等字段**做判断。
5. `/api/dashboard/overview` 的 `from`/`to`（提交 `5f8ba79`）是最容易误解的一处：它们**只影响「任务趋势」与「评判等级分布」两张图**，上方六张指标卡永远是当前总量——所以「把区间改成近一年后项目数没变」不是缺陷，而是刻意口径（见 2.12「关键设计点」4）。另一个易错点是**参数格式**：必须传 `YYYY-MM-DD`（`ISO.DATE`），传成 `YYYY-MM-DD HH:mm:ss` 会在绑定阶段失败并返回 1001 参数校验错误；而同类的审计筛选接口（第 86 号）用的是 `ISO.DATE_TIME`，两者不能互换。区间边界（开始晚于结束、超过 366 天）由服务层拒绝并以 HTTP 200 + 错误码返回，接口层不做校验，因此**前端必须自己先把区间收敛在 366 天以内**，否则一次参数错误就会让整页总览加载失败（09 分册 2.3.6 的做法就是在日期选择处直接截断并提示）。

## 3. 本册小结

- 本册共覆盖 **12 个文件、1574 行代码**（`backend/src/main/java/com/ees/controller/` 全部 Controller），梳理出 **104 个 HTTP 端点**：Auth 4、Health 2、User 11、Project 12、Indicator 12、DataSource 11、DataBatch 10、Snapshot 6、Task 8、Result 12、Report 4、System 12。（行数为实测：`AuthController` 79 + `HealthController` 91 + `UserController` **218** + `ProjectController` 104 + `IndicatorController` 146 + `DataSourceController` 159 + `DataBatchController` 143 + `SnapshotController` 88 + `TaskController` 102 + `ResultController` 166 + `ReportController` 106 + `SystemController` **172** = **1574**；其中 `AuthController` 因更早一次为 `/api/auth/me` 补回 `menus` 而由 71 行增至 79 行，`UserController` 先因权限字典补上 `{"result:compare","结果横向对比"}` 由 216 行增至 217 行、本轮提交 `2a3d1d9` 又因补上 `{"data:source:create","新建数据源"}` 与 `{"data:source:update","编辑/删除数据源"}` 两条而由 217 行增至 **218 行**，`ReportController` 因提交 `ce6c264` 为下载接口补写 Javadoc 而由 98 行增至 106 行——**只增字典项与注释、逻辑未改**，端点总数仍是 104；**本次提交 `5f8ba79` 另把 `SystemController` 由 167 行增至 172 行**——驾驶舱 `overview` 新增 `from`/`to` 两个可选参数、1 行注释与 `java.time.LocalDate` 导入，本册合计因此由 **1569** 增至 **1574**。这 172 行里**没有任何新端点**：端点总数仍是 104，新增的只是既有驾驶舱端点的两个查询参数。）

- **接口层的职责边界是「四件事」**：路径与参数绑定、`@PreAuthorize` 鉴权、`ApiResponse` 统一包装、下载流写头。所有业务规则（编码唯一性、状态机迁移、数据范围过滤、SQL 只读白名单、参数结构与取值校验）都在 service 层，接口层最典型的写法就是一行 `return ApiResponse.ok(xxxService.yyy(...));`。**例外只有三处**：`UserController` 与 `SystemController` 直接注入 Repository（用户与质量规则无跨表规则），`ResultController` 注入两个 service（导出复用了报告模块）。

- **权限写法统一为「细粒度码 or SYSTEM_ADMIN」**，与 `data.sql` 里 `SYSTEM_ADMIN` 的 `["*"]` 形成双保险；细粒度码与角色的对应关系见 1.2 表（该表只有 `SYSTEM_ADMIN` 与 `EVALUATOR` 两列，因为角色精简后系统只保留这两类角色）。**没有细粒度码的写接口只有三个**：`POST /api/audit-logs/purge`、`PUT /api/configs/{key}`、`PUT /api/configs`，它们只认 `SYSTEM_ADMIN` 角色码——这是平台级动作的刻意收口。**本轮新增一处「两个细粒度码并列」的例外**：`GET /api/reports/{id}/download` 写成 `hasAuthority('report:download') or hasAuthority('result:export') or hasRole('SYSTEM_ADMIN')`，原因是报告导出已收紧为仅系统管理员、而「评估结果」页的导出走「`result:export` 生成 → 本接口取回」两步，必须让生成侧权限也能取回文件（见 2.11「关键设计点」4）。

- **两个接口仍登记为免登录**（`/api/health`、`/api/info`，外加 `/api/auth/login` 与 `/error`），对应 `application.yml` 的 `ees.security.permit-paths`，由 `SecurityConfig` 第 49/57 行统一放行。原因很实际：运维脚本要在无人登录时探活，前端顶栏健康标签也轮询 `/api/health`；而 `/api/info` 当初是为「登录页在未登录状态渲染底部页脚」才放进白名单的，如今该页脚已随提交 `59aa33b` 删除、主布局侧栏版本号又随提交 `546ef92` 删除，**前端已无任何调用方，这个免登录理由已不成立**（返回字段不含敏感信息，故仍留作运维只读探针；**是否收紧为需鉴权属待定事项，本次未改**）。**新增免登录路径必须用精确路径，不能用 `/api/auth/**` 这类通配**，否则会把 `/logout`、`/me`、`/change-password` 一起暴露。

- **下载类接口共 4 个方法**（指标体系模板、数据模板、错误明细、报告下载），全部绕开 `ApiResponse`、直接返回 `ResponseEntity<Resource>`：内存生成的小文件用 `ByteArrayResource`（模板、错误明细），磁盘上的大文件用 `FileSystemResource`（报告）。`Content-Disposition` 一律 `attachment` + `filename` / `filename*=UTF-8''` **双写同一串 UTF-8 percent-encoding 值**，并先把 `URLEncoder` 产生的 `+` 还原成 `%20`——这是中文文件名不乱码、不丢扩展名的完整条件。前端在新窗口下载时必须用 `?token=`（`JwtAuthenticationFilter` 支持查询参数取令牌），这是「浏览器不发送 Authorization 头」的必然结果。

- **易被误解的三处**：① `@RequestParam(required=false)` 只解决「可以不传」，真正让空串不参与 SQL 条件的是服务层的 `blankToNull`（前端传 `keyword=` 时若不归一会变成 `LIKE '%%'` 的无效条件）；② `charts` 系列接口无论要哪一类图，服务端都**先算完八类再取一项**，这是「与表格同源、实现只有一份」的取舍，不是性能缺陷；③ 报错的两种风格并存——「业务失败」用 `ApiResponse.fail(...)`（`code!=0`，HTTP 仍 200），「业务结果不如预期」用 `code=0` + `data` 里的 `success`/`passed`/`valid`/`blocking` 字段（导入有错误行、连接测试失败、SQL 校验不通过、基准未通过、任务提交后异步失败），前端必须按接口约定分别处理。

- **可优化项（本册在阅读中发现的重复与不一致）**：`asLong` 容错转换在 `DataSourceController`、`SnapshotController`、`ReportController` 中逐字重复了三份；`download(...)` 字节流下载在 `IndicatorController` 与 `DataBatchController` 中各写了一份；`{reportId,reportCode,fileName,reportType,fileSize,downloadUrl}` 六个字段的响应组装在 `ResultController` 与 `ReportController` 中各写了一份；`blank`/`blankToNull` 在每个类里各写一份。此外，`/api/permissions` 的静态字典仍缺少若干正在使用的权限码（本轮补齐 `data:source:create`/`data:source:update` 两条后为 6 个，见 2.3「易错点」第 1 条），`/charts` 与 `/charts/{chartType}` 的非法类型提示文案不一致，`archive` 类接口在 `ResultController` 用的是 `result:publish`，而 `result:archive` 这个名目在权限字典与 `data.sql` 里都不存在、也没有任何接口在读它（当前 `result:publish` 由 `EVALUATOR` 显式持有、`SYSTEM_ADMIN` 通过 `["*"]` 持有）。这些都不影响功能，但在维护与答辩时值得说明。
