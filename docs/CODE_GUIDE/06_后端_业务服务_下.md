## 2. 逐文件详解

### 2.1 `backend/src/main/java/com/ees/service/DataBatchService.java`

**作用**：数据接入的唯一入库闸门。把「上传的表格文件」或「数据库只读抽取得到的行集合」统一转成
`TabularReader.TableData`，跑同一套七类质量规则，产出数据批次 `data_batch` + 原始记录 `raw_data_record`
+ 质量报告 `qualityReport` + 错误明细，并把是否「阻断」写进批次状态（`VALIDATED` / `FAILED`）。
同时它也是**批次级数据权限**的把关点：列表查询按当前账号可见项目取交集，按 id 直读（详情、记录、错误明细、
质量报告、重校验、删除）与写入（导入、抽取）都要项目可见（提交 `e295085`，见 2.4.9）。

**被谁使用**：`controller/DataBatchController`（分页、详情、导入、记录、错误行、质量报告、重校验、删除、模板与错误明细导出）、
`SnapshotService`（`batchService.get` / `saveBatch` 读批次并回写 `SNAPSHOTTED`）、
`DataSourceService`（第 315 行调用 `createBatchFromRows` 完成抽取入库）、
`util/ExcelTemplateWriter`（用 `TEMPLATE_COLUMNS` 生成导入模板表头）。

**关键设计点**：
1. 文件导入与数据库抽取**共用 `validate` 主体**（第 287 行），保证两条接入路径的质量口径完全一致（方案 5.1「数据接入 ≥ 2 种」）。
2. 批次级阻断条件与条目级严重级**分离**：错误条目上的 `severity` 只用于展示与规则留痕，是否阻断整批只由 4 条 `blockingReasons` 白名单决定（第 474-494 行），这是修过的真实缺陷点。
3. `project_code` 必须写**项目编码**而不是批次号（第 181、256、668 行），否则「批次→快照→任务→结果」的项目维度追溯链断裂（方案 5.4）。
4. **列表取交集、按 id 直读 403**（提交 `e295085`）：`search` 把 `visibleProjectIds()` 作为 `projectId in :ids` 传给仓储，与请求里的
   `projectId` 是**交集**关系（传了不可见的项目 → 空列表，不报错）；`get` 与新增的 `requireBatchVisible` 则在「查得到」之后
   再 `checkVisible(所属项目)`，越权直接 403。`importFile` / `createBatchFromRows` 也各加一道 `checkVisible(projectId)`，
   使「看」和「写」两个方向都不能越出可见项目（策略与实测见 2.4.9）。

#### 2.1.1 `importFile` 全流程（扩展名 → 落盘 → 解析 → 校验 → 入库 → 质量报告）

```
① validateExtension  → ② storeFile 落盘留档 → ③ TabularReader.read 解析
→ ④ 表头最小集校验 → ⑤ 生成批次号并保存批次头（拿到主键）
→ ⑥ validate（七类规则） → ⑦ raw_data_record 全量入库
→ ⑧ 统计 + qualityReport + errorDetail 回写 → ⑨ 返回结果 Map
```

- **顺序不可调换**：留档必须在解析之前（第 160 行），否则解析失败的文件就永久丢失，用户无法自证「我上传的是什么」。
- **先落库批次头、后写原始记录**：批次头先 `save` 才能拿到自增主键，否则 `raw_data_record.batch_id` 无处可挂。
- **先入库原始记录、后写统计**：`validRows/errorRows` 等来自同一份内存结果，但落库顺序保证即使统计回写失败，明细也已完整保存（最坏情况是统计为空，可经 `revalidate` 重建）。
- **状态只有两个**：`VALIDATED`（可继续生成快照）与 `FAILED`（阻断，必须修数据后重新导入或改规则后 `revalidate`）。

#### 2.1.2 `validate` 中七类质量规则的逐条实现

代码从 `data_quality_rule` 读版本化的规则（第 291 行），七类**规则类型**与 `db/data.sql` 的种子数据对应关系如下
（表中实际有 8 条规则，`QR-REQUIRED` 与 `QR-COVERAGE` 同为 `REQUIRED` 类型）：

| # | 规则类型 | 种子规则 | 默认严重级 | 判定位置 | 命中后的后果 |
|---|---|---|---|---|---|
| ① | `REQUIRED` 必填字段缺失 | `QR-REQUIRED` | BLOCK | 第 339-355 行 | 该行无效 + `requiredFieldMissing++`；**阻断整批** |
| ② | `MISSING` 缺失值 | `QR-MISSING` | BLOCK | 第 356-362 行 | 该行无效 + `missingValues++`；按策略 `BLOCK` 阻断、`DROP` 提示剔除 |
| ③ | `FORMAT` 数值格式非法 | `QR-FORMAT` | BLOCK | 第 363-375 行 | **只标记该行**无效 + `formatErrors++`；批次不因此阻断 |

#### 2.1.3 「阻断 / 告警 / 按行错误」三档判定的依据（修复前后差异）

三档的**判定位置不同**，这是理解本文件的关键：

| 档位 | 判定依据 | 代码位置 | 表现 |
|---|---|---|---|
| 阻断整批 | `blockingReasons` 非空（4 条白名单） | 第 477-494 行 | 批次 `status = FAILED`；`SnapshotService.createFromBatch` 第 120-123 行直接拒绝生成快照 |
| 告警（批次级） | `blockingReasons` 中的 `DROP` 提示等 | 第 484-486 行 | 报告里出现原因，但 `blocking = false` |
| 按行错误 | 每行 `valid` 与错误条目 `severity` | 第 339-439 行 | 该行 `raw_data_record.valid = false`，计入 `errorRows`，可在错误明细中导出修正 |

**为什么数值格式非法不阻断整批**：`QR-FORMAT` 规则在表里的严重级是 `BLOCK`，容易被误读成「该错误阻断批次」。
代码的实际语义是：错误条目上的 `severity` 只表示**这一条的严重程度**（用于前端红/橙/灰着色与规则留痕），
批次是否阻断**只由第 478-493 行的四条白名单决定**，其中没有 `formatErrors`。

修复前后对比：

| | 早期实现（缺陷） | 当前实现 |
|---|---|---|
| 触发 | 任一行 `indicator_value` 非数值 | 同上 |
| 处理 | `blocking = true` → 批次 `FAILED` | `valid=false` 且 `formatErrors++`，`blocking` 不变 |
| 后果 | 一行脏数据导致**整批 1000 行全部不可用**，用户必须改文件重传 | 只有问题行被剔除，其余行立即可用，错误明细给出「建议修正为数值后重新导入该行」 |
| 验收对应 | — | ACCEPTANCE 1.4.3「格式非法按行标记：错误行标记『数值格式非法』，有效行仍可用」 |

工程原因：验收数据往往是现场台账，混入「约 90」「90 分」「N/A」是常态；把格式问题升级为整批阻断，会把
「可修的单点问题」变成「阻塞整条评估链路的问题」。而必填字段缺失、缺失值、指标未覆盖、方向未确认这四类
**会让算法无法产生有意义的结果**（缺对象/缺指标/标准化无定义），因此必须阻断——这正是方案 5.3 的分档本意。

#### 2.1.4 重复记录识别键与策略分支

- 识别键：`objectCode + "|" + dataTime(parsed) + "|" + indicatorCode`（第 415-416 行），键集合按批次内存态维护。
- 不含批次号：同一文件重复导入两次，第二次的每一行都会与「同一批次内已出现的行」比较。由于键集合是**每次
  `validate` 新建**的，跨批次重复（导入两次同一文件）实际靠 ACCEPTANCE 1.4.5 的告警来自 `unitMismatchCount`/
  重复告警以外的提示，本方法只能识别**批内重复**——这一点务必在看验收结果时区分清楚。
- 策略分支：`duplicateSeverity` 命中时记错误；只有规则被改成 `BLOCK` 才把 `valid` 置 false（第 421-423 行），
  默认 WARN 保证重复行仍进入后续快照，由快照阶段「同对象同指标取时间最新一条」自然去重。
- 时间参与键值的副作用：`dataTime` 解析失败时为 `""`，同对象同指标的多条无时间记录会被判为重复（见易错点）。

#### 2.1.5 指标覆盖校验与 `units` 校验

- **覆盖校验**（第 442-461 行）：只比较版本内 `leaf = true` 的**叶子指标**集合与数据中出现过的 `indicatorsSeen`，
  差集非空即报「数据未覆盖必需指标」。用叶子指标而非全部指标，是因为只有叶子指标参与评分（`ScoringSupport`
  与各算法的 `metas` 都由叶子构成），父节点由子节点权重合成，不需要原始数据。
- **units 校验**（第 402-407 行）：当行内单位非空且与指标定义单位不相同即记 INFO 级错误；行内单位为空时用
  指标定义单位补齐（第 384-386 行），因此「不写单位」不会被误判为不一致。

#### 2.1.7 `ValidationOutcome` 为什么单列五个计数器

`ValidationOutcome` 内部类（第 676-691 行）除通用统计外，专门单列
`requiredFieldMissing`、`missingValues`、`formatErrors` 三个 `int` 与
`indicatorNotCovered`、`directionUnknown` 两个 `boolean`，原因是：

1. 这四个（三数两布尔）**恰好是阻断判定的输入**（第 478-493 行），把它们与「只用于展示的计数」分开，
   阻断逻辑就不需要再遍历 `errors` 列表去猜语义；
2. `errors` 列表里 `requiredFieldMissing` 与「指标未在版本中」共用同一个 `REQUIRED` 严重级，
   仅凭 `severity` 无法区分，必须另立计数器；
3. `missingValues` 与 `directionUnknown` 需要与**系统参数**（缺失值策略）组合判断，单独持有状态更清晰。

`records`、`errors`、`qualityReport`、`validRows`、`errorRows`、`objectCount`、`indicatorCount`、`blocking`
则是三条调用路径（导入 / 抽取 / 重校验）共用的出口字段。

#### 2.1.8 `createBatchFromRows` 与 `importFile` 的差异

| 维度 | `importFile`（文件导入） | `createBatchFromRows`（数据库抽取入库） |
|---|---|---|
| 行数据来源 | `TabularReader.read(InputStream, fileName)` 从上传字节解析 | 由 `DataSourceService.extract` 用 `ResultSetMetaData.getColumnLabel` 构造成 `List<Map<String,String>>` |
| 行号 | 源文件物理行号（Excel 第 N 行 / CSV 记录号 +1） | 从 2 开始递增（虚拟行号，源表没有稳定行号） |
| 文件留档 | `storeFile` 落盘 + `fileHash`(SHA256) | 不落盘、不算哈希 |
| 来源标识 | `sourceType = FILE`，`sourceRef`/`fileName`/`fileSize`/`storedPath` | `sourceType = DATABASE`，`sourceRef = "数据源 <名称> 抽取"`，另存 `dataSourceId` + `querySql` |
| 表头 | 文件真实表头（中英文皆可） | 第一行 Map 的 key 顺序 |
| 后续步骤 | 校验 → 入库 → 统计 → 返回 Map（给前端） | 校验 → 入库 → 统计 → 返回 `DataBatch`（给抽取服务拼响应） |
| 共用 | 同一个 `validate`、同一套 `qualityReport` 字段、同一个「`blocking` → `FAILED`」状态规则 | 同左 |

一句话：**两条接入路径只在「数据怎么进来、来源怎么留痕」上不同，质量口径完全一致**——这是方案 5.1
「数据库、文件两种接入方式结果等价」的实现保证。

#### 2.1.9 `storeFile` 落盘策略、文件名清洗与 `projectCodeOf`

- 目录策略：`{ees.storage.upload-dir}/{subDir}/{yyyy-MM-dd}/`，`toAbsolutePath().normalize()` 消除 `..`；
  `subDir` 由调用方给（批次文件传 `"batch"`），为后续其它上传（如指标体系）预留分目录。
- 文件名策略：`System.currentTimeMillis() + "_" + sanitize(原名)`。前缀时间戳保证**同一文件重复上传不互相覆盖**，
  同时保留原名便于人工辨认；`sanitize` 把 `\ / : * ? " < > |` 全部替换为 `_`。
- 失败容忍：任何异常只 `log.warn` 并返回 `null`，`stored_path` 存 null。留档是「加分项」，不能因为磁盘满
  就让业务导入失败。
- `projectCodeOf` 为什么必须是项目编码：第 668-674 行注释写明「保证批次、快照、任务的项目编码一致可追溯」。
  `DataSnapshot.projectCode` 直接抄批次（`SnapshotService` 第 215 行），`EvaluationTask.projectCode` 抄快照
  （`TaskService` 第 202 行），`EvaluationResult.projectCode` 抄任务（第 466 行）。只要最上游写的是**项目编码**，
  整条链路的结果都能按项目聚合（驾驶舱项目态势、结果横向对比、导出报告的「项目编码」栏）。
  **修复前的缺陷**：早期实现把批次号（或直接用批次的主键/编码）写进 `project_code`，导致
  `data_batch.project_code` 与 `project.project_code` 不是同一套取值，于是：追溯信息里的「项目编码」与项目管理页对不上；
  驾驶舱按项目统计、`ProjectRepository` 派生查询归不到项目上；跨表按项目编码串联（批次↔快照↔任务↔结果）断链。
  修复方式就是统一由 `projectId` 反查 `Project.projectCode`，并且**只有在项目确实存在时才写入**（否则写 null，
  以免造出假的编码）。

**易错点/注意**：
1. `DIRECTION` 规则的严重级读了却没用于方向校验：第 463-472 行的错误条目严重级硬编码 `"WARN"`，且
   `directionUnknown` 一旦为真**无条件阻断**，与 `QR-DIRECTION` 表里 `WARN` 的语义不完全一致（表里其实是
   「提示」，代码里是「阻断」）。这是刻意的从严处理（方向缺失会让标准化结果不可信），但改表不会改变行为，
   修改规则时要看代码而不是只看规则表。
2. `validate` 里对 `targetVersionId` 非空时**再查一次** `indicatorService.codeIndex(targetVersionId)`
   （第 444 行），而 `importFile`/`createBatchFromRows` 已在第 193-194 / 266-267 行查过一次，一次导入会查两遍
   指标版本。数据量不大时无感，若要优化可把 `indicatorIndex` 直接传入 `validate`。
3. 重复键使用**解析后的 `dataTime`**：时间无法解析（如 "2026年3月"）时值为 `""`，同对象同指标的多条无时间记录
   会被判为重复；同时时间解析失败只是 WARN，故这类数据会「静默」进入快照并参与「取最新一条」的比较（`null`
   时间排在最后）。
4. `delete` 软删批次却**物理删除原始记录**，删除后无法再 `revalidate`；若已生成快照，快照值仍独立存在
   （快照是复制而非引用），结果是「批次查不到但快照还能用」，这是刻意的不可变快照语义，不是 bug。
5. **数据权限的「两道闸门」不是重复而是分工**（提交 `e295085`）：`get`/`requireBatchVisible` 里的
   `checkVisible` 是 `visibleProjectIds()` 的**第二次**调用（第一次在 `search` 里做交集）——列表接口走
   「集合 + `in`」，按 id 接口走「单值 + `contains`」。两者都不能省：只做列表过滤挡不住「知道 id 就能直读」，
   只做按 id 校验则列表页会漏数据。策略与实测见 2.4.9。

### 2.2 `backend/src/main/java/com/ees/service/DataSourceService.java`

**作用**：以**只读账号 + 受限 SQL**接甲方业务库（方案 5.1 / 9.1）：维护数据源（密码 AES 加密存储、

#### 2.2.2 密码 AES 加密保存与 `******` 掩码保留原值的逻辑

- 加密（第 129 行 → `CryptoUtils.encrypt`）：算法 `AES/GCM/NoPadding`，12 字节随机 IV + 128 位认证标签，
  密钥由 `sha256("ees-datasource::" + jwtSecret)` 派生，输出 `ENC:` + Base64(IV‖密文)。库里存的是 `ENC:...`
  （ACCEPTANCE 1.4.13 要求 Navicat 看到的不是明文）。
- 读取（第 366 行 → `CryptoUtils.decrypt`）：无 `ENC:` 前缀时按历史明文原样返回，保证老数据仍可用；
  解密失败提示「可能加密密钥已变更，请重新录入数据源密码」。
- 掩码保留原值的三分支（第 127-132 行）：

| 前端提交的 `dbPassword` | 行为 | 原因 |
|---|---|---|
| 非空且不是 `******` | `CryptoUtils.encrypt` 后覆盖 | 用户确实改了密码 |
| 等于 `******` | **不覆盖**，沿用库里原密文 | 用户只是编辑名称/URL 等其它字段，表单回显的就是掩码，若直接存密文串会把真实密码冲掉 |
| 空/未传 且库里原值为 null | 抛 1001「请填写数据源密码」 | 新建数据源必须给密码；更新时若原本已有密码则允许留空（沿用原值） |

#### 2.2.3 `validateReadOnlySql` 的五道只读闸门

| 闸门 | 行号 | 手段 | 拦住的典型输入 |
|---|---|---|---|
| ① 去尾分号 | 340-343 | `while (s.endsWith(";")) s = s.substring(...).trim()` | `SELECT * FROM t;`（正常用户习惯，直接放行） |
| ② 单条语句 | 344-346 | 残留 `;` 即拒绝 | `SELECT 1; DROP TABLE x`（ACCEPTANCE 1.4.11） |
| ③ 必须 SELECT/WITH | 347-349 | 正则 `^\s*(select\|with)\b` | `DELETE FROM indicator`、`UPDATE ...`（ACCEPTANCE 1.4.10） |
| ④ 关键字黑名单 | 350-357 | 对整条 SQL 小写后按词边界匹配 12 个写操作关键字 | `WITH x AS (...) INSERT ...`（CTE 包装的写操作） |
| ⑤ 禁止注释 | 358-361 | 出现 `--` 或 `/*` 即拒绝 | 用注释拼接/隐藏语句的注入变形 |

**为什么白名单 + 黑名单双重**：两者防的攻击面不同，互补而非冗余。

- 只做黑名单（关键字）：无法表达「我只要你做查询」这一意图，`SELECT ... INTO OUTFILE`、`SELECT ... FOR UPDATE`、
  以及各种存储过程调用（若未列入关键字）都可能漏过。
- 只做白名单（必须 SELECT 开头）：挡不住「先 SELECT 再顺手写」的复合语句与注释注入，也无法限制 CTE 里的写操作。
- 组合后形成**正向意图（只查）+ 负向禁区（不写）+ 结构约束（单条、无注释）**的三层收口，再叠加
  「只读账号 + `setReadOnly(true)` + 超时 + 行数上限」，构成方案 9.1 要求的纵深防护。
- 边界说明：正则与关键字匹配都是**文本级**防护，不是 SQL 解析器；关键字列表可在
  `ees.datasource-connector.forbidden-keywords` 增补（例如甲方库特有的 `backup`、`shutdown`）。
  真正的兜底是**只读数据库账号**，文本校验只是「尽量早失败、给用户明确提示」。

#### 2.2.4 `testConnection` / `listTables` / `previewFields` 的实现与分页写法兜底

- `testConnection`：返回产品名/版本、驱动名/版本、实际 URL、`conn.isReadOnly()`、耗时，并把结果与时间写回
  `data_source.status / last_test_result / last_test_at`，用户在列表页就能看到「最后测试是否通过」。
- `listTables`：优先按 `catalog + schema` 精确查，查空则放宽到 `(null, null, "%")` 全库查；结果去重（`LinkedHashSet`）
  后按名排序。这是为「驱动不报告 schema」或「schema 名与用户填的不一致」准备的兜底，避免出现空列表。
- `previewFields`：先取列元数据，再取**一行样例值**。取样例值的 SQL 按库分流：

| 库类型 | 写法 | 原因 |
|---|---|---|
| 默认（MySQL/PostgreSQL/金仓等） | `SELECT * FROM t LIMIT 1` | 标准且高效 |
| `ORACLE`、`DM`（达梦） | `SELECT * FROM t WHERE ROWNUM <= 1` | Oracle 语法无 `LIMIT`；达梦兼容 Oracle 语法 |
| `SQLSERVER` | `SELECT TOP 1 * FROM t` | SQL Server 语法无 `LIMIT` |

  三种写法都只需「取到第一行即可」，故不追求统一分页语义。样例值读取失败（权限不足、表锁、转换异常）
  只记 `log.debug`，不影响列清单返回。

#### 2.2.5 `extract` 的 `setQueryTimeout` / `setMaxRows` / 截断标记与审计意义

- `ps.setQueryTimeout(ees.datasource-connector.query-timeout-seconds)`（默认 120s）：**服务器端**超时，
  防止一条慢 SQL 长时间占用生产库连接与线程。
- `ps.setMaxRows(maxRows + 1)`（`maxRows` 取数据源自身配置，缺省 200000）：JDBC 层截断，**多取一行**用于
  判断「是否还有更多数据」；循环里 `count >= maxRows` 时 `truncated = 1; break;`。
- `ps.setFetchSize(1000)` + `TYPE_FORWARD_ONLY` / `CONCUR_READ_ONLY`：流式只读游标，避免一次性把结果集
  全部拉进内存（MySQL 需配合流式特性，此处至少保证语义只读）。
- `truncated` 的**审计意义**：响应里同时给出 `truncated: true` 与 `maxRows`，明确告诉用户「本次批次不是全量数据」。
  若没有这个标记，用户会以为评估覆盖了全部样本，而实际上只评估了前 N 行——这属于「结果可信度」问题，不只是
  接口细节。抽取完成后 `log.info` 记录数据源代码、批次号与行数；正式的**审计留痕**由 `config/AuditFilter`
  对 `POST /api/data-sources/{id}/extract` 记录（模块 `DATASOURCE`，含操作者、耗时、成功与否，请求体中还带 `querySql`），
  实现方案 9.1「抽取过程写入审计」。

**易错点/注意**：
1. `open()` 里的 `conn.setReadOnly(true)` 是**提示性**的：MySQL 驱动会把它转成 `SET SESSION TRANSACTION READ ONLY`，
   而部分驱动只是设置标志位。真正保证不写库的是**只读账号权限**，代码里 `DataSourceEntity.readOnly` 字段也仅作记录。
2. `validateReadOnlySql` 会把 `--` 当作注释拒绝，因此**任何包含双减号的合法 SQL 也会被拒**（例如字符串常量里的
   `'--备注'`）。这是保守策略的代价，遇到时必须改写 SQL（如用 `concat` 拼串）。
3. 关键字是「按词边界匹配整条 SQL 小写文本」，若表名/列名恰好叫 `delete_flag`，包含 `delete` 但词边界不成立
   （`delete_flag` 中 `delete` 后面是 `_`，`\b` 不匹配），可正常通过；但表名 `create`（真名）会被误杀。
4. `extract` 方法标注 `@Transactional`，而其中包含**长耗时的外部 IO**（连接与查询）。事务期间占用数据库连接
   （本项目是 MySQL 应用库连接）会拉长事务时间，高并发下应把它拆成「查询 + 事务性入库」两段。

#### 2.3.1 生成快照的完整流程与「同对象同指标取时间最新一条」

```
批次（必须非 FAILED）
 → 版本解析（显式 or 批次绑定）
 → 有效原始记录读入
 → 去重：对象 → 指标 → 保留 dataTime 最新的一条（重复条数计数）
 → 取叶子指标（按 sortOrder 排序）
 → 构造 AlgorithmRequest.IndicatorMeta / ObjectData
 → effectiveRanges 求标准化上下界
 → 对象 × 指标 笛卡尔积生成 snapshot_value
    ├─ 缺数据 → missing=true
    └─ 有数据 → normalize → 越界则 outlier=true
 → 分片 saveAll
 → 回写 checksum / dataRange / qualityReport
 → 批次置 SNAPSHOTTED
```

去重策略的取舍：同一对象同一指标在同一批次里出现多次，常见原因是「多次测量」或「重复导入」。快照是
**评估输入**，一次评估只能用一条值，因此必须给出确定性规则。取「时间最新」符合试验数据的直觉（最新一次测点
代表当前状态），并把被丢弃的条数记进 `duplicateResolved`，使「丢了几条」可核查；旧记录替换逻辑对
`dataTime` 为 null 的记录采取「后到者赢」的兜底，避免无时间数据把有时间的值挤掉又说不清顺序。

#### 2.3.2 为什么复用 `ScoringSupport.effectiveRanges` + `MathSupport.normalize`

- 同一个值可能在两处出现：①快照预览/结果页展示的 `normalizedValue`；②算法内部计算 `contribution` 用的
  标准化值。若用两套实现，任何边界细节（区间型指标的越界折算、`span` 为 0 时返回 1、`direction` 为空默认
  按 `POSITIVE`）都可能不一致，出现「表格里 0.6917、算法里用了 0.6850」的验收事故（ACCEPTANCE 1.5.3 / 1.7.13）。
- 复用同一个静态方法 + 同一份 `ranges` 后，**展示值 = 计算值**在构造上成立，而不是靠约定维持。
- `effectiveRanges` 的语义（`ScoringSupport` 第 26-59 行）：指标定义里同时给了 `minValue`/`maxValue` 就用定义值
  （`derivedFromData = false`）；否则用**本批数据的实际最小/最大值**派生（`derivedFromData = true`）；两者都没有时
  退化为 `[0,1]`。把它写进快照质量报告，用户才能判断「这次评估的标准化基准是定义值还是本批数据派生值」。
- 注意 `MathSupport.normalize` 的方向语义：`NEGATIVE → (hi - value) / span`，`INTERVAL →` 区间内 1、区间外按
  到最近的边界距离线性衰减，结果统一钳制到 [0,1]；这正是验收 1.5.3 里 A11（负向 0~60）算出 0.6917 的依据。

#### 2.3.3 `checksum`（SHA256）的构造与用途、`normalizationRanges` 的留痕价值

- 构造（第 276-277、293 行）：对**每个有原始值的单元格**生成一行
  `对象编码|指标编码|原始值(PlainString)`，按对象（`LinkedHashMap` 插入顺序）与指标（`sortOrder`）稳定排序后
  `\n` 连接，整体做 SHA-256，十六进制小写存储于 `data_snapshot.checksum`。
- 设计要点：①只纳入**原始值**，不纳入标准化值——标准化值可由原始值 + `normalizationRanges` 复算，纳入反而
  会让「同一份原始数据、不同算法范围」产生不同指纹；②顺序稳定，使同一份数据重复生成快照得到相同指纹；
  ③`missing` 的格子不参与（缺失不是值）。
- 用途：①**完整性校验**：事后若有怀疑，重算指纹即可判断 `snapshot_value` 是否被改动过（快照不可变的证据）；
  ②**可复算性声明**：报告中「数据快照 <编号>」可与指纹一起构成「这份结果基于哪份数据」的强标识。
- `normalizationRanges`（第 305 行）：把当次生效的 `code → {min, max, derivedFromData}` 写进质量报告。
  价值在于**可追溯性与可解释性**：`derivedFromData = true` 意味着上下界来自本批数据（换一批数据同一原始值的
  标准化值就会变），评估结论必须连同这批数据的范围一起解释；仅凭 `normalizedValue` 无法看出这一点。

#### 2.3.4 分批 `saveAll`、`markUsed` 与「已被任务使用的快照不可删除」

- 分批 1000（第 283-286 行）：单个快照值行数 = 对象数 × 叶子指标数（如 200 对象 × 60 指标 = 12000 行）。
  一次性 `saveAll` 会：①JPA 一级缓存堆积 12000 个实体，内存与脏检查开销大；②生成一条超长 `INSERT` 语句，
  受 `max_allowed_packet` 限制；③事务回滚代价高。按 1000 分片能把每条 SQL 控制在合理长度，也让日志与
  异常定位更清楚。
- `markUsed`（第 340-347 行）：只在**任务执行成功**时调用（`TaskService` 第 354 行），因此 `USED` 的语义是
  「已产出结果、必须长期保留以支撑历史追溯」。`usedCount` 支持「同一快照被多个任务复用」（评价同一批数据
  用不同算法/参数对比）。
- 「已被任务使用的快照不可删除」（第 333-335 行）：`evaluation_result.snapshot_code` 是字符串引用而非外键，
  如果允许删除快照，历史结果就会指向一个查不到的快照编号，方案 5.4 的可追溯链断裂。因此用状态而非外键来
  维持这条不变量：**有结果 → 快照必须存在**。
- 为什么生成快照前要拒绝 `FAILED` 批次：`FAILED` 表示存在必填字段缺失、缺失值（策略 BLOCK）、指标未覆盖或
  方向未确认等**阻断级**问题；这类数据一旦固化，后续所有任务都会带着「已知不可信」的输入跑出看似正常的分数。
  在入口拒绝，比在结果页加免责声明更可靠。注意校验发生在 `SnapshotService` 而不是靠调用方自觉，属于
  「在服务层重述不变量」的防御式写法。**这一处也顺带承担了快照生成的项目权限校验**：第 119 行的
  `batchService.get(batchId)` 本身就会对批次所属项目 `checkVisible`（见 2.4.9），越权时在生成快照之前就已 403。

**易错点/注意**：
1. `createFromBatch` 里被丢弃的重复记录**只计数不留明细**（第 151 行），用户无法在快照页看到「哪几条被覆盖了」；
   需要定位时必须回到批次的原始记录与错误明细里去比对。
2. 快照的 `objectCount` 来自 `objects`（有有效记录的对象数），而 `indicatorCount` 来自 `metas`（叶子指标数），
   因此 `recordCount = objectCount × indicatorCount` 恒成立（笛卡尔积）；若某对象在数据里从未出现，它**不会**
   出现在快照中（缺整行而非缺格子），这是「对象集合由数据决定」的正常语义。
3. `overview` 的 `missingCount/outlierCount` 用实时 `count` 查询，而快照头里的 `missingCount` 是生成时快照；
   两者理论一致，若有人手工改过 `snapshot_value` 才会不一致（此时以实时值为准并结合 `checksum` 判断）。
4. `get` 用 `findById`（无 `deleted` 过滤），与其它服务（`findByIdAndDeletedFalse`）写法不同；`data_snapshot`
   表若将来加入逻辑删除字段，这里需要同步修改，否则会读到已删快照。注意 `get` 现在**同时承担数据权限闸门**
   （第 88-89 行 `checkVisible`），因此「查不到」仍是 1004、「查得到但不可见」是 403，两者的错误码不要混淆。

### 2.4 `backend/src/main/java/com/ees/service/TaskService.java`

**作用**：评估任务的**全生命周期**服务（方案 4.5 / 8.3）：创建（输入校验链）→ 异步执行 → 状态机与状态历史
→ 快照+指标体系+参数装配算法请求 → 结果与明细落库（含并列名次）→ AHP 一致性留痕 → 取消 / 重试。
同时它是**任务级数据权限**的集中点：列表按可见项目取交集，`get` 兼作全类详情闸门（详情、状态、状态历史、
取消、重试都走它），因此越权按 id 直读任务在入口即 403（提交 `e295085`，见 2.4.9）。

**被谁使用**：`controller/TaskController`（分页、recent、创建、详情、status、history、cancel、retry）；
`ResultService`（`taskRepository` 直连仓储，不注入本服务）；`ReportService`（同样直连仓储取任务）。

**关键设计点**：
1. **异步执行 + 独立事务**（`@Async("evaluationExecutor")` + `execute` 的 `REQUIRES_NEW`）：算法可能跑几十秒，
   不能让 HTTP 请求等待；而失败状态必须**独立提交**才能落库，见 2.4.2。
2. **快照 → 算法的桥** `buildRequest`：把 `snapshot_value`（已是标准化输入）与叶子指标元数据装配成
   `AlgorithmRequest`，缺失值进 `missingIndicators` 而不是丢弃，见 2.4.4。
3. **结果可追溯**：`extra` 补算法版本与任务号、`task_status_history` 记前后状态与操作者、
   `ahp_consistency` 存矩阵/特征向量/λmax/CI/RI/CR，对应方案 5.4 与验收 1.6.7 / 1.8.3 / 2.10。
4. **列表取交集、按 id 直读 403**（提交 `e295085`）：`search` 把 `visibleProjectIds()` 作为 `projectId in :ids`
   与请求参数取交集（不可见项目 → 空页而不是错误页）；`get(id)` 在 `findByIdAndDeletedFalse` 命中之后再
   `checkVisible(task.getProjectId())`，越权直接 403。因为 `detail`/`status`/`history`/`cancel`/`retry`/`execute`
   全都经由 `get` 或直接调仓储，这一处校验把任务侧几乎所有按 id 的读取都覆盖了（策略与实测见 2.4.9）。

#### 2.4.2 `@Async("evaluationExecutor")` 异步执行与 `REQUIRES_NEW` 的原因

- `executeAsync` 只做「调用 execute + 兜底日志」，真正的业务在 `execute`；`@Async` 让调用方（HTTP 请求线程）
  立即返回 `taskId`，前端轮询 `/status` 观察进度（验收 1.6.9「异步不阻塞」）。线程池
  `evaluationExecutor` 由 `AsyncConfig` 定义：核心线程 = `max(2, ees.algorithm.max-concurrent-tasks)`，
  最大线程 = 2×核心，队列 500，关闭时等待 60 秒（避免服务停机把正在跑的任务腰斩）。
- `execute` 上的 `@Transactional(propagation = REQUIRES_NEW)` 是必须的：
  1. 它运行在**另一个线程**，没有调用方事务可继承，默认 `REQUIRED` 等于新开事务，但语义上显式声明更清楚；
  2. 更关键的是**失败也必须落库**：`execute` 内部 catch 住异常后写 `FAILED` 状态、错误码、耗时。如果这些写操作
     与「算法计算」共享一个会被回滚的事务，一旦最后一步抛异常，失败状态就随之回滚，任务会永远停在 `RUNNING`。
     `REQUIRES_NEW` 让状态更新在独立事务中提交，只有「本段代码的异常」才会回滚本段。
  3. 另有一个附带好处：`transition` 自身也标注了 `@Transactional`，独立事务避免长事务（算法计算期间）持有
     数据库连接。
- 代价与风险：`create` 是 `@Transactional` 的方法，其中第 241 行就发起了异步执行——异步线程可能在**主事务提交前**
  查 `taskRepository.findById(taskId)`，此时读不到该任务，`execute` 会在第 293-296 行静默返回。见易错点 1。

#### 2.4.3 `transition` 状态机与 `task_status_history` 的写入

- 状态集合（API.md §6）：`DRAFT / VALIDATING / QUEUED / RUNNING / SUCCESS / FAILED / CANCELED / TIMEOUT /
  PENDING_REVIEW / PUBLISHED / ARCHIVED`。本服务负责其中除「复核/发布」（`ResultService` 负责）与 `TIMEOUT`
  （超时由配置 `task-timeout-seconds` 约定，本类未实现定时超时判定）之外的全部迁移。
- 典型路径：
  - 成功：`DRAFT → VALIDATING → QUEUED → RUNNING → SUCCESS`（并触发快照 `USED`）；
  - 算法失败：`… → RUNNING → FAILED`（错误码来自算法，如 4003）；
  - 排队中取消：`QUEUED → CANCELED`（`execute` 入口消费标志位）；
  - 运行中取消：`RUNNING → CANCELED`（算法返回后、落库前消费标志位）；
  - 重试：新任务 `QUEUED → RUNNING → …`，原任务不动。
- `transition` 的三条规则：①同状态幂等（`from.equals(to)` 直接返回，不写历史）；②先改实体并 `save` 再写历史，
  保证历史里 `task_id` 有效；③每条历史都带 `fromStatus/toStatus/reason/operator/operatorId`，
  满足验收 1.6.7。注意 `operator` 有 `"system"`（异步执行）与真实用户名（创建/取消/重试）两种取值。

```
 + indicatorService.indicators(versionId) → 叶子指标（sortOrder 升序）→ IndicatorMeta[]
 + snapshot_value（按对象编码、指标编码升序）
      ├─ missing 或 rawValue 为空 → ObjectData.missingIndicators
      └─ 有值                    → ObjectData.values[原始值]
 = AlgorithmRequest（统一输入契约，附录 B.1）
```

- 三部分来源清晰分责：**指标元数据**决定标准化方向/上下界/权重；**快照值**提供原始数据；**任务参数**提供算法
  专属输入（AHP 矩阵、模糊评语集、组合流程）。
- `inputRef` 只放 `snapshotId`（快照编号），因为完整输入摘要已单独存在 `task.inputSummary` 里，避免输入对象过重。
- 关键取舍：`ObjectData.values` 传的是**原始值**，标准化交给算法内部的 `ScoringSupport`/`MathSupport`。
  快照里那份 `normalizedValue` 是「展示用同源副本」（2.3.2），两者不会互相污染。
- `allowForceOnCrFail` 的三层取值：任务参数 → 系统参数 `algorithm.allow.force`（默认 false）→ 硬默认 false。
  默认 false 意味着 CR 超限直接失败（方案 6.2、验收 1.6.5）。

#### 2.4.5 `saveResults` 的排序、并列名次与两次落库

- 排序：按 `totalScore` 降序，`null` 视为 -1（排最后），用副本排序不改变算法返回对象。
- 并列名次：`rank` 仅在分数与前一元素差异 > 1e-9 时推进到 `i + 1`，得到标准竞赛排名（1,2,2,4）。
  容差 1e-9 是为了让「数学上相等但因浮点尾差不同」的两条结果被判为并列。
  若算法自己给了 `ranking`，优先用算法的（第 485 行 `or.getRanking() == null ? rank : or.getRanking()`）。
- 两次落库：先 `resultRepository.save(er)` 拿到 `evaluation_result.id`，再用它作为 `result_detail.result_id`
  批量 `saveAll`。明细内含 15 个字段（指标编码/名称/层级/父编码/单位/方向/原始值/标准化值/权重/贡献值/得分/
  单指标等级/`rankNo`/备注），是结果表格与八类图形的**唯一数据源**。
- `extra` 的两处补充（第 481-484 行）：合并算法对象级 `extra` 后补 `algorithmVersion` 与 `taskCode`，
  使结果页与导出文件即使不 join 任务表也能显示算法版本（验收 2.10）与任务编号。
- `warnings` 用 `mergeWarnings` 合并对象级与结果级告警；`reviewed="NONE"`、`publishStatus="DRAFT"` 是复核/发布
  状态机的起点。

#### 2.4.6 `saveConsistency` / `extractConsistency` 如何捞出 AHP 一致性记录

- **直接执行**（`algorithm = AHP`）：算法把一致性检验结果放在 `AlgorithmResult.extra.consistency`（List<Map>），
  `extractConsistency` 第 556-557 行直接返回。
- **组合流程**（`algorithm = COMBO`）：`extra.stages` 是「阶段名 → 阶段 `AlgorithmResult`」的 Map，AHP 阶段的一致性
  记录嵌在阶段结果的 `extra.consistency` 里；第 559-566 行遍历 `stages.values()`，找到第一个含 `consistency` 的
  阶段结果并返回。
- 多层级 AHP（`parameters.nodes`）会输出**多条**一致性记录（每个判断矩阵一条），因此整条链路都是 `List` 语义；
  落库时逐条写 `ahp_consistency`，任务详情接口 `detail()` 也返回列表（验收 1.8.3 的「AHP 中间结果」）。
- 通过与否：`passed` 布尔直接落库，未通过时补一条中文 `warning`，前端可以只展示「未通过的矩阵」提醒用户修正。

#### 2.4.7 `cancel` 的 `cancelFlags` 机制与 `retry` 生成新执行实例

- `cancelFlags` 是 `ConcurrentHashMap<Long, Boolean>`：`cancel` 只做 `put`（不动状态？“先 put 再 transition”），
  真正消费（`remove`）发生在 `execute` 的两个检查点（第 297、318 行）。
  这样设计的原因是：取消请求来自 HTTP 线程，而任务正在异步线程里跑，**无法直接中断**（Java 线程中断对算法
  代码不安全），因此采用「协作式取消 + 检查点」：算法自然返回后检查标志，若已取消则不写结果、直接落
  `CANCELED`。
- 检查点在「结果落库之前」，保证不会出现「用户看到已取消、结果却写进了库」的半成品状态。
- 局限：①在内存中，多实例部署时取消只在处理请求的节点生效（本项目为单机私有化部署，可接受）；
  ②任务若因线程池排队而长期未执行，标志位会驻留内存（键为任务 ID，量级很小）；③算法内部不可打断，
  长任务取消后仍需等算法算完才回到检查点。
- `retry` 生成**新执行实例**：新 `taskCode`、`retryOf` 指向原任务主键、`retryCount` 递增、任务名后缀「（重试）」，
  输入字段全部复制。好处是：①原任务的失败原因、错误码、耗时、状态历史完整保留（复盘依据）；
  ②新任务有独立的 `evaluation_result` 记录，任务与结果始终一对一，不会出现「同一任务号两批结果」。
  `retry` 直接以 `QUEUED` 起步（跳过 `VALIDATING`），因为输入在原任务创建时已校验过、快照未变。

#### 2.4.8 `validateParameters` 对四种算法参数的预校验

| 算法 | 必须提供的参数 | 缺省行为 | 行号 |
|---|---|---|---|
| `AHP` | `matrix` + `criteria`，或 `nodes`（多层） | 都没有则抛 4004；`allowForceOnCrFail` 可选 | 255-260 |
| `FUZZY` | 无 | `gradeNames`/`gradeScores`/`operator` 全用系统默认（`M_PLUS`） | 261-263 |
| `WEIGHTED` | 无 | 阈值默认 90/80/60/0，权重来自指标体系 | 274-276 |
| `COMBO` | `comboFlow` 缺省补 `["AHP","WEIGHTED"]`；因默认含 AHP，仍必须给 `matrix` 或 `nodes` | 缺矩阵抛 4004 | 264-273 |

设计意图：**把「一定失败」的输入挡在排队之前**。异步执行的好处是页面不卡，但如果参数明显非法还放进队列，
用户会先看到「已排队/运行中」再看到失败，体验与排查成本都更差。

**易错点/注意**：
1. **`create` 的异步竞态**：`create` 带 `@Transactional`，第 241 行在事务**提交前**就调用 `executeAsync`。
   若异步线程抢在主事务提交前执行 `findById(taskId)`，`execute` 第 294-296 行会因查不到任务而**静默返回**，
   任务将永久停留在 `QUEUED`（无历史、无错误）。稳妥做法是注册事务同步回调（`TransactionSynchronizationManager`
   的 `afterCommit`）或在 `create` 返回后再触发；当前实现依赖「异步线程启动 + 连接获取 + 查询」通常慢于
   本方法剩余几行代码提交事务，属于概率性风险（验收 1.6.1 正常路径不易触发）。
2. **`retry` 不写状态历史**：第 616 行的 `transition(task,"QUEUED", "由任务 X 重试生成新执行实例")` 因
   `task.getStatus()` 已是 `QUEUED` 而被「同状态幂等」短路（第 630-632 行），该说明性历史**不会落库**。
   结果是重试任务的 `task_status_history` 首条记录是 `execute` 里的 `QUEUED → RUNNING`，缺少「由谁重试、
   从哪个任务来」的信息（`retryOf` 字段仍在任务表上，信息未丢失）。
3. `create` 未回填 `task.projectName`（第 197-216 行只设了 `projectCode`），于是 `saveResults` 里
   `er.setProjectName(task.getProjectName())` 写的是 `null`，`evaluation_result.project_name` 为空。
   导出报告与结果追溯用的是 `ProjectService.get()` 拿到的项目实体名称，所以界面不受影响；但若将来有页面
   直接读 `evaluation_result.project_name` 展示，会是空白。
4. `TIMEOUT` 状态在状态集合里存在（`retry` 允许重试超时任务），但本类**没有超时判定逻辑**：
   `ees.algorithm.task-timeout-seconds`（默认 900）未在此使用，超时任务需要由外部手段（如 C++ 引擎返回超时
   错误码 5002）产生。
5. `SecurityUtils` 是未使用的导入（第 28 行），本类通过方法参数接收 `operator`/`operatorId`，因此不需要从
   安全上下文取；`container` 里若开启 `-Werror` 类检查需要清理。数据权限走的是 `ProjectService`（它自己用
   `SecurityUtils.require()` 取当前用户），所以本类不需要直接持有 `LoginUser`。
6. **不要在异步线程里调 `visibleProjectIds()` / `checkVisible()`**：这两个方法依赖 `SecurityUtils.require()`
   读取 `SecurityContext`，而 `executeAsync` 跑在 `ees-eval-` 线程池里、没有请求上下文。因此数据权限必须在
   `create`（HTTP 线程）阶段校验完毕，`execute` 内部只用直连仓储的 `findById`——这不是漏校验，而是刻意的分层，
   见 2.4.9。

#### 2.4.9 数据权限（本册四个服务共同改动）：列表取交集、按 id 直读 403（提交 `e295085`）

> 本节是本册 4 个服务（`DataBatchService` / `SnapshotService` / `TaskService` / `ResultService`）共同的数据权限改动汇总，
> 其中任务与结果两处是本次实测发现问题的直接来源；各文件的逐行落点见 2.1、2.1.10、2.3、2.5 各节。

**修复前的问题**（承接 2.7.5：上一轮 `747fec4` 只修了驾驶舱统计）：**列表接口与按 id 直读都没有按数据权限过滤**。
实测一个**可见项目为 0** 的评估人员账号（`dataScope = PROJECT`，项目成员表里没有任何项目、也不是任何项目负责人）：

| 接口 | 修复前 | 修复后 |
|---|---|---|
| `GET /api/evaluation-tasks` | 15 条（全库） | **0 条** |
| `GET /api/evaluation-results` | 48 条（全库） | **0 条** |
| `GET /api/data-batches` | 6 条（全库） | **0 条** |
| `GET /api/snapshots` | 6 条（全库） | **0 条** |
| 任务详情 / 结果详情 / 批次记录（按 id 直读） | 200（返回别人的数据） | **403「无权访问该项目」** |
| 管理员（对照） | 15 / 48 | 15 / 48（**不受影响**） |

**两条策略**（这是本节最需要记住的部分）：

1. **列表查询用「取交集」——传了不可见的 `projectId` 返回空列表，而不是报错。**
   4 个 `search` 都是同一个写法（`DataBatchService` 第 81-93 行、`SnapshotService` 第 72-82 行、
   `TaskService` 第 105-119 行、`ResultService` 第 59-71 行）：

   ```java
   List<Long> ids = projectService.visibleProjectIds();   // null = 不限制（管理员 / ALL）
   if (ids != null && ids.isEmpty()) {                    // 无可见项目 → 空集合不能进 in ()
       return PageResult.empty(page, size);
   }
   Page<...> p = repository.search(projectId, ids, ...);  // 请求条件 与 可见集合 取交集
   ```

   仓储里是 `and (:ids is null or t.projectId in :ids)`，与请求自带的 `(:projectId is null or t.projectId = :projectId)`
   是 **and 关系，即交集**。这样做而不是抛 403 的原因是**前端会把 `localStorage['ees_project_id']` 里的项目 id
   一直带给请求**——如果换成报错，用户切到「项目已被删除 / 无权访问」的历史上下文时，整个列表页会变成错误页
   而无法自救（页面上没有「清掉这个项目」的入口）；返回空列表则页面正常显示「暂无数据」，用户换个项目筛选即可。
2. **按 id 直读直接 403——这才是明确的越权。**
   `get` 与新增的 `requireXxxVisible` 守卫在「记录确实存在」之后调用 `projectService.checkVisible(所属项目)`，
   不可见即 `BizException(FORBIDDEN, "无权访问该项目")` → HTTP 403：

   | 服务 | 守卫 | 覆盖的入口 |
   |---|---|---|
   | `TaskService` | `get` 内联校验（第 126 行） | 详情、状态、状态历史、取消、重试（都经由 `get`） |
   | `ResultService` | `requireTaskVisible`（第 94-102 行，注释里写明「任务不存在时不在这里报错」）/ `requireResultVisible`（第 105-110 行） | `get`、`byTask`、`details`、`buildAllCharts`、8 个图表、`compare`、`exportPayload`（共 14 个方法、15 处调用；`fullView`/`textView` 经 `get` 与 `buildAllCharts` 间接受控） |
   | `DataBatchService` | `requireBatchVisible`（第 104-111 行） | 记录、错误明细、质量报告、重新校验、删除 |
   | `SnapshotService` | `requireSnapshotVisible`（第 93-100 行） | 指标值、数量、概览、删除、标记已用 |

   **顺序很重要：先查「是否存在」，再判「是否可见」。**
   任务是「不存在」时仍走原有的 1004「评估任务不存在」，**不报 403**——如果一律 403，就会把「这个 id 根本不存在」
   和「存在但你无权看」混为一谈，既让排查困难，也等于用错误码泄露了「该 id 是否存在」。`ResultService.requireTaskVisible`
   的 Javadoc 把这条原则写在源码里：「任务不存在时不在这里报错，交给调用方原有的『查不到结果』逻辑处理，
   避免把『任务不存在』与『无权访问』混为一谈。」守卫用 `ifPresent(...)` 而不是 `orElseThrow`，正是这个意思。
3. **写入侧同样收口**：`DataBatchService.importFile`（第 153-156 行）与 `createBatchFromRows`（第 239-242 行）
   在 `projectId != null` 时 `checkVisible(projectId)`——只能把数据导进自己可见的项目；`TaskService.create`
   第 171 行、`SnapshotService.createFromBatch` 第 119 行（经 `batchService.get`）同理。**列表过滤防「看」，
   这些检查防「写」，两者缺一不可。**

**实现要点与代价**：

- 四个服务里有**两个**需要新增依赖：`DataBatchService` 7→8 个、`SnapshotService` 6→7 个，新增的都是 `ProjectService`；
  `ResultService` 与 `TaskService` 早已注入 `ProjectService`（前者用于 `exportPayload` 取项目与 `compare`，
  后者用于 `create` 的可见性校验），本次只是把它的用途扩展到守卫，因此构造器没变。本册的行数增长
  （+118）全部来自这些校验与守卫，没有其它逻辑改动。
- 守卫都会**先查一次实体**再判可见性，等于每个按 id 的接口多一次主键查询。这是刻意的取舍：数据权限是安全属性，
  宁可多一次按主键查询，也不要把 `projectId` 从请求里取来直接信任（那正是修复前的缺陷）。
- `checkVisible` 内部是 `visibleProjectIds()` + `contains(projectId)`：**管理员 / `dataScope = ALL` 时返回 `null`，
  直接放行**，因此管理员的实测结果与修复前完全一致（15 / 48 不变）。
- 全库级能力（用户数、可用算法）不在项目范围内，本册 4 个服务没有、也不应该把它们纳入过滤；
  「公共指标体系版本」的可见性规则属 05 分册的 `IndicatorService`（同一提交 `e295085` 一并修复），
  这里不重复说明。

#### 2.5.1 `fullView` 一次返回文本 + 表格 + 图形 + 追溯

`fullView` 是结果分析页的主接口（`GET /api/evaluation-results/{id}`），一次组装七块数据：

| 键 | 来源 | 用途 |
|---|---|---|
| `result` | `get(resultId)` | 结果头（得分、等级、排名、向量、权重、贡献值、extra） |

| `parsedVector[]` | `parseDoubleList(r.getVector())` | 模糊综合评判向量的数值数组 |
| `weights{}` / `contributions{}` | `JsonUtils.toMap` | 指标权重与贡献值字典 |

`get(resultId)` 校验结果所属项目可见（越权 403），第 151 行 `buildAllCharts(taskId, resultId, projectId)`

#### 2.5.2 `buildTextConclusion` 的结论生成、薄弱/优势取法与 `buildImprovements` 排序依据

- **结论模板**：`被评估对象 <编码>（<名称>）采用 <算法中文名> 评估，综合得分 <2位小数>，评判等级为"<等级>"。
  在本次任务的 <N> 个被评估对象中排名第 <R> 位。`
  — 信息密度由高到低：对象 → 算法 → 分数 → 等级 → 相对位置。等级用中文引号包裹，导出 Word/PDF 时排版清晰。
- **薄弱指标**（前 3）：按 `contribution` **升序**，跳过 `contribution <= 0`。
- **优势指标**（前 3）：按 `contribution` **降序**。
- 为什么用贡献值：`contribution = 权重 × 标准化得分`（由算法输出）。单纯看低分会把「权重 0.02 的无关指标」
  误报为薄弱项；单纯看权重会把「高分的重要指标」误报为薄弱项。贡献值把两者合成一个可直接排序的量。
- **改进建议排序**：`weight × (100 − score)` 降序取前 5。该式是「若把该指标提升到满分，综合得分最多能涨多少」
  的一阶近似（提升空间 × 影响力），因此排在最前的就是「性价比最高」的改进方向。阈值 `score < 80` 与默认
  等级阈值中「良 = 80」对齐，即只对未达良好水平的指标给建议。

#### 2.5.4 八类图形逐个讲

**① `barChart` 柱状图**

- 数据来源：`result_detail`（某一结果的指标明细；无 `resultId` 时取任务下最优结果的明细）。
- 结构：`categories[]` = `指标名(编码)`（按得分降序）；`series` = 三条 `type:"bar"`，分别是「得分」「贡献值」「权重」；
  另有 `sortable: true`。
- 为什么这样算：柱状图要在**同一横轴上对比三类量纲不同的数值**（得分 0~100、贡献值 0~1、权重 0~1），
  因此三条 series 共用 categories 但各自由前端决定是否显示；按得分为降序是用户最常问的「哪项最差」的直觉顺序。
  `round(...,4)` 保证与表格数值逐位一致（验收 1.7.13 对比的就是这个值）。

**② `lineChart` 折线图**

- 数据来源：`evaluation_result` 按**项目 + 对象编码**过滤出的历史结果（同对象跨任务/跨批次）。
- 结构：`categories[]` = 任务编号；`series` = 一条折线（名称 `"<对象> 综合得分"` 或 `"综合得分"`）；
  另返回 `objectCode`。
- 为什么这样算：趋势的主体是「同一个被评估对象随时间/批次的变化」，所以必须按 `objectCode` 过滤，否则会把
  不同对象混成一条线。横轴用任务编号（而不是时间）是因为同一时间可能跑多个任务，编号唯一且天然有序。
  空数据时返回 `emptyReason`「请至少完成两次评估任务」——**单点无法成趋势**，提示比空图有用。

**③ `pieChart` 饼图 / 环形图**

- 数据来源：`weightPie` 来自当前结果的全部明细权重；`levelPie` 来自同一任务下全部结果的 `level` 计数。
- 结构：`weightPie:[{name, value, percent}]`、`levelPie:[{name, value}]`、`series:[weightPie]`、`showPercent: true`。
- 为什么这样算：饼图适合展示**占比构成**，因此选了两个真正是「整体的一部分」的量：指标权重（和为 1）与
  等级分布（各等级对象数）。权重饼的 `percent` 由后端算好（`weight × 100`，2 位小数），前端不重算；
  `levelPie` 里 `level` 为 null 的归入「未评级」，避免出现无名扇区。

**④ `radarChart` 雷达图**

- 数据来源：`result_detail` 按任务查询（`findByTaskIdOrderByIdAsc`），按对象分组。
- 结构：`indicatorNames[]`、`indicatorCodes[]`（去重后按出现顺序）、`max: 100`、`series` 每个对象一条
  `{name, value[], type:"radar"}`。
- 为什么这样算：雷达图的价值是**多对象在同一组维度上的形状对比**，所以必须按任务取全部对象的明细并在
  同一指标顺序下取值。`max` 固定 100 而不是按数据自适应，是为了让不同任务的雷达图可直接视觉比较；
  指标顺序沿用明细查询顺序（指标编码升序），保证各对象的 `value[]` 与 `indicatorNames[]` 一一对应。

**⑤ `scatterChart` 散点图**

- 数据来源：任务下明细，按对象聚合成「对象 → {指标编码: 得分}」。
- 结构：`xIndicatorCode`/`yIndicatorCode`/`xIndicatorName`/`yIndicatorName`、`availableIndicators:[{code,name}]`、
  `points:[[x, y, 对象]]`、`series`。
- 为什么这样算：散点图用于观察**两项指标之间的相关性**，因此每个点是一个对象。默认取前两个指标作为轴，
  同时给出 `availableIndicators` 让前端提供轴切换下拉（API.md §7.2 明确该字段用途）。第三维用对象编码，
  悬停时显示「哪个对象落在该位置」（验收 1.7.8）。缺任一坐标的对象被跳过（`x != null && y != null`），
  不填补 0，避免伪造出「都集中在原点」的假相关。

**⑥ `heatmapChart` 热力图**

- 数据来源：任务下明细，按「指标编码 × 对象编码」聚合得分。
- 结构：`xLabels[]` = 指标编码、`yLabels[]` = 对象编码、`data:[{value:[x, y, 得分], indicatorCode, objectCode, indicatorName}]`、
  `min`、`max`。
- 为什么补 `indicatorCode`/`objectCode`：ECharts 热力的 `value` 只有坐标与数值，**前端无法从坐标反推业务含义**；
  后端额外附带两个编码（以及指标名），前端 tooltip 才能显示「对象 OBJ-003 的 A11 得分 82.5」而不是
  「(2, 5): 82.5」。同时 `min`/`max` 由后端按真实数据算出并传给 `visualMap`，避免前端重算色阶导致与表格数值
  不一致（方案 7.3）。缺失的组合补 `BigDecimal.ZERO`（笛卡尔积必须完整，否则 ECharts 会留空洞）。

**⑦ `boxplotChart` 箱线图**

- 数据来源：任务下每个指标在所有对象上的得分集合。
- 结构：`categories[]`（指标中文名）、`boxData:[[min, q1, median, q3, max]]`、`outliers:[[...]]`、
  `series`（`type:"boxplot"`，前端另叠加一层散点画离群点）。
- 为什么这样算：箱线图回答的是「这个指标在各对象上的分布是否稳定、有没有异常对象」。五分位由 `quantile`
  （第 844-859 行）计算：`pos = q × (n − 1)`，两侧取整后按小数部分**线性插值**——这是与 Excel `QUARTILE.INC`
  一致的「含端点插值」口径（`n=1` 时直接返回该值，避免除零）。离群点用 **1.5×IQR 栅栏**
  （`q1 − 1.5×IQR` / `q3 + 1.5×IQR`，Tukey 规则），这是箱线图的标准定义；`outliers` 与 `boxData` 分开返回，
  因为 ECharts 的 boxplot series 不会自动画离群点，需要前端用第二层 `scatter` 叠加。

**⑧ `rankBarChart` 排名条形图**

- 数据来源：`evaluation_result` 按任务查询（已按 `totalScore` 降序，即名次顺序）。
- 结构：`categories[]`（`对象编码 对象名称`）、`rankings[]`（结果自带的名次，含并列）、`levels[]`（评判等级）、
  `series:[{name:"综合得分", data:[...], type:"bar", rankings:[...]}]`。
- 为什么按等级着色、为什么把 `levels`/`rankings` 单独给：后端不画图，但**决定颜色与提示文案所需的分类信息
  必须由后端给出**。前端 `chartOptions.ts` 的 `rankBarOption` 用 `levels` 查 `GRADE_COLOR` 给每根柱子着色，
  用 `rankings` 在 tooltip 里显示「第 N 名」，而横向条形图自下而上绘制需要**反转数组**（对象、分数、名次、等级
  四个数组必须同时反转才能对齐）——这也是把四个数组等长并列返回的原因。名次直接取结果表的 `ranking`
  （由 `TaskService.saveResults` 的并列名次算法算出），前端不再排序，保证与结果列表顺序一致。

#### 2.5.5 为什么图形数据全部由后端算好

- 方案 7.3 与验收 1.7.13 要求「表格中 A11 的得分与柱状图中 A11 的数值完全一致」。若前端各自计算
  （例如自己按明细算权重百分比、自己求箱线图四分位），就会出现两套浮点口径（插值方式、四舍五入位数、
  缺失值处理），迟早出现不一致，且无法定位是谁的错。
- 后端统一处理带来三个确定性：①**唯一数据源**（`result_detail` / `evaluation_result`）；②**统一精度**
  （`round` 到 4 位小数，与 `score-scale` 一致）；③**统一缺失语义**（缺失补 0、数据不足给 `emptyReason`）。
- 前端职责被压缩为「把后端给的数组翻译成 ECharts option」，`frontend/src/utils/chartOptions.ts` 里没有任何
  统计计算——这是可以用代码审查确认的边界（该文件只做 axis/series/tooltip 组装与数组反转）。
- 附带好处：图形数据可以脱离浏览器复用（导出、截图、未来的报表插图），因为它是纯数据。

#### 2.5.6 `compare` 横向对比矩阵的构造

- 取数：给了 `taskId` 用该任务下全部对象结果；否则用该项目的最近 10 条结果（`findTop10ByProjectIdOrderByIdDesc`）。
- 两次遍历的原因：第一次遍历收集**指标编码全集**（`LinkedHashSet`）与每个结果的明细缓存 `detailMap`；
  第二次遍历组装行。之所以要先把编码全集收齐，是因为不同结果可能指标集不同（不同指标体系版本），
  矩阵的列必须是并集，缺的位置留空（`indicatorScores` 里没有该键）而不是补 0——补 0 会被误读为「该指标得 0 分」。
- 行的结构：`resultId/taskCode/objectCode/objectName/totalScore/level/ranking/algorithm/indicatorScores{}`，
  外层返回 `indicatorCodes[] / rows[] / count`，前端据此渲染成「对象为行、指标为列」的对比表。
- 口径提示：**`compare` 现在会做数据范围校验**（提交 `e295085`）：第 715-717 行对 `projectId` 调
  `checkVisible`，第 718 行再 `requireTaskVisible(taskId)`——即项目维度与任务维度各自校验一次，越权 403。
  这一点与修复前不同：修复前它只依赖控制器 `@PreAuthorize('result:compare'|'result:list')` 的**权限点**授权，
  知道别人的 `projectId`/`taskId` 就能对比别人的数据；现在权限点之外还叠加了项目成员范围（与 `TaskService.create`
  的显式 `checkVisible` 同口径）。`projectId` 为 null（只传 `taskId`）时由任务侧守卫兜住，反之亦然。

#### 2.5.7 `review` / `publish` / `archive` 的状态流转与任务状态联动

| 动作 | 结果状态变化 | 任务状态联动 | 行号 |
|---|---|---|---|
| `SUBMIT` 提交复核 | `reviewed = PENDING`，记录备注/审核人/时间 | `SUCCESS → PENDING_REVIEW` | 668-683 |
| `APPROVE` 通过 | `reviewed = APPROVED` | 不变 | 655-660 |
| `REJECT` 退回 | `reviewed = REJECTED`，`publishStatus = DRAFT` | 不变 | 661-667 |
| `publish` 发布 | `publishStatus = PUBLISHED` + `publishedAt/By` | 任务状态置 `PUBLISHED`（无条件） | 687-702 |
| `archive` 归档 | `publishStatus = ARCHIVED` | 不变 | 704-710 |

- 三种复核动作都在**结果表**上留痕（`reviewed/reviewComment/reviewedBy/reviewedAt`），任务表只承载
  「等待审核」这一节点，避免把审核明细塞进任务表。
- 发布的两条限制：①`REJECTED` 的结果不允许发布（必须重跑评估，避免「被退回的结论又被发布」）；
  ②发布**不会自动要求先 APPROVE**——这是当前实现的宽松点：只要不是 REJECTED 就能发布（`reviewed` 为
  `NONE` 也可发布）。若流程上要求「必须先审核通过」，需要在此处补一条前置判断。
- 发布把任务状态置为 `PUBLISHED` 时**未检查任务当前状态**（如多对象结果逐个发布，任务状态在第一次发布时就
  变成 `PUBLISHED`，之后状态不变）；`DashboardService.taskSuccess` 统计包含 `PUBLISHED`，因此统计数据不会
  因发布而丢失。
- 归档只改结果的 `publishStatus`，不动任务状态：归档是结果级的最终处置（下架到历史库），若同时改任务状态会
  影响任务列表的筛选与驾驶舱统计口径。

**易错点/注意**：
1. `buildImprovements` 的排序 lambda 直接 `(BigDecimal) b.get("weight")` 与 `(BigDecimal) b.get("score")` 强转：
   `weight` 因过滤条件 `weight > 0` 保证非空，但 **`score` 可能为 null**（`score` 只用于 `< 80` 判断，null 按 0 处理
   从而进入列表），此时 `((BigDecimal) b.get("score")).doubleValue()` 会抛 `NullPointerException`。
   触发条件：某条明细 `score = null` 且 `weight > 0`（算法未给单指标得分）。`textView` 与 `exportPayload` 之外的
   调用路径都可能踩到，建议改为 `valueOf` 风格的空值安全取值。
2. `fullView` 返回的 `text` **不含** `improvements`（那是 `textView` 独有的键）。若前端两个接口混用，切换标签时会
   出现「改进建议时有时无」，需要按接口文档使用。
3. `SecurityUtils` 是未使用的导入（第 13 行）；`nullToEmpty`（第 873-875 行）是未被任何代码引用的私有方法；
   `snapshotValueRepository` 依赖被注入但未使用。都属于可清理的死代码（功能无损）。
4. 各图形方法的 `emptyReason` 文案是中文且面向用户，前端**必须展示原因而不是空图**（API.md §7.2 的硬性要求）；
   新增图形时需沿用该约定，否则验收 1.7.5 类检查项会失败。
5. **新增按 id 取数的接口时，必须同时加守卫**：`requireTaskVisible` / `requireResultVisible` 是「记得调用才生效」
   的普通私有方法（不是 AOP 切面），漏掉一处就等于开了一个越权读的口子——本次修复前正是「8 个图表 + 导出载荷 +
   对比都直接查仓储」造成的。守卫清单与实测见 2.4.9。
6. 守卫会**各查一次实体**（`requireResultVisible` 查结果、`requireTaskVisible` 查任务），因此像
   `compare`（两个入参都校验）或 `fullView`（`get` + `buildAllCharts` 各校验一次）会出现同一请求内 2~3 次
   按主键查询。数据量小、收益是安全边界清晰；若将来对性能敏感，可在一次请求内缓存可见项目集合。

#### 2.6.1 `generate` 三种格式的统一入口与 `ReportRecord` 状态

- 统一入口：`generate(taskId, resultId, type, operator)`。类型先 `toUpperCase()` 再白名单校验
  （`EXCEL/WORD/PDF/JSON`，JSON 是调试用副产物）。
- 所有格式共享同一份 `payload`（来自 `ResultService.exportPayload`），所以 Excel/Word/PDF 三者内容必然一致
  （同一批 `results` 与 `detailRows`），这是验收 1.9.1~1.9.4 能够同时通过的结构性原因。
- `ReportRecord` 状态机：

| 状态 | 含义 | 何时写入 |
|---|---|---|
| `GENERATING` | 已受理、正在生成 | 第 143 行（生成动作之前） |
| `READY` | 文件已生成，可下载 | 第 172 行（写出成功并 `Files.size` 成功后） |
| `FAILED` | 生成失败，含 `errorMsg` | 第 177-178 行（任何异常） |

- 下载接口 `fileOf` 只放行 `READY` 且磁盘文件存在的记录，因此「记录状态」与「文件实体」双重把关。

#### 2.6.3 `writeWord` 用 POI XWPF 的段落/表格构造

- 文档结构：`title`（居中 22pt 加粗）→ 两行居中信息 → 四个 `heading`（13pt 加粗）小节，
  正文用 `para`（10pt）与 `XWPFTable`。
- 表格构造三要素：`doc.createTable(rows, cols)` 建表 → `setCell(table, row, col, value)` 逐格填值
  （内部用 `getRow/getCell` 并做越界与 900 字符截断保护）→ 文档末尾 `doc.write(out)`。
- 表格尺寸与列数匹配内容：任务信息 7×4（键值对布局）、综合结果 `n+1`×5、指标明细 `n+1`×8。
- 空数据分支：无结果输出「本次任务未产生评估结果。」，无明细输出「无指标明细数据。」，保证文档结构完整。
- 局限提示：Word 表格**没有分页控制**（`setTableLayout`/跨页重复表头未设置），明细行很多时表头只出现在第一页；
  这也是 PDF 侧重「版面」、Excel 侧重「全量数据」的分工原因。

#### 2.6.4 `writePdf` 的排版与中文字体解析优先级

- 排版参数：A4 + 边距 48/48/56/48；标题 18pt 加粗居中；小节标题 13pt 加粗；正文 10pt；表头淡蓝底、单元格 padding 4。
- 表格列宽用**相对权重**（`setWidths(new float[]{...})`）：任务信息 1 : 2.2（键窄值宽）、综合结果
  0.7/1.4/2.2/1.2/1（对象名称最宽）、指标明细 7 列等宽略调（对象与指标略宽）。
- **中文字体解析优先级**（第 516-545 行）：

| 优先级 | 来源 | 代码 | 特点 |
|---|---|---|---|
| ① | `ees.report.pdf-font-path` 单文件路径 | 第 518-521 行加入候选 | 运维明确指定的字体，最可控 |
| ② | `ees.report.pdf-font-search-paths` 列表 | 第 522-524 行整批加入候选 | 常见做法是列 `C:/Windows/Fonts/simsun.ttc`、`msyh.ttc` 等；逐个 `new File(p).exists()` 探测 |
| ③ | `openpdf-fonts-extra` 内置 CJK 字体 | 第 538-544 行 `createFont(pdfFontName, pdfFontEncoding, NOT_EMBEDDED)`，默认 `STSong-Light` + `UniGB-UCS2-H` | **不嵌入**（PDF 体积小），依赖阅读器自带的 Adobe CJK CMap；无外网、无系统字体时仍可显示中文 |

- `.ttc` 必须用 `",0"` 索引（第 528-530 行）：TTC 是字体集合容器，OpenPDF 需要「文件路径,子字体索引」的形式选择
  其中一个字体（`0` 即第一个，Windows 的 `simsun.ttc` 里索引 0 就是宋体）；直接传 `.ttc` 路径会因无法确定
  子字体而失败。
- 前两级命中时用 `IDENTITY_H + EMBEDDED`：Identity-H 编码 + 字体嵌入，内容自包含、任何阅读器都能正确显示，
  代价是 PDF 体积略增。
- 三级都失败时抛 1500 并明确提示「请在 `ees.report.pdf-font-path` 中指定 .ttf/.ttc 字体文件路径」——把部署
  问题指到配置项，而不是抛一个底层字体异常。

#### 2.6.5 指标明细超过 800 行时 PDF 截断的原因

- 代码（第 476-490 行）：`int limit = Math.min(detailRows.size(), 800);` 只写前 800 行，超限时追加一行提示
  「（指标明细超过 800 行，完整数据请导出 Excel 报表）」。
- 原因：①PDF 表格是**分页排版**，OpenPDF 会把长表拆到很多页，页数随行数线性增长（几千行 → 上百页），
  生成时间与内存占用都不可控；②PDF 的定位是「可打印的结论报告」，全量明细本就不是它的用途；
  ③Excel 天然适合全量明细（三个工作表 + 冻结表头 + 数值可再计算）。
- 工程取舍：**明确截断并告知替代方案**，而不是静默只导出一部分。提示文字直接写在 PDF 正文里，用户即使
  只拿到 PDF 也知道数据被裁剪了、该去哪里取全量。验收 1.9.1~1.9.3 的分工也印证这一点：Excel 检查三个工作表
  （含全量明细），Word 检查结构与可追溯信息，PDF 只检查中文显示正常。

#### 2.6.6 导出内容如何带项目/任务/版本/生成时间

- 三种格式都包含以下标识（验收 1.9.4 的硬性要求）：

| 标识 | Excel | Word | PDF |
|---|---|---|---|
| 项目编码/名称 | Sheet1 前两行 | 副标题行 + 任务信息表 | 副标题行 |
| 任务编号/名称 | Sheet1 | 任务信息表第 1 行 | 任务信息表第 1 行 |
| 评估算法 + 算法版本 | Sheet1 | 任务信息表第 2 行 | 任务信息表第 2 行 |
| 指标体系版本 / 数据快照 | Sheet1 | 任务信息表第 3 行 | 任务信息表第 3 行 |

- 加上 `report_record` 里的报表编号与文件名（`报表编号_任务编号.ext`），报告从**库内记录**到**文件内容**再到
  **文件名**三层都能定位到具体任务，配合 `AuditFilter` 的 `EXPORT` 模块审计（记录导出人、报表编号、格式与时间），
  构成验收 1.9.5 的完整链路。

**易错点/注意**：
1. `generate` 标注 `@Transactional`，而 catch 块里保存 `FAILED` 状态后**又抛出** `BizException`：
   在同事务中抛出运行时异常会触发回滚，`FAILED` 状态与 `errorMsg` 很可能**一起被回滚**，最终库里留下的仍是
   `GENERATING` 记录（这与「失败要有痕迹」的设计意图相悖）。如果要确保失败痕迹落库，应当用
   `REQUIRES_NEW` 的独立方法写失败状态，或只记录日志并返回失败结果而不抛异常。
2. `writePdf` 的字体候选列表来自配置的「搜索路径」，**没有内置默认的 Windows 字体列表**：全新环境若没配
   `pdf-font-search-paths`，会直接使用 `STSong-Light`（依赖 `openpdf-fonts-extra` 依赖是否在包里）。离线部署时
   应确认该依赖已打包，或在 `application.yml` 里显式配置系统字体路径。
3. `title/heading/para/setCell` 都是 `static` 方法且直接操作传入的文档对象，没有返回新对象：调用顺序即文档顺序，
   增删段落时要注意顺序，不要以为它们是「追加到末尾」的独立构建器。
4. PDF/Word 的明细行数没有统一的「行数上限配置」：PDF 硬编码 800，Word 全量。若某任务对象数与指标数很大
   （如 500 对象 × 60 指标 = 30000 行），Word 导出会非常慢且文件巨大——这是当前实现的已知伸缩性边界。

### 2.7 `backend/src/main/java/com/ees/service/DashboardService.java`

**作用**：综合驾驶舱总览（方案 7.4）：先**解析并校验统计区间**（提交 `5f8ba79`），再把当前账号的**数据权限生效范围**
归一到 `ids`，按该范围汇总项目、指标体系版本、用户、算法、任务、批次、快照、结果的核心指标，并给出等级分布、
算法使用、最新结果、任务告警、任务趋势与项目态势。
**「任务趋势」折线图与「评判等级分布」饼图共用同一个统计区间**（默认近 7 天，由前端传 `from`/`to` 决定），
上方指标卡（项目数 / 任务数 / 结果数 / 已发布 / 平均分等）始终是"当前总量"、**不随区间变化**；
页面承诺的「项目、任务、快照与结果均按数据权限过滤」由此在**所有由项目派生的字段**上兑现。

**被谁使用**：`controller/SystemController`（`GET /api/dashboard/overview?projectId=&from=&to=`）。

**关键设计点**：
1. **只展示已授权数据，且先把范围归一**：`visible = projectService.visibleProjectIds()`（`null` = 不限制）；
   带 `projectId` 时先 `projectService.checkVisible(projectId)`，不可见直接 **403「无权访问该项目」**；随后
   `ids = projectId != null ? List.of(projectId) : visible`，见 2.7.1。
2. **统计口径按「任务是否算成功」合并状态**：`RUNNING+QUEUED` 算运行中，`SUCCESS+PUBLISHED+PENDING_REVIEW`
   算成功，见 2.7.2。
3. **异常优先**：`alerts` 只挑 `FAILED/TIMEOUT` 且最多 5 条，让驾驶舱先暴露问题而不是先报喜。
4. **「生效范围」三分支贯穿全方法**（提交 `747fec4`）：`all`（`ids == null`，管理员 / ALL 范围）走原有的
   **全库**方法；`none`（`ids` 为空集合，项目级用户一个项目都看不到）**直接返回 0 / 空数组、不发查询**
   （既守权限，也避免 SQL `in ()`）；其余情况一律按 `ids` 走仓储的 `…In` / `…ProjectIdIn` 方法。被过滤的字段
   清单、两个私有辅助方法与空集合短路的细节见 2.7.2，修复背景与实测数据见 2.7.5。
5. **「全部项目」与「按项目」两支必须各有对称的聚合查询**：`overview()` 早期用 `scope == null` 区分两支，
   `resultCount` / `publishedResultCount` / `avgScore` 三项都要分别走全库方法与按项目方法。早期「全部项目」
   分支只写了计数、缺了后两项的聚合实现（值被写死为 `0` / `null`），导致未选项目时「平均得分」卡片恒显示
   "- 分"，详见 2.7.4（提交 `c05676e` 修复）。
6. **全库级能力不属于项目数据、保持原样**：`userCount` / `enabledUserCount` / `algorithmCount` / `algorithms`
   回答的是"系统里有几个账号、装了哪些算法"，与项目范围无关，因此**不做**任何范围过滤（第 121-124 行）。
7. **统计区间是"两个图表的维度"，不是"整页的筛选条件"**（提交 `5f8ba79`）：第 81-91 行解析出 `rangeStart` /
   `rangeEnd` 并换算成**左闭右开**的 `rangeFromTs` / `rangeToTs`，全方法只有两处消费它 —— 第 158-161 行的
   「评判等级分布」与第 247-249 行的「任务趋势」取数；第 283-285 行把生效区间回显为 `rangeFrom` / `rangeTo`，
   让前端标题与日期控件与后端理解一致。默认值刻意设计为"`to` 缺省取今天、`from` 缺省取 `to` 往前 6 天"，
   因此**不传参数时与改动前的行为完全一致（近 7 天）**。校验两条：开始晚于结束、或天数超过 366，都抛

8. **指标卡不随区间变化**：项目数 / 任务数 / 结果数 / 已发布 / 平均分 / 算法使用这些字段读的都是**不带时间条件**

#### 2.7.1 统计区间与生效范围：`from`/`to` 的解析校验、`visible` / `ids` / `all` / `none` 与 `checkVisible`

`overview()` 的开头做两件事，都**不查任何业务数据**。

**（1）统计区间：解析、校验与回显（第 81-91 行，提交 `5f8ba79`）**

- **补默认值**：`rangeEnd = to != null ? to : LocalDate.now()`、`rangeStart = from != null ? from : rangeEnd.minusDays(6)`。
  两个参数都不传时得到「今天往前 6 天 ～ 今天」共 7 天，**与改动前的硬编码"近 7 天"完全一致**；只传 `to` 时自动
  往前推 6 天，只传 `from` 时结束日取今天。这一条是"默认行为不变"的保证，也是回归测试的基准用例。
- **校验两条**：`rangeStart.isAfter(rangeEnd)` → `BizException(ErrorCode.PARAM_INVALID, "统计开始日期不能晚于结束日期")`；
  `ChronoUnit.DAYS.between(rangeStart, rangeEnd) + 1 > 366` → `BizException(ErrorCode.PARAM_INVALID, "统计区间最长支持 366 天")`。
  `+ 1` 是因为区间**含首尾两天**（2026-09-01～2026-09-30 是 30 天）。按本项目既有约定，业务异常以
  **HTTP 200 + 错误码**返回，前端拦截器统一弹提示，因此超长区间不会把页面打成错误页（前端另有一层"超过 366 天
  自动截断"的兜底）。限长的目的很实际：趋势图要按天预置日期键，不做上界就等于允许一次请求生成几万个数据点。
- **换算时间戳**：`rangeFromTs = rangeStart.atStartOfDay()`、`rangeToTs = rangeEnd.plusDays(1).atStartOfDay()`，
  得到**左闭右开**的 `[rangeFromTs, rangeToTs)`，与仓储里 `>= :from and < :to` 的写法配套；对用户呈现的仍是
  「含首尾两天」的闭区间。这一步把"日期"翻译成"时刻"，之后全方法只传时间戳。
- **只有两处消费区间**：第 158-161 行的「评判等级分布」与第 247-249 行的「任务趋势」；第 283-285 行把补全并校验
  **之后**的区间回显为 `rangeFrom` / `rangeTo`（前端据此显示标题与日期控件，不必自己重算默认值）。指标卡、算法使用、
  最新结果、任务告警、项目态势都**不读**这两个变量 —— 这就是「指标卡不随区间变化」的实现方式（见关键设计点 8）。

- `visibleProjectIds()`（`ProjectService` 第 58-74 行）的语义：**返回 null 表示不限制**（超级管理员或数据范围
  `ALL`）；否则返回「项目成员表中的项目 ID ∪ 我作为负责人的项目 ID」，**可能为空集合**。
- 带 `projectId` 时先 `projectService.checkVisible(projectId)`（第 97-101 行）：不可见抛
  `BizException(ErrorCode.FORBIDDEN, "无权访问该项目")` → HTTP 403，与 `ProjectService.get(id)` 同一口径。
  **这一步是安全检查，不能与"范围归一"合并**：归一用 `List.of(projectId)` 直接构造集合，它本身不校验可见性。

  把它切成三支：

| 分支 | 触发条件 | 含义 | 后续动作 |
|---|---|---|---|
| `all` | `ids == null` | 超级管理员 / `dataScope = ALL`，不看任何限制 | 走仓储里原有的**全库**方法（`count()`、`countGroupByAlgorithm()`、`avgScoreAll()`…） |
| `none` | `!all && ids.isEmpty()` | 项目级用户，但一个可见项目都没有 | **短路返回 0 / 空数组，不发查询**（`null` 用于 `avgScore`），同时避免 SQL `in ()` |
| 其余 | `ids` 非空 | 指定了单个项目（`[x]`），或项目级用户的可见集合 | 一律走 `…In` / `…ProjectIdIn` 方法，并把 `ids` 作为参数 |

- 三支的边界要说清楚：**`projectId != null` 时 `all` 必然为 `false`**（因为 `ids` 是 `List.of(projectId)`，不是
  `null`），所以"管理员 + 选中项目 1"走的是第三支而不是第一支 —— 这正是「项目数」从 3 修正为 1、
  「算法使用」跟随所选项目的实现基础（见 2.7.5）。
- `projectCount` 在三支下的取值各不相同：`all` → 「ACTIVE + DRAFT」项目数（不含归档）；`[x]` → 固定 **1**；
  `none` / 项目级用户 → `ids.size()`。
- 两个不受范围影响的地方：①项目态势 `projects` 用 `projectService.all()`（第 270 行），它内部自己调用
  `visibleProjectIds()` 过滤，**修复前后都按权限**（历次改动都未动它）；②用户数与可用算法是系统级数据，
  刻意不过滤（第 121-124 行）。
- **区间与范围是两个正交的维度**：范围回答"看哪些项目"（三支），区间回答"看哪段时间"（只影响两张图）。代码里
  没有把两者相乘展开 —— 范围靠 `all` / `none` / `ids` 三分支、区间靠 `rangeFromTs` / `rangeToTs` 两个时间戳，
  各写一遍即可，两张图的取数方法同时接收这两组参数（`countGroupByLevelInRange(all ? null : ids, rangeFromTs, rangeToTs)`、
  `findForTrend(all ? null : ids, rangeFromTs, rangeToTs)`）。实测组合见 2.7.6。

#### 2.7.3 两张图（等级分布 / 任务趋势）怎么随区间算，其余部分怎么算

先讲**会随区间变化**的两项（提交 `5f8ba79` 的核心）：

- **评判等级分布（饼图）**：`countGroupByLevelInRange(all ? null : ids, rangeFromTs, rangeToTs)`（第 158-161 行）
  —— 仍是 `GROUP BY level` 的分组聚合，但只统计**结果创建时间落在 `[rangeFromTs, rangeToTs)` 内**的行；
  `projectIds == null` 表示管理员 / 不限制，`level` 为 null 归「未评级」，`none` 时不查库、直接给空数组。
  它与趋势图**共用同一对时间戳**，所以前端一改区间两张图一起变。修复前它统计的是**全部历史结果**
  （旧方法 `countGroupByLevel(null)` / `countGroupByLevelIn(ids)`，现已删除），这才出现"趋势变了、饼图不变"
  的口径错位（见 2.7.6）。
- **任务趋势（折线图）**：先在 `rangeStart` 到 `rangeEnd` 上**逐日预置键**（`byDay`，初值 0，第 243-246 行），
  再用 `taskRepository.findForTrend(all ? null : ids, rangeFromTs, rangeToTs)` 取**区间内的全部任务**（第 247-249 行），
  按 `createdAt.toLocalDate()` 落到桶里（第 250-258 行），最后转成 `[{date, taskCount}]`。
  桶的数量就是区间天数（近一周 7、近一个月 30、近一年 365），预置键保证"某天没任务"也出现在图上、折线不断档。
  **这里顺带修掉了一个既有缺陷**：`5f8ba79` 之前趋势是在「最近 20 条任务」里数数（与告警共用 `recentTasks`），
  区间一拉长（近一个月 / 近一年）必然漏计 —— 因为那 20 条根本覆盖不到整个区间。现在改为按区间直查数据库，
  趋势是**区间内全量**而不是抽样。`none` 时任务列表为空，但仍会生成"区间长度个全 0 日期点"，前端显示一条 0 线
  而不是空白。

其余部分**都不随区间变化**（口径见 2.7.2）：

- **算法使用**：`countGroupByAlgorithm()` 或 `countGroupByAlgorithmIn(ids)` 的分组聚合，返回
  `[algorithm, algorithmVersion, count]` 三元组；中文名由 `ResultService.algorithmLabel` 补上。
  **提交 `747fec4` 之后它跟随生效范围**（选中项目时只看该项目）；修复前无论是否选项目都是全库口径（见 2.7.5）。
  它**不带时间条件**，因此区间变化时它不动。
- **最新结果**：取最近 10 条结果（按 `id` 倒序 ≈ 按写入时间倒序），字段含任务编号、项目编码、对象编码/名称、
  综合得分、等级、排名、算法与中文名、创建时间。用 `id` 而不是 `createdAt` 排序是稳妥做法（`createdAt` 可能
  因批量写入而相同）。它是"当前最新"，与统计区间无关。
- **任务告警**：只扫描最近 20 个任务（管理员全库、项目级用户限可见项目），命中 `FAILED`/`TIMEOUT` 的前 5 条即停。
  语义是「近期异常」而非「全部异常」，与驾驶舱「一眼看到当前有没有问题」的定位一致；`errorCode`/`errorMsg`
  直接展示，用户可据此跳转任务详情重试。**它刻意不跟随统计区间**：把区间拉回一年前，告警仍然是"最近发生了什么"。
- **项目态势**：`projectService.all()`（已按可见范围过滤）逐个项目统计任务数、结果数与平均分；任务数用
  `findByProjectIdAndDeletedFalseOrderByIdDesc(p.getId()).size()`（把整表查回来只为了拿 size，数据量大时
  应改为 `countByProjectId...`），平均分用 `avgScoreByProject` 并保留 2 位小数。同样是"当前总量"。

#### 2.7.4 修复「平均得分」在「全部项目」视图恒显示 “-” 的缺陷（提交 `c05676e`）

> 本节记录的是**较早一轮**修复（提交 `c05676e`），解决"没选项目时聚合查询缺失"；2.7.5 记录的是第二轮
> （提交 `747fec4`），解决"统计没按数据权限过滤"；2.7.6 记录的是最新一轮（提交 `5f8ba79`），解决"两张图不能按
> 自定义区间统计"。三者作用在同一段代码的不同方面（本节的第 148-156 行、2.7.5 的第 93-105 行、2.7.6 的
> 第 81-91 / 158-161 / 240-266 行），不要混淆。

**现象**：驾驶舱在**「全部项目」视图**（顶部不选项目，即 `projectId == null` → 本轮的 `all` 分支）下，
「平均得分」卡片恒显示 “- 分”，只有选中具体项目后卡片才有数字；同时「已发布」卡片恒为 0。

**原因（在后端，不是前端）**：`overview()` 当时按 `scope == null` 分了两支，「全部项目」这一支当初只写了
计数、没有聚合实现 —— `publishedResultCount` 被写死为 `0`、`avgScore` 被写死为 `null`。前端 `views/Dashboard.vue`
第 64 行绑定的是 `:value="fmtScore(overview.avgScore)"`，取不到值就格式化成 “-”，所以「平均得分」显示 “-”
是后端该分支没有实现的必然结果。只有选中具体项目时才会走 `avgScoreByProject`，卡片才有数字。

**改前 → 改后**（`DashboardService.overview()` 第 148-156 行）：

| 字段 | 改前（`scope == null` 分支） | 改后（现在的 `all` 分支） |
|---|---|---|
| `publishedResultCount` | `0`（写死） | `resultRepository.countByPublishStatus("PUBLISHED")` |
| `avgScore` | `null`（写死） | `resultRepository.avgScoreAll()` |

「按项目」分支（当时是 `scope != null`，现在是"选中项目 / 可见集合"一支）保持原样：
`countByProjectIdAndPublishStatus(scope, "PUBLISHED")` 与 `avgScoreByProject(scope)`。两个新查询加在
`EvaluationResultRepository`（逐行说明见 03 分册 2.44 与分组说明（7）），与按项目版本完全对称。

**影响面**：「全部项目」视图的「平均得分」由 “-” 变为真实平均值；「已发布」由恒 0 变为真实计数。后者在修复前
**恰好**与事实一致（库中 48 条结果全部是 `DRAFT`），但属**潜在缺陷** —— 一旦有人发布结果，卡片仍会显示 0，

1. `rangeToTs` 是**结束日 +1 天的 00:00**，仓储条件写 `< :to`。看到响应里 `rangeTo = 2026-09-30`、而查询里出现

2. `from`/`to` 是 `LocalDate`，**没有时区参数**，一律按服务器默认时区解释（`atStartOfDay()`）。跨时区部署或多地

3. 趋势图的点数等于区间天数：近一年 = 365 个点。这是刻意的（用户要看到完整走势），但也意味着前端折线图的
   `xAxis` 会很长；若要支持"按周/按月聚合"，改动点在服务端的分桶循环（第 243-246 行生成键的方式），
   而不是仓储查询。
4. 新增统计字段时仍要先问一句"它该不该随区间变化"：需要就把它接到 `rangeFromTs` / `rangeToTs`（并在仓储里加
   左闭右开的区间条件），不需要就照 2.7.2 的三分支写。**不要把区间塞进 `all` / `none` 三分支里** —— 两者是正交维度
   （见 2.7.1 末条）。

#### 2.8.1 `flatten` 如何把算法输出压平成可比较的字段集合

`flatten`（第 150-179 行）按固定优先级把 `AlgorithmResult` 摊平成一个 `Map<String,Object>`，键与
`expected_payload` 的键对齐：

| 步骤 | 行号 | 取值 | 放入的键 | 说明 |
|---|---|---|---|---|
| 1 | 152-153 | `r.getScore()` / `r.getLevel()` | `score` / `level` | 顶层综合分与等级（加权平均法、模糊综合评判的标准输出） |
| 2 | 155-161 | `extra.consistency` 的**第 0 个元素**（`list.get(0)`，必须是 Map）逐键摊平 | `matrixSize` / `weights` / `lambdaMax` / `ci` / `ri` / `cr` / `passed` 等 | **从 `consistency[0]` 取数**：AHP 的预期值（`weights/lambdaMax/ci/cr/ri/passed`）都写在这一条一致性记录里；取第 0 条即最外层判断矩阵的检验结果 |
| 3 | 160 | `extra` 其余键 `putIfAbsent` | `stages` 等 | `putIfAbsent` 保证不覆盖第 2 步已写入的同名键（如 `extra.weights` 不会盖掉一致性里的 `weights`） |
| 4 | 162-166 | `objectResults.get(0)` 的 `vector` / `weights` / `totalScore` | 同名键 | 单对象算法（模糊评判）的向量与得分在对象结果里；同样用 `putIfAbsent` |
| 5 | 167-169 | 第一个对象结果的 `extra` 逐键 `putIfAbsent` | 任意 | 引擎写在对象级 `extra` 里的中间量（如 `normalized` 之外的自定义字段） |
| 6 | 170-176 | 第一个对象结果的 `details[]` 中的 `normalizedValue` 收成列表 | `normalized` | 对应 `BASE-WEIGHTED-001` 的预期 `[0.9, 0.8, 0.7]` |

设计要点：
- **只取第 0 个对象结果**：基准样例都是单对象/单矩阵的「最小可判定算例」，多对象场景由业务回归覆盖，
  基准只验证算法封装本身的数值正确性。
- **`put` 与 `putIfAbsent` 混用是有意的**：一致性记录（步骤 2）用 `put` 可覆盖同名的顶层键（`weights` 以判断矩阵
  特征向量为准，这是 AHP 基准真正要验的东西）；后续步骤一律 `putIfAbsent`，保证不会把已经确定的字段覆盖成
  另一来源的值。因此 `flatten` 的结果对同一键是**确定且可预测**的，这正是「基准可复现」的前提。
- 未摊平到预期键的字段（如完整 `extra` 结构）依然通过响应的 `actualRaw` 原样返回，供人工排查。

#### 2.8.2 绝对/相对容差的判定

- 数值判定（第 82-88 行）：`diff = |expected − actual|`；`rel = diff / max(|expected|, 1e-12)`；
  通过条件 `diff <= absTol || rel <= relTol`。
- 为什么用「或」而不是「且」：两种容差覆盖不同量级——小数值（如 CI = 0.0）只能用绝对容差衡量，大数值
  （如 λmax = 5.0727）更关心相对误差。用「或」意味着**任一尺度上够接近即算通过**，避免小量级算例被
  相对误差误杀、大量级算例被绝对误差误杀。
- 容差取值（`db/data.sql`）：

| 样例 | 算法 | 绝对/相对容差 | 依据 |
|---|---|---|---|
| `BASE-AHP-001` 3 阶完全一致矩阵 | AHP | 0.0001 / 0.0001 | 精确解 0.6/0.3/0.1，CR = 0，属可精确复现的算例 |
| `BASE-AHP-002` Saaty 5 阶矩阵 | AHP | 0.002 / 0.002 | 特征向量为迭代近似解（λmax 5.0727），经典文献值本身有舍入 |
| `BASE-FUZZY-001` 一级模糊模型 | FUZZY | 0.0001 / 0.0001 | `M(·,+)` 合成是纯算术，可精确复现 |
| `BASE-WEIGHTED-001` 正向指标归一 | WEIGHTED | 0.0001 / 0.0001 | 归一化与加权求和均可精确复现 |

- 向量比对（`compareList`，第 181-199 行）：先比长度（不等直接失败），再逐项按同一套双容差规则判定；
  任一项超差即整体失败。长度检查是重要的**结构性防线**：如果引擎把评判向量维度算错，长度不等会立刻暴露，
  而不会被「前几项都对」掩盖。

#### 2.8.3 `runAll` 的汇总与「算法基准 4/4 PASS」

- `runAll` 遍历**启用状态**的样例（`findByEnabledTrueOrderByIdAsc`，按 id 升序，保证运行顺序与展示顺序一致），
  逐个调用 `run`，返回结果列表。
- 每个元素至少含 `baselineCode`、`passed`、`result`；成功项还含 `comparisons/actualRaw/expected`，
  异常项含 `error`。因此「4/4 PASS」的判定方式就是：**列表长度 4（启用样例数），每一项 `passed == true`**。
- 单个样例异常被吞掉（转成 `result: "ERROR"`）而不是中断整批，是为了让一次运行就能看到「哪个算例挂了」，
  符合验收「全部运行」的操作方式。
- 与验收项的对应（ACCEPTANCE 2.1「算法基准 → 全部运行 → 通过 4 / 4，全部 PASS」）：

| 验收关注点 | 本服务的实现 |
|---|---|
| 用甲方确认的标准样例 | 样例来自 `algorithm_baseline` 表（`db/data.sql` 种子 4 条），可在系统内维护 |
| 数值可比对 | `flatten` 把算法输出压平成与 `expected_payload` 同名的键集合 |
| 浮点容差 | `abs_tolerance` / `rel_tolerance` 表字段，默认 0.0001，Saaty 算例 0.002 |
| 差异有记录 | `last_run_result`（截断 1900）+ 响应里的 `comparisons[]`（逐字段 expected/actual/note） |
| 算法版本可追溯 | 响应 `algorithmVersion` 取自注册表（如 `java-ahp-1.0.0`），验收 2.10 |

**易错点/注意**：
1. `run` 标注 `@Transactional`，而内部调用的是**纯计算**（算法引擎）＋一次状态回写。算法在事务内执行会占用
   连接，基准样例虽小无碍，但如果将来加入大算例（大规模判断矩阵），应把计算移出事务。
2. `flatten` 只取 `objectResults.get(0)`：若某算例故意包含多个对象（如对比两条曲线），只有第一个对象会被比对，
   其余对象即使数值错误也不会让基准失败。基准样例应保持「单对象 + 少量关键字段」的形态。
3. `runAll` 的顺序依赖 `id` 升序，与「4/4」的展示顺序一致；如果后续通过界面新增样例，其 id 更大、排在后面，
   前端若固定展示 4 项需要同步调整。
4. `setScoreScale(8)` 与业务默认 4 位不同：基准故意用更高精度（8 位）以减少「业务展示精度」对容差判定的干扰；
   不要因为业务侧改了 `score-scale` 就认为基准也应跟着改——基准的固定参数正是它可作为**回归基线**的原因。

**关键结论（这一层的职责边界与易被误解的地方）**：

1. **质量校验的「严重级」不等于「是否阻断整批」**。`validate` 从 `data_quality_rule` 读出每类规则的严重级用于
   错误条目展示，但批次级阻断只由四条白名单条件（必填字段缺失、缺失值按 BLOCK 策略、指标未覆盖、方向未确认）
   决定。数值格式非法、越界、重复、单位不一致都只作用于**单行或告警**——这正是修过的真实缺陷：早期版本一行
   非法即令整批 `FAILED`，现在是「只有问题行进不了快照，其余数据立即可用」（ACCEPTANCE 1.4.3）。
2. **`project_code` 必须一路是项目编码**。`DataBatchService.projectCodeOf` 是这条链的起点，快照、任务、结果全部
   抄上游（批次→快照→任务→结果）。早期把它写成批次号导致项目维度追溯与驾驶舱统计失准；现在每一步都只传项目
   编码，且结果表冗余存这些编码，使「任务记录被删后追溯仍然完整」。
3. **快照是整条链路的契约点**：只有在快照阶段做一次「去重 + 缺失/越界标记 + 与算法同源的标准化 + SHA256 指纹 +
   `normalizationRanges` 留痕」，后端的任务执行与前端的三类展示才可能对同一个数值达成一致（验收 1.5.3 / 1.7.13）。
   快照一旦被任务使用即 `USED`、不可删除，是历史结果不可变的实现手段。
4. **任务层是「编排」而不是「计算」**：`buildRequest` 把快照、叶子指标与任务参数装配成 `AlgorithmRequest`，
   唯一的算法调用点是 `AlgorithmRegistry.get(...).evaluate(...)`；本层负责状态机、独立事务、结果落库与
   并列名次、AHP 一致性留痕、取消与重试。算法阈值/精度全部来自 `ees.algorithm.*` 与系统参数，改配置不改代码。
   两处需注意的实现细节：`create` 在事务提交前触发异步执行（存在任务滞留 `QUEUED` 的竞态），`retry` 的说明性
   状态历史因「同状态幂等」而不会落库。
5. **八类图形的数值全部由后端算好**（方案 7.3）：后端的职责是「决定数值、精度、缺失语义与提示文案」，
   前端只把数组翻译成 ECharts option。图形数据不足时必须返回 `emptyReason` 中文原因；需要分类信息的图形
   （热力图的 indicatorCode/objectCode、排名条形图的 rankings/levels）额外附带业务字段，否则前端无法生成
   tooltip 与着色。
6. **导出与基准是「可验证性」的两个出口**：三种导出格式共享同一份 `exportPayload`，因此内容天然一致，并统一
   携带项目/任务/版本/生成时间；PDF 因版面原因把明细硬截断到 800 行并提示改用 Excel，这一「明确截断 + 告知
   替代方案」的做法应作为后续新增报表的默认约定。算法基准则把算法输出 `flatten` 成与预期同名的键集合，按
   绝对/相对双容差逐项比对并全量留痕，是验收「算法基准 4/4 PASS」与算法版本可追溯的直接支撑。
7. **同一份统计必须同时写对三个维度："视角维度"、"范围维度"与"区间维度"**：「驾驶舱」的每个字段首先要按
   `all`（管理员 / ALL 范围、全库）与"受限范围"两支取值，受限那一支还要再分"指定项目 / 可见集合"与"空集合"
   两种情况 —— 这就是 `overview()` 里 `visible`/`ids`/`all`/`none` 的由来（见 2.7.1、2.7.2）；此外还有第三个
   维度**统计区间**（提交 `5f8ba79`）：只有「任务趋势」与「评判等级分布」随它变化，其余字段都是"当前总量"。
   三类真实缺陷都出在这里：
   ①提交 `c05676e` 修的是"视角维度"缺一支 —— 「全部项目」分支用 `0`/`null` 占位，界面上就是「平均得分」恒显示
   “-”、「已发布」恒为 0（详见 2.7.4）；
   ②提交 `747fec4` 修的是"范围维度"整段缺失 —— 页面承诺按数据权限过滤，实现里却只有「项目数」过滤了，
   可见项目为 0 的评估人员仍能看到任务 15 / 快照 6 / 批次 6 / 结果 48 / 均分 80.23，而且 `?projectId=` 不做
   可见性校验（详见 2.7.5）；
   ③提交 `5f8ba79` 修的是"区间维度"的口径不一致与既有缺陷 —— 两张图原先口径不同（饼图统计全部历史结果、
   折线图只在"最近 20 条任务"里数数），区间一拉长必然漏计；现在两张图共用同一对左闭右开时间戳，
   饼图跟随区间、折线图按区间全量分桶（详见 2.7.6，实测 2020 区间下等级分布为空而指标卡结果数仍为 42）。
   这类缺陷在当日数据库状态恰好"看起来是对的"时不会被发现（当时 48 条结果全为 `DRAFT`），因此新增统计字段时
   必须**同时**核对：全范围、单项目、空范围、以及"该不该随区间变化"四种取值。
8. **数据权限必须「列表」与「按 id」两条路一起堵**（提交 `e295085`，见 2.4.9）。上一轮 `747fec4` 只修了驾驶舱
   的**聚合统计**，列表接口与按 id 直读仍是全库口径 —— 实测一个可见项目为 0 的评估人员账号仍能列出
   **15 个任务 / 48 条结果 / 6 个批次 / 6 个快照**（修复后均 0 条），并能按 id 直读别人的任务详情、结果详情与
   批次记录（修复前 200，修复后 **403「无权访问该项目」**；管理员对照 15 / 48 不受影响）。两条策略值得记住：
   ①**列表取交集**：把 `visibleProjectIds()` 作为 `t.projectId in :ids` 与请求自带的 `projectId` 取 and，
   传了不可见的项目只返回空列表而**不报错**——因为前端会把 `localStorage['ees_project_id']` 的历史上下文一直带着，
   报错会把页面打成无法自救的错误页；②**按 id 直读直接 403**：但顺序必须是「先查是否存在、再判是否可见」，
   不存在仍走原来的 1004「不存在」，否则等于用状态码泄露「这个 id 在不在」。③写入侧（导入 / 抽取 / 建任务 /
   生成快照）另加 `checkVisible(projectId)`，「看」和「写」两个方向都不能越出可见项目。
   实现上的代价是每个按 id 接口多一次按主键查询与一个新增依赖（`ProjectService`），并且因为
   `visibleProjectIds()` 依赖 `SecurityUtils` 的安全上下文，**不能在异步执行线程里调用**——
   数据权限必须在 `create`（HTTP 线程）阶段校验完毕。
