## 1. 界面速览

| 区域         | 作用                            |
| ---------- | ----------------------------- |
| 左侧树        | 测试计划的全部结构。**所有东西都是右键「添加」出来的** |
| 右侧面板       | 选中哪个节点，就配置哪个节点                |
| 工具栏绿色 ▶    | 启动（Ctrl+R）                    |
| 工具栏红色 ■    | **停止**（有确认框，选「是」会等当前样本跑完）     |
| 工具栏 🧹     | 清除结果（只清当前选中监听器的结果）            |
| 工具栏 🧿     | 清除全部（清所有监听器结果）                |
| 右上角 `!` 警告 | 有黄色三角说明这个测试计划有问题，点开看          |

**JMeter 的核心心智模型**：左侧是一棵树，**数据从左往右流**——  
线程组产生「虚拟用户」，每个用户按树里的顺序依次执行取样器，配置元件/断言/定时器按作用域生效。

## 2. 最关键的一条规则：组件作用域

这一条搞懂了，后面全都顺。**子节点会继承父节点的配置元件、断言、定时器。**

| 组件类型                       | 作用范围                      |
| -------------------------- | ------------------------- |
| 配置元件（HTTP请求默认值、信息头管理器、CSV） | 同级 + 所有子孙节点               |
| 断言                         | 同级 + 所有子孙节点               |
| 定时器                        | 同级 + 所有子孙节点               |
| 前置/后置处理器                   | **只作用于它挂着的那个取样器**（或同级取样器） |
| 监听器                        | 只收集它所在层级的样本               |

所以推荐的结构长这样：

```
测试计划
├── 用户定义的变量          ← 全局变量（baseUrl、用户名等）
├── HTTP请求默认值          ← 所有请求共用的服务器/端口
├── HTTP信息头管理器        ← 所有请求共用的 Content-Type
└── 线程组
    ├── 仅一次控制器
    │   └── 00 登录         ← 每个线程只登录一次
    │       └── JSON提取器  ← 提取 token 到变量
    ├── 事务控制器「业务闭环」
    │   ├── 01 驾驶舱
    │   ├── 02 项目列表
    │   └── 03 指标树
    └── 聚合报告
```

## 3. 第一个请求：GET /api/health（免登录，先跑通）

`/api/health` 不需要 token，最适合拿来验证「JMeter 能不能连上」。

### 3.1 建测试计划

打开 JMeter 后左侧已经有一个「测试计划」。点它，右侧：

- **名称**：`效能评估系统压测`
- 其他保持默认

### 3.2 加 HTTP 请求默认值

右键「测试计划」→ **添加 → 配置元件 → HTTP请求默认值**

| 字段       | 值           |
| -------- | ----------- |
| 协议       | `http`      |
| 服务器名称或IP | `127.0.0.1` |
| 端口号      | `8080`      |

> 这样后面每个 HTTP 请求只写路径就行，换环境只改这一处。

### 3.3 加线程组

右键「测试计划」→ **添加 → 线程(用户) → 线程组**

| 字段            | 含义           | 先填  |
| ------------- | ------------ | --- |
| 线程数（用户）       | 并发虚拟用户数      | `1` |
| Ramp-Up 时间（秒） | 多少秒内把线程全部启动完 | `1` |
| 循环次数          | 每个线程跑几轮      | `1` |

> **Ramp-Up 的理解**：线程数 100、Ramp-Up 10，就是「10 秒内均匀地每秒起 10 个用户」。  
> 填 0 等于瞬间全部启动（容易把服务打懵，也可能压不出真实曲线）。

### 3.4 加 HTTP 请求

右键「线程组」→ **添加 → 取样器 → HTTP请求**

| 字段 | 值             |
| -- | ------------- |
| 名称 | `00 健康检查`     |
| 方法 | `GET`         |
| 路径 | `/api/health` |

### 3.5 加监听器

右键「线程组」→ **添加 → 监听器 → 查看结果树**  
再右键 → **添加 → 监听器 → 聚合报告**

### 3.6 跑起来

点工具栏绿色 ▶。到「查看结果树」看：

- 左侧出现 `00 健康检查`
- 点它 → 右侧「响应数据」能看到 `{"code":0,...,"status":"UP"...}`
- 图标是绿色 ✅ 表示成功

**到这一步，环境就通了。**

## 4. 关联：把登录拿到的 token 传下去

系统除 `/api/health`、`/api/info`、`/api/auth/login` 外**全部要 JWT**。  
所以必须先登录、提取 token、再带着 token 请求。

### 4.1 登录响应长什么样

```json
{
  "code": 0,
  "message": "登录成功",
  "data": {
    "token": "eyJhbGciOiJIUzUxMiJ9....",
    "tokenType": "Bearer",
    "expiresIn": 28800,
    "user": { "id": 1, "username": "admin", "roleCode": "SYSTEM_ADMIN", ... }
  }
}
```

token 在 `data.token`。

### 4.2 加登录请求

右键「线程组」→ **添加 → 取样器 → HTTP请求**

| 字段       | 值                         |
| -------- | ------------------------- |
| 名称       | `00 登录`                   |
| 方法       | `POST`                    |
| 路径       | `/api/auth/login`         |
| 消息体数据    | 见下                        |
| 参数/消息体数据 | 选 **消息体数据**（Body Data）标签页 |

「消息体数据」里粘贴：

```json
{"username":"admin","password":"admin123"}
```

> 注意：选了「消息体数据」后，JMeter 不会自动加 `Content-Type: application/json`。  
> 这一步要靠下面的信息头管理器，或者在这里勾「编码」并在 HTTP请求默认值里统一加头。

### 4.3 加 HTTP 信息头管理器（全局）

右键「测试计划」→ **添加 → 配置元件 → HTTP信息头管理器**

| 名称             | 值                                |
| -------------- | -------------------------------- |
| `Content-Type` | `application/json;charset=UTF-8` |
| `Accept`       | `application/json`               |

### 4.4 提取 token

右键 **`00 登录`** 这个请求 → **添加 → 后置处理器 → JSON提取器**

| 字段                         | 值                 | 说明                 |
| -------------------------- | ----------------- | ------------------ |
| Names of created variables | `token`           | 变量名，后面用 `${token}` |
| JSON Path expressions      | `$.data.token`    | 从响应 JSON 里取        |
| Match No.                  | `1`               | 取第 1 个匹配           |
| Default Values             | `TOKEN_NOT_FOUND` | 取不到时的兜底值，**一定要填**  |

> **为什么要填默认值**：如果取不到还不填，JMeter 会直接把 `${token}` 原样发出去，  
> 你会看到一堆 401 却不知道是提取失败了。

### 4.5 把 token 加到请求头

右键「线程组」→ **添加 → 配置元件 → HTTP信息头管理器**（这个放在线程组下）

| 名称              | 值               |
| --------------- | --------------- |
| `Authorization` | `Authorization` |

> **作用域坑**：这个头管理器在线程组下，所以**登录请求自己也会带上** `Authorization: Bearer TOKEN_NOT_FOUND`。  
> 对 `/api/auth/login` 无害（它不校验），但如果你介意，可以把头管理器改成挂在每个需要 token 的请求下面。

### 4.6 验证

在「查看结果树」里点 `00 登录` → 看「请求」标签页，确认：

- `Authorization: Bearer eyJ...` 已经带上了真实 token（不是 `TOKEN_NOT_FOUND`）

## 5. 断言：让 JMeter 自己判断对错

没有断言时，JMeter 只要**收到 HTTP 响应**就算成功 —— 哪怕返回的是 500 或 `{"code":5000}`。  
所以断言必须加。

### 5.1 响应断言（检查 HTTP 状态码）

右键目标请求 → **添加 → 断言 → 响应断言**

| 字段     | 值      |
| ------ | ------ |
| 应用范围   | 主样本    |
| 测试字段   | `响应代码` |
| 模式匹配规则 | `等于`   |
| 要测试的模式 | `200`  |

### 5.2 JSON 断言（检查业务码）

右键目标请求 → **添加 → 断言 → JSON断言**

| 字段                          | 值        |
| --------------------------- | -------- |
| Assert JSON Path exists     | `$.code` |
| 附加断言值                       | ✅ 勾上     |
| Expected Value              | `0`      |
| Match as regular expression | ❌ 不勾     |

> 这个系统所有接口成功时都返回 `{"code":0}`，所以这条断言可以**挂在线程组上**，一次覆盖全部接口。

### 5.3 持续时间断言（性能断言）

右键目标请求 → **添加 → 断言 → 持续时间断言**

- **持续时间（毫秒）**：`500`

> 超过 500ms 就标红。**注意**：这不会中断压测，只是把样本标为失败，  
> 方便你在报告里一眼看出「有多少请求超过了 SLA」。

## 6. 参数化：让不同用户跑不同数据

### 6.1 用户定义的变量（最简）

右键「测试计划」→ **添加 → 配置元件 → 用户定义的变量**

| 名称         | 值           |
| ---------- | ----------- |
| `baseUrl`  | `127.0.0.1` |
| `port`     | `8080`      |
| `username` | `admin`     |
| `password` | `admin123`  |

之后在请求里写 `${username}` 即可。

### 6.2 CSV 数据文件设置（多账号并发）

先在项目根建一个 `test-users.csv`：

```csv
username,password
admin,admin123
evaluator,eval123
```

右键「线程组」→ **添加 → 配置元件 → CSV 数据文件设置**

| 字段          | 值                                        |
| ----------- | ---------------------------------------- |
| 文件名         | `test-users.csv`（相对 JMeter 启动目录，建议写绝对路径） |
| 文件编码        | `UTF-8`                                  |
| 变量名称        | `username,password`                      |
| 忽略首行        | `True`（有表头时）                             |
| 分隔符         | `,`                                      |
| 遇到文件结束符再次循环 | `True`                                   |
| 遇到文件结束符停止线程 | `False`                                  |
| 线程共享模式      | `当前线程`（每个线程独立从头读）                        |

然后在登录请求的消息体里写：

```json
{"username":"${username}","password":"${password}"}
```

> **系统只有 2 个内置账号**（admin / evaluator）。想让 100 个线程各用各的账号，  
> 得先用管理员账号通过 `POST /api/users` 批量建用户。

### 6.3 函数助手（生成随机/唯一数据）

菜单 **工具 → 函数助手对话框**，选函数、填参数、点「生成」拿到语法：

| 函数            | 用途    | 示例                          |
| ------------- | ----- | --------------------------- |
| `__Random`    | 随机整数  | `${__Random(1,99999)}`      |
| `__UUID`      | 唯一字符串 | `${__UUID()}`               |
| `__time`      | 当前时间戳 | `${__time(yyyyMMddHHmmss)}` |
| `__threadNum` | 当前线程号 | `${__threadNum}`            |
| `__counter`   | 递增计数器 | `${__counter(FALSE)}`       |

**这个系统压测时最常用的是 `__UUID`** —— 因为项目编号、数据源编号等字段有唯一约束，  
建项目时必须用不重复的值：

```json
{"projectCode":"PRJ-LOAD-${__UUID()}","projectName":"压测项目 ${__threadNum}","status":"ACTIVE"}
```

## 7. 定时器：决定「压力是什么形状」

不加定时器时，每个线程会**尽可能快地**发请求 —— 这是「暴力压」，  
往往一开始就把服务打挂，测不出性能拐点。

| 定时器          | 作用               | 什么时候用             |
| ------------ | ---------------- | ----------------- |
| **常数定时器**    | 固定间隔（如 1000ms）   | 模拟「用户思考时间」，把压力摊平  |
| **常数吞吐量定时器** | 让整体稳定在目标 TPS     | 做「恒定压力」测试，看长期稳定性  |
| **同步定时器**    | 集合点，攒够 N 个线程再同时发 | 模拟「秒杀」「整点上报」的瞬间冲击 |
| **高斯随机定时器**  | 随机间隔，更接近真人       | 更真实的用户行为模拟        |
| **统一随机定时器**  | 区间内均匀随机          | 同上                |

### 7.1 常数定时器

右键「线程组」→ **添加 → 定时器 → 常数定时器**，线程延迟填 `1000`（毫秒）。  
→ 每个线程每次请求之间停 1 秒。

### 7.2 常数吞吐量定时器（做 TPS 目标）

右键「线程组」→ **添加 → 定时器 → 常数吞吐量定时器**

| 字段    | 值                 |
| ----- | ----------------- |
| 目标吞吐量 | `100`             |
| 基于    | `所有活动线程`          |
| 计算吞吐量 | `所有活动线程`（或按分钟/小时） |

→ 不管多少线程，整体都压到约 100 TPS。

> **这是最推荐的压力形态**：固定 TPS 跑 10 分钟，看响应时间和错误率是否稳定。

### 7.3 同步定时器（集合点）

右键「线程组」→ **添加 → 定时器 → 同步定时器**

| 字段       | 值               |
| -------- | --------------- |
| 模拟用户组的数量 | `50`（等够 50 个线程） |
| 超时时间（毫秒） | `5000`          |

→ 50 个线程攒齐后**同时**发出请求，制造瞬时峰值。

> ⚠️ 「模拟用户组的数量」必须 ≤ 线程数，否则永远等不满，只能等超时。

## 8. 逻辑控制器：组织测试逻辑

| 控制器           | 作用                               |
| ------------- | -------------------------------- |
| **事务控制器**     | 把多个请求合成一个「事务」，聚合报告里按事务统计（TPS 才准） |
| **仅一次控制器**    | 里面的请求每个线程只跑一次（**登录必须放这里**）       |
| **循环控制器**     | 里面的请求循环 N 次                      |
| **如果(If)控制器** | 按条件决定跑不跑                         |
| **随机控制器**     | 随机挑一个子节点跑                        |
| **吞吐量控制器**    | 按比例分配流量                          |

### 8.1 事务控制器（关键）

右键「线程组」→ **添加 → 逻辑控制器 → 事务控制器**

| 字段                                                                    | 值      |
| --------------------------------------------------------------------- | ------ |
| 名称                                                                    | `业务闭环` |
| Generate parent sample                                                | ✅ 勾上   |
| Include duration of timer and pre/post processors in generated sample | ✅ 勾上   |

把「驾驶舱 + 项目列表 + 指标树」拖进去。  
→ 聚合报告里会多出一行「业务闭环」，那一行的吞吐量才是**每秒完成多少套业务**。

### 8.2 仅一次控制器

右键「线程组」→ **添加 → 逻辑控制器 → 仅一次控制器**，把 `00 登录` 拖进去。  
→ 100 个线程只登录 100 次，而不是每轮循环都登录。

## 9. 监听器与报告：怎么看结果

### 9.1 查看结果树（View Results Tree）

**只用来调试**。它会把每个请求的请求体、响应体全存内存，压测时开着**必 OOM**。  
正式压测前**必须禁用它**（右键 → 禁用），或干脆删掉。

### 9.2 聚合报告（Aggregate Report）—— 最重要

| 列               | 含义          | 关注点                |
| --------------- | ----------- | ------------------ |
| Label           | 请求/事务名      | —                  |
| # Samples       | 总样本数        | 等于 线程数 × 循环数 × 请求数 |
| Average         | 平均响应时间 (ms) | 容易被极值拉偏            |
| Median          | 中位数 (ms)    | 50% 的请求快于它         |
| **90% Line**    | 90 分位       | **最该看的指标**，比平均值真实  |
| 95% Line        | 95 分位       | SLA 常用             |
| 99% Line        | 99 分位       | 长尾                 |
| Min / Max       | 最小/最大       | Max 异常大说明有抖动       |
| **Error %**     | 错误率         | **> 0.1% 就要查**     |
| Throughput      | 吞吐量（默认每秒）   | **TPS**            |
| Received KB/sec | 每秒接收        | 网络是否成瓶颈            |

**判断标准**：TPS 不再随并发上升、90% 线陡增、Error% 抬头 —— 这就是**性能拐点**。

### 9.3 汇总报告（Summary Report）

和聚合报告类似，多了「标准差」，少了分位细节。

### 9.4 响应时间图（Response Time Graph）

右键 → **添加 → 监听器 → 响应时间图**，能直观看到响应时间随时间的变化曲线。  
压测时看这条线是否**随时间持续爬升**（说明有资源泄漏或队列堆积）。

### 9.5 生成 HTML 报告（带图表，最正式）

**GUI 模式下**：菜单 **工具 → 生成 HTML 报告**，选 `.jtl` 文件。

**正式压测走命令行**（见第 11 节），会直接产出交互式 HTML。

## 10. 本系统的完整测试场景（每个功能都覆盖）

系统接口分 9 组，建议按下面顺序逐个压。

### 10.1 场景 A：只读接口（最安全，先做）

| 请求     | 路径                                                          | 断言                               |
| ------ | ----------------------------------------------------------- | -------------------------------- |
| 健康检查   | `GET /api/health`                                           | 响应码 200 + `$.data.status` = `UP` |
| 系统信息   | `GET /api/info`                                             | `$.code` = 0                     |
| 驾驶舱    | `GET /api/dashboard/overview`                               | `$.code` = 0                     |
| 项目列表   | `GET /api/projects?page=1&size=20`                          | `$.code` = 0                     |
| 项目下拉   | `GET /api/projects/options`                                 | `$.code` = 0                     |
| 指标版本列表 | `GET /api/indicator-versions?page=1&size=20`                | `$.code` = 0                     |
| 指标树    | `GET /api/indicator-versions/1/tree`                        | `$.code` = 0                     |
| 数据批次列表 | `GET /api/data-batches?page=1&size=20`                      | `$.code` = 0                     |
| 快照列表   | `GET /api/snapshots?page=1&size=20`                         | `$.code` = 0                     |
| 任务列表   | `GET /api/evaluation-tasks?page=1&size=20`                  | `$.code` = 0                     |

## 11. ⚠️ 本系统的压测敏感点（必读）

这些是**读代码确认过的**，不是猜测。

### 11.1 登录失败 5 次 → 账号锁定 15 分钟

代码位置：`service/AuthService.java:97-118`

- 密码错误累计到 **5 次**：`status` 置为 `LOCKED`，`locked_until = now + 15min`
- 锁定期间**即使密码正确也拒绝**（锁定检查在密码校验之前）
- 15 分钟后自动失效；**登录成功也会自动解锁并清零计数**

**后果**：如果你用错密码压登录接口，`admin` 会被锁，你自己也进不去界面了。

**恢复 SQL**（用 Navicat 或命令行执行）：

```sql
UPDATE efficiency_evaluation.sys_user
SET login_fail_count = 0, locked_until = NULL, status = 'ENABLED'
WHERE username IN ('admin','evaluator');
```

**压登录接口的正确姿势**：

- 一律用正确密码（`admin/admin123`）
- 如果一定要测「错误密码」的响应，**并发不要超过 4，循环不要超过 1**
- 压之前先查一次状态：

```sql
SELECT username, status, login_fail_count, locked_until FROM efficiency_evaluation.sys_user;
```

### 11.2 系统没有任何限流 / 熔断

`grep` 全项目：没有 RateLimit、Sentinel、Resilience4j、@Throttle。  
**意味着压力会 100% 打到 Tomcat → Hikari → MySQL**，没有任何缓冲。  
好处是能测出真实瓶颈，坏处是很容易打挂。

### 11.3 审计日志会放大写请求

`config/AuditFilter.java`：所有 `POST/PUT/DELETE/PATCH` 自动写一条 `sys_audit_log`。  
压写接口时，**实际 DB 写入量是请求量的 2 倍**。

### 11.4 评估任务并发上限 4

`EesProperties.maxConcurrentTasks = 4`，任务超时 900 秒。  
压任务接口时，并发 > 4 的请求会排队，**响应时间会线性增长** —— 这不是 bug。

### 11.5 数据库连接池 50

`application-prod.yml`：`hikari.maximum-pool-size: 50`。  
并发超过 50 且每个请求都占连接时，会出现「等待连接」→ 响应时间陡增。  
**这是最可能的第一个瓶颈。**

### 11.6 Tomcat 默认线程数 200

没改过的话是 `max-threads=200`。超过 200 并发会排队。

### 11.7 JWT 有效期 8 小时

`jwt-expire-minutes: 480`。压测超过 8 小时 token 会失效，重新登录即可。

## 12. 怎么找到「拐点」：阶梯加压

不要一上来就 1000 并发。按阶梯来：

| 轮次 | 线程数 | Ramp-Up | 持续时间 | 目的           |
| -- | --- | ------- | ---- | ------------ |
| 1  | 10  | 10s     | 2min | 基线           |
| 2  | 50  | 10s     | 2min | 常态           |
| 3  | 100 | 10s     | 2min | 观察           |
| 4  | 200 | 20s     | 2min | 接近 Tomcat 上限 |
| 5  | 300 | 30s     | 2min | 找拐点          |
| 6  | 500 | 60s     | 2min | 找崩溃点         |

**每轮记录**：TPS、90% 响应时间、Error%、CPU、内存、MySQL 连接数。

**拐点的标志**（三条同时出现）：

1. TPS 不再上升（甚至下降）
2. 90%/99% 响应时间急剧上升
3. Error% 从 0 变成非 0

**持续时间怎么设**：勾选线程组的「调度器」，填「持续时间（秒）」= 120。

## 13. 常见坑

| 现象                  | 原因             | 解法                                                                 |
| ------------------- | -------------- | ------------------------------------------------------------------ |
| 全部请求 401            | token 没提取到     | 检查 JSON 提取器的 JSON Path 和默认值；在结果树里看实际发出的 `Authorization` 头          |
| 全部请求 403            | 账号权限不够         | `evaluator` 没有 `report:*` 权限，用 `admin`                             |
| 中文乱码                | 编码不一致          | HTTP请求默认值里勾「内容编码」填 `UTF-8`                                         |
| 压测中 JMeter 卡死/OOM   | 查看结果树存了太多数据    | 禁用所有「查看结果树」                                                        |
| 吞吐量上不去，但服务 CPU 很低   | 客户端成瓶颈         | 增加 JMeter 堆内存，或改用分布式压测                                             |
| 端口耗尽                | Windows 动态端口不够 | 调大 `MaxUserPort` / `TcpTimedWaitDelay`                             |
| 线程数 100 但 TPS 只有 20 | 定时器拖慢 / 服务端排队  | 检查是否加了常数定时器                                                        |
| `.jtl` 文件打不开        | 是二进制格式         | 在 jmeter.properties 里设 `jmeter.save.saveservice.output_format=csv` |

## 16. 附录 A：结构自查表（照着打勾）

搭完计划后，逐条核对。**每一条都对应一个真实踩过的坑。**

| # | 检查项 | 怎么查 | 错了会怎样 |
| - | --- | --- | --- |
| 1 | **监听器挂在「线程组」下**，不是挂在某个请求下 | 树里看 `查看结果树`/`聚合报告` 的缩进层级 | 挂在请求下 → 只能看到那一个请求的结果，其它请求**完全不统计**，聚合报告数字凭空少一半 |
| 2 | **登录放在「仅一次控制器」里** | 登录请求的父节点是不是 `仅一次控制器` | 不放 → `线程数 × 循环次数` 次登录。200×10 = **2000 次登录**，每次后端要 UPDATE 用户表 + 写 **2 条**审计日志 |
| 3 | **请求顺序：登录在最前** | 树的从上到下顺序 | 业务请求排在登录前 → 第一次迭代拿不到 token，直接 401 |
| 4 | **断言用 `$.code = 0`，不是 `= 200`** | JSON 断言里的期望值 | 本系统成功码是 **0**；写 200 会让所有请求"失败" |
| 5 | **`Authorization` 头 = `Bearer ${token}`**，且作用域覆盖业务请求 | 信息头管理器的层级 | 没加或层级太低 → 全部 401（`{"code":2001}`） |
| 6 | **`Content-Type` 头存在** | 同上 | 登录 POST 会 415 |
| 7 | **正式压测前禁用「查看结果树」** | 右键 → 禁用 | 200 线程的结果全塞进 GUI 表格 → JMeter 自己 OOM |
| 8 | **线程数先小后大** | 先 10/5/5 跑通再加 | 一上来 200 → 后端连接池打穿（见附录 B） |
| 9 | **URL 里的 `&` 在 .jmx 里要写 `&amp;`** | 手工改 XML 时注意 | XML 解析失败，计划打不开 |

**快速自检**：跑一次后看聚合报告的样本数。`线程数 × 循环次数 = 每个业务请求的样本数`，`登录样本数 = 线程数`。对不上就是第 1 或第 2 条错了。

## 17. 附录 B：本轮压测已发现的真实瓶颈（重要）

这不是理论，是**已经实测复现**的结果。

### B.1 现象

后端日志 `backend/data/logs/evaluation-backend.log` 中出现：

```
ERROR  EesHikariPool - Connection is not available, request timed out after 30001ms
       (total=50, active=50, idle=0, waiting=188)
```

- 日志中出现 **6277 次**
- 单次运行日志暴涨到 **50 MB / 35 万行**
- 时间段：23:01:39 → 23:21（正好是 200 线程压测期间）

### B.2 原因链

```
200 个并发请求
  → 每个请求要一个数据库连接
  → Hikari 池上限只有 50
  → 50 个连接瞬间被占满 (active=50, idle=0)
  → 剩下 188 个请求排队等连接 (waiting=188)
  → 等满 30 秒后抛 SQLTransientConnectionException
  → 请求全部失败，JMeter 侧看到 Connection refused / 超时
```

**瓶颈不在 CPU、不在 Tomcat 线程数（200），而在数据库连接池（50）。**

### B.3 对照数据

| 场景 | 线程数 | 结果 |
| --- | --- | --- |
| 正常（后端健康） | 10 | **310 样本 / Err 0.00% / Avg 11ms / TPS 64.7** |
| 过载 | 200 | 连接池耗尽，6277 次超时，大量 500 |

各接口正常耗时基线（10 线程实测，可用来判断是否劣化）：

| 接口 | 平均 | 最大 |
| --- | --- | --- |
| `/api/auth/login` | 104.7 ms | 231 ms |
| `/api/health` | 2.4 ms | 4 ms |
| `/api/info` | 1.9 ms | 4 ms |
| `/api/dashboard/overview` | 26.9 ms | 66 ms |
| `/api/projects` | 6.2 ms | 28 ms |
| `/api/indicator-versions/1/tree` | 8.1 ms | 30 ms |
| `/api/evaluation-results` | 6.2 ms | 15 ms |

### B.4 这个结论怎么用

- **写进压测报告**：「系统在 200 并发下数据库连接池成为瓶颈，建议将 `spring.datasource.hikari.maximum-pool-size` 从 50 上调，并配合 MySQL `max_connections`（当前 151）一起评估。」
- **验证方法**：把线程数从 10 逐步加到 50 / 100 / 200，记录 TPS 和错误率，找到拐点。
- **压测后一定要重启后端**：连接池被打穿后，服务即使"看起来还在"（`/api/health` 能返回），实际已经不可用，且日志会持续膨胀。

> ⚠️ 压测完记得重启后端再继续做别的事，否则你会遇到莫名其妙的超时。

### B.5 怎么一眼定死「是不是连接池的锅」—— jstack 线程快照

日志里的 `Connection is not available` 只是**结果**。要拿到**证据**，抓一次线程快照：

```bash
# 1) 先找到后端 PID（IDEA 控制台 / 任务管理器 / netstat 里的监听进程号）
netstat -ano | findstr :8080
# 2) 抓快照
"D:\Dev\tools\jdk-21\bin\jstack.exe" <PID> > jstack.txt
```

然后在 `jstack.txt` 里搜关键字：

```bash
grep -c "ConcurrentBag.borrow" jstack.txt     # 有多少线程在排队等连接
grep -c "Thread.State" jstack.txt             # 总线程数
```

**判读方法（本次实测的真实快照）**：

| 观察 | 含义 |
| --- | --- |
| 大量 `http-nio-8080-exec-*` 卡在 `com.zaxxer.hikari.util.ConcurrentBag.borrow` | 线程全在**排队等数据库连接** |
| `ees-io-*` 线程也在 `ConcurrentBag.borrow` | 连异步线程池都被拖住了 |
| **没有任何线程**的栈里有 `com.mysql` / `HikariProxyConnection` | **连接被借出去后没人用、也没人还 → 连接泄漏** |
| MySQL 侧 `SHOW PROCESSLIST` 里连接全是 `Sleep` | 同上，连接没在跑 SQL，是被"占着" |
| `SHOW PROCESSLIST` 没有 `Waiting for lock` | 排除锁等待 |

> **一句话判据**：如果"等连接"的线程一大堆，但"用连接"的线程一个都没有 —— 那就是**连接泄漏**，不是慢查询、不是锁、不是 CPU。

**泄漏一旦发生，池不会自愈。** 表现是：零负载下 `/api/health` 的 `database.costMs` 仍然稳定等于
`connection-timeout`（本项目 30000ms）。连续测 5 次都 ≈29.6s 就是确诊。**唯一有效手段是重启后端。**

### B.6 为什么登录一失败，日志就刷 `JWT 解析失败: Invalid compact JWS`

这是**同一根因的下游症状**，看到它不用去查 JWT 代码：

```
连接池耗尽 → 登录请求拿不到连接、超时失败
          → JSON 提取器取不到 token，回落到默认值
          → 后续请求发出 Authorization: Bearer ${token}（未替换的字面量）
          → 后端解析失败，每个请求打一条 "JWT 解析失败: Invalid compact JWS"
```

所以**日志里 `JWT 解析失败` 的数量 ≈ 失败的业务请求数**。它是连接池问题的"回声"，
不是鉴权模块有 bug。
